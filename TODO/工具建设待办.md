## P0：分析前主动提问能力

Agent 在跑分析前，需要根据问题类型主动向用户补**业务参数和缺失标识**。不要把“用 MI / SQL / 广告平台 API 哪个工具”交给用户决定；这是 agent 的路由责任。

工具路由原则：

1. 有 verified SQL / 语义模型能稳定回答时，优先复用。
2. 需要页面口径或 campaign 级 ROI360 时，优先走 MI / CK 语义层。
3. 需要事实源、预测偏差、安装/激活用户数分母、S2S、素材前端时，走 MaxCompute SQL。
4. 归因到媒体后，若问题涉及“主动管控 / 预算 / 状态 / 出价变化”，agent 应自主尝试广告平台操作记录工具。
5. 只有缺少必要参数、账号映射或权限时，才向用户追问。

通用必问：

1. 分析对象：产品 / 包体 / store / OS。
2. 国家或地区。
3. 时间窗口：异常窗口、baseline 窗口。
4. 口径：all / paid_only；是否排除 organic / preinstall。
5. 粒度：media_source / campaign / adset / ad / material / event。

按问题类型加问：

| 问题类型 | 额外要问 |
|---|---|
| DNU 下滑 | 若需判断主动管控且工具缺上下文，只问缺失的 `customer_id` / `campaign_id` / account 映射或权限归属 |
| ROI / 回收 | revenue_source 用 sdk 还是 af，是否需要两版；成熟窗口看 D7/D30/D60 还是 ROI360 |
| campaign 放量 / 停投 | 是否已有阈值表；允许输出“动作候选”还是只能输出“观察名单” |
| 素材冷启动 | 最小曝光/消耗门槛；是否需要 ROI join |
| 点位复盘 | 事件池、cohort 窗口、观察窗口、扫描范围/成本上限 |

## P1：ai_ck 产物自动刷新调度(后续做成功能)

状态：`todo`（基础件已就绪,缺"调度 + 告警"这层）

背景:ai_ck 的可复跑产物(freshness / 版本登记 / example 验证 / metric sanity / profile 索引)目前都靠**手动触发**,带时间戳会过时。回归已能"检测过期"但不能"自动刷新"。

已就绪基础件:

| 件 | 路径 |
|---|---|
| 一键刷新(5 步,CK-only 绕开 MC 挂起) | `tools/scripts/refresh_ai_ck.sh` |
| 过期检测 gate(阈值 3 天,警告级) | `eval/agent_regression/run_regression.py` ARTIFACTS |
| 各探测脚本 | `probe_freshness.py` / `probe_table_versions.py` / `verify_ck_example_queries.py` / `verify_ck_metric_sanity.py` / `build_ai_ck_profile_index.py` |

功能化要补:

| 能力 | 说明 |
|---|---|
| 调度执行 | 定时跑 `refresh_ai_ck.sh`(macOS launchd / cron,或 CI 定时);内网才跑 MC 那半边 |
| 失败告警 | metric sanity 出现非 sane(指标变 0/空)、freshness 转 stale、版本族出现"全死"时,主动通知(而不只是回归里留警告) |
| 过期硬门 | 可选:把过期从"警告"升级为"CI 失败",强制保持新鲜 |
| 运行留痕 | 每次刷新写一条 `refresh_log`(时间、各步 pass/fail、关键值),便于追溯口径漂移 |

依赖/边界:

- MC 探测需内网;调度环境要能区分"内网/非内网"决定是否跑 MaxCompute。
- 凭据仍只走仓库外环境变量,不入仓。
- 这是 infra/运行环境层能力,需用户确定跑在哪(本机常驻 / 服务器 / CI)后再实现。
