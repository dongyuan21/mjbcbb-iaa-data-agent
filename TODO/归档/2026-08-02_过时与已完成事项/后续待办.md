## 1. 自研开源 DataAgent runtime POC

### 启动条件

只读 POC 已具备启动基础；进入 runtime 实现前需要保持以下条件：

- `ai_hive` 核心口径无冲突。
- `ai_ck` 至少完成 P0 表在线 `DESCRIBE` 验证。
- `knowledge/draft_knowledge` 中 P0 草稿已审核并 promote 或明确驳回，避免未审核 Obsidian 内容污染 agent 召回。
- `da_assets` 至少沉淀 10 条 verified SQL（数量以 SQL 晋升报告和自动快照为准）。
- 至少有 3 个 analysis SOP。
- 至少有 1 个 decision case 完整记录到后验结果。

### 统一路线

不再比较外部承载路线。自研开源 DataAgent runtime 的第一版范围如下：

| 模块 | 第一版职责 | 不做事项 |
|---|---|---|
| 任务路由 | 读取 `AGENT_RETRIEVAL_MAP.yaml`，输出任务类型、first-read、allowed assets 和门禁列表 | 不做全仓无差别 RAG |
| 资产加载 | 读取表卡、semantic contract、verified SQL、SOP、policy 和 catalog | 不默认召回 raw / draft / TODO |
| SQL 编排 | 优先复用 verified SQL；必要时生成带字段证据的 candidate SQL | 不跳过 schema / dry-run / 小窗口验证 |
| 执行门禁 | freshness、PII、source、owner、snapshot、raw-draft gate | 不自动放量、停投、降预算 |
| 结果输出 | 结论、证据、SQL、freshness、数据源、置信度、风险、needs_decision | 不输出用户级明细或敏感字段 |
| 资产回写 | candidate SQL、validated SQL、SOP、decision case、TODO | 不把候选资产直接晋升为 verified |

### POC 验收问题

1. “昨天 BB GP 各渠道 安装/激活用户数分母 达成率为什么变化？”
2. “哪些 campaign 可以放量，哪些应该观察？”
3. “某个点位有映射但 MI 没 ROI 数据，原因是什么？”
4. “同一批 campaign SDK 回收和 AF 回收差异有多大？”
5. “按 DA 的日复盘 SOP 生成一份简报。”

### 评估维度

- 能否正确选择表和口径。
- SQL 是否稳定带分区和日期过滤。
- 是否能引用 verified SQL。
- 是否能解释结果并给出动作建议。
- 是否可记录过程、SQL、结论，便于闭环。

## 2. 闭环层

### 暂定记录模型

```text
question
  -> context_retrieved
  -> sql_generated
  -> sql_result_summary
  -> conclusion
  -> human_decision
  -> action_taken
  -> aftereffect
  -> reusable_rule
```

### 第一阶段形式

先不建数据库，用 `da_assets/decision_cases/*.md` 记录。

### 后续可建表

| 表 | 作用 |
|---|---|
| `agent_questions` | 记录用户问题、上下文、任务类型 |
| `agent_sql_runs` | 记录 SQL、数据源、执行状态、结果摘要 |
| `agent_conclusions` | 记录 agent 结论、证据、置信度 |
| `human_decisions` | 记录人采纳/驳回/修改 |
| `delivery_actions` | 记录投放动作 |
| `aftereffect_reviews` | 记录 D+1/D+3/D+7 后验 |
| `semantic_rules` | 从 case 中沉淀的可复用规则 |

### 安全边界

- 第一版只读分析，不直接操作广告平台。
- 任何预算调整、停投、放量动作必须由人确认。
- 不保存明细级 PII。
- SQL 结果只保存聚合摘要，原始大结果不落盘。
