# 默认证据闭环与“证据覆盖—终态裁决”生产启用

- 状态：`主干已实现并本地回归 / Test enforce 已验证 / 默认 off / Prod 未验收`
- 优先级：`P0`
- 发布门：`production-default-evidence`
- 依赖：先完成并验收[知识状态与 Runtime 授权一致性收口](知识状态与Runtime授权一致性收口.md)。否则终态裁决即使判断严格，也可能把错误资格的资产当作证据。
- 不在本任务中重做：QuestionContract、claim attribution、ClaimCoverage、持久化和 wait/resume 的已有实现。

## 名词：证据覆盖—终态裁决链

**证据覆盖—终态裁决链**不是一个独立 Agent，而是现有 Runtime 组件共同完成的一段控制面流程：

| 组件 | 职责 |
|---|---|
| `QuestionContract` | 把用户问题拆成带版本的 required claim 和约束 |
| claim attribution / `ClaimCoverage` | 判断每个 claim 是否有合法、已绑定的证据 |
| `TypedOutcome` | 记录无数据、缺知识、需要澄清、超时等明确失败或等待原因 |
| 权威状态回读模块 | 将上述结果持久化、回读并校验后，作为本轮权威状态 |
| 终态裁决模块 | 从覆盖结果和 TypedOutcome 得出 `complete`、`partial`、`incomplete`、`waiting_clarification`、`failed` 或 `unknown` |

它处在 **Runtime 控制面**，不是表卡/语义层、数据查询引擎、模型提示词或前端组件。更具体地说，`QuestionContract` 是本轮运行合同；证据绑定横切查询和知识读取；终态裁决横切同步 API、SSE 和 Worker 的回答提交。

```mermaid
flowchart LR
  Q["用户问题"] --> C["QuestionContract\n本轮 claim 与约束"]
  C --> X["受控查询与知识读取"]
  X --> E["证据绑定与 ClaimCoverage"]
  E --> O["TypedOutcome"]
  O --> A["持久化并回读权威状态"]
  A --> T["TerminalDecision\n完成、部分完成、等待或失败"]
  T --> R["回答发布边界"]
```

## 是什么

这项工作要把一条规则变成系统默认行为：**业务答案中的每个关键结论，必须有与它匹配的证据；没有，就不能把整题说成“已完成”。**

证据覆盖—终态裁决链已经能根据证据给出 `complete`、`partial`、`incomplete` 等终态，也已经在 Test 环境验证过 `enforce`。但当前默认配置仍是 `off`。在 `off` 或 `shadow` 下，这条链会记录判断，却不会阻止候选文本直接作为最终回答发出。

本任务不是要求所有问题都跑 SQL，也不是再建设一套证据系统。它做的是把现有终态裁决接到默认发布门上，并让不同问题使用正确的证据标准。

## 当前实现进展（2026-08-04）

已完成、但尚未改变生产配置的部分：

- 每条 Runtime route 都必须声明 `required_evidence_mode`，并有回归门禁检查取值和 live SQL route 的一致性。
- Runtime 已把该策略传进 claim coverage。`executed_data` route 只有合格、非探活的核心 SQL 执行记录可以支撑 required claim；没有合格记录或归因无法建立时，覆盖率明确落为 `incomplete`，不会把候选文本当作完成依据。
- 回答 finalizer 同样读取该策略：强证据 route 没有可信核心执行证据时，不发布候选业务结论。
- ClaimCoverage、TypedOutcome、权威回读和同步 API/SSE/Worker 的既有终态出口继续共用同一份 `TerminalDecision`。本轮覆盖了证据归因、持久化、回读和 Runtime 出口回归。

仍未完成的是生产启用：Prod 仍保持 `off`，还没有 route allowlist、生产 canary、观察窗口或回滚记录。因此本事项不能关闭。

| 问题里的结论 | 最低证据 | 不能当作证据的东西 |
|---|---|---|
| 当前 ROI、消耗、收入、趋势、归因 | 已绑定 DataContract 的实际查询结果，且字段、粒度和 freshness 匹配 | SQL 文本、表名、执行计划、`SELECT 1`、`max(dt)` |
| 已确认的业务口径、阈值、规则 | 当前适用的 confirmed policy、semantic contract 或权威资产 | raw、draft、TODO、过期快照 |
| 表字段或 schema | 合法表卡；若问“当前”，还要有 live schema 或 freshness 证据 | 仅有 catalog 或旧 schema 导出 |
| 架构和代码行为 | 当前源码、测试，必要时加运行证据 | 只引用设计文档 |
| 需要用户选择的事项 | 已持久化的 pending/clarification 和新 revision | 擅自补全用户意图 |

## 为什么要做

现在的规则分成两层：

1. **已经写清并实现的通用规则**：终态裁决模块在 `enforce` 下会依据 ClaimCoverage 和 TypedOutcome 推导终态；`complete` 表示全部 required claim 已回答，`partial` 表示只回答了一部分，`incomplete` 表示没有回答任何 required claim。`unknown` 不会被映射成 `complete`。
2. **已落地、但尚未生产启用的政策部分**：每条 route 已声明证据类型；`executed_data` 已接入 Runtime finalizer 和 claim coverage。仍需为每条 claim 完善最低证据，并决定哪些 route 进入 Prod `enforce`。

因此这是一个真实缺口：不是修一个崩溃或错误条件的 bug，也不是推翻重构。它由三部分组成：

| 工作性质 | 本任务里的内容 |
|---|---|
| 控制面缺口修复 | 强证据业务结论没有合格证据时，不能被候选文本绕过并标为完成 |
| 小规模新建设 | 将 route/claim 的证据模式做成可读取、可测试的策略，并补一致性门禁 |
| 既有能力接线与发布 | 复用已有 ClaimCoverage、TypedOutcome、持久化和 TerminalDecision，把它们接入默认发布边界并分档启用 |

已有的通用 finalizer 会在部分明显失败的场景拦截回答，例如核心 SQL 已尝试但没有可信结果、候选文本为空，或 route 明确要求 SQL。

问题在于，未被明确标为强 SQL 的业务结论仍可能走过这层拦截：模型写出一个看起来完整的答案，系统没有足够证据却仍将其发布。这会让用户分不清“查到并验证了”与“模型根据上下文推断”。

还必须避免另一种错误：用一个全局 `has_sql` 开关处理所有问题。政策解释、代码说明和澄清问题不该被强行要求 SQL；反过来，freshness 探测成功也不能支持一个 ROI 数字。判断单位应是 claim 的类型，而不是整题有没有 SQL。

## 要怎么做

### 1. 先把规则写清楚

- [ ] 为每条生产 route 或 task profile 声明 `required_evidence_mode`：`none`、`repository`、`executed_data`、`mixed`、`user_input`。
- [ ] 为 ROI、投放、用户指标、归因、素材效能等业务 route 标出 required claim，以及每类 claim 的最低证据。
- [ ] 对照 `require_sql_in_answer`、`require_executed_sql_match` 和 QuestionContract，找出规则不一致的分支；没有明确规则的业务 route 不能默认放行。
- [ ] 给 Prod 定一份明确配置：哪些 route 先 `enforce`，哪些暂留 `shadow`，并写明负责人和原因；不得因为代码默认值而隐式保持 `off`。

交付物是一份能被代码和回归读取的 route/claim 策略，而不是另一份说明文档。

### 2. 让终态裁决真正决定能否发布答案

- [ ] 强证据 route 只有在权威 `TerminalDecision.terminal_status=complete` 时，才允许输出完整业务结论。
- [ ] `partial`、`incomplete`、`waiting_clarification`、`failed`、`unknown` 各有对应且有限的用户输出；被门禁拒绝的候选文本不得漏出。
- [ ] 一次查询只支持 attribution 已验证的 claim，不能因为查到一个指标就把整题标为完成。
- [ ] 把业务结果、freshness、schema 发现和连通性证据分开；探活和分区探测只能说明“能否查”和“数据新不新”，不能支持 KPI 值。
- [ ] 保持失败原因可区分：0 行、过期、知识缺失、合同缺失、政策重定向、超时和基础设施故障不能被压成同一个失败状态。

### 3. 按可回滚的顺序启用

按 `off → shadow → internal enforce → route allowlist → 小流量 → 强证据 route 默认 enforce` 推进。每一档都要记录观察窗口、负责人、错放率、误拒率、`unknown` 比例，以及 `partial/incomplete` 的分布和回滚阈值。

- [ ] 回滚只能从 `enforce` 退回 `shadow/off`；已经写入的 contract revision、coverage、outcome 和 wait snapshot 必须保留。
- [ ] 每档核对 API、Worker、Freshness 三服务的 commit、registry/policy revision、health/ready 和镜像/构建来源。
- [ ] Prod 使用新 session 做一次无重试 canary；Test 成功不能写成 Prod 证据。

### 4. 把规则变成长期门禁

- [ ] 真实问题集的 `evidence_requirements` 必须和 route/claim 策略一致。
- [ ] 新业务 route 未声明 evidence mode 时 fail closed，不能默认当作 `none`。
- [ ] 每周抽样复核错放和误拒，分别记录证据不足、证据资格错误、attribution 错误和答案漏 claim。
- [ ] 做必要的观测，但 trace 只保存 identity、枚举、计数、hash 和 reason code；不保存问题、答案、SQL、rows、知识正文或凭证。

## 必测场景

1. 数值 claim 没有合格的实际查询证据：结果不能是 `complete`。
2. 只有 freshness probe 成功：不能据此回答 ROI、消耗或收入。
3. SQL 成功但 0 行：返回 `query_no_rows`，不能把业务值写成 0。
4. 证据过期或 freshness 不覆盖目标窗：按 claim 输出 `partial/incomplete` 和限制条件。
5. 一个 claim 有证据、另一个没有：整题只能 `partial`。
6. 政策或架构解释：可凭当前代码和权威文档完成，不强制业务 SQL。
7. 表卡、catalog、知识状态冲突：证据资格构建必须 fail closed。
8. 在 `off/shadow/enforce` 间切换和回滚：历史状态不丢失，`unknown` 不得变成 `complete`。

## 什么时候算完成

- 强证据业务 route 在正式配置中默认受 `TerminalDecision` 约束，不再隐式继承 `off`。
- 每个 required claim 都有类型正确、来源合法、attribution 已验证的证据；不满足时，用户看到的状态与 `partial/incomplete/waiting/failed` 一致。
- Test 和 Prod 的证据分开记录；Prod 有同版本配置、单次无重试 canary 和可执行的回滚记录。
- 新 route 没有声明证据模式时，门禁会失败，不会在默认分支无证据完成。
- 审计记录能解释为什么放行或拒绝，但不泄漏业务原文、SQL、结果行或凭证。
