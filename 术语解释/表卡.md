# 表卡

## 定义

表卡不是严格的行业标准名，而是本工程对“可被 Agent 使用的数据表说明书”的约定叫法。

它接近以下概念的组合：

- 数据目录条目
- data asset card
- table contract
- schema + query guide
- Agent 可用表说明

在本工程里，表卡不是单纯字段清单，而是告诉 Agent：

- 这张表是什么。
- 一行数据代表什么粒度。
- 查这张表必须带哪些过滤条件。
- 哪些字段能作为指标、维度、join key。
- 哪些字段有 PII 或输出限制。
- 哪些口径、日期、回收源、时区、分区容易用错。
- 哪些示例 SQL 已经验证过或仍是候选。

## 为什么需要表卡

Agent 写 SQL 最大的风险不是不知道字段名，而是误用表：

- 把 `dt`、`active_date`、`event_date` 混用。
- 不加分区或日期过滤。
- 把同名字段当成 join key。
- 把截图、旧快照、字段名猜测当成 verified 事实。
- 把 CK 查询副本当成 MaxCompute 事实源。
- 把 ratio 指标直接 `SUM` 或 `AVG`。

表卡的作用是把这些使用边界写成稳定资产，让 Agent 在查表和写 SQL 前有依据。

## 表卡不是什么

| 不是 | 原因 |
| --- | --- |
| 不是 DDL | DDL 只说明字段和类型，不说明业务粒度、join、pitfalls |
| 不是字段 profile | profile 只回答“字段在不在”，表卡回答“能不能这样用” |
| 不是 verified SQL | verified SQL 是可复用查询，表卡是表级使用契约 |
| 不是业务最终口径 | 业务默认口径仍可能需要 `knowledge/`、`knowledge/agent_knowledge/semantic_contract/` 或 owner 确认 |
| 不是原始证据 | 表卡应引用证据，不应把 raw / draft 直接升级成事实 |

## 在工程里的位置

表卡主要放在：

```text
ai_hive/agent_knowledge/tables/*.yaml
ai_ck/agent_knowledge/tables/*.yaml
```

其中：

- `ai_hive/agent_knowledge/tables/*.yaml`：MaxCompute / Hive 事实源和主题表表卡。
- `ai_ck/agent_knowledge/tables/*.yaml`：ClickHouse / MI 报表层查询副本和主链路表卡。
- `ai_ck/engineering_artifacts/table_card_schema/TABLE_TEMPLATE.yaml`：CK 表卡模板，不是某张具体表。

## 表卡和其他资产的关系

| 资产 | 作用 | 和表卡的关系 |
| --- | --- | --- |
| `catalog.yaml` | 表目录、优先级、领域标签、入口索引 | 指向表卡，不替代表卡 |
| `agent_manifest.yaml` | Agent 挂载和召回边界 | 告诉 Agent 何时读表卡 |
| `table_profiles/` | 轻量字段画像 | 用于字段发现，不替代表卡口径 |
| `schema_exports/` | 线上 schema 基线 | 给脚本检测漂移和生成画像，不默认给 Agent 问答 |
| `knowledge/agent_knowledge/semantic_contract/` | 跨表实体、指标、维度、join 契约 | 从表卡抽象更高层语义 |
| `da_assets/verified_sql/` | 已验证可复用 SQL | 可以反向补强表卡证据 |
| `knowledge/` | 业务政策、SQL 协议、指标口径 | 补充表卡外的业务规则 |

## 一张合格表卡应包含什么

最少应包含：

- `documentation_status`
- `source_docs`
- `table.fqn`
- `grain`
- `date_fields`
- `query_rules`
- `columns`
- `known_pitfalls`
- `example_queries`

进入 Agent 默认召回或高频查询时，还应补齐：

- PII / 敏感字段说明
- `join_keys` 及证据
- `metric_fields`
- `semantic_groups`
- freshness / SLA / 分区延迟说明
- related tables
- 已验证样例 SQL 或小窗口验证记录

## 深卡 / 完整表卡

`深卡` 不是行业标准，也不是一类新资产。

在本工程里，它只是历史文档里对“完整表卡”的简称，通常指 `ai_hive/agent_knowledge/tables/*.yaml` 或 `ai_ck/agent_knowledge/tables/*.yaml` 中已经补齐口径、日期规则、join keys、known pitfalls、示例查询和证据链的表卡。

后续文档优先写“完整表卡”。如果旧文件里还出现 `深卡`，按“完整表卡”理解。

## 状态边界

表卡常见状态：

| 状态 | 含义 |
| --- | --- |
| `stub` | 只有骨架，不能作为默认事实 |
| `partial` | 有部分字段或规则，但缺少关键验证 |
| `partial_verified` | 部分口径或样例已验证，仍有待确认项 |
| `complete` | 结构完整，能指导 Agent 安全查询 |
| `verified` | 关键口径、样例 SQL、freshness 和证据链已通过验证 |

状态不能靠填写完整字段自动升级。必须有证据：live probe、schema 校验、verified SQL、页面 / 代码对账或 owner 确认。

## 一句话判断

如果一个文件只告诉你“表里有什么字段”，它不是完整表卡。

如果它还能告诉你“这张表什么时候能用、怎么查、不能怎么查、和谁能 join、哪些口径需要小心”，它才是本工程意义上的表卡。
