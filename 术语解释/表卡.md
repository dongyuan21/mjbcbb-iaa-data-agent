# 表卡

## 定义

表卡不是严格的行业标准名，而是本工程对「可被 Agent 使用的数据表说明书」的约定叫法。

它接近以下概念的组合：

| 中文 | 英文 / 常见叫法 | 说明 |
| --- | --- | --- |
| 数据目录条目 | data catalog entry | 告诉系统有哪些表 |
| 数据资产卡 | data asset card | 表作为可复用资产的说明 |
| 表契约 | table contract | 约定怎么用、不能怎么用 |
| 结构 + 查询指南 | schema + query guide | 字段结构 + 查法护栏 |
| Agent 可用表说明 | agent-usable table guide | 给 Agent 写 SQL 前读的说明书 |

在本工程里，表卡不是单纯字段清单，而是告诉 Agent：

- 这张表是什么。
- 一行数据代表什么粒度。
- 查这张表必须带哪些过滤条件。
- 哪些字段能作为指标、维度、关联键。
- 哪些字段有隐私限制或输出限制。
- 哪些口径、日期、回收源、时区、分区容易用错。
- 哪些示例 SQL 已经验证过或仍是候选。

## 中英术语对照（读 YAML 时先看这张表）

表卡文件是 YAML，字段名用英文；下文说明用中文。先对照再读正文，可减少中英夹杂。

### 顶层字段

| YAML 字段名（英文） | 中文含义 | 作用 |
| --- | --- | --- |
| `documentation_status` | 文档完备状态 | stub / partial / complete / verified 等 |
| `last_verified` | 最近验证日期 | 关键口径或样例上次核实的时间 |
| `source_docs` | 来源文档 | 可追溯证据路径，不是 raw 本身 |
| `schema_source` | 结构来源说明 | 字段从哪次探测 / 导出拿到（常见于 ClickHouse 卡） |
| `table` | 表身份块 | 全名、别名、层级、领域、一句话摘要 |
| `grain` | 粒度 | 一行代表什么 |
| `partitions` | 分区字段 | MaxCompute / Hive 侧常见，如 `dt` |
| `date_fields` | 日期字段语义 | ClickHouse 侧常见；Hive 也可补 |
| `freshness` | 新鲜度约定 | 分区字段、延迟、刷新说明、探测 SQL |
| `query_rules` | 查询规则 | 必过滤、隐私字段、扫描窗口、注意点 |
| `join_keys` | 关联键 | 推荐和哪些表用哪些列关联 |
| `columns` | 字段清单 | 逐列 name / type / 语义或注释 |
| `column_groups` | 字段分组 | 用分组代替逐列枚举（Hive 可用） |
| `columns_same_as` | 字段同构引用 | 声明与另一张表字段相同 |
| `metric_fields` | 表内可聚合指标 | 单表内 SUM / 比率公式（常见于 ClickHouse） |
| `semantic_groups` | 语义分组 | 维度 / 指标等字段归类 |
| `known_pitfalls` | 已知陷阱 | DDL 看不出的误用点 |
| `example_queries` | 示例查询 | 小窗口、带过滤的安全样例 SQL |
| `related_tables` | 相关表 | 同源、上下游或常一起查的表 |

### `table` 子字段

| YAML 字段名 | 中文含义 |
| --- | --- |
| `fqn` | 全限定表名（fully qualified name），如 `hungry_studio.xxx` / `shucang_market.xxx` |
| `view_fqn` | 视图全名（ClickHouse 常见；页面常走 view） |
| `alias` | 别名 |
| `layer` | 数仓层级或表类型 |
| `domain` | 业务领域标签 |
| `one_line_summary` | 一句话摘要 |

### `query_rules` 子字段

| YAML 字段名 | 中文含义 |
| --- | --- |
| `must_filter` | 必带过滤条件（日期 / 分区等） |
| `pii_columns_do_not_log` | 禁止落日志 / 输出的隐私字段 |
| `pii_aggregation_only` | 仅允许聚合、禁止明细输出的字段 |
| `max_scan_without_approval` | 未经额外确认时允许扫描的最大窗口 |
| `notes` | 查询注意点 |

### 状态与质量相关词

| 英文 / 取值 | 中文 |
| --- | --- |
| `stub` | 骨架卡，不能当默认事实 |
| `partial` | 部分完备 |
| `partial_verified` | 部分已验证 |
| `complete` | 结构完整，可指导受限查询 |
| `verified` | 关键口径与证据已验证 |
| `deprecated_stale` | 已废弃或过期 |
| PII | 个人隐私信息（Personally Identifiable Information） |
| SLA | 服务等级约定（如新鲜度延迟） |
| FQN | 全限定表名 |
| live probe | 实时连通与分区探测 |
| snapshot | 快照（可能过期，需与实时探测区分） |

### 两个知识库简称

| 工程目录 | 简称 | 对应引擎 | 表卡角色 |
| --- | --- | --- | --- |
| `ai_hive/` | Hive / MaxCompute 知识库 | MaxCompute（ODPS） | 事实源、主题表、训练与复核优先源 |
| `ai_ck/` | ClickHouse 知识库 | ClickHouse（库名常为 `shucang_market`） | MI / ROI360 报表查询层、看板对齐 |

下文用「Hive 表卡」「ClickHouse 表卡」指这两套 YAML，避免正文反复夹杂路径缩写。

## 为什么需要表卡

Agent 写 SQL 最大的风险不是不知道字段名，而是误用表：

- 把 `dt`、`active_date`、`event_date` 混用。
- 不加分区或日期过滤。
- 把同名字段当成关联键。
- 把截图、旧快照、字段名猜测当成已验证事实。
- 把 ClickHouse 查询副本当成 MaxCompute 事实源。
- 把比率类指标直接 `SUM` 或 `AVG`。

表卡的作用是把这些使用边界写成稳定资产，让 Agent 在查表和写 SQL 前有依据。

## 表卡不是什么

| 不是 | 原因 |
| --- | --- |
| 不是表结构定义（DDL） | DDL 只说明字段和类型，不说明业务粒度、关联、陷阱 |
| 不是字段画像（profile） | 画像只回答「字段在不在」，表卡回答「能不能这样用」 |
| 不是已验证 SQL | 已验证 SQL 是可复用查询；表卡是表级使用契约 |
| 不是业务最终口径 | 默认口径仍可能需要 `knowledge/`、语义契约或 owner 确认 |
| 不是原始证据 | 表卡应引用证据，不应把 raw / draft 直接升级成事实 |

## 在工程里的位置

```text
ai_hive/agent_knowledge/tables/*.yaml          # Hive / MaxCompute 表卡
ai_ck/agent_knowledge/tables/*.yaml            # ClickHouse 表卡
ai_hive/engineering_artifacts/table_card_schema/TABLE_TEMPLATE.yaml
ai_ck/engineering_artifacts/table_card_schema/TABLE_TEMPLATE.yaml
```

- Hive 表卡：事实源与主题表；层级多用 `ods` / `dwd` / `dim` / `dws` / `ads`。
- ClickHouse 表卡：报表查询副本与主链路表；层级多用 `fact` / `dim` / `view` / `aggregate`。
- 两个 `TABLE_TEMPLATE.yaml` 是新建表卡时的骨架，不是某张具体表。

## Hive 表卡结构（`ai_hive`）

权威模板：`ai_hive/engineering_artifacts/table_card_schema/TABLE_TEMPLATE.yaml`  
准入规范：`ai_hive/engineering_artifacts/Hive表准入标准.md`

### 推荐骨架（按阅读顺序）

```yaml
documentation_status: stub | partial | complete | ...
last_verified: null
source_docs: []

table:
  fqn: "hungry_studio.table_name"
  alias: []
  layer: ods | dwd | dim | dws | ads
  domain: []
  one_line_summary: ""

grain: ""
partitions:          # Hive / MC 侧主时间护栏，常见为 dt
  - name: dt
    required: true
    format: "yyyy-MM-dd"

query_rules:
  must_filter: [dt]
  pii_columns_do_not_log: []
  pii_aggregation_only: []
  max_scan_without_approval: "1 day"

join_keys: []
columns: []          # 或 column_groups / columns_same_as
semantic_groups: {}
known_pitfalls: []
example_queries: []
related_tables: []
```

### Hive 侧重点

| 区块 | 读法 |
| --- | --- |
| 分区 `partitions` | 多数表有 `dt`；小时表还有 `hour`。过滤优先写分区，不要和业务日期字段混用。 |
| 隐私 | 以 `ai_hive/agent_knowledge/PII_POLICY.yaml` 为真理源；表卡里的隐私字段必须与政策一致。 |
| 字段合同 | `columns`、`column_groups`、`columns_same_as` 三选一即可满足门禁。 |
| 指标 | 跨表指标不写在表卡正文的 `metrics` 里；归语义契约层。单表可聚合说明可放字段注释或语义分组。 |
| 目录 | Hive 表卡默认要求出现在 `ai_hive/agent_knowledge/catalog.yaml`。 |

### Hive 准入等级（简表）

| 等级 | 状态大致对应 | 能做什么 |
| --- | --- | --- |
| L0 | `stub` | 只表示发现过，禁止写业务 SQL |
| L1 | `partial` / `complete`（仅结构） | 可查字段和分区，不能默认复杂关联 |
| L2 | `complete` + 查询护栏 | 可生成受限 SQL，并说明风险 |
| L3 | `partial_verified` / `verified` | 可进高频默认分析或语义层候选 |

`complete` 不等于 `verified`。Hive / MaxCompute 是事实源，默认召回比 ClickHouse 更保守。

## ClickHouse 表卡结构（`ai_ck`）

权威模板：`ai_ck/engineering_artifacts/table_card_schema/TABLE_TEMPLATE.yaml`  
准入规范：`ai_ck/engineering_artifacts/ClickHouse表准入标准.md`（讨论稿，核心 ROI 表仍按完整卡要求补齐）

### 推荐骨架（按阅读顺序）

```yaml
documentation_status: stub | partial | complete | ...
last_verified: null
schema_source: ""     # 如 system.columns 导出说明
source_docs: []

table:
  fqn: shucang_market.table_name
  view_fqn: null      # 页面常读 view 时必填
  alias: []
  layer: fact | dim | view | aggregate
  domain: []
  one_line_summary: ""

grain: ""

freshness:
  partition_field: active_date
  partition_grain: day
  expected_latency_hours: null
  refresh: ""
  probe: "SELECT max(active_date) AS latest FROM {fqn}"

date_fields:          # CK 侧主日期语义；很多表没有 dt
  - name: active_date
    required: true
    format: yyyy-MM-dd
    timezone: ""

query_rules:
  must_filter: []
  pii_columns_do_not_log: []
  max_scan_without_approval: "7 days"
  notes: []

join_keys: []
columns: []
metric_fields: []     # 单表内可聚合指标与公式
semantic_groups: {}
known_pitfalls: []
example_queries: []
related_tables: []
```

### ClickHouse 侧重点

| 区块 | 读法 |
| --- | --- |
| `view_fqn` | MI / ROI360 常查视图；物理表与 view 都要标清默认走哪张。 |
| `date_fields` | 多数报表用 `active_date` 等业务日期，不一定有 `dt`。 |
| `freshness` | 新鲜度探测字段必须与真实过滤字段一致，不能照搬 Hive 的 `dt`。 |
| `metric_fields` | 写单表内 SUM / 比率公式；比率禁止直接对行做 AVG。 |
| 物理形态 | 需区分物理表、View、Distributed、`_local`、staging / test；后几类默认不召回。 |
| 目录 | ClickHouse 卡可不强制进 catalog 全表列表，但入默认召回仍应登记。 |

### ClickHouse 准入等级（简表）

| 等级 | 状态大致对应 | 能做什么 |
| --- | --- | --- |
| L0 | `stub` / 仅有画像 | 只表示发现过 |
| L1 | `partial` | 可查字段与大致用途，不能默认下业务结论 |
| L2 | `complete` | 多数 CK 表的常规目标：带日期过滤的受限 SQL |
| L3 | `verified` 或完整卡 + 验证证据 | 核心 ROI / 日报 / 投放治理 / 高频默认召回 |

## Hive 卡 vs ClickHouse 卡：一眼对照

| 维度 | Hive 表卡（`ai_hive`） | ClickHouse 表卡（`ai_ck`） |
| --- | --- | --- |
| 引擎 / 库 | MaxCompute，`hungry_studio.*` | ClickHouse，`shucang_market.*` |
| 定位 | 事实源、明细、训练与争议复核 | 报表 OLAP、看板对齐、小窗口验证 |
| 层级 `layer` | `ods` / `dwd` / `dim` / `dws` / `ads` | `fact` / `dim` / `view` / `aggregate` |
| 时间护栏 | 偏 `partitions`（常 `dt`） | 偏 `date_fields`（常 `active_date`） |
| 视图 | 较少强调 | 常有 `view_fqn` |
| 单表指标公式 | 较少用 `metric_fields` | 常用 `metric_fields` |
| 隐私门禁 | 强绑 `PII_POLICY.yaml` | 表卡内声明；整体策略仍遵守只读与脱敏 |
| 字段写法 | `columns` / `column_groups` / `columns_same_as` | 多为全量 `columns` |
| catalog | 表卡默认必须登记 | 可渐进登记 |

两套卡**共用**的核心契约：`documentation_status`、`table`、`grain`、`query_rules`、`join_keys`、`known_pitfalls`、`example_queries`、`source_docs`。

## 表卡和其他资产的关系

| 资产 | 作用 | 和表卡的关系 |
| --- | --- | --- |
| `catalog.yaml` | 表目录、优先级、领域标签、入口索引 | 指向表卡，不替代表卡 |
| `agent_manifest.yaml` | Agent 挂载和召回边界 | 告诉 Agent 何时读表卡 |
| `table_profiles/` | 轻量字段画像 | 用于字段发现，不替代表卡口径 |
| `schema_exports/` | 线上结构基线 | 给脚本检测漂移和生成画像，不默认给 Agent 问答 |
| 语义契约 `semantic_contract/` | 跨表实体、指标、维度、关联契约 | 从表卡抽象更高层语义 |
| `da_assets/verified_sql/` | 已验证可复用 SQL | 可以反向补强表卡证据 |
| `knowledge/` | 业务政策、SQL 协议、指标口径 | 补充表卡外的业务规则 |
| `freshness_snapshot.json` | 新鲜度快照 | 表卡写约定；快照写当前探测结果，二者勿混 |

## 一张合格表卡应包含什么

最少应包含：

- 文档完备状态
- 来源文档
- 表全名
- 粒度
- 日期 / 分区语义（Hive 偏分区，ClickHouse 偏日期字段）
- 查询规则
- 字段合同（清单、分组或同构引用）
- 已知陷阱
- 示例查询

进入 Agent 默认召回或高频查询时，还应补齐：

- 隐私 / 敏感字段说明
- 关联键及证据
- 表内指标字段（尤其 ClickHouse）
- 语义分组
- 新鲜度 / 延迟 / 分区说明
- 相关表
- 已验证样例 SQL 或小窗口验证记录

门禁脚本：`tools/scripts/check_table_card_quality.py`  
硬错误必须清零；质量缺口进 `eval/表卡质量门禁报告.md` 排期治理。

## 完整表卡（旧称「深卡」）

「深卡」不是行业标准，也不是一类新资产。

在本工程里，它只是历史文档里对「完整表卡」的简称，通常指已经补齐口径、日期规则、关联键、已知陷阱、示例查询和证据链的 YAML 表卡。

后续文档优先写「完整表卡」。如果旧文件里还出现「深卡」，按「完整表卡」理解。

## 状态边界

| 状态 | 含义 |
| --- | --- |
| `stub` | 只有骨架，不能作为默认事实 |
| `partial` | 有部分字段或规则，但缺少关键验证 |
| `partial_verified` | 部分口径或样例已验证，仍有待确认项 |
| `complete` | 结构完整，能指导 Agent 安全查询 |
| `verified` | 关键口径、样例 SQL、新鲜度和证据链已通过验证 |
| `deprecated_stale` | 已废弃或内容过期，勿当现行事实 |

状态不能靠填写完整字段自动升级。必须有证据：实时探测、结构校验、已验证 SQL、页面 / 代码对账或 owner 确认。

## 一句话判断

如果一个文件只告诉你「表里有什么字段」，它不是完整表卡。

如果它还能告诉你「这张表什么时候能用、怎么查、不能怎么查、和谁能关联、哪些口径需要小心」，它才是本工程意义上的表卡。
