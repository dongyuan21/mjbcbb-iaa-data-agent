# PI 路由误判与空结果掩盖重大问题

> 状态：corrected_online_replay_verified
> 日期：2026-06-23
> 级别：重大问题
> 范围：Data Agent Runtime / PI 调用链 / MaxCompute SQL 复核

## 问题概览

线上问题：

```text
查询 app_name='b-b_gp'、media='googleadwords_int' 分国家的激活 D0/D7 收入均值
```

PI 的回复不满足要求。复核发现该问题不是“数据为空”，而是 Runtime/PI 调用链同时出现三个缺陷：

1. 路由误判：业务取数问题被路由到 `table_question`，没有进入 `text2sql_or_sql_planning` 的 SQL 协议链。
2. SQL 口径误套：PI 把行为表侧 `app_name='b-b_gp'` 套到了激活表侧，导致激活表核心查询返回 0 行。
3. 空结果被掩盖：核心 SQL 返回 0 行后，PI 没有继续做 MaxCompute smoke 诊断，最终文本只展示分区 probe，答非所问。

## 实时证据

本次复核执行了 MC 与 CK 连通性和目标表 probe，不使用旧快照替代当前事实。

- MC `SELECT 1` 成功。
- MC `dwd_market_appsflyer_activation_push_data_di` 最新分区为 `2026-06-23`。
- MC `dws_b-b_all_user_multi_dim_hi` 最新分区为 `2026-06-23`。
- CK `SELECT 1` 成功。
- CK 代表表 `shucang_market.tj_ad_spend_active_v2` 最新 `active_date` 为 `2026-06-22`。

关键业务 smoke：

- 激活表使用 `app_name='b-b_gp'` + `media_source='googleadwords_int'` 返回 0 行。
- 同一激活表使用 `bundle_id='com.block.juggle'` + `media_source='googleadwords_int'` 有大量激活，激活侧真实 `app_name` 为 `b-b!`。
- 行为/收入表 `dws_b-b_all_user_multi_dim_hi` 使用 `app_name='b-b_gp'` 有数据。

因此，正确判断是：产品口径必须分表处理，不能把行为表 `app_name` 直接套到激活表。

## 根因

### 路由层

`KnowledgeRouter.route()` 旧逻辑会把 task objective 里的英文 token 做子串匹配。`table_question` 的 objective 中含有 `a`、`or` 等短词，它们会命中用户问题里的 `app_name`、`googleadwords_int`，从而把业务 SQL 问题误打到表问答路由。

### 执行层

PI prompt 只要求最多 4 次工具调用，没有把“核心业务 SQL 0 行必须 smoke 诊断”定义为硬约束。PI 在两个分区 probe 后执行了两个核心 SQL，两个核心 SQL 均为 0 行，但没有继续拆分过滤条件。

### 汇总层

`synthesize_tool_answer()` 旧逻辑会跳过 `rows=[]` 的成功查询，再回头格式化前面的非空 probe。结果是用户看到的像是“查询成功”，实际展示的是分区日期，不是业务答案。

### 落库层

线上记录中 SQL 证据主要在 assistant message metadata 的 `pi_tool_results`，`data_agent_query_records` 为空，给后续复核增加了成本。

## 已执行修复

1. 修复路由：
   - 移除 objective token 子串加分。
   - 增加业务取数信号：`app_name`、`bundle_id`、`media_source`、`country`、`国家`、`激活`、`收入`、`D0/D7`、`均值` 等。
   - 对业务取数问题强制抬高 `text2sql_or_sql_planning`，并降低误进 `table_question` / Google 配置路由的概率。

2. 修复 PI prompt：
   - 工具上限从 4 次调整到 6 次，为 smoke 诊断留预算。
   - 明确 `SELECT 1`、`MAX(dt)`、`freshness` 只能作为上下文，不能作为业务答案。
   - 明确核心 SQL 0 行时必须诊断日期、产品端、bundle_id/app_name、media、国家和 join 前后行数。

3. 修复答案合成：
   - 识别 `ok=true` 但 `row_count=0` / `rows=[]` 的核心业务 SQL。
   - 返回“核心查询返回 0 行，未形成业务答案”，不再把 probe 结果包装成最终答案。

4. 修复落库：
   - 当 `tool_executions` 缺失时，将 `pi_tool_results` 转换成 query records。
   - trace 的 `tool_calls` 中保留 `pi_tool_results`，方便审计。

5. 新增回归测试：
   - 今天的线上问题必须路由到 `text2sql_or_sql_planning`。
   - 表适用性问题仍路由到 `table_question`。
   - PI 合成答案遇到核心 SQL 0 行必须输出未完成状态。
   - `pi_tool_results` 能回填 query record 所需字段。

## 为什么 Codex 这次没有犯同样错误

不是因为 Codex 天生不会错，而是 Codex 这次走的是更强的复核流程：

1. Codex 没有只信 PI 最终回答，而是读了真实 trace、metadata 和 SQL。
2. Codex 按工作区铁律先跑 MC/CK 连通性与目标表 probe。
3. Codex 对 0 行结果没有停止，而是继续做激活表、行为表、join 前后的 smoke。
4. Codex 把“激活表 app_name 与行为表 app_name 不同”作为分表口径问题处理，而不是把 0 行当业务事实。

这说明差异来自执行协议和验证闭环，不是来自某个模型的神秘能力。PI 要减少这类错误，必须把 Codex 这次使用的强制 live probe、0 行 smoke、分表口径检查、证据落库做成 Runtime 机制。

## 验收标准

- 今天线上问题的路由不再进入 `table_question`。
- 核心 SQL 0 行时，不输出业务成功答案。
- 后续 trace 能从 query records 或 `tool_calls.pi_tool_results` 直接复核 SQL、row_count、duration 和错误。
- 重新跑同类问题时，若没有完成 smoke 诊断，答案必须明确标记为未完成。

## 历史回填决策

对 2026-06-23 之前已写入生产 MySQL、但缺少 `query_records` 的历史 trace，本轮不做批量回填。

原因：

1. 历史记录仍可从 assistant metadata 的 `pi_tool_results` 做只读复核，不影响问题审计。
2. 批量改写历史生产日志会混淆“原始线上事实”和“事后补写事实”。
3. 新版本已经把 `tool_executions`、`pi_tool_results` 和 `query_records` 一并落库，后续新 trace 从源头修正。

执行策略：

- 历史样本：只读复核，不改线上历史记录。
- 新样本：要求 trace、assistant metadata、query_records 三处同时形成证据链。
- 复核入口：统一收敛到 `tools/scripts/pi_review_tool.py`，避免再手工拼接 SSO、HTTP 和 MySQL。
