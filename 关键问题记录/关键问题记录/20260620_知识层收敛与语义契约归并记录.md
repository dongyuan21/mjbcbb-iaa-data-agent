# 20260620 知识层收敛与语义契约归并记录

> 记录日期：2026-06-20
> 范围：`ai_hive/`、`ai_ck/`、`knowledge/` 与原 `semantic_model/` 的目录边界、召回边界和维护归属
> 触发：`ai_hive` / `ai_ck` 完成三层划分后，新增 `semantic_model` 与 `knowledge` 的职责重叠逐步放大，用户指出四个文件夹边界不清会导致 Agent 知识重复沉淀、维护困难和上下文爆炸。
> 当前结论：原顶层 `semantic_model/` 已归并为 `knowledge/agent_knowledge/semantic_contract/`；顶层不再保留独立 `semantic_model` 目录。

## 一、问题是什么

三层治理先从 `ai_ck`、`ai_hive` 开始，核心收益是把资产按用途拆成：

| 层级 | 用途 | 默认召回 |
|---|---|---:|
| Agent 用的知识层 | 日常问答、选表、写 SQL、解释口径 | 是，按命中读取 |
| 工程建设沉淀层 | 构建、同步、探测、门禁、回归 | 否 |
| 审计 / 归档层 | 来源追溯、历史探索、未晋升材料 | 否 |

但当 `knowledge/` 也完成三层化以后，顶层 `semantic_model/` 继续独立存在会产生三个问题：

1. **目录语义重复**：`knowledge/` 已经是已审核业务知识、政策、报告知识和召回边界的根；`semantic_model/` 也是 Agent 用的跨表语义知识。两个顶层目录都像“知识根”，新人和 Agent 都难判断先读谁。
2. **同一事实可能双写**：跨表指标、治理状态、诊断规则既可能写进 `knowledge/policies`，也可能写进 `semantic_model/metrics.yaml` / `governance.yaml`。一旦业务规则更新，两个位置容易不一致。
3. **Agent 上下文膨胀**：默认 bootstrap 同时读 `knowledge` 与 `semantic_model`，会把政策散文、语义 YAML、编译模型、历史审计材料混到同一层，增加无效上下文。

这个问题不是命名洁癖，而是后续工程化补 Hive 表、CK 表、SQL 规则、语义口径时的归属问题。归属不清，知识越补越像平铺文件堆。

## 二、为什么没有把 semantic_model 融进 ai_hive / ai_ck

用户追问过：`semantic_model` 的知识为什么不能融到 `ai_ck` / `ai_hive`？

结论是：**不能按物理库归属跨表语义**。原因如下：

| 资产 | 正确职责 | 不适合承接跨表语义的原因 |
|---|---|---|
| `ai_hive/` | MaxCompute / Hive 单表表卡、MC 口径决策、PII、分区、join 证据 | 只代表 MC 侧事实源；把 CK/MI 或跨源 ROI 语义塞进来会让 Hive 表卡变成业务百科 |
| `ai_ck/` | ClickHouse / MI 表卡、页面字段、CK 指标语义、样例验证 | 只代表 CK / MI 查询层；正式事实、历史归因和 MC 源表不应被 CK 目录吸收 |
| `semantic_contract` | 跨表实体、指标、维度、join、治理状态、诊断规则的机器契约 | 它消费 `ai_hive` / `ai_ck` / `knowledge/policies`，不拥有物理表 |

因此，`ai_hive` 和 `ai_ck` 是“表怎么查、字段怎么用”的事实层；`semantic_contract` 是“多个事实层怎样组成业务问题”的合约层。把合约塞回任一物理表目录，都会把跨源问题变成单源偏见。

## 三、为什么最终并入 knowledge

`semantic_model` 不能融进 `ai_hive` / `ai_ck`，但也不应该继续作为顶层目录。最终选择是：

```text
knowledge/
  agent_knowledge/
    semantic_contract/
      model.json
      metrics.yaml
      dimensions.yaml
      entities.yaml
      joins.yaml
      governance.yaml
      diagnostics.yaml
  engineering_artifacts/
    semantic_contract/
  audit_archive/
    semantic_contract/
```

这等于保留语义层的机器结构，但把它纳入 `knowledge` 的三层治理。

| 原职责 | 新位置 | 召回边界 |
|---|---|---|
| Agent 运行时语义模型 | `knowledge/agent_knowledge/semantic_contract/model.json` | 默认入口 |
| 源 YAML | `knowledge/agent_knowledge/semantic_contract/*.yaml` | 维护 / 排错时读取，不默认全量塞上下文 |
| 编译与 SQL composer 回归 | `knowledge/engineering_artifacts/semantic_contract/` | 工程维护，不作为业务事实 |
| 未晋升语义候选 | `knowledge/audit_archive/semantic_contract/` | 审计线索，不默认召回 |

这样做后，`knowledge` 成为唯一的业务/语义知识根；`semantic_contract` 是其中的机器可读契约子层，而不是另一个知识根。

## 四、最终归属规则

后续补材料时按下面规则走：

| 新增内容 | 归属 |
|---|---|
| 新 MaxCompute / Hive 表、字段、分区、PII、must_filter、单表 example SQL | `ai_hive/agent_knowledge/tables/` |
| 新 CK / MI 表、字段画像、页面字段、CK 样例验证、MI 页面能力 | `ai_ck/agent_knowledge/` |
| CK / MI 专属指标解释，如 ROI360 页面字段、蓝底预估、页面筛选器 | `ai_ck/agent_knowledge/metrics/` |
| 跨表实体、指标、维度、join、治理状态、异常诊断 | `knowledge/agent_knowledge/semantic_contract/` |
| SQL 写作协议、业务分析协议、投放治理政策、默认召回边界 | `knowledge/agent_knowledge/policies/` |
| 历史报告里抽出的阈值、经验、试运行规则 | `knowledge/agent_knowledge/report_knowledge/`，必须带周期和适用边界 |
| 可复用且已验证 SQL | `da_assets/verified_sql/` |
| 候选 SQL | `da_assets/candidate_sql/` |
| 待 DA / owner 拍板事项 | `TODO/` |
| 原始导出、截图、docx、未审核草稿 | `raw_exports/`、`da_assets/raw/` 或对应 `audit_archive/`，不进默认召回 |

关键原则：

1. 表卡不写成业务百科；只保留单表事实、过滤、PII、join 证据和安全示例。
2. 政策不复制进语义契约；语义契约引用政策结论或状态，不搬运整段政策正文。
3. `model.json` 是跨表语义运行时入口；源 YAML 是维护材料，不默认整包召回。
4. 未经验证的候选语义进入 audit / TODO，不进入默认 `model.json`。

## 七、遗留观察项

1. 新增 Hive / CK 表时，表卡准入模板需要持续提醒“跨表指标不要写进表卡正文”，否则语义会慢慢回流到 `ai_hive` / `ai_ck`。
2. `ai_ck/agent_knowledge/metrics/` 与 `semantic_contract/metrics.yaml` 有天然边界：前者解释 MI / CK 页面与指标，后者定义可组合的跨表机器指标。后续维护时应避免互相复制。
3. `knowledge/agent_knowledge/report_knowledge/` 的历史阈值如果被纳入当前判断，必须显式晋升为 policy 或 semantic_contract 状态，不能靠历史报告默认生效。
4. `tools/scripts/check_*` 中保留旧 `semantic_model/` 路径检测规则，目的是防止后续文档重新引用旧目录。
