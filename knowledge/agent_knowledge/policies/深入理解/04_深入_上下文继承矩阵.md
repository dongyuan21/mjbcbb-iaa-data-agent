# 深入 04 · 上下文继承矩阵

> 系列导航：[总纲索引](00_总纲索引.md) · 上一篇：[03 判定信号与判定流程](03_深入_判定信号与判定流程.md) · 下一篇：[05 常见误判与反模式](05_深入_常见误判与反模式.md)
> 本篇讲判完 turn_kind 后，task context 里每个字段具体怎么操作：继承、清空、还是替换。

---

## 一、为什么需要一张矩阵

判完 turn_kind 只是第一步。真正的上下文管理是**字段级**的：同一个 follow_up，改维度时只覆盖 grain，其余全继承；改端时只覆盖 platform，其余全继承。如果只判到 turn_kind 就笼统地"继承上下文"，会出现两种错：

1. **该覆盖的没覆盖**：用户说「换成 iOS」，系统继承了上一轮的 platform=Android，没改。
2. **不该继承的继承了**：用户说「CPI 呢」，系统把 ROI360 的 `revenue_source=sdk` 也继承过来，但 CPI 根本不需要收入口径。

所以必须有一张**字段 × turn_kind（× 子模式）**的操作矩阵，精确到每个字段该怎么动。

---

## 二、task context 的字段清单

先把 task context 里要管理的字段列全。这是矩阵的"行"：

| 字段 | 含义 | 来源 |
|---|---|---|
| `bundle_id` / `app_name` | 产品 | 用户输入或追问 |
| `country` / `region` | 国家/地区 | 用户输入 |
| `platform` | 平台（iOS/Android/ALL） | 用户输入 |
| `active_date_range` | 时间窗口 | 用户输入 |
| `metric` | 主指标（ROI360/ROI7/DNU/CPI/留存...） | 用户输入 |
| `grain` | 维度/粒度（campaign/media_source/country/adset...） | 用户输入 |
| `revenue_source` | 收入口径（sdk/af） | 用户输入或默认 sdk |
| `cost_metric` | 消耗口径（cost_zhe折后/cost_raw折前） | 用户输入或默认折后 |
| `organic_mode` | organic 口径（all/paid_only） | 默认两版并列 |
| `compare_window` | 对照窗口（异动归因用） | 用户输入 |
| `task_type` | 任务类型（roi_analysis/dnu_analysis/retention...） | 系统识别 |
| `prev_sql` | 上一轮生成的 SQL | 系统产出 |
| `prev_result` | 上一轮查询结果摘要 | 系统产出 |
| `inherited_from` | 继承自哪一轮 | 系统标记 |
| `corrected_fields` | 本轮改了哪些字段 | 系统标记 |

---

## 三、核心继承矩阵

这是本篇的主表。每种 turn_kind 对每个字段的操作：

| 字段 | standalone | follow_up | correction | topic_switch |
|---|---|---|---|---|
| `bundle_id` | 重置 | 继承（除非改产品） | 继承（除非纠正产品） | 重置 |
| `country` | 重置 | 继承（除非改国家） | 继承（除非纠正国家） | 重置 |
| `platform` | 重置 | 继承（除非改端） | 继承（除非纠正端） | 重置 |
| `active_date_range` | 重置 | 继承（除非改时间） | 继承（除非纠正时间） | 重置 |
| `metric` | 重置 | 继承（除非换指标） | **替换为纠正值** | 重置 |
| `grain` | 重置 | 继承（除非改维度） | 继承（除非纠正维度） | 重置 |
| `revenue_source` | 重置 | 继承（除非改口径）* | **替换为纠正值** | 重置 |
| `cost_metric` | 重置 | 继承（除非改口径）* | **替换为纠正值** | 重置 |
| `organic_mode` | 重置 | 继承 | 继承（除非纠正） | 重置 |
| `compare_window` | 重置 | 继承（除非加对照） | 继承 | 重置 |
| `task_type` | 重置 | 继承 | 继承（除非纠正触及硬口径） | 重置 |
| `prev_sql` | 清空 | 可复用/可改 | 在基础上改 | 清空 |
| `prev_result` | 清空 | 可参考 | 在基础上改 | 清空 |

\* 见第四节"口径字段的特殊处理"。

### 矩阵的三种操作

- **重置**：丢弃旧值，按本轮重新收集/追问。
- **继承**：沿用上一轮的值，本轮不动。
- **替换为纠正值**：用用户纠正后的值覆盖。

### 记忆口诀

```
standalone / topic_switch → 清空重建（全字段重置）
follow_up                 → 继承 + 局部覆盖（只动用户改的字段）
correction                → 继承 + 单字段替换（只动被纠正的字段）
```

## 四、口径字段的特殊处理（follow_up 的隐蔽坑）

`revenue_source` 和 `cost_metric` 在 follow_up 里不能无脑继承，要**按新指标的依赖关系**判断。

### 4.1 问题：换指标时口径字段可能失效

```
轮1: BB 美国 7天 ROI360 sdk
  → context: {metric:ROI360, revenue_source:sdk, cost_metric:cost_zhe}

轮2: 「CPI 呢」
  → follow_up 换指标子模式
```

CPI 的定义是 `消耗 / 注册数`，**不涉及收入**。所以：
- `cost_metric`（cost_zhe）：CPI 需要 → **继承**。
- `revenue_source`（sdk）：CPI 不需要 → **丢弃**，不继承。

如果无脑继承 `revenue_source=sdk`，系统可能把它套到 CPI 计算里，跑出错值。

### 4.2 口径字段依赖表

按新 metric 判断哪些口径字段还有意义：

| 新 metric | 需要 cost_metric? | 需要 revenue_source? |
|---|---|---|
| ROI360 / ROI7 / ROAS | ✅ | ✅ |
| CPI / IPM | ✅ | ❌ |
| DNU / 激活数 | ❌ | ❌ |
| 留存率 | ❌ | ❌ |
| eCPM / ARPU | ❌ | ✅（涉及广告收入） |
| LTV | ✅ | ✅ |

**规则**：follow_up 换指标时，按这张表决定 `revenue_source` / `cost_metric` 是继承还是丢弃。丢弃的字段不能留给下一个 follow_up 用——下次换回 ROI 时要重新收。

### 4.3 这为什么不是 standalone

有人会想：换指标后口径字段变了，干脆当 standalone 重建算了。

**不行**，原因：
- 产品、国家、时间、平台这些字段是安全继承的，重建会逼用户重报。
- 换指标是典型的 follow_up 子模式，用户预期是"接着看"，不是"另起"。
- 正确做法是：继承安全字段 + 按依赖表处理口径字段 + 标记 `corrected_fields` 让用户看到改了什么。

## 五、correction 的字段替换细节

correction 看起来简单（只替换被纠正字段），但有两个细节容易漏。

### 5.1 纠正指标名时的连带替换

用户说「不是 ROI7 是 ROI360」：

| 字段 | 操作 | 说明 |
|---|---|---|
| `metric` | ROI7 → ROI360 | 直接替换 |
| `task_type` | 可能要变 | ROI360 走 MI 入口，task_type 可能从 `roi_analysis` 变 `mi_roi360_analysis` |
| `prev_sql` | 丢弃重写 | ROI7 和 ROI360 的 SQL 路径完全不同 |
| 入口资产 | 重新召回 | 要读 MI ROI360 协议，不是数仓 date_diff 逻辑 |

所以 correction 纠正指标名时，不只是改 `metric` 字段，还要连带处理 `task_type`、`prev_sql` 和召回资产。这就是 [02 四种详解](02_深入_四种turn_kind详解.md) 3.6 节说的"触及业务硬口径必须重读业务协议"。

### 5.2 纠正口径时的字段替换

用户说「消耗用折前」：

| 字段 | 操作 |
|---|---|
| `cost_metric` | cost_zhe → cost_raw |
| `prev_sql` | 在原 SQL 上替换 cost 字段，不重写 |
| 其余 | 全继承 |

这种纠正不触及硬口径，只改字段值，SQL 可以局部改。区分"纯字段值纠正"和"触及硬口径纠正"是 correction 落地的关键，详见 [07 与现有协议的关系](07_深入_与本仓库现有协议的关系.md)。

## 六、topic_switch 的清空细节

topic_switch 的动作是"清空+重建"，但清空要清干净，不能留残渣。

### 6.1 必须清空的字段

**全部字段都要清**，包括：
- 业务字段（产品/时间/口径/维度...）
- `task_type`（任务类型）
- `prev_sql` / `prev_result`（上一轮的 SQL 和结果）
- `inherited_from` / `corrected_fields`（继承标记）

### 6.2 容易漏清的字段

| 字段 | 为什么容易漏 | 后果 |
|---|---|---|
| `organic_mode` | 默认值看起来无害 | 带着上一轮的 paid_only 口径跑新话题 |
| `compare_window` | 上一轮没用就忘了 | 新话题莫名带了个对照窗口 |
| `prev_result` | 觉得"只是参考" | 误把上一轮结果当本轮基线 |

**规则**：topic_switch 时，task context 应该被**整体重置为初始状态**，只保留 `status: active` 和新的 `turn_id`。任何字段残留都是潜在的口径串台源。

### 6.3 清空后的提示

建议在输出里轻量声明清空动作：

```
【上下文】已切换到新话题，旧上下文（BB/美国/ROI360）已清除。
【本轮】实验 123 留存，重新收集参数。
```

这帮用户确认旧上下文确实没了，避免用户以为还在继承。

---

## 七、矩阵的执行顺序

判完 turn_kind 后，字段操作按以下顺序执行：

```
1. 按 turn_kind 决定大动作（清空 / 继承 / 替换）
2. 按 follow_up 子模式决定覆盖哪些字段（如适用）
3. 按口径依赖表处理 revenue_source / cost_metric（如换指标）
4. 按 correction 是否触及硬口径决定是否重读业务协议（如适用）
5. 更新 inherited_from 和 corrected_fields 标记
6. 输出上下文声明（继承了什么、改了什么、清了什么）
```

这个顺序在 [06 落地实现要点](06_深入_落地实现要点.md) 里落成 task_context 的更新逻辑。

---

## 八、本篇小结

1. **上下文管理是字段级的**，不能笼统"继承上下文"。每种 turn_kind × 每个字段都有明确的操作。
2. **核心矩阵**：standalone/topic_switch 全字段重置；follow_up 继承+局部覆盖；correction 继承+单字段替换。
3. **口径字段是 follow_up 的隐蔽坑**：换指标时 `revenue_source` / `cost_metric` 要按新指标的依赖表判断继承还是丢弃，不能无脑继承。
4. **correction 纠正指标名会连带替换**：不只改 `metric`，还要处理 `task_type`、`prev_sql`、召回资产（触及硬口径）。
5. **topic_switch 必须清干净**：全部字段重置，包括容易漏的 `organic_mode` / `compare_window` / `prev_result`。
