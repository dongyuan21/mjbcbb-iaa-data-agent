> 本篇讲怎么把 turn_kind 判定和上下文管理落成可执行的数据结构、流程编排和输出规范。

## 一、整体流程编排

turn_kind 判定不是孤立的一步，它嵌在整条执行链路的最前面。完整流程：

```
用户输入
  │
  ▼
[1] turn_kind 判定
    ├── correction / topic_switch / standalone / follow_up
    └── (follow_up 进一步判子模式)
  │
  ▼
[2] 上下文操作（按 04 矩阵）
    ├── 清空（standalone / topic_switch）
    ├── 继承 + 局部覆盖（follow_up）
    └── 继承 + 单字段替换（correction，触及硬口径则重读协议）
  │
  ▼
[3] 识别任务类型（ROI / DNU / 留存 / 实验 / 点位...）
  │
  ▼
[4] 收集 / 继承必填参数
  │
  ▼
[5] 召回资产 + freshness 检查
  │
  ▼
[6] SQL 生成与执行
  │
  ▼
[7] 结果校验
  │
  ▼
[8] 输出（含上下文声明）
```

**关键原则**：[1][2] 是对话编排层（本系列负责），[3] 及以后是业务执行层（由 `第一层分析Agent协议.md` 等业务协议负责）。两层解耦，但编排层必须先跑完，业务层才能在正确上下文上执行。

## 二、task_context 数据结构

这是上下文管理的核心数据结构。建议维护一个显式对象，而不是靠模型记忆：

```yaml
task_context:
  # —— 元信息 ——
  turn_id: 4                    # 当前轮次 ID
  turn_kind: follow_up          # 本轮 turn_kind 判定结果
  turn_submode: change_metric   # follow_up 子模式（仅 follow_up 有）
  status: active                # active / cleared / partial
  inherited_from: turn_3        # 继承自哪一轮（standalone/topic_switch 为 null）
  corrected_fields:             # 本轮改了哪些字段
    - metric
  correction_type: null         # 纯字段值 / 硬口径（仅 correction 有）

  # —— 业务字段 ——
  task_type: roi_analysis       # 任务类型
  bundle_id: com.bb.xxx         # 产品
  app_name: BB
  country: US                   # 国家
  platform: iOS                 # 平台（本轮被 follow_up 覆盖）
  active_date_range:            # 时间窗口
    - '2026-07-11'
    - '2026-07-17'
  metric: CPI                   # 指标（本轮被换指标子模式覆盖）
  grain: media_source           # 维度
  revenue_source: null          # 收入口径（换指标后按依赖表丢弃）
  cost_metric: cost_zhe         # 消耗口径（CPI 需要，继承）
  organic_mode:                 # organic 口径
    - all
    - paid_only
  compare_window: null          # 对照窗口

  # —— 执行产物 ——
  prev_sql: null                # 上一轮 SQL（换指标后作废）
  prev_result: null             # 上一轮结果摘要
  recalled_assets: []           # 本轮召回的资产
```

### 字段设计要点

1. **元信息和业务字段分开**：元信息管"本轮是什么性质"，业务字段管"查什么"。
2. **`status` 字段是判定的地基**：`active` 才能被继承，`cleared` 表示已清空，`partial` 表示残缺（偏向 standalone）。
3. **`corrected_fields` 让操作可追溯**：用户和系统都能看到本轮改了什么，方便发现串口径。
4. **`correction_type` 区分硬口径**：决定是否触发业务协议重读（见 [07](07_深入_与本仓库现有协议的关系.md)）。

## 三、turn_kind 判定的代码骨架

把 [03 决策树](03_深入_判定信号与判定流程.md) 落成代码：

```python
def classify_turn_kind(user_input: str, prev_context: TaskContext) -> TurnKindResult:
    # Step 1: 语气信号 - correction
    if has_correction_signal(user_input):
        sub = classify_correction_type(user_input, prev_context)
        return TurnKindResult(
            kind="correction",
            submode=None,
            corrected_fields=sub.fields,
            correction_type=sub.hard_or_soft,  # 硬口径 / 纯字段值
        )

    # Step 2: 语气信号 - topic_switch
    if has_explicit_switch_signal(user_input):
        return TurnKindResult(kind="topic_switch")

    # Step 3: 上下文状态
    if prev_context is None or prev_context.status == "cleared":
        return TurnKindResult(kind="standalone")

    if prev_context.status == "partial":
        if not has_strong_followup_signal(user_input):
            return TurnKindResult(kind="standalone")

    # Step 4: 结构 + 词汇信号
    has_full = has_product_or_metric_anchor(user_input)
    has_followup_lex = has_pronoun_or_incremental_verb(user_input)

    if has_full and not has_followup_lex:
        if domain_overlaps(prev_context, user_input):
            return TurnKindResult(kind="follow_up", submode="change_product")
        else:
            return TurnKindResult(kind="topic_switch")
    elif has_followup_lex or is_short_missing_subject(user_input):
        sub = classify_followup_submode(user_input)
        return TurnKindResult(kind="follow_up", submode=sub)

    # Step 5: 兜底
    return TurnKindResult(kind="standalone")
```

### 信号检测函数的实现要点

```python
# 语气信号词表（最强优先级）
CORRECTION_PATTERNS = [
    r"不是.{1,10}是",      # 不是 ROI7 是 ROI360
    r"我说的是",           # 我说的是预估
    r"我指的是",
    r"刚才说错了",
    r"不对.{0,5}应该是",
]
SWITCH_PATTERNS = [
    r"不看.{1,10}了",
    r"换个话题",
    r"先不查这个",
    r"不查.{1,10}了",
]

# 增量动词 → follow_up 子模式
INCREMENTAL_VERB_MAP = {
    "换成": "change_platform",      # 换成 iOS（需结合宾语判断）
    "拆": "change_grain",           # 媒体拆一下
    "按": "change_grain",           # 按国家分
    "下钻": "change_grain",
    "加": "add_compare",
    "去掉": "change_grain",
}
```

**注意**：增量动词到子模式的映射不是一对一，要结合宾语判断。比如"换成 iOS"是改端，"换成 af"是改口径。实际实现要词表 + 宾语分类。

## 四、上下文操作的代码骨架

判完 turn_kind 后，按 [04 矩阵](04_深入_上下文继承矩阵.md) 执行字段操作：

```python
def apply_turn_kind(context: TaskContext, result: TurnKindResult, user_input: str) -> TaskContext:
    if result.kind in ("standalone", "topic_switch"):
        # 清空重建
        new_ctx = TaskContext(status="active", turn_id=context.turn_id + 1)
        new_ctx.inherited_from = None
        return new_ctx

    if result.kind == "follow_up":
        # 继承 + 局部覆盖
        new_ctx = copy(context)
        new_ctx.turn_id = context.turn_id + 1
        new_ctx.inherited_from = context.turn_id
        new_ctx.corrected_fields = []

        # 按子模式覆盖字段
        for field in fields_to_override(result.submode, user_input):
            new_ctx.set_field(field, extract_value(field, user_input))
            new_ctx.corrected_fields.append(field)

        # 口径字段按依赖表处理（换指标时）
        if result.submode == "change_metric":
            handle_metric_dependency(new_ctx)

        return new_ctx

    if result.kind == "correction":
        # 继承 + 单字段替换
        new_ctx = copy(context)
        new_ctx.turn_id = context.turn_id + 1
        new_ctx.inherited_from = context.turn_id
        new_ctx.corrected_fields = result.corrected_fields
        new_ctx.correction_type = result.correction_type

        # 替换被纠正字段
        for field in result.corrected_fields:
            new_ctx.set_field(field, extract_correction(field, user_input))

        # 触及硬口径则重读协议、丢弃 prev_sql
        if result.correction_type == "hard":
            new_ctx.prev_sql = None
            new_ctx.protocol_reload_needed = True

        return new_ctx
```

### 口径依赖处理

```python
METRIC_DEPENDENCY = {
    "ROI360":   {"cost_metric": True,  "revenue_source": True},
    "ROI7":     {"cost_metric": True,  "revenue_source": True},
    "CPI":      {"cost_metric": True,  "revenue_source": False},
    "DNU":      {"cost_metric": False, "revenue_source": False},
    "retention":{"cost_metric": False, "revenue_source": False},
    "eCPM":     {"cost_metric": False, "revenue_source": True},
    "LTV":      {"cost_metric": True,  "revenue_source": True},
}

def handle_metric_dependency(ctx: TaskContext):
    dep = METRIC_DEPENDENCY.get(ctx.metric, {})
    if not dep.get("revenue_source", True):
        ctx.revenue_source = None  # 丢弃，不继承
    if not dep.get("cost_metric", True):
        ctx.cost_metric = None
```

## 五、输出声明规范

每轮输出开头声明上下文来源，让用户看到继承了什么、改了什么。这是发现串口径的第一道防线。

### standalone / topic_switch 的输出

```
【上下文】已切换到新话题 / 新问题，旧上下文已清除。
【本轮】实验 123 留存，重新收集参数。
```

### follow_up 的输出

```
【上下文】继承自上一轮：BB / 美国 / 近7天 / ROI360 / sdk
【本轮改动】platform → iOS（follow_up: 改端）
```

### correction 的输出

```
【上下文】继承自上一轮：BB / ROI7 / 近7天
【纠正】roi_source: actual → forecast_blue
【注意】预估值不能伪装成真实回收，已标注 roi_source=forecast_blue
```

### correction 触及硬口径的输出

```
【上下文】继承自上一轮：BB / 近7天
【纠正】metric: ROI7 → ROI360（触及硬口径）
【重读协议】已重新读取 MI ROI360 协议
【换入口】数仓 date_diff → MI ROI360 入口
【丢弃】上一轮 SQL 已作废，重新生成
```

### 输出声明的规则

1. **必须声明继承的字段**：让用户看到"系统用了上一轮的什么"。
2. **必须声明改动的字段**：让用户看到"本轮改了什么"。
3. **触及硬口径必须声明重读协议**：让用户知道"不是简单改名字"。
4. **topic_switch 必须声明清空**：让用户确认旧上下文没了。

## 六、兜底追问机制

判定不确定时，触发兜底追问（[03 红线原则](03_深入_判定信号与判定流程.md) 第五节）。

### 触发条件

```python
def should_fallback_clarify(result: TurnKindResult, context: TaskContext, user_input: str) -> bool:
    # 信号冲突
    if has_conflicting_signals(user_input):
        return True
    # 领域部分重叠，判不准
    if result.kind == "follow_up" and domain_partial_overlap(context, user_input):
        return True
    # 高风险场景（ROI / 投放治理）
    if context.task_type in HIGH_RISK_TYPES and result.kind == "follow_up" and result.confidence < THRESHOLD:
        return True
    return False
```

### 追问话术模板

| 场景 | 话术 |
|---|---|
| follow_up vs topic_switch 不确定 | 「你是想在 {产品} 的基础上改，还是另起一个新问题？」 |
| 同领域换产品不确定 | 「你说的"{指标}"是接着 {上轮产品} 看，还是查 {本轮产品} 的？」 |
| correction 对象不确定 | 「你纠正的是 {字段A} 还是 {字段B}？」 |

### 追问的输出

```
【需要确认】我不确定你是想：
  A. 在 BB 的基础上换成 iOS 看（follow_up）
  B. 另起一个新问题（新话题）
请选 A 或 B，或者补充说明。
```

## 七、与业务执行层的接口

turn_kind 编排层跑完后，要把处理好的 task_context 交给业务执行层。接口约定：

### 编排层输出给业务层的字段

```yaml
# 编排层产出的 task_context，交给业务层
handoff:
  task_context: <上面的 task_context 对象>
  ready_for_business: true          # 上下文已就绪
  protocol_reload_needed: false     # 是否需要业务层重读协议（correction 硬口径时为 true）
  fallback_clarify_needed: false    # 是否需要先追问用户（true 时业务层暂不执行）
```

### 业务层的约定

业务层（`第一层分析Agent协议.md` 等）收到 handoff 后：
1. 先检查 `fallback_clarify_needed`：为 true 则先追问，不执行业务。
2. 检查 `protocol_reload_needed`：为 true 则重读对应业务协议。
3. 用 `task_context` 里的字段执行任务识别、参数收集、召回、SQL、校验、输出。

这个接口保证编排层和业务层解耦：编排层只管上下文边界，业务层只管业务执行。

## 八、测试与验证

落地后怎么验证 turn_kind 判定对不对？建议建一组测试用例：

### 测试用例结构

```yaml
- id: tc_001
  description: follow_up 改端
  prev_context:
    task_type: roi_analysis
    bundle_id: BB
    metric: ROI360
    platform: Android
  user_input: "换成 iOS"
  expected:
    turn_kind: follow_up
    submode: change_platform
    corrected_fields: [platform]
    inherited: [bundle_id, metric, country, active_date_range]
```

### 必须覆盖的场景

| 场景 | 用例编号 | 验证点 |
|---|---|---|
| 会话第一句 | tc_000 | standalone，无继承 |
| follow_up 改端 | tc_001 | 继承产品/指标，覆盖 platform |
| follow_up 换指标 | tc_002 | 口径字段按依赖表处理 |
| correction 纯字段值 | tc_003 | 只改字段，不重读协议 |
| correction 硬口径 | tc_004 | 重读协议，丢弃 prev_sql |
| topic_switch 显式 | tc_005 | 清空全部字段 |
| standalone 当 follow_up（R2） | tc_006 | 自带完整参数 + 领域切换 → topic_switch |
| 信号冲突兜底 | tc_007 | 触发追问 |

这组用例可以纳入本仓库的 `eval/agent_regression/` 回归体系。

## 九、本篇小结

1. **流程编排**：turn_kind 判定是整条链路第一道闸，跑完才进业务执行层。
2. **task_context 是核心数据结构**：显式维护元信息 + 业务字段 + 执行产物，不靠模型记忆。
3. **判定和执行分离**：判定层产 TurnKindResult，执行层按矩阵操作字段。
4. **口径字段按依赖表处理**：换指标时 revenue_source/cost_metric 不能无脑继承。
5. **输出声明是防串口径的第一道防线**：每轮声明继承/改动/清空，让用户看得见。
6. **兜底追问机制**：判不准宁可问，不乱继承，高风险场景优先兜底。
7. **编排层和业务层解耦**：通过 handoff 接口传递，编排层不管业务，业务层不管上下文边界。
