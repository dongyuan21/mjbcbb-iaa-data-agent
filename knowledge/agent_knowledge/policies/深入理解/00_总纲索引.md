## 一、为什么要有 turn_kind

多轮对话里，用户每一句话的「性质」是不一样的。如果系统不分类型，把每轮都当独立问题处理，会出现两类典型故障：

1. **该继承的不继承**：用户先问「看下 BB 的 ROI360」，下一句「换成 iOS」。如果系统把「换成 iOS」当独立新问题，就会反问「看什么产品？看什么指标？」——用户明明只改了一个维度，却被要求把全套参数重报一遍，体验很差。
2. **该清空的不清空**：用户先做 ROI360，突然说「查实验 123 的留存」。如果系统还在继承上一轮的产品/时间/口径，就可能把「BB」「美国」「ROI7 窗口」悄悄带进实验留存查询，跑出张冠李戴的数。

`turn_kind` 就是用来在「回答之前」先做一次**轮次性质判定**，决定本轮要继承什么、清空什么、纠正什么。它不是业务逻辑，是**对话编排逻辑**——在真正去召回表卡、生成 SQL 之前，先把上下文边界画对。

一句话总结：

> **turn_kind 解决的是"这一轮站在哪一轮的肩膀上"的问题。判对了，上下文自然连续；判错了，要么反复追问，要么偷偷串口径。**

## 二、四种 turn_kind 详解

### 1. standalone（独立新问题）

**定义**：本轮与前面没有任何继承关系，是一个全新话题的开端。

**特征**：
- 用户**自带完整参数**（或准备接受系统追问补全）。
- 不依赖上一轮的产品、时间、口径、维度。
- 通常是会话的第一句，或话题被明确切断后的第一句。

**判定信号**：
- 出现完整的问题结构：「产品 + 指标 + 时间 + 维度」至少有产品或指标锚点。
- 句子里**没有指代词**（「它」「这个」「换成」「不是」）。
- 话题领域切换：上一轮讲投放，这一轮直接讲实验/埋点/素材冷启动。

**例子**：
- 「看下 BB 的 ROI360」（会话第一句）
- 「实验 123 的 D1 留存是多少」（突然切到实验领域）
- 「皇室麻将最近一周美国 DNU 拆一下媒体」（自带产品+时间+国家+维度）

**系统行为**：
- **清空**上一轮的 task context（产品、时间、口径、维度、revenue_source、cost_metric 等）。
- 按新问题重新走「识别任务类型 → 收集必填参数 → 召回资产」全流程。
- 缺参数就追问，**不要**从上一轮继承参数来"补全"本轮。

**反模式**：用户第一句「BB 的 ROI7」之后，第二句突然说「MB 的留存」。如果系统判定为 standalone（正确），就该清掉 ROI7 上下文，重新收 MB 留存参数；如果误判成 follow_up，可能把 ROI7 的时间窗口/收入源悄悄套到 MB 留存查询上。

---

### 2. follow_up（追问/继承）

**定义**：本轮接着上一轮问，要**继承**前面的产品、时间、口径，只做局部修改或下钻。

**特征**：
- 用户只说了**改动的那一部分**，其余默认沿用上一轮。
- 句子短、带指代、带「换成 / 拆一下 / 也看下 / 加个 / 去掉」等增量动词。
- 不重新声明产品或主指标。

**典型子模式**（理解 follow_up 的关键）：

| 子模式 | 用户在改什么 | 例子 |
|---|---|---|
| 改维度 | 加/换 group by | 「媒体拆一下」「按国家分」 |
| 改端 | iOS ↔ Android | 「换成 iOS」「GP 呢」 |
| 改时间 | 换日期窗口 | 「看上周的」「拉到昨天」 |
| 改口径 | sdk ↔ af / 折后 ↔ 折前 | 「用 af 看下」「折前消耗」 |
| 改粒度 | campaign → adset → ad | 「下钻到 adset」 |
| 加对照 | 加对比组 | 「加上同期对比」 |
| 同主体换指标 | 同产品同窗口换看一个数 | 「留存呢」「CPI 呢」 |

**判定信号**：
- 句子里**缺主语/缺时间**，但能从上一轮补上。
- 出现指代词：「它」「这个产品」「那张表」。
- 出现增量动词：「拆 / 换 / 加 / 去掉 / 下钻 / 也看下 / 对比」。
- 指标词单独出现：「CPI 呢」「留存呢」（隐含"还是那个产品那个窗口"）。

**系统行为**：
- **继承**上一轮的：产品、时间窗口、revenue_source、cost_metric、organic 口径等**未明确改动的字段**。
- **只覆盖**用户本轮明确改动的字段。
- 不追问已继承的字段；只追问本轮新引入但缺失的字段。
- 输出时声明「继承自上一轮」的字段，方便用户发现串口径。

**例子与继承映射**：

```
轮1: 「BB 美国最近 7 天 ROI360，sdk 收入」
轮2: 「换成 iOS」
  → 继承: BB / 美国 / 7天 / ROI360 / sdk
  → 覆盖: platform = iOS

轮3: 「媒体拆一下」
  → 继承: BB / 美国 / 7天 / ROI360 / sdk / iOS
  → 覆盖: grain = media_source

轮4: 「CPI 呢」
  → 继承: BB / 美国 / 7天 / iOS / media_source
  → 覆盖: metric = CPI（同主体换指标，窗口/维度继承）
```

**反模式**：用户说「换成 iOS」，系统却追问「看什么产品？看什么指标？」——这是把 follow_up 误判成 standalone，破坏了对话连续性。

### 3. correction（纠正）

**定义**：用户在**纠正系统上一轮的理解或口径**，不是新需求，是修上一轮的错。

**特征**：
- 用户指出系统理解错了，或自己上一轮说错了。
- 带「不是…是…」「我说的是…」「错了」等否定/更正语气。
- 纠正对象是**口径/参数/指标名**，不是加新维度。

**典型纠正对象**：

| 纠正类型 | 例子 |
|---|---|
| 纠正指标名 | 「不是 ROI7 是 ROI360」「我说的是预估不是实际」 |
| 纠正口径 | 「消耗用折前」「收入要 af 的」 |
| 纠正产品 | 「不是 BB 是 MB」 |
| 纠正时间 | 「不是上周是上周一到周日」 |
| 纠正维度 | 「不是按国家是按媒体」 |

**判定信号**：
- 出现否定+更正结构：「不是 X 是 Y」「X 不对，应该是 Y」。
- 出现「我说的是 / 我指的是 / 刚才说错了」。
- 纠正的是一个**已在上一轮出现过的字段**，而非新字段。

**系统行为**：
- **不重新走全流程**，而是在上一轮 task context 基础上**替换被纠正的字段**。
- 明确回显纠正后的口径，让用户确认改对了：「明白，改成 ROI360（预估），其余沿用」。
- **不要**把纠正当成新需求重新收参数。
- 如果纠正触及业务硬口径（如 ROI7 vs ROI360 的窗口定义），必须同步读对应业务协议，不能只改字段名。

**例子**：

```
轮1: 「BB 的 ROI7」
轮2（系统）: 输出 ROI7（date_diff<=6）
轮3: 「我说的是预估不是实际」
  → 纠正: roi_source = forecast（蓝底预估）
  → 继承: BB / ROI7 / 其余
  → 必须标注: roi_source=forecast_blue，不能伪装成真实回收

轮4: 「不是 ROI7 是 ROI360」
  → 纠正: metric = ROI360
  → 注意: ROI360 是 MI 页面概念，要走 MI ROI360 入口，不是简单改 N
```

**反模式**：用户说「我说的是预估不是实际」，系统却重新问「看什么产品？什么时间窗口？」——纠正只改一个字段，不该推翻整轮上下文。

---

### 4. topic_switch（切话题）

**定义**：用户**明确换主题**，要清掉旧上下文，开新任务。

**特征**：
- 主题领域彻底切换：投放 → 实验 / 埋点 / 素材 / 数据质量。
- 用户可能带「不看 X 了，看 Y」「换个话题」等显式切换语。
- 也可能没有切换语，但新问题自带完整参数且与上一轮毫无关联——这时和 standalone 表现一致，区别在于**意图**（standalone 可能是会话起点，topic_switch 一定是从旧话题跳出）。

**判定信号**：
- 出现显式切换语：「不看 X 了」「换个话题」「先不查这个」。
- 新问题领域与上一轮不同，且**自带完整参数**（说明用户不想继承任何东西）。
- 新问题的产品/指标/时间与上一轮完全不重叠。

**topic_switch vs standalone 的区别**：

| 维度 | standalone | topic_switch |
|---|---|---|
| 上下文状态 | 之前无上下文（会话起点）或已被清空 | 之前有活跃上下文，需要主动清掉 |
| 系统动作 | 直接建新 context | 先清旧 context，再建新 context |
| 判定难点 | 几乎无难点 | 难在判断"是切话题还是同领域 follow_up" |

**系统行为**：
- **主动清空**上一轮 task context（产品、时间、口径、维度、中间结果）。
- 不继承任何字段。
- 按新问题重新走完整流程。
- 可在输出中轻量提示「已切换到新话题」，帮用户确认旧上下文已清除。

**例子**：
- 「不看 ROI 了，查实验 123 的留存」（显式切换语 + 新领域）
- 「BB 的 ROI7」→「MB 的 D1 留存拆媒体」（产品+指标+领域全换，自带参数，判 topic_switch）

**反模式**：用户说「不看 ROI 了，查实验留存」，系统却还在用 BB 的产品上下文去查实验留存——这是没清掉旧 context。

## 三、判定信号与判定流程

判定 turn_kind 不是靠单一信号，而是**多信号叠加**。建议按以下顺序判断：

### 判定决策树

```
Step 1: 有否定/更正语气？（不是…是… / 我说的是… / 错了）
  → YES → correction
  → NO  → Step 2

Step 2: 有显式切换语？（不看X了 / 换话题 / 先不查这个）
  → YES → topic_switch
  → NO  → Step 3

Step 3: 本轮自带完整参数（产品+指标锚点）且与上一轮无指代关系？
  → YES → 上一轮有活跃上下文？
            → YES → topic_switch（从旧话题跳到新话题）
            → NO  → standalone（会话起点或上下文已空）
  → NO  → Step 4

Step 4: 句子短、缺主语、带指代/增量动词（拆/换/加/也看下）？
  → YES → follow_up
  → NO  → 兜底：当 standalone 处理（宁可追问，不乱继承）
```

### 关键信号清单

| 信号 | 指向 |
|---|---|
| 「不是…是…」「我说的是」 | correction |
| 「不看X了」「换话题」 | topic_switch |
| 指代词（它/这个/那个） | follow_up |
| 增量动词（拆/换/加/下钻/也看下） | follow_up |
| 单指标词（CPI呢/留存呢） | follow_up（同主体换指标） |
| 自带产品+指标+时间，无指代 | standalone 或 topic_switch |
| 会话第一句 | standalone |
| 领域彻底切换 | topic_switch |

### 兜底原则

> **判定不确定时，宁可当 standalone 追问，不要当 follow_up 乱继承。**

理由：误判成 standalone 顶多多问一句，用户成本小；误判成 follow_up 会偷偷串口径，跑出错的数，用户成本大。在投放/ROI 场景里，串口径可能直接导致错误的停投/放量建议，这是红线问题。

## 四、上下文继承矩阵

不同 turn_kind 对上下文字段的操作：

| 字段类型 | standalone | follow_up | correction | topic_switch |
|---|---|---|---|---|
| 产品 (bundle_id) | 重置 | 继承（除非用户改） | 继承（除非纠正产品） | 重置 |
| 时间窗口 | 重置 | 继承（除非用户改） | 继承（除非纠正时间） | 重置 |
| 指标 (metric) | 重置 | 继承（除非换指标） | 替换为纠正值 | 重置 |
| 维度 (grain) | 重置 | 继承（除非用户改） | 继承（除非纠正维度） | 重置 |
| 口径 (revenue_source/cost_metric) | 重置 | 继承（除非用户改） | 替换为纠正值 | 重置 |
| 平台 (platform) | 重置 | 继承（除非用户改） | 继承（除非纠正平台） | 重置 |
| 上一轮 SQL / 中间结果 | 清空 | 可复用 | 在基础上改 | 清空 |
| 上一轮 task type | 清空 | 继承 | 继承 | 清空 |

**记忆口诀**：
- standalone / topic_switch = **清空重建**
- follow_up = **继承+局部覆盖**
- correction = **继承+单字段替换**

## 五、常见误判与反模式

### 反模式 1：把 follow_up 当 standalone

**表现**：用户说「换成 iOS」，系统反问「请问看什么产品？什么指标？什么时间？」

**根因**：没识别指代/增量动词，把短句当不完整新问题。

**后果**：体验差，用户要重报全套参数。

**修法**：先检查上一轮是否有活跃上下文 + 本轮是否缺主语，再决定要不要追问。

### 反模式 2：把 standalone 当 follow_up

**表现**：用户说「MB 的 D1 畘存」，系统偷偷带上上一轮 BB 的美国窗口去查。

**根因**：看到自带产品名就以为是同领域追问，没检查领域是否切换。

**后果**：串口径，跑出错误数据。

**修法**：本轮自带完整参数 + 领域切换时，判 topic_switch 或 standalone，强制清空旧 context。

### 反模式 3：把 correction 当新需求

**表现**：用户说「我说的是预估不是实际」，系统重新问「好的，请问看什么产品的预估？」

**根因**：没识别否定+更正结构，把纠正当全新问题。

**后果**：用户要重报参数，且纠正意图被吞掉。

**修法**：检测到「不是…是…」「我说的是」就进 correction 分支，只替换被纠正字段。

### 反模式 4：topic_switch 不清上下文

**表现**：用户说「不看 ROI 了，查实验 123 留存」，系统还在用 BB + 美国 + 7天窗口去查实验。

**根因**：识别到了新问题，但没主动清旧 context。

**后果**：跨领域串口径，最危险的一种。

**修法**：topic_switch 必须显式清空 task context，并在输出中提示「已切换话题」。

### 反模式 5：纠正触及业务硬口径却只改字段名

**表现**：用户说「不是 ROI7 是 ROI360」，系统只把 metric 字段从 ROI7 改成 ROI360，没切到 MI ROI360 入口。

**根因**：correction 只做字符串替换，没检查纠正对象的业务定义。

**后果**：ROI360 是 MI 页面概念，有独立的 forecast/summary 逻辑，简单改 N 会跑错。

**修法**：correction 触及业务硬口径时，必须同步读对应业务协议（如 MI ROI360 协议、ROI_N 窗口定义），重新选入口和资产。

## 六、落地实现要点

### 1. turn_kind 判定放在流程最前面

在「识别任务类型 → 收集参数 → 召回资产」**之前**，先做 turn_kind 判定。伪流程：

```
用户输入
  → turn_kind 判定（correction / topic_switch / standalone / follow_up）
  → 上下文操作（清空 / 继承 / 替换）
  → 识别任务类型（ROI / DNU / 留存 / 实验 / 点位...）
  → 收集/继承必填参数
  → 召回资产 + freshness 检查
  → SQL 生成与执行
  → 结果校验 + 输出
```

### 2. task context 数据结构

建议维护一个显式的 task context 对象，而不是靠模型记忆：

```yaml
task_context:
  turn_kind: follow_up          # 本轮判定结果
  task_type: roi_analysis       # 任务类型
  bundle_id: com.bb.xxx         # 产品
  country: US                   # 国家
  platform: iOS                 # 平台（本轮被 follow_up 覆盖）
  active_date_range: [2026-07-11, 2026-07-17]  # 时间窗口
  metric: ROI360                # 指标
  revenue_source: sdk           # 收入口径
  cost_metric: cost_zhe         # 消耗口径
  grain: media_source           # 维度（本轮被 follow_up 覆盖）
  inherited_from: turn_3        # 继承自哪一轮
  corrected_fields: [platform]  # 本轮改了哪些字段
```

### 3. 输出中声明继承关系

每轮输出开头声明本轮上下文来源，方便用户发现串口径：

```
【上下文】继承自上一轮：BB / 美国 / 7天 / sdk / ROI360
【本轮改动】platform → iOS（follow_up）
```

### 4. 兜底追问

判定不确定时，不要硬猜，可以**主动问一句**确认 turn_kind：

> 「你是想在 BB 的基础上换成 iOS 看，还是另起一个新问题？」

这在高风险场景（ROI/投放治理）里比乱继承安全。

### 5. 与业务协议联动

turn_kind 只管对话编排，不管业务口径。当判定为 correction 且纠正对象是业务硬口径（ROI7↔ROI360、sdk↔af、折前↔折后）时，必须触发对应业务协议的重新读取，不能只改字段名。本仓库的业务协议入口见 `第一层分析Agent协议.md` 和 `投放与ROI预估SQL协议.md`。

---

## 七、与本仓库现有协议的关系

| 本协议负责 | 其他协议负责 |
|---|---|
| 轮次性质判定（standalone/follow_up/correction/topic_switch） | 任务类型识别（ROI/DNU/留存/实验/点位）→ `第一层分析Agent协议.md` |
| 上下文继承/清空/纠正的字段操作 | 字段业务口径定义（ROI_N 窗口、revenue_source、cost_metric）→ `投放与ROI预估SQL协议.md` |
| 判定兜底原则（宁追问不乱继承） | SQL 生成护栏、freshness 检查、结果校验 → `第一层分析Agent协议.md` |
| correction 触发业务协议重读的信号 | 业务硬口径本身 → 各业务协议 |

**执行顺序**：turn_kind 判定 → 上下文操作 → 任务类型识别 → 业务协议读取 → 参数收集 → 召回 → SQL → 校验 → 输出。

turn_kind 是这条链路的**第一道闸**，判错了后面全错；判对了，后面的业务协议才能在正确的上下文上执行。
