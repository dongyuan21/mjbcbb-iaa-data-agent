# 深入 02 · 四种 turn_kind 详解

> 系列导航：[总纲索引](00_总纲索引.md) · 上一篇：[01 为什么要有 turn_kind](01_深入_为什么要有turn_kind.md) · 下一篇：[03 判定信号与判定流程](03_深入_判定信号与判定流程.md)
> 本篇逐种展开四种 turn_kind 的定义、特征、子模式、判定信号、系统行为和反模式。

---

## 总览

| turn_kind | 一句话定义 | 上下文动作 | 核心特征 |
|---|---|---|---|
| standalone | 独立新问题，无继承 | 清空重建 | 自带完整参数，无指代 |
| follow_up | 追问/继承，局部修改 | 继承+局部覆盖 | 短句，指代/增量动词 |
| correction | 纠正上一轮的理解或口径 | 继承+单字段替换 | 否定+更正结构 |
| topic_switch | 明确换主题 | 主动清空+重建 | 显式切换语或领域全换 |

下面逐种深入。

---

## 1. standalone（独立新问题）

### 1.1 定义

本轮与前面没有任何继承关系，是一个**全新话题的开端**。用户自带完整参数（或准备接受系统追问补全），不依赖上一轮的任何字段。

### 1.2 什么时候是 standalone

- **会话的第一句**：没有任何上文可继承。
- **话题被明确切断后的第一句**：上一轮已 topic_switch 清空，本轮自然 standalone。
- **用户直接抛一个完整新问题**：自带产品+指标锚点，且与上一轮无指代关系。

### 1.3 判定信号

| 信号 | 说明 |
|---|---|
| 完整问题结构 | 「产品 + 指标 + 时间 + 维度」至少有产品或指标锚点 |
| 无指代词 | 没有「它」「这个」「换成」「不是」 |
| 领域锚点清晰 | 句子里明确出现产品名/指标名/表名 |
| 会话起点 | 第一句默认 standalone |

### 1.4 例子

```
✅ 「看下 BB 的 ROI360」                  （会话第一句，自带产品+指标）
✅ 「实验 123 的 D1 留存是多少」           （自带实验号+指标，领域切换）
✅ 「皇室麻将最近一周美国 DNU 拆媒体」     （自带产品+时间+国家+维度）
```

### 1.5 系统行为

1. **清空**上一轮 task context 的所有字段。
2. 按新问题重新走完整流程：识别任务类型 → 收集必填参数 → 召回资产。
3. 缺参数就追问，**绝不**从上一轮继承参数来"补全"本轮。
4. 建立新的 task context，标记 `inherited_from: null`。

### 1.6 反模式

**误判成 follow_up**：用户第一句「BB 的 ROI7」之后，第二句突然说「MB 的留存」。如果系统判成 follow_up，可能把 ROI7 的时间窗口/收入源悄悄套到 MB 留存查询上。

**正确做法**：本轮自带完整参数（MB + 留存）+ 领域/产品切换 → 判 standalone 或 topic_switch，清空旧 context。

### 1.7 standalone vs topic_switch 的边界

这是最容易混的地方，详细对比见 [04 上下文继承矩阵](04_深入_上下文继承矩阵.md) 和 [07 与现有协议的关系](07_深入_与本仓库现有协议的关系.md)。这里先给结论：

- **区别只在"之前有没有活跃上下文"**。
- standalone：之前无上下文（起点）或已清空 → 直接建新 context。
- topic_switch：之前有活跃上下文 → **必须主动清**再建新 context。
- 用户输入相同时（都是自带完整新问题），系统动作不同。

## 2. follow_up（追问/继承）

### 2.1 定义

本轮接着上一轮问，要**继承**前面的产品、时间、口径，只做局部修改或下钻。用户只说了**改动的那一部分**，其余默认沿用上一轮。

### 2.2 follow_up 的七种子模式（理解关键）

follow_up 不是一种单一行为，而是"在已有上下文上做局部修改"的一族行为。按"改了什么"分七类：

| 子模式 | 用户在改什么 | 例子 | 覆盖字段 |
|---|---|---|---|
| 改维度 | 加/换 group by | 「媒体拆一下」「按国家分」 | grain |
| 改端 | iOS ↔ Android | 「换成 iOS」「GP 呢」 | platform |
| 改时间 | 换日期窗口 | 「看上周的」「拉到昨天」 | active_date_range |
| 改口径 | sdk ↔ af / 折后 ↔ 折前 | 「用 af 看下」「折前消耗」 | revenue_source / cost_metric |
| 改粒度 | campaign → adset → ad | 「下钻到 adset」 | grain（更细） |
| 加对照 | 加对比组 | 「加上同期对比」 | compare_window |
| 同主体换指标 | 同产品同窗口换看一个数 | 「留存呢」「CPI 呢」 | metric |

**理解这七种子模式的意义**：
- 每种子模式只覆盖**特定字段**，其余字段全部继承。
- 系统不需要猜用户想改什么，靠子模式就能精确定位"改哪个字段"。
- 判定 follow_up 后，进一步判子模式，能让上下文操作更精确（见 [06 落地实现要点](06_深入_落地实现要点.md) 的 task_context 结构）。

### 2.3 判定信号

| 信号 | 说明 | 指向子模式 |
|---|---|---|
| 指代词 | 「它」「这个产品」「那张表」 | 通用 follow_up |
| 增量动词 | 「拆/换/加/去掉/下钻/也看下/对比」 | 按动词对应子模式 |
| 单指标词 | 「CPI 呢」「留存呢」 | 同主体换指标 |
| 缺主语 | 句子短，没产品名 | 继承产品 |
| 缺时间 | 没说时间窗口 | 继承时间 |

### 2.4 例子与继承映射

这是理解 follow_up 的核心——看每一轮**继承了什么、覆盖了什么**：

```
轮1: 「BB 美国最近 7 天 ROI360，sdk 收入」
  → 建 context: {产品:BB, 国家:US, 时间:近7天, 指标:ROI360, 口径:sdk}

轮2: 「换成 iOS」
  → 继承: BB / 美国 / 7天 / ROI360 / sdk
  → 覆盖: platform = iOS
  → 结果: {产品:BB, 国家:US, 时间:近7天, 指标:ROI360, 口径:sdk, 平台:iOS}

轮3: 「媒体拆一下」
  → 继承: BB / 美国 / 7天 / ROI360 / sdk / iOS
  → 覆盖: grain = media_source
  → 结果: {..., 维度:media_source}

轮4: 「CPI 呢」
  → 继承: BB / 美国 / 7天 / iOS / media_source
  → 覆盖: metric = CPI
  → 注意: 同主体换指标，窗口/维度继承，但收入口径可能需要重新判断
```

### 2.5 系统行为

1. **继承**上一轮 task context 中**未明确改动**的字段。
2. **只覆盖**用户本轮明确改动的字段（按子模式定位）。
3. **不追问**已继承的字段；只追问本轮新引入但缺失的字段。
4. 输出时声明「继承自上一轮」的字段，方便用户发现串口径。
5. 标记 `inherited_from: <上一轮id>` 和 `corrected_fields: [本轮改的字段]`。

### 2.6 反模式

**误判成 standalone**：用户说「换成 iOS」，系统反问「请问看什么产品？什么指标？」——把 follow_up 当独立问题，破坏连续性。

**正确做法**：检测到指代/增量动词 + 上一轮有活跃上下文 → 判 follow_up，继承未改动字段。

### 2.7 follow_up 的隐蔽坑：同主体换指标时的口径联动

「CPI 呢」看起来只是换 metric，但 CPI 的分母是 `total_registers`，而 ROI360 的口径涉及 `revenue_source` 和 `cost_metric`。换指标时：

- **窗口、维度、平台**：安全继承。
- **收入口径、消耗口径**：要检查新指标是否还需要这些口径。CPI 不涉及收入，但涉及消耗（`cost_metric`），所以 `cost_metric` 继承，`revenue_source` 可丢弃。

这个坑在 [05 常见误判与反模式](05_深入_常见误判与反模式.md) 里专门讲。结论：**follow_up 换指标时，不能无脑继承所有口径字段，要按新指标的依赖关系重新判断哪些字段还有意义。**

## 3. correction（纠正）

### 3.1 定义

用户在**纠正系统上一轮的理解或口径**。不是新需求，是修上一轮的错。纠正对象是**已在上一轮出现过的字段**，而非新字段。

### 3.2 纠正对象的五类

| 纠正类型 | 例子 | 被纠正字段 |
|---|---|---|
| 纠正指标名 | 「不是 ROI7 是 ROI360」「我说的是预估不是实际」 | metric / roi_source |
| 纠正口径 | 「消耗用折前」「收入要 af 的」 | cost_metric / revenue_source |
| 纠正产品 | 「不是 BB 是 MB」 | bundle_id |
| 纠正时间 | 「不是上周是上周一到周日」 | active_date_range |
| 纠正维度 | 「不是按国家是按媒体」 | grain |

### 3.3 判定信号

| 信号 | 说明 |
|---|---|
| 否定+更正结构 | 「不是 X 是 Y」「X 不对，应该是 Y」 |
| 显式更正语 | 「我说的是」「我指的是」「刚才说错了」 |
| 纠正对象已存在 | 被纠正的字段在上一轮出现过（不是新字段） |

**关键区分**：纠正 vs follow_up 改字段。
- follow_up「换成 iOS」：上一轮**没说**平台，本轮**新增/修改**。
- correction「不是 iOS 是 Android」：上一轮**已经说了** iOS，本轮**否定**它。

### 3.4 例子

```
轮1: 「BB 的 ROI7」
轮2（系统）: 输出 ROI7（date_diff<=6）
轮3: 「我说的是预估不是实际」
  → 纠正: roi_source = forecast（蓝底预估）
  → 继承: BB / ROI7 / 其余
  → 必须标注: roi_source=forecast_blue，不能伪装成真实回收

轮4: 「不是 ROI7 是 ROI360」
  → 纠正: metric = ROI360
  → 注意: ROI360 是 MI 页面概念，要走 MI ROI360 入口，不是简单改 N
```

### 3.5 系统行为

1. **不重新走全流程**，在上一轮 task context 基础上**替换被纠正的字段**。
2. **明确回显**纠正后的口径，让用户确认改对了：「明白，改成 ROI360（预估），其余沿用」。
3. **不要**把纠正当成新需求重新收参数。
4. **触及业务硬口径时必须重读业务协议**（见 3.6）。

### 3.6 correction 的关键规则：触及硬口径要重读业务协议

这是 correction 最容易出错的地方。纠正分两类：

| 纠正类型 | 系统动作 | 例子 |
|---|---|---|
| **纯字段值纠正** | 只替换字段值，不动入口/资产 | 「不是 BB 是 MB」（换个 bundle_id） |
| **触及业务硬口径的纠正** | 替换字段 + 重读业务协议 + 换入口/资产 | 「不是 ROI7 是 ROI360」 |

**为什么 ROI7→ROI360 不是纯字段替换**：

- ROI7 是数仓概念，底层 `date_diff<=6`，走 CK 或 MC。
- ROI360 是 **MI 页面概念**，有独立的 forecast_version、revenue_source、summary 逻辑，走 MI ROI360 入口。
- 简单把 `metric` 从 ROI7 改成 ROI360，会继续用数仓的 date_diff 逻辑去算，跑出来根本不是 MI 页面那个 ROI360。

所以纠正触及硬口径时，必须：
1. 替换字段值。
2. 重读对应业务协议（MI ROI360 协议 / ROI_N 窗口定义）。
3. 重新选入口和召回资产。

详见 [07 与本仓库现有协议的关系](07_深入_与本仓库现有协议的关系.md)。

### 3.7 反模式

**误判成新需求**：用户说「我说的是预估不是实际」，系统重新问「好的，请问看什么产品的预估？」——把纠正当独立问题，推翻整轮上下文。

**正确做法**：检测到否定+更正结构 → 进 correction 分支，只替换被纠正字段。

## 4. topic_switch（切话题）

### 4.1 定义

用户**明确换主题**，要清掉旧上下文，开新任务。与 standalone 的区别在于：**之前有活跃上下文需要主动清掉**。

### 4.2 什么时候是 topic_switch

- **显式切换语**：「不看 X 了」「换个话题」「先不查这个」。
- **领域彻底切换 + 自带完整参数**：上一轮讲投放，这一轮直接讲实验/埋点/素材，且新问题自带产品+指标+时间。

### 4.3 判定信号

| 信号 | 说明 |
|---|---|
| 显式切换语 | 「不看X了」「换话题」「先不查这个」 |
| 领域切换 | 投放→实验 / 投放→埋点 / 投放→素材 |
| 自带完整参数 | 新问题有产品+指标锚点，不依赖继承 |
| 与上一轮无重叠 | 产品/指标/时间完全不重叠 |

### 4.4 topic_switch vs standalone 的对比

这是本篇最重要的对比。两者输入可能一模一样（都是自带完整新问题），但系统动作不同：

| 维度 | standalone | topic_switch |
|---|---|---|
| 上下文状态 | 之前无上下文（起点）或已清空 | 之前**有活跃上下文** |
| 系统动作 | 直接建新 context | **先清旧 context**，再建新 context |
| 判定难点 | 几乎无难点 | 难在判断"切话题还是同领域 follow_up" |
| 典型场景 | 会话第一句 | 从 ROI 跳到实验留存 |

**为什么必须分**：如果不分，系统在"有旧上下文"时容易忘记清，导致口径串台（故障 B）。topic_switch 的核心价值就是**强制清空动作**。

### 4.5 例子

```
✅ 「不看 ROI 了，查实验 123 的留存」
   （显式切换语 + 领域切换 + 自带参数 → topic_switch）

✅ 轮1: 「BB 的 ROI7」
   轮2: 「MB 的 D1 留存拆媒体」
   （产品+指标+领域全换，自带参数，上一轮有活跃上下文 → topic_switch）
```

### 4.6 系统行为

1. **主动清空**上一轮 task context 的所有字段（产品、时间、口径、维度、中间结果）。
2. **不继承任何字段**。
3. 按新问题重新走完整流程。
4. 可在输出中轻量提示「已切换到新话题」，帮用户确认旧上下文已清除。

### 4.7 反模式

**没清上下文**：用户说「不看 ROI 了，查实验留存」，系统还在用 BB 的产品上下文去查实验留存——这是 topic_switch 判对了但**清空动作没执行**。

**正确做法**：判 topic_switch 后，第一步就是显式清空 task context，再建新 context。

### 4.8 topic_switch vs 同领域 follow_up 的边界

最难判的边界：用户从「BB 的 ROI7」跳到「MB 的 ROI7」，是 topic_switch 还是 follow_up？

判定原则：
- **产品换了 + 其他全继承**：如果用户只换了产品，其余（指标/时间/口径）都沿用 → 其实是 follow_up（改产品子模式）。
- **产品换了 + 指标/领域也换了**：多字段切换 + 自带完整参数 → topic_switch。

简单说：**只换一个字段是 follow_up，换一片是 topic_switch**。边界模糊时，按 [03 判定信号与判定流程](03_深入_判定信号与判定流程.md) 的兜底原则处理。

## 五、四种类型的边界关系图

```
                    有活跃上文?
                   /          \
                 NO            YES
                 |              |
            standalone     有否定/更正?
                            /        \
                          YES         NO
                           |           |
                      correction   有显式切换语?
                                      /       \
                                    YES        NO
                                     |          |
                               topic_switch   自带完整参数+无指代?
                                               /        \
                                             YES         NO
                                              |          |
                                         topic_switch  follow_up
                                       (或standalone
                                        若判为同领域)
```

## 六、本篇小结

1. **standalone**：独立新问题，清空重建。会话起点或自带完整参数无指代。
2. **follow_up**：追问/继承，有**七种子模式**（改维度/端/时间/口径/粒度/加对照/换指标），每种子模式只覆盖特定字段。隐蔽坑：换指标时口径字段不能无脑全继承。
3. **correction**：纠正，否定+更正结构，只替换被纠正字段。**触及业务硬口径必须重读业务协议**，不能只改字段名。
4. **topic_switch**：切话题，主动清空+重建。与 standalone 的唯一区别是"之前有活跃上下文需要主动清"。与 follow_up 的边界是"换一个字段 vs 换一片"。

下一篇 [03 判定信号与判定流程](03_深入_判定信号与判定流程.md) 讲怎么把上面这些信号组合成一个可执行的判定流程。
