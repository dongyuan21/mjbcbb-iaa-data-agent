> 系列导航：[总纲索引](00_总纲索引.md) · 上一篇：[06 落地实现要点](06_深入_落地实现要点.md) · 下一篇：—
> 本篇讲 turn_kind 在本仓库具体协议体系里的定位、分工和联动规则。

## 一、turn_kind 在执行链路里的位置

本仓库已有一套成熟的业务执行协议（第一层分析、SQL 写作、投放治理、MI ROI360 等）。turn_kind 不是替代它们，而是嵌在它们**前面**的一道闸。

完整链路：

```
用户输入
  │
  ▼
[对话编排层] ← turn_kind 协议（本系列）
  ├── turn_kind 判定
  ├── 上下文操作（清空/继承/纠正）
  └── handoff 给业务层
  │
  ▼
[业务执行层] ← 现有业务协议
  ├── 识别任务类型          ← 第一层分析Agent协议.md
  ├── 收集/继承必填参数      ← 第一层分析Agent协议.md
  ├── 召回资产 + freshness  ← 第一层分析Agent协议.md
  ├── SQL 生成与执行         ← SQL写作业务协议.md / 投放与ROI预估SQL协议.md
  ├── 结果校验              ← 第一层分析Agent协议.md
  └── 输出                  ← 第一层分析Agent协议.md
```

**核心定位**：turn_kind 是第一道闸。判对了，业务协议在正确上下文上执行；判错了，后面全错。

## 二、分工边界

| 本协议（turn_kind）负责 | 业务协议负责 |
|---|---|
| 轮次性质判定（standalone/follow_up/correction/topic_switch） | 任务类型识别（ROI/DNU/留存/实验/点位） |
| 上下文继承/清空/纠正的字段操作 | 字段业务口径定义（ROI_N 窗口、revenue_source、cost_metric） |
| 判定兜底原则（宁追问不乱继承） | SQL 生成护栏、freshness 检查、结果校验 |
| correction 触发业务协议重读的信号 | 业务硬口径本身 |
| 口径字段按指标依赖表处理 | 指标口径的权威定义 |

**原则**：编排层只管"上下文边界"，业务层只管"业务执行"。两层解耦，通过 handoff 接口传递（见 [06 落地实现要点](06_深入_落地实现要点.md) 第七节）。

## 三、与第一层分析Agent协议的联动

`第一层分析Agent协议.md` 是业务执行层的主入口。turn_kind 与它的联动点：

### 3.1 任务类型识别的衔接

turn_kind 判完后，task_context 带着继承/清空后的字段交给第一层分析协议。第一层协议的「Step 1: 识别任务类型」此时：

- **standalone / topic_switch**：task_context 是空的，按本轮用户输入重新识别任务类型。
- **follow_up**：task_context 带着继承的 `task_type`，通常沿用上一轮任务类型（除非换指标跨领域）。
- **correction**：task_context 带着纠正后的字段，`task_type` 通常不变；但触及硬口径时可能要换（如 ROI7→ROI360 从 `roi_analysis` 变 `mi_roi360_analysis`）。

### 3.2 必填参数收集的衔接

第一层协议的「Step 2: 收集必填参数」有一张必填参数表（bundle_id / country / active_date_range / revenue_source / cost_metric 等）。turn_kind 影响这张表怎么填：

| 参数 | standalone | follow_up | correction |
|---|---|---|---|
| bundle_id | 必须从本轮收 | 继承（除非改产品） | 继承（除非纠正产品） |
| active_date_range | 必须从本轮收 | 继承（除非改时间） | 继承 |
| revenue_source | 默认 sdk | 按指标依赖表（[06](06_深入_落地实现要点.md)） | 替换为纠正值 |
| cost_metric | 默认 cost_zhe | 按指标依赖表 | 替换为纠正值 |

**联动规则**：第一层协议的"必填参数"判定要参考 turn_kind——已继承的字段不追问，只追问缺失且无法继承的。

### 3.3 freshness 检查的衔接

第一层协议的「Step 4: 强制 freshness 检查」对每种 turn_kind 的行为：

| turn_kind | freshness 检查 |
|---|---|
| standalone / topic_switch | 必须重新检查（新任务，新表） |
| follow_up | 通常沿用上一轮 freshness（同表同窗口）；改时间/改指标时要重查 |
| correction | 通常沿用；触及硬口径换入口时要重查 |

## 四、与投放与ROI预估SQL协议的联动

`投放与ROI预估SQL协议.md` 定义 ROI / 回收 / 成本相关的业务口径。turn_kind 与它的联动核心在 **correction 触及硬口径**时。

### 4.1 硬口径纠正的协议重读

当 correction 纠正以下字段时，必须重读 `投放与ROI预估SQL协议.md`（或对应专项协议）：

| 纠正 | 触发的协议重读 | 原因 |
|---|---|---|
| ROI7 ↔ ROI360 | MI ROI360 协议（`skills/mi_skill/SKILL.md`） | 数仓概念 vs MI 页面概念，入口不同 |
| sdk ↔ af | 投放与ROI预估SQL协议.md | 收入源切换，SQL 路径不同 |
| 折后 ↔ 折前 | 投放与ROI预估SQL协议.md | cost_metric 切换，字段不同 |
| 实际 ↔ 预估 | 投放与ROI预估SQL协议.md + ROI360 页面协议 | roi_source 切换，涉及 forecast_blue |

### 4.2 联动流程

```
correction 判定
  → 检查 correction_type
  → 如果是硬口径:
      → 标记 protocol_reload_needed = true
      → 业务层收到 handoff 后重读对应协议
      → 按新协议重新选入口、召回资产、生成 SQL
      → 丢弃 prev_sql
```

### 4.3 不能只改字段名的原因

以「不是 ROI7 是 ROI360」为例：

| 维度 | ROI7（数仓） | ROI360（MI 页面） |
|---|---|---|
| 入口 | CK / MC | MI ROI360 页面 |
| 窗口逻辑 | date_diff <= 6 | MI 页面的 forecast + summary |
| 收入源 | sdk / af | MI 页面的 revenue_source 字段 |
| 蓝底预估 | 无 | 有（forecast_blue） |

如果 correction 只把 `metric` 从 ROI7 改成 ROI360，继续用数仓 date_diff 逻辑算，跑出来的根本不是 MI 页面的 ROI360。所以必须重读 MI ROI360 协议，换入口。

## 五、与投放ROI治理政策的联动

`投放ROI治理政策.md` 是本仓库的红线协议（"投放治理：必须输出预警，禁止输出最终投放动作"）。turn_kind 与它的联动在**兜底原则**上。

### 5.1 高风险场景的兜底

投放治理类问题（ROI 红线、黄线、停投预警）属于高风险场景。turn_kind 判定在这些场景里要**优先兜底**：

- 涉及 ROI / 红线 / 黄线 / 停投 / 放量的 follow_up，判定置信度低时触发追问。
- 不确定是 follow_up 还是 topic_switch 时，宁可追问确认，不乱继承口径。
- 原因：串口径会让预警本身失真，可能引发错误的投放决策，违背治理政策。

### 5.2 correction 在治理场景的谨慎处理

治理场景里的 correction 要特别小心：

- 用户纠正「红线是 1.2 不是 1.0」→ 这是纠正阈值，不只是改字段，要重读 `report_knowledge/` 里的权威阈值（见 AGENTS.md 的事实切面优先级）。
- 用户纠正「这个产品在 trial_active」→ 影响是否适用 trial 阈值，要重读治理政策。

**规则**：治理场景的 correction，凡是涉及阈值/红线/适用范围的，都按硬口径纠正处理，触发协议重读。

## 六、与 SQL写作业务协议的联动

`SQL写作业务协议.md` 定义 SQL 写作的业务认知和规范。turn_kind 与它的联动在 **follow_up 改字段后的 SQL 局部修改**上。

### 6.1 follow_up 的 SQL 处理

| follow_up 子模式 | SQL 处理 |
|---|---|
| 改维度（grain） | 在原 SQL 改 GROUP BY，其余不动 |
| 改端（platform） | 在原 SQL 加/改 platform 过滤条件 |
| 改时间（active_date_range） | 在原 SQL 改 dt/active_date 过滤 |
| 改口径（revenue_source/cost_metric） | 在原 SQL 换字段，可能涉及 join 表切换 |
| 改粒度（campaign→adset） | 可能要换表（campaign 表 → adset 表），SQL 重写 |
| 同主体换指标 | SQL 重写（不同指标计算逻辑不同） |

**规则**：follow_up 的 SQL 处理分两类——局部改（改维度/端/时间）可以复用 prev_sql 改；重写类（换粒度跨表/换指标）要重新生成。这影响 [06](06_深入_落地实现要点.md) handoff 里是否保留 `prev_sql`。

### 6.2 correction 的 SQL 处理

| correction 类型 | SQL 处理 |
|---|---|
| 纯字段值纠正 | 局部改（换字段值） |
| 硬口径纠正 | 丢弃 prev_sql，按新协议重新生成 |

## 七、turn_kind 协议的权威性与边界

### 7.1 本协议的定位

- **是**：对话编排层的执行规程，定义轮次分类、上下文操作、判定流程、落地实现。
- **不是**：业务口径定义。ROI7 窗口、sdk/af 区别、红线阈值等业务事实由对应业务协议定义。
- **不是**：任务类型识别。ROI/DNU/留存/实验的分类由 `第一层分析Agent协议.md` 负责。

### 7.2 与 AGENTS.md 的关系

本协议遵循 AGENTS.md 的以下规则：
- 第 7 条：涉及 ROI/投放治理时区分 reviewed/draft/verified——turn_kind 的 correction 在治理场景要重读权威阈值。
- 第 8 条：评估前先验证读取能力——turn_kind 不影响这条，但 follow_up 沿用 freshness 时要确认快照未过期。
- 事实切面优先级：correction 纠正阈值时读 `report_knowledge/`，纠正规则时读 `policies/`。

### 7.3 修改本协议的约束

修改本协议（turn_kind 分类、判定流程、继承矩阵）后：
- 按 AGENTS.md 第 11 条运行 `check_knowledge_consistency.py`。
- 按 AGENTS.md 第 12 条运行 `check_authority_map.py`。
- 同步 `catalog.yaml`。
- 如果改了判定流程或矩阵，建议同步更新 `eval/agent_regression/` 的回归用例。

## 九、本篇小结

1. **turn_kind 是执行链路的第一道闸**，嵌在业务协议前面，判对上下文边界后业务协议才能正确执行。
2. **与第一层分析协议联动**：任务类型识别、必填参数收集、freshness 检查都要参考 turn_kind 的判定结果。
3. **与 SQL 写作协议联动**：follow_up 的 SQL 局部改 vs 重写，correction 的纯字段值 vs 硬口径，都影响 SQL 处理方式。
4. **与投放治理政策联动**：高风险场景优先兜底，治理类 correction 按硬口径处理触发协议重读。
5. **编排层和业务层解耦**：通过 handoff 传递 task_context，两层各司其职。
6. **修改本协议要跑门禁**：check_knowledge_consistency.py + check_authority_map.py + 同步 catalog。
