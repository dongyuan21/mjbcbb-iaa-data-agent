# 深入 05 · 常见误判与反模式

> 系列导航：[总纲索引](00_总纲索引.md) · 上一篇：[04 上下文继承矩阵](04_深入_上下文继承矩阵.md) · 下一篇：[06 落地实现要点](06_深入_落地实现要点.md)
> 本篇用真实场景讲五类典型误判：表现、根因、后果、修法。排障时优先看本篇。

---

## 总览：五类反模式

| 编号 | 反模式 | 误判方向 | 危害等级 |
|---|---|---|---|
| R1 | 把 follow_up 当 standalone | follow_up → standalone | 中（体验差） |
| R2 | 把 standalone 当 follow_up | standalone → follow_up | 高（串口径） |
| R3 | 把 correction 当新需求 | correction → standalone | 中（纠正被吞） |
| R4 | topic_switch 不清上下文 | topic_switch → follow_up | 极高（跨领域串口径） |
| R5 | correction 只改字段名不重读协议 | correction 执行错 | 高（跑错数） |

危害等级按"是否跑出错数据"分：体验问题中等，数据错误高，跨领域串口径极高。

---

## R1 · 把 follow_up 当 standalone

### 表现

```
轮1: BB 美国近 7 天 ROI360 sdk
轮2: 换成 iOS
系统: 「请问要看什么产品？什么指标？什么时间窗口？」
用户: ……（刚说过又要重报）
```

### 根因

系统没识别指代/增量动词，把短句「换成 iOS」当不完整新问题。典型原因：
- 判定逻辑只看"句子是否完整"，短句就当独立问题。
- 没检查上一轮是否有活跃 task context。
- 没维护"增量动词 → follow_up"的映射。

### 后果

- **体验差**：用户每轮都要重报背景，感觉系统"听不懂"。
- **效率低**：本来一句话能推进的事要三四轮。
- **用户信任下降**：反复追问会让用户怀疑系统能力。

### 修法

1. 判定流程第一步先查上下文状态（[03 决策树](03_深入_判定信号与判定流程.md) Step 3）：有活跃 context 才往下判 follow_up。
2. 维护增量动词词表：换成/拆/加/去掉/下钻/也看下/对比 → follow_up 信号。
3. 短句 + 缺主语 + 有上文 → 默认 follow_up，不追问已继承字段。

### 正确行为

```
轮2: 换成 iOS
系统: 【继承】BB / 美国 / 7天 / ROI360 / sdk
      【改动】platform → iOS
      [输出 iOS 版 ROI360 结果]
```

## R2 · 把 standalone 当 follow_up

### 表现

```
轮1: BB 美国近 7 天 ROI360 sdk
轮2: MB 的 D1 留存拆媒体
系统: 【继承】BB / 美国 / 7天 / sdk
      [用 BB 的上下文查 MB 留存，跑出错数据]
```

用户明明问的是 MB 留存，系统却带着 BB + 美国 + 7天 + sdk 去查。

### 根因

系统看到"留存拆媒体"就当是 follow_up，没检查：
- 产品从 BB 换成了 MB（自带完整产品锚点）。
- 指标从 ROI360 换成了留存（领域相关但口径全变）。
- 用户没说"接着看"，是自带完整参数的新问题。

典型原因：
- 只看"领域是否相关"（都是投放领域），没看产品/指标是否切换。
- 没判"自带完整参数"这个结构信号。

### 后果（致命）

- **跑出错数据**：用 BB 的美国 7 天 sdk 口径查 MB 留存，数字看起来合理但口径全错。
- **错误数据可能引发错误投放决策**：在 ROI/投放治理场景，这是红线问题。
- **用户难发现**：系统不会主动声明"我继承了 BB"，错误很隐蔽。

### 修法

1. 判定流程里加"自带完整参数 + 无指代"的检查（[03 决策树](03_深入_判定信号与判定流程.md) Step 4）。
2. 本轮自带产品锚点且与上一轮产品不同 → 偏向 topic_switch 或 standalone，不判 follow_up。
3. 多字段切换（产品+指标都换）→ topic_switch，强制清空。
4. 兜底原则：判不准宁可追问「是接着 BB 看，还是查 MB？」，不乱继承。

### 正确行为

```
轮2: MB 的 D1 留存拆媒体
系统: 判定 topic_switch（产品+指标切换，自带完整参数）
      【清空】BB / 美国 / 7天 / ROI360 / sdk
      【新上下文】MB / 留存 / media_source
      [追问国家、时间，或按默认查]
```

## R3 · 把 correction 当新需求

### 表现

```
轮1: BB 的 ROI7（系统理解成实际回收）
轮2: 我说的是预估不是实际
系统: 「好的，请问要看什么产品的预估回收？什么时间窗口？」
用户: 我刚才都说了……
```

### 根因

系统没识别否定+更正结构，把「我说的是预估」当全新需求。典型原因：
- 判定逻辑只看"是否有产品/指标锚点"，"预估"被当成了新指标。
- 没维护"我说的是 / 不是 X 是 Y" → correction 的语气信号映射。

### 后果

- **纠正意图被吞**：用户想修上一轮的口径，系统却推翻整轮重来。
- **用户要重报参数**：本来只改一个字段，变成重报全套。
- **可能丢失原上下文**：如果系统当 standalone 处理，上一轮的 BB/时间可能被清掉。

### 修法

1. 判定流程第一步扫语气信号（[03 决策树](03_深入_判定信号与判定流程.md) Step 1）：检测到"我说的是 / 不是 X 是 Y" → 直接 correction。
2. correction 不重新走全流程，只在上一轮 context 上替换被纠正字段。
3. 回显纠正结果让用户确认：「明白，改成预估（roi_source=forecast），其余沿用」。

### 正确行为

```
轮2: 我说的是预估不是实际
系统: 【纠正】roi_source: actual → forecast_blue
      【继承】BB / ROI7 / 其余
      [重新输出预估版 ROI7，标注 roi_source=forecast_blue]
```

## R4 · topic_switch 不清上下文

### 表现

```
轮1: BB 美国近 7 天 ROI360 sdk
轮2: 不看 ROI 了，查实验 123 留存
系统: [用 BB + 美国 + 7天 去查实验 123 留存]
      [跑出"BB 美国近 7 天 sdk 口径下的实验 123 留存"]
```

这是最危险的反模式：判对了 topic_switch（或根本没判），但**清空动作没执行**。

### 根因

两种可能：
1. **没判 topic_switch**：把"查实验 123 留存"当 follow_up，继承了 BB 上下文。
2. **判对了但没清**：判定逻辑识别了切换，但字段操作层没执行清空，旧 context 残留。

第二种更隐蔽，因为判定层"看起来对了"，问题出在执行层。

### 后果（极高危）

- **跨领域串口径**：投放上下文（BB/美国/sdk）套到实验留存查询上，完全张冠李戴。
- **数据完全错误**：实验留存和投放口径本就无关，串了之后数字没有业务意义。
- **用户极难发现**：系统输出可能不声明继承了什么，用户以为查的是纯净的实验留存。

### 修法

1. topic_switch 判定后，**第一步就是显式清空 task context**（[04 矩阵](04_深入_上下文继承矩阵.md) 第六节）。
2. 清空要清干净：全部字段重置，包括容易漏的 `organic_mode` / `compare_window` / `prev_result`。
3. 清空后在输出里声明：「已切换到新话题，旧上下文（BB/美国/ROI360）已清除」。
4. task context 加 `status` 字段：topic_switch 后旧 context 标 `cleared`，新建 context 标 `active`。

### 正确行为

```
轮2: 不看 ROI 了，查实验 123 留存
系统: 判定 topic_switch
      【清空】task context 全部重置
      【新上下文】实验 123 / 留存
      声明: 已切换到新话题，旧上下文已清除。
      [追问实验留存的必要参数，或按默认查]
```

## R5 · correction 只改字段名不重读协议

### 表现

```
轮1: BB 的 ROI7（走数仓 date_diff<=6）
轮2: 不是 ROI7 是 ROI360
系统: 【纠正】metric: ROI7 → ROI360
      [继续用数仓 date_diff<=6 逻辑算"ROI360"]
      [跑出来的根本不是 MI 页面那个 ROI360]
```

### 根因

correction 只做了字符串替换，把 `metric` 从 ROI7 改成 ROI360，但没检查：
- ROI360 是 **MI 页面概念**，有独立的 forecast_version、revenue_source、summary 逻辑。
- ROI7 是数仓概念，底层 `date_diff<=6`。
- 两者不是同一个入口，不能简单换名字。

### 后果（高危）

- **跑错数**：用数仓逻辑算出来的"ROI360"不是 MI 页面的 ROI360，数值对不上。
- **口径伪装**：系统标了 `metric=ROI360`，但实际用的是 ROI7 的算法，用户以为看的是 MI ROI360。
- **影响投放决策**：ROI360 常用于投放治理预警，算错了会导致错误的预警。

### 修法

correction 分两类处理（[04 矩阵](04_深入_上下文继承矩阵.md) 第五节）：

| 纠正类型 | 系统动作 | 例子 |
|---|---|---|
| 纯字段值纠正 | 只替换字段值 | 「不是 BB 是 MB」 |
| 触及硬口径纠正 | 替换 + 重读业务协议 + 换入口 | 「不是 ROI7 是 ROI360」 |

触及硬口径的判断标准：被纠正的字段值对应不同的**业务入口或计算逻辑**。常见硬口径纠正：
- ROI7 ↔ ROI360（数仓 vs MI 页面）
- sdk ↔ af（收入源切换）
- 折后 ↔ 折前（消耗口径）
- 实际 ↔ 预估（roi_source）

遇到这类纠正，必须：
1. 替换字段值。
2. 重读对应业务协议（MI ROI360 协议 / ROI_N 窗口定义 / 投放与ROI预估SQL协议）。
3. 重新选入口和召回资产。
4. 丢弃 `prev_sql`，重新生成。

### 正确行为

```
轮2: 不是 ROI7 是 ROI360
系统: 判定 correction（触及硬口径）
      【纠正】metric: ROI7 → ROI360
      【重读协议】MI ROI360 协议
      【换入口】数仓 date_diff → MI ROI360 入口
      【丢弃】prev_sql（ROI7 的 SQL 作废）
      [按 MI ROI360 协议重新召回资产、生成 SQL]
```

## 六、反模式的共同根源

把五个反模式放一起看，根因集中在三处：

### 6.1 没把上下文状态纳入判定

R1、R2、R4 都和"没检查上一轮有没有活跃 context"有关。如果判定流程第一步就查上下文状态，很多误判可以避免。

### 6.2 信号识别不全

R1 没识别增量动词，R3 没识别语气信号，R5 没识别硬口径纠正。需要维护完整的信号词表和映射规则。

### 6.3 字段操作不精确

R4 清空没清干净，R5 只改字段名不换入口。判定对了但执行层出错，说明字段操作必须按 [04 矩阵](04_深入_上下文继承矩阵.md) 精确执行，不能笼统处理。

## 七、排障速查

遇到问题时，按反模式编号对照排查：

| 现象 | 先查 |
|---|---|
| 系统反复追问已说过的参数 | R1（follow_up 当 standalone） |
| 跑出的数据口径不对 | R2（standalone 当 follow_up）或 R4（topic_switch 没清） |
| 用户纠正后系统重报参数 | R3（correction 当新需求） |
| 跨领域查询串了上一轮口径 | R4（topic_switch 没清） |
| 纠正指标名后数据对不上 | R5（correction 没重读协议） |

---

## 八、本篇小结

1. **五类反模式**覆盖了 turn_kind 判定和执行的主要坑：R1/R2 是判定方向错，R3 是纠正被吞，R4 是清空没做，R5 是纠正没触达硬口径。
2. **危害分级**：体验问题（R1/R3）中等，数据错误（R2/R5）高，跨领域串口径（R4）极高。
3. **共同根源**：上下文状态没纳入判定、信号识别不全、字段操作不精确。
4. **排障优先级**：先查数据对不对（R2/R4/R5），再查体验好不好（R1/R3）。
