# 深入 03 · 判定信号与判定流程

> 系列导航：[总纲索引](00_总纲索引.md) · 上一篇：[02 四种 turn_kind 详解](02_深入_四种turn_kind详解.md) · 下一篇：[04 上下文继承矩阵](04_深入_上下文继承矩阵.md)
> 本篇讲怎么把各种信号组合成一个可执行的判定流程，以及判不准时怎么办。

---

## 一、为什么判定不能靠单一信号

上一篇讲了每种 turn_kind 的判定信号，但实际判定时**不能只看一个信号**，原因：

1. **信号有歧义**：「换成 iOS」既可能是 follow_up（改端），也可能是 topic_switch（从 ROI 跳到 iOS 某个完全不同的分析）——取决于上一轮在干什么。
2. **信号会缺席**：用户不一定每次都说「我说的是」「不看 X 了」，很多纠正/切换是隐式的。
3. **信号会冲突**：用户说「换成 iOS，另外看下留存」——既有 follow_up 信号（换端），又有换指标信号，还可能隐含切话题。

所以判定必须是**多信号叠加 + 上下文感知**的流程，而不是"看到关键词就归类"。

---

## 二、四类判定信号

把所有信号归成四类，便于系统化处理：

### 2.1 语气信号（最强，优先级最高）

| 信号 | 指向 | 强度 |
|---|---|---|
| 否定+更正（「不是 X 是 Y」「X 不对，应该是 Y」） | correction | 极强 |
| 显式更正语（「我说的是」「我指的是」「刚才说错了」） | correction | 极强 |
| 显式切换语（「不看 X 了」「换话题」「先不查这个」） | topic_switch | 极强 |

**特点**：语气信号几乎不会被其他信号覆盖。检测到否定+更正就基本锁定 correction；检测到显式切换语就基本锁定 topic_switch。

### 2.2 结构信号（看句子完整度）

| 信号 | 指向 | 说明 |
|---|---|---|
| 句子短 + 缺主语 | follow_up | 省略了产品/时间，靠继承补 |
| 自带完整参数（产品+指标锚点） | standalone / topic_switch | 不依赖继承 |
| 单指标词单独出现（「CPI 呢」） | follow_up（换指标） | 隐含"同主体同窗口" |

### 2.3 词汇信号（看动词和指代词）

| 信号 | 指向 |
|---|---|
| 指代词（它/这个/那个/那张表） | follow_up |
| 增量动词（拆/换/加/去掉/下钻/也看下/对比） | follow_up |
| 领域锚点词（实验/埋点/素材/点位 vs ROI/DNU/CPI） | 配合结构信号判 topic_switch |

### 2.4 上下文信号（看历史状态，最关键）

| 信号 | 指向 |
|---|---|
| 上一轮有活跃 task context | follow_up / correction / topic_switch 三选一 |
| 上一轮无活跃 context（起点或已清空） | standalone |
| 被纠正字段在上一轮出现过 | correction |
| 新问题领域与上一轮不同 | topic_switch（若自带完整参数） |

**上下文信号是判定的地基**：没有它，语气/结构/词汇信号都无法最终定性。

---

## 三、判定决策树（完整版）

把四类信号串成一个决策流程。按优先级从高到低判断：

```
输入: 用户本轮文本 + 上一轮 task context 状态

Step 1: 语气信号扫描
  有否定+更正 / 显式更正语?
    → YES → correction（终止）
    → NO  → Step 2

Step 2: 语气信号扫描
  有显式切换语?
    → YES → topic_switch（终止）
    → NO  → Step 3

Step 3: 上下文状态检查
  上一轮有活跃 task context?
    → NO  → standalone（终止，无上文可继承）
    → YES → Step 4

Step 4: 结构 + 词汇信号判断
  本轮自带完整参数（产品+指标锚点）且无指代/增量动词?
    → YES → 领域与上一轮重叠?
              → YES → follow_up（同领域换主体，可能是换产品子模式）
              → NO  → topic_switch（领域切换 + 自带参数 = 切话题）
    → NO  → Step 5

Step 5: follow_up 确认
  有指代词 / 增量动词 / 单指标词 / 缺主语?
    → YES → follow_up（进一步判子模式）
    → NO  → 兜底: standalone（宁可追问，不乱继承）
```

### 决策树的设计逻辑

为什么是这个顺序？

1. **语气信号最先**：因为它们强度最高、最不易歧义。先处理掉明确的 correction 和 topic_switch，剩下的才需要细判。
2. **上下文状态第二**：决定了"有没有继承的可能"。无上文直接 standalone，不用再往下判。
3. **结构+词汇信号最后**：这些信号有歧义，必须结合上下文状态才能定性。比如"自带完整参数"在有上文时可能是 topic_switch，在无上文时就是 standalone。
4. **兜底 standalone**：所有信号都不明确时，宁可当独立问题追问，不冒险继承。这是红线原则（见第五节）。

## 四、判定流程的执行细节

### 4.1 上下文状态怎么判

"上一轮有活跃 task context"不是看对话历史长短，而是看**是否有一个未过期的 task context 对象**：

- 会话第一句：无 task context → standalone。
- 上一轮 topic_switch 后：旧 context 已清，新 context 刚建 → 有活跃 context。
- 上一轮执行出错中断：context 可能残缺 → 标 `context_partial`，判定时偏向 standalone。

实现上，task context 应该带一个 `status` 字段：`active` / `cleared` / `partial`。判定时读这个字段。

### 4.2 "自带完整参数"怎么判

不是要求用户把所有字段都说全，而是看**有没有足够的锚点独立成问**。最低标准：

- 有**产品锚点**（产品名/bundle_id）或**指标锚点**（ROI/DNU/留存/CPI）至少一个。
- 不依赖上一轮的指代就能理解问题意图。

反例：「换成 iOS」没有产品锚点也没有指标锚点 → 不是自带完整参数 → follow_up。
正例：「MB 的留存」有产品+指标锚点 → 自带完整参数。

### 4.3 "领域是否重叠"怎么判

用 task_type 做粗判：

| 上一轮 task_type | 本轮领域词 | 重叠? |
|---|---|---|
| roi_analysis | ROI / 回收 / 消耗 | 重叠 |
| roi_analysis | 实验 / 实验 ID / 方案 | 不重叠 |
| roi_analysis | DNU / 激活 / 媒体 | 部分重叠（看是否同主体） |
| experiment_analysis | 留存 / 方案 / 组别 | 重叠 |

部分重叠的情况最难，靠兜底原则处理。

### 4.4 follow_up 子模式的二次判定

判完 follow_up 后，还要进一步判是七种子模式的哪一种（见 [02 四种详解](02_深入_四种turn_kind详解.md) 的 2.2 节）。子模式判定靠增量动词和指标词：

| 信号 | 子模式 |
|---|---|
| 「拆/分组/按 X 分」 | 改维度 |
| 「换成 iOS/Android/GP」 | 改端 |
| 「看上周/拉到昨天/换日期」 | 改时间 |
| 「用 af/sdk/折前/折后」 | 改口径 |
| 「下钻/展开到 adset/ad」 | 改粒度 |
| 「加对比/同期/对照」 | 加对照 |
| 单指标词（「CPI 呢」「留存呢」） | 同主体换指标 |

子模式决定覆盖哪个字段，是 [04 上下文继承矩阵](04_深入_上下文继承矩阵.md) 的执行依据。

## 五、兜底原则（红线）

> **判定不确定时，宁可当 standalone 追问，不要当 follow_up 乱继承。**

### 为什么这是红线

比较两类误判的代价：

| 误判 | 表现 | 代价 |
|---|---|---|
| 误判成 standalone（实际是 follow_up） | 多问一句「看什么产品？」 | 体验差一点，但数据安全 |
| 误判成 follow_up（实际是 standalone/topic_switch） | 偷偷串口径，跑错数 | **数据错误，可能引发错误投放决策** |

在投放/ROI 场景，串口径可能直接导致错误的停投/放量建议，这是本仓库 AGENTS.md 明确的红线（"投放治理：必须输出预警，禁止输出最终投放动作"）。错误数据会让预警本身失真。

所以兜底必须是**向安全侧倒**：宁可多问，绝不乱继承。

### 兜底追问的话术

判定不确定时，主动问一句确认 turn_kind，比硬猜安全：

> 「你是想在 BB 的基础上换成 iOS 看，还是另起一个新问题？」

> 「你说的"留存"是接着上面的 BB 美国窗口看，还是查别的产品的留存？」

这种追问成本低（一句话），但能避免口径串台的高代价。

### 什么时候该兜底

| 场景 | 动作 |
|---|---|
| 信号冲突（既有 follow_up 信号又有切换信号） | 兜底追问 |
| 领域部分重叠，判不准 | 兜底追问 |
| 上一轮 context 状态是 partial | 偏向 standalone |
| 涉及 ROI/投放治理等高风险场景 | 优先兜底追问 |

## 六、判定流程的伪代码

把决策树落成可执行的伪代码：

```python
def classify_turn_kind(user_input, prev_context):
    # Step 1: 语气信号 - correction
    if has_correction_signal(user_input):  # 否定+更正 / 我说的是
        return "correction"

    # Step 2: 语气信号 - topic_switch
    if has_explicit_switch_signal(user_input):  # 不看X了 / 换话题
        return "topic_switch"

    # Step 3: 上下文状态
    if prev_context is None or prev_context.status == "cleared":
        return "standalone"

    if prev_context.status == "partial":
        # 残缺上下文，偏向 standalone
        if not has_strong_followup_signal(user_input):
            return "standalone"

    # Step 4: 结构 + 词汇信号
    has_full_params = has_product_or_metric_anchor(user_input)
    has_followup_lex = has_pronoun_or_incremental_verb(user_input)

    if has_full_params and not has_followup_lex:
        # 自带完整参数 + 无指代
        if domain_overlaps(prev_context, user_input):
            return "follow_up"  # 同领域换主体
        else:
            return "topic_switch"  # 领域切换
    elif has_followup_lex or is_short_with_missing_subject(user_input):
        return "follow_up"
    else:
        # 兜底
        return "standalone"
```

这只是一个骨架，实际实现还要处理子模式判定、兜底追问触发条件等。完整落地见 [06 落地实现要点](06_深入_落地实现要点.md)。

## 七、判定流程的边界情况

### 7.1 用户一句话里混了多种意图

「换成 iOS，顺便看下留存」

- 既有改端（follow_up），又有换指标（follow_up）。
- 两个 follow_up 子模式叠加，不是冲突。
- 处理：判 follow_up，一次覆盖两个字段（platform + metric）。

### 7.2 用户纠正后又追加新需求

「不是 ROI7 是 ROI360，媒体也拆一下」

- 前半句是 correction，后半句是 follow_up 改维度。
- 处理：以 correction 为主判定（语气信号优先），在 correction 的基础上同时执行 follow_up 的维度覆盖。即：纠正 metric + 覆盖 grain，其余继承。

### 7.3 隐式切话题（无切换语）

「实验 123 的留存」

- 无显式切换语，但领域从投放切到实验，且自带完整参数。
- 上一轮有活跃 context → Step 4 → 领域不重叠 → topic_switch。

### 7.4 同领域换产品

轮1「BB 的 ROI7」→ 轮2「MB 的 ROI7」

- 领域重叠（都是 ROI），产品换了，其余可继承。
- 判 follow_up（换产品子模式），只覆盖 bundle_id。

这是 topic_switch vs follow_up 最容易判错的边界。原则：**同领域 + 只换一个字段 = follow_up；跨领域或换一片 = topic_switch**。

---

## 八、本篇小结

1. **判定靠四类信号叠加**：语气信号（最强）> 上下文状态 > 结构信号 > 词汇信号。
2. **决策树五步**：先扫纠正 → 再扫切换 → 查上下文状态 → 结构+词汇定性 → 兜底 standalone。
3. **上下文状态是地基**：没有它，其他信号无法最终定性。
4. **兜底是红线**：判不准宁可当 standalone 追问，不冒险继承。投放/ROI 场景串口径代价远大于多问一句。
5. **边界情况靠主判定 + 附加操作**：混意图时以语气信号主判定，叠加执行其他操作。
