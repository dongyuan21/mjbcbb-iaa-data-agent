# 实验配置与方案查询规则

> 状态：active  
> 创建日期：2026-06-19  
> 适用范围：产品实验、方案号、AB 组别、实验起止时间、批次、实验整体效果、RR1 / RR3 / RR7、人均留存天数、时长、局数和收入对比。

## 使用边界

本文用于实验查询的选表、日期、粒度和字段边界，不直接提供 verified SQL。

可以作为当前默认规则使用：

- 区分实验配置表和实验效果表。
- 当实验起止时间、批次、是否底板、方案号缺失时，优先补元信息而不是直接反问。
- 判断 BB / DT 实验效果表的选表优先级和关键口径差异。

不能直接作为 verified 事实使用：

- 未进入 `ai_hive/agent_knowledge/catalog.yaml` 和表卡的候选表。
- 未经过 schema / 小窗口验证的字段、收入单位和预计算指标。
- 方案尾号 01 / 04 等组别经验；只能作为 `heuristic_group_role`，不能替代配置或 owner 确认。

## 配置表和效果表分工

| 问题 | 优先路径 | 说明 |
|---|---|---|
| 这个实验什么时候开始 / 结束 | 实验配置表 | 补 `starttime`、`endtime`、批次、发布时间、冻结时间等元信息。 |
| 这个方案号属于哪一期 | 实验配置表 | BB 产品实验看 BB 配置表；DT / 跨产品看全产品配置视图。 |
| 商业化算法实验有哪些广告单元和档位 | 商业化配置表 | 不用产品实验配置表替代商业化配置表。 |
| 实验组表现如何 | 实验方案效果表 | 按用户、方案、留存天或 active_date 聚合指标。 |
| 缺少实验时间但用户已给方案号 | 先查配置再取数 | 不默认追问日期。 |

配置表只补元信息，不是指标事实表；效果指标仍来自实验方案表、留存表、行为表或 verified SQL。

## 配置查询规则

| 场景 | 候选表 | 关键字段 / 过滤 |
|---|---|---|
| BB 产品实验配置 | `hungry_studio.dim_block_blast_abtest_conf_sq_ha` | `plan`、`starttime`、`endtime`、`is_db`、`pici_name_org`、`pici_name`、`dt`、`hour='23'` |
| DT / 全产品实验配置 | `hungry_studio.dim_all_app_ab_test_plan_conf_view` | `app_name`、`plan`、`plan_type`、`is_db`、`pici_name`、`ing_time`、`freeze_time`、`redirect_time`、`release_time` |
| MB / nova 实验配置 | `hungry_studio.dim_nova_nebula_all_ab_plan_conf_ha` | 需要表卡 intake 后确认字段和 hour 规则 |
| BB GP 商业化 / 算法配置 | `hungry_studio.dim_block_blast_gp_ad_realization_ab_pici_adunit_base_conf_ha` | `adunit`、`price_type`、`pici`、`adwaynum`、`start_date_time`、`end_date_time` |

执行规则：

- `dim_block_blast_abtest_conf_sq_ha` 是分区表，必须带 `dt` 和 `hour='23'`。
- `dim_all_app_ab_test_plan_conf_view` 是跨产品配置视图，必须用 `app_name` 过滤产品和端。
- `ing_time`、`freeze_time`、`redirect_time`、`release_time` 这类 Unix 时间戳字段展示时需转换成人可读时间。
- 商业化配置的 `pici` 不一定是纯数字，可能有后缀；按期查询时用前缀匹配，例如 `pici LIKE '145%'`，不要直接 `pici = '145'`。
- 商业化广告单元档位中 `high` / `mid` / `low` 只适用于已确认的商业化配置；小包例外见 `小包广告单元映射.md`。

## 实验效果选表优先级

### Block Blast

| 优先级 | 表族 | 粒度 | 场景 | 边界 |
|---|---|---|---|---|
| 1 | `dws_block_blast_all_new_abtest_user_way_agg_hi` | 用户 × 方案，周期聚合 | 实验整体效果、人均留存 / 时长 / 局数 / 收入 | 全量快照；无 `is_ab`；收入单位和预计算 eCPM 需表卡确认。 |
| 2 | `dws_block_blast_all_new_abtest_user_retention_hi` | 用户 × 留存天 × 方案 | RR1 / RR3 / RR7、active_date 趋势、留存天拆分 | 有 `is_ab` 时需过滤 `is_ab = 1`。 |
| 3 | `dws_block_blast_gp_new_abtest_active_join_user_ab_retention_hi`、`dws_block_blast_ios_new_abtest_active_join_user_ab_retention_hi` | 单端用户 × 留存天 × 方案 | 历史 SQL 兼容 | 只在新双端表不可用或复核旧 SQL 时使用。 |

### Double Tile

| 优先级 | 表族 | 粒度 | 场景 | 边界 |
|---|---|---|---|---|
| 1 | `dws_block_collection_all_new_abtest_user_way_agg_hi` | 用户 × 方案，周期聚合 | 实验整体汇总、人均指标 | 已聚合，不需要 `EXPLODE`。 |
| 2 | `dws_block_collection_all_new_abtest_user_retention_hi` | 用户 × 留存天 × 方案 | RR1 / RR3 / RR7、渠道分组、active_date 趋势 | DT retention 无 `is_ab`，用 `install_date >= starttime` 等实验期条件筛选。 |
| 3 | `dws_block_collection_all_new_abtest_user_multi_dim_hi` | 用户 × 天 | 按天行为趋势 | 方案号在 `abtest_result` 数组中，需要 `EXPLODE`；能用 retention 的 active_date 时优先不用它。 |

如果这些表未进入表卡，输出 `candidate_table_requires_intake`，不能把源材料字段当已治理字段。

## 日期和快照规则

- 全量实验效果表通常取最新可用 `dt` 和 `hour='23'`，业务日期用 `install_date`、`active_date` 或 `retention_days` 过滤。
- 已下线或离线实验可能不在最新分区保留效果数据；应先查配置表获取 `endtime` / 观测截止时间，再按表卡规则选择分区。
- 上线不足 2 日的实验可能没有完整留存或效果数据，输出时标注 `immature_experiment_window`。
- 不用 `MAX_PT()` 偷懒取分区；需要最新分区时先 probe 或按表卡规则说明。

## 指标口径

| 指标 | 规则 |
|---|---|
| 人均留存天数 | 实验整体效果默认优先，不要误写成 RR。 |
| RR1 / RR3 / RR7 | 必须使用 `retention_days = 0` 的分母和目标留存日的 `is_start` 分子。 |
| 人均时长 / 局数 / 收入 | 分母必须说明是用户数、实验用户数还是 D0 用户数。 |
| 收入 | BB 样例中存在 `ad_revenue * 1000` 写法；进入项目 SQL 前必须确认当前表单位，不能盲乘。 |
| ECPM | 优先用明确公式 `收入 / PV * 1000`；预计算 `ecpm` 字段需确认口径后使用。 |
| banner | 必须说明收入是否含 banner，且字段族和单位一致。 |

## 方案号和组别

- `plan` / `user_waynum` 通常对应实验方案号，但进入 SQL 前仍以表卡和配置表字段为准。
- 方案尾号 `01`、`02`、`03` 常见为对照组，`04` 及以后常见为实验组，但存在单特性反转实验等例外。
- 方案号可包含端、层、组等信息，但不要只靠字符串拆分决定业务含义。
- 输出对照组 / 实验组标签时，如果没有配置或 owner 确认，应标 `heuristic_group_role`。

## 输出要求

实验 SQL 输出必须说明：

- 是补配置，还是取效果。
- 使用的配置表 / 效果表、粒度、分区、`hour`、`app_name`。
- 实验窗口是否成熟、是否已下线、是否需要历史分区。
- 人均留存天数与 RR 指标的区别。
- 收入单位、是否含 banner、是否使用预计算 eCPM。
- 表和字段是否已表卡化、schema probe 或小窗口验证。

可复用 SQL 晋升仍遵守 `da_assets/SQL晋升治理.md`。
