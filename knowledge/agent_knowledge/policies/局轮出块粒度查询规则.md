# 局轮出块粒度查询规则

> 状态：active  
> 创建日期：2026-06-19  
> 适用范围：Block Blast 局粒度、轮维度、出块维度玩法分析，尤其是局内体验、出题策略、连击、复活、盘面权重和块级行为。

## 使用边界

本文定义局 / 轮 / 块三层粒度的选择顺序、字段语义风险和扫描护栏，不直接提供 verified SQL。

可以作为当前默认规则使用：

- 判断需求应停留在局表、下钻到轮表，还是继续下钻到出块表。
- 约束 `game_type`、`game_id`、`round_id`、累计字段、抽样表和白名单事件回补的使用方式。
- 说明候选表在进入表卡前只能作为 schema probe / candidate SQL 的对象。

不能直接作为 verified 事实使用：

- 未进入 `ai_hive/agent_knowledge/catalog.yaml` 和 `ai_hive/agent_knowledge/tables/` 的局 / 轮 / 出块表字段。
- 未小窗口验证的 cast、JSON 字段、累计字段差分逻辑。
- 样例 SQL 的执行结果。

## 粒度选择

默认选择能覆盖需求的最粗粒度：

```text
局表 > 轮表 > 出块表 > 白名单事件明细
```

| 粒度 | 适合问题 | 典型字段 | 使用边界 |
|---|---|---|---|
| 局粒度 | 局均 combo、通关数、尝试次数、局时长、复活弹窗点击 | `game_id`、`game_type`、`game_time`、`combo_cnt`、`init_matrix_weight`、`revive_show_cnt` | 优先使用；增量表按 `dt` 过滤。 |
| 轮维度 | 每轮盘面权重、理论 / 实际出题策略、轮耗时、连击演化 | `round_id`、`matrix_complex_value`、`time_diff_in_seconds`、`rec_strategy`、`rec_strategy_fact` | 只有局表无法覆盖时使用；约 30% 抽样，不能当全量用户事实。 |
| 出块维度 | 左中右块位、放块顺序、块组合、策略命中 | `block_id`、`index_id`、`block_index_id` | 只有轮表仍无法覆盖时使用；扫描风险最高。 |
| 白名单事件明细 | 局 / 轮 / 块表没有的 UI 曝光、点击过程或原始属性 | `event_name`、`properties` JSON | 必须遵守 `白名单事件表查询协议.md`，先用小人群和事件过滤限流。 |

如果用户只是问“局均”“人均”“通关”“复活点击率”“平均时长”，不要默认下钻到轮表或出块表。

## 必要过滤

`game_type` 是局 / 轮 / 出块查询的强制业务过滤。常见枚举：

| game_type | 含义 |
|---|---|
| `0` | 无尽 |
| `2` | 关卡 / 旅行 |
| `6` | 土耳其方块 |
| `10` | 谜题 |
| `99` | 新手引导 |

执行规则：

- 必须过滤 `dt`，并下推到最内层 CTE。
- 必须过滤 `game_type`，除非用户明确要求全模式对比；全模式对比也要在输出中展开模式维度。
- 涉及实验分析时，先用实验 / 留存表圈定 `distinct_id` 和实验方案，再 join 局 / 轮 / 块表，减少扫描。
- `distinct_id` 只用于内部 join 和聚合，不输出用户级明细。
- 所有比率分母用 `NULLIF(..., 0)`，并说明分母是局数、用户数、通关数、曝光数还是轮数。

## 局粒度规则

局粒度适合大多数玩法体验指标：

- 局数：`COUNT(DISTINCT game_id)`。
- 局均指标：先按用户或局聚合，再用 `SUM(metric) / NULLIF(SUM(game_cnt), 0)`。
- 通关数：按需求明确 `result_type = '1'`、`travel_id + travel_lv` 或其他通关定义。
- 复活点击率：点击数 / 曝光数，必须说明是否全模式、旅行模式或带进度阈值。

盘面字段：

- `init_matrix` 是局开始时盘面状态的 JSON 二维数组字符串。
- `init_matrix_weight` 是字符串型盘面权重，参与数值运算前必须 `CAST` 为 `DOUBLE`。
- `CAST(init_matrix_weight AS DOUBLE) < 0` 表示空盘面；正值表示有残留块盘面。

## 轮维度规则

轮维度适合分析单局内轮次节奏、策略和连击演化。

当轮值可直接聚合：

- `matrix_complex_value`：当前轮盘面权重。
- `time_diff_in_seconds`：当前轮耗时，可按需求求和或均值。
- `rec_strategy` / `rec_strategy_fact`：理论 / 实际出题策略。
- `combo_cnt`：当前轮 combo 连击序号。
- `is_combo_status_cnt`：是否处于 combo 状态。

累计值禁止二次累计：

| 字段 | 语义 |
|---|---|
| `gain_score` | 截至该轮累计得分 |
| `clear_screen_cnt` | 截至该轮累计清屏次数 |
| `blast_cnt` | 截至该轮累计爆炸次数 |
| `multiple_block_step_cnt` | 截至该轮累计多消步数 |
| `blast_row_col_cnt` | 截至该轮累计消除行列数 |
| `game_combo_cnt` | 截至该轮累计 combo 段数 |

禁止对这些累计字段再做 `SUM() OVER()` 或窗口累计。需要“上一轮之前累计值”时用：

```sql
LAG(gain_score, 1, 0) OVER (
  PARTITION BY distinct_id, game_id
  ORDER BY CAST(round_id AS BIGINT)
)
```

需要“当前轮增量”时，用当前累计值减去上一轮累计值，并先处理类型转换和空值。

## 出块维度规则

出块维度只在问题明确需要块级细节时使用，例如：

- 出块顺序。
- 左 / 中 / 右位置分布。
- block 组合。
- 理论和实际出题策略下的块分布。

执行规则：

- 必须过滤 `dt` 和 `game_type`。
- 先用目标用户、目标局或目标轮缩小范围，再查出块明细。
- 和轮表 join 时，至少使用 `distinct_id + game_id + round_id`；和局表 join 时，至少使用 `distinct_id + game_id`。
- `index_id` 用于左 / 中 / 右位置，`block_index_id` 用于放块顺序；含义进入 SQL 前仍需 schema / 样本验证。

## 白名单事件回补

当局 / 轮 / 块表缺少 UI 曝光、点击过程或 `properties` 字段时，才回到白名单事件表。

执行规则：

- 必须过滤 `dt`、`event_name` 和 `game_type`。
- 必须限制实验人群或目标用户窗口。
- JSON 字段提取遵守 `白名单事件表查询协议.md`。
- 事件明细只作为补充链路，不能替代已有聚合主题表做常规玩法指标。

## 输出要求

生成或审查 SQL 时必须说明：

- 当前使用局、轮、出块还是白名单事件明细。
- 为什么需要该粒度；若不是局表，说明局表不能覆盖的字段。
- `game_type`、日期窗口、实验人群和 join key。
- 是否存在约 30% 抽样、扫描范围、COUNT DISTINCT 或用户明细风险。
- 表和字段是否已表卡化、schema probe 或小窗口验证。

可复用 SQL 晋升仍遵守 `da_assets/SQL晋升治理.md`。
