# 用户行为留存画像查询规则

> 状态：active  
> 创建日期：2026-06-19  
> 适用范围：用户行为聚合、用户留存、用户画像 / 标签快照相关 SQL 的选表、分区、粒度和输出边界。

## 使用边界

本文沉淀用户行为、留存和画像主题的查询规则，不直接提供 verified SQL。

可以作为当前默认规则使用：

- 判断用户行为、留存、画像问题应优先走哪类表。
- 区分分区日期和业务日期，避免把全量快照表当增量表使用。
- 规范 `distinct_id`、`device_id`、`app_name`、`hour`、banner 字段和 PII 输出边界。

不能直接作为 verified 事实使用：

- 未进入 `ai_hive/agent_knowledge/catalog.yaml` 和 `ai_hive/agent_knowledge/tables/` 的候选表。
- 未经过 schema probe 或小窗口验证的字段。
- 源材料中的样例 SQL 结果。

## 主题路由

| 主题 | 典型问题 | 优先表型 | 粒度 | 必须说明 |
|---|---|---|---|---|
| 用户行为 | DAU、时长、局数、冷启动、广告行为聚合 | `user_multi_dim` | 用户 × 天 | `dt` 是分区 / 行为日期；共享表必须带 `app_name`。 |
| 用户留存 | RR1 / RR3 / RR7、新用户首日表现、活跃留存 | `retention` | 用户或设备 × 留存日 | 分区日和 `install_date` / `active_date` / `anchor_date` / `activity_date` 不要混用。 |
| 用户画像 | 某天用户属性、渠道、国家、设备、实验标签下钻 | `dim_*_user_ha`、`dim_*_user_label_ha` | 用户 × 快照分区 | 全量快照用最新可用 `dt` / `hour`，输出聚合，不输出用户明细。 |

当前已治理表优先读对应表卡；未在 catalog 中出现的同主题表只能输出 `candidate_table_requires_intake`。

## 用户行为查询规则

用户行为表适合做分日趋势、用户行为聚合和新用户安装信息归一。

执行规则：

- 大表必须过滤 `dt`；共享表必须同时过滤 `app_name`。
- 只输出聚合结果，`distinct_id` 只用于去重、join 或内部中间层，不输出用户明细。
- 需要“每个用户一条安装信息”时，可先用 `is_current_install_user = 1` 圈安装记录，再按 `app_name, distinct_id` 聚合，安装日期取 `MIN(dt)`。
- 地理、版本、渠道等随时间变化字段使用 `MAX_BY(field, dt)` 这类明确规则时，必须说明“取窗口内最后一次可见值”。
- 胜率、有效游戏时长占比等临时组合指标只能标为 `custom_metric`，不能当项目 confirmed 指标。

禁止：

- 用 `SELECT *` 拉取用户明细。
- 在未确认表卡字段前，把源材料里的字段名直接放进 production SQL。
- 把 `country_cn` 用作国家过滤主键；国家层级过滤仍用 `国家等级映射.md` 的 ISO 2 位 `country`。

## 留存查询规则

留存表常见为全量快照或准全量快照，必须区分：

| 日期字段 | 含义 | 用法 |
|---|---|---|
| `dt` | 分区 / 快照日期 | 取最新可用分区，或按 freshness / 表卡规则取指定分区。 |
| `hour` | 小时快照 | 有 `hour` 分区时优先取最终小时，例如 `hour = '23'`。 |
| `install_date` / `anchor_date` | cohort 起点 | 作为新增 / 安装 cohort 日期过滤和分组。 |
| `active_date` / `activity_date` | 活跃发生日 | 作为行为或留存发生日期过滤和分组。 |
| `retention_days` | 留存日龄 | RR1 / RR3 / RR7 等分子分母都必须显式使用。 |

执行规则：

- 全量快照表不要对 `dt` 做业务日期范围扫描；业务日期范围放到 `install_date`、`active_date`、`anchor_date` 或 `activity_date`。
- 有 `hour` 分区时必须过滤 `hour`；共享表必须过滤 `app_name`。
- RR 计算必须同时包含 `retention_days = 0` 的分母和目标留存日龄的分子。
- 人均首日指标必须明确分母是新用户数、安装数、设备数还是活跃数。
- 引入成本表时，必须说明成本表分区和业务日期是否与 cohort 日期一致。

Nova 系留存 / 行为表涉及 banner 时，优先使用 SDK banner 字段：

```text
sdk_banner_ad_revenue
sdk_banner_ad_pv
```

不要在未确认前用旧的 `banner_ad_revenue`、`banner_ad_pv` 替代 SDK banner 字段。

## 用户画像查询规则

画像 / 标签表适合做截至某个快照分区的用户属性下钻，例如国家、渠道、campaign、设备、版本、实验标签。

执行规则：

- 全量快照默认取最新可用 `dt`；有 `hour` 分区时取最终小时。
- BB GP / iOS 独立画像表按表名判断端；nova / collection 共享画像表必须过滤 `app_name`。
- `distinct_id`、`device_id`、广告标识、IP、经纬度、token 等只能内部 join 或聚合，不输出明细。
- 和行为、留存、收入表 join 时，优先用表卡确认的 join key；只有 `distinct_id` 同时存在并且粒度兼容时才可 join。
- `af_media_source`、`appsflyer_install_media_source`、`af_campaign`、`appsflyer_install_campaign` 等渠道字段存在多个候选时，必须在输出中说明 fallback 顺序。

禁止：

- 把快照画像字段当作历史任意日期的事实，除非表卡或分区验证支持该日期。
- 将 `app_name` 等同于 `bundle_id`；跨表 join 时要分别确认。
- 输出用户级属性列表。
