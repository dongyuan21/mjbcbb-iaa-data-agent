# 小包广告单元映射

> 状态：active  
> 创建日期：2026-06-19  
> 适用范围：小包广告单元 Clean Unit ID 与兜底 / 中价 / 高价档位映射，覆盖麻将 GP、麻将 iOS、木块安卓、木块 iOS。

## 使用边界

本文用于小包场景下按广告单元档位分析填充率、PV、收入、ECPM 等指标。

机器可读映射见：[小包广告单元映射.csv](小包广告单元映射.csv)。

可以作为当前默认规则使用：

- 将小包 `ad_unit_id` 映射到 `高价`、`中价`、`兜底`。
- 按小包 Package、广告格式和 Role 生成 Clean Unit ID 列表。
- 在白名单事件表中用 `GET_JSON_OBJECT(properties, '$.ad_unit_id')` 对齐 Clean Unit ID。

不能直接作为 verified SQL 使用：

- 未经过表卡、schema probe 或小窗口验证的事件表字段。
- 未确认当前线上生效版本时，不得只取其中一套 Unit ID。
- 不得把通用 BB 商业化配置表的 `price_type` 作为小包档位来源。

## 字段含义

| 字段 | 含义 |
|---|---|
| `package` | 小包产品 / 端。 |
| `app_name` | 白名单事件表或行为表中的产品过滤字段。 |
| `ad_type` | 广告格式，`Interstitial` 为插屏，`Rewarded` 为激励。 |
| `role` | 中文档位：高价 / 中价 / 兜底。 |
| `price_type` | 通用英文档位：`high` / `mid` / `low`。 |
| `clean_unit_id` | 与事件 `properties.ad_unit_id` 对齐的广告单元 ID。 |
| `sheet_source` | 原始维护表来源页签说明，作为排查线索。 |
| `max_unit_id` | 配置侧长描述，只作人工核对，不作为 join key。 |

## SQL 使用规则

当需求同时满足“小包”和“兜底 / 中价 / 高价 / price_type 分档”时：

1. 先按 `package` 过滤小包产品。
2. 再按 `ad_type` 过滤插屏或激励。
3. 再按 `role` / `price_type` 取 `clean_unit_id` 列表。
4. 在白名单事件表中用 `GET_JSON_OBJECT(properties, '$.ad_unit_id')` 匹配。
5. 共享表必须带 `app_name`，事件查询必须带 `dt`、`event_name`。

填充率默认口径：

```text
load 成功次数 / load 请求次数
```

事件侧常见写法：

```sql
COUNT(CASE WHEN GET_JSON_OBJECT(properties, '$.load_status') = '1' THEN 1 END)
/ NULLIF(COUNT(1), 0)
```

## 强制禁止

- 不用 `dim_block_blast_gp_ad_realization_ab_pici_adunit_base_conf_ha.price_type` 替代小包档位。
- 不用 `ad_adunit_rprm` 中的 `_high` / `_mid` / `_low` 单独替代本映射。
- 不用 `MAX Unit ID` 长描述做事件 join。
- 不把 `ad_unit_id` 当成商业化配置表主 join key；通用商业化配置仍以方案号 `adwaynum` 为主。

## 多套 Unit ID

同一 package / ad_type / role 可能存在多套 Clean Unit ID。默认规则是：

```text
只要 ad_unit_id 命中任一 Clean Unit ID，就归属该 role
```

如果用户只关心当前线上生效的一套，必须先向投放 / 商业化 owner 确认，或用配置 / 实时小窗口验证缩小 ID 列表。

## 与商业化协议的关系

小包广告单元映射是商业化广告单元分析的专项例外：

- 非小包 BB 商业化实验：优先按 `商业化SQL协议.md` 使用商业化配置表。
- 小包兜底 / 中价 / 高价：优先使用本文和配套 CSV。

具体表字段、分区、PII、freshness 和 SQL 晋升仍遵守 `白名单事件表查询协议.md`、`商业化SQL协议.md` 和 `da_assets/SQL晋升治理.md`。
