# 白名单事件表查询协议

> 状态：active  
> 创建日期：2026-06-19  
> 适用范围：白名单事件表、埋点行为、玩法链路、商业化链路和实验人群事件明细查询。

## 使用边界

白名单事件表是事件明细级大表，适合补充聚合主题表覆盖不到的行为细节。它不应成为默认第一选择。

优先级：

```text
verified_sql / 聚合主题表 / 实验主题表 / 留存主题表
→ 白名单事件表补充行为细节
→ 原始 SQL 样例仅作候选，必须验证
```

使用白名单事件表前必须先判断：

- 聚合主题表是否已覆盖指标。
- 是否能先用实验表、留存表或用户表圈定小人群。
- 是否真的需要事件级 `properties`。

## 必带过滤

| 场景 | 必带条件 |
|---|---|
| 所有白名单事件查询 | `dt`、`event_name` |
| 共享产品表 | `app_name` |
| BB GP / iOS 独立表 | 端由表名决定；必要时补 `bundle_id` |
| 实验人群事件查询 | 先在实验 / 用户主题表圈人，再按 `distinct_id` 限制事件表 |
| 长窗口行为分析 | 默认不超过 30 日；更长窗口必须说明扫描风险和替代表路径 |

禁止：

- 不带 `event_name` 扫白名单事件表。
- 用白名单事件表替代已有聚合主题表做常规 DAU / 留存 / 收入。
- 输出用户级明细、设备 ID、IP、user_agent 或原始 `properties` 全量内容。
- 把 `event_name` 直接等同于 AF / S2S / PGP 事件名；跨系统映射需另证。

## 表族选择

| 产品 / 表族 | 查询要求 |
|---|---|
| BB GP / iOS 白名单事件表 | 优先按端使用已有表卡；必须带 `dt` 和 `event_name`。 |
| nova collection all 白名单事件表 | 用于 MB、BC、JM、NB、MathCross 等 nova 系产品；必须带 `app_name`。 |
| block collection all 白名单事件表 | 用于 DT；必须带 `app_name`。 |

如果用户只给产品名：

1. 先按 `SQL表路由协议.md` 推断 `app_name` / 端。
2. 再查 `ai_hive/agent_knowledge/catalog.yaml` 是否有对应表卡。
3. 表卡不存在时输出 `candidate_table_requires_intake` 或先做 schema probe。

## 常见事件用途

| 事件 / 事件族 | 常见用途 | 注意事项 |
|---|---|---|
| `ta_app_start` | APP 启动、冷启、启动链路 | 可用 `#resume_from_background` 区分前后台恢复，但字段存在性需验证。 |
| `g_game_start` | 开局、关卡、局内初始状态 | 必须按产品确认 `game_type` / `game_mode`。 |
| `g_game_end` | 结算、胜负、分数、时长、道具、关卡完成 | 注意重开、失败、异常时长和分数封顶。 |
| `g_move_step` | 步骤、操作时长、局内过程 | 只在需要步骤级细节时使用，优先先圈定人群和局。 |
| `ad_load_start` / `ad_load_end` | 广告 load、load 成功率、加载时间 | 必须区分广告格式、ADX 渠道和 load_status。 |
| `s_ad_show_action` | action 到 ready 转化、广告展示请求 | 常用 `s_ad_type`、`s_ad_ready`、`s_ad_public_adwaynum`。 |
| `appLovin_sdk_ad_revenue` | SDK 广告收入回传 | 收入字段需验证单位；不要与聚合收入字段混用。 |

## JSON 字段处理

白名单事件表的业务字段经常在 `properties` 中，写 SQL 时必须：

- 只提取需要的 JSON path，不选择整列 `properties`。
- 对数值字段使用 `CAST`，并处理空字符串和非法值。
- 在输出说明里写明 JSON path 和字段语义来源。
- 对 `game_count`、`game_score`、`game_time_real`、`load_time`、`revenue` 等高风险字段写异常处理。

常见 JSON path：

| 类型 | JSON path |
|---|---|
| 实验 / 广告方案 | `$.s_ad_public_adwaynum`、`$.s_ad_series_id` |
| 广告格式 | `$.ad_type`、`$.s_ad_type`、`$.adFormat` |
| 广告单元 | `$.ad_unit_id`、`$.adUnitId` |
| ADX / network | `$.s_ad_extra_platform`、`$.networkName` |
| load | `$.load_status`、`$.load_time`、`$.corridor_floor` |
| ready | `$.s_ad_ready` |
| 收入 | `$.revenue`、`$.ad_revenue`、`$.ecpm` |
| 玩法 | `$.game_type`、`$.game_mode`、`$.game_id`、`$.game_count`、`$.level_id`、`$.game_score`、`$.game_time_real` |

## 实验人群 + 白名单事件

实验分析需要白名单事件细节时：

1. 先在实验主题表或配置表确定 `distinct_id` 人群、方案号和实验窗口。
2. 再用白名单事件表按 `distinct_id`、`dt`、`event_name`、`app_name` 限制。
3. 最终只输出聚合结果，不输出用户级明细。

常见错误：

- 白名单事件表直接全量扫实验周期。
- 事件窗口与实验入组 / 安装窗口混在一起。
- 只用 `distinct_id` join，但没有控制日期窗口和产品过滤。

## 输出要求

白名单事件 SQL 输出必须说明：

- 为什么不用更粗粒度主题表。
- 使用的事件名、JSON path、产品过滤、日期窗口。
- 是否先圈定人群。
- 扫描风险和窗口大小。
- 验证状态：未跑、schema probe、dry-run、小窗口或 verified。
