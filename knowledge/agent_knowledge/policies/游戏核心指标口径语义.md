# 游戏核心指标口径语义

> 状态：active  
> 创建日期：2026-06-19  
> 适用范围：Block Blast、Double Tile、Mahjong Blast 等游戏 KPI、留存、时长、局数、广告变现和商业化链路 SQL 的口径标准化。

## 使用边界

本文沉淀游戏核心指标的业务语义和写 SQL 时必须暴露的口径，不直接提供 verified SQL。

可以作为当前默认规则使用：

- 判断用户说的 DAU、新用户、留存、人均局数、人均收入、ECPM、广告密度等指标对应什么业务口径。
- 区分 BB、DT、MB 在广告收入、活跃口径、局数和异常值处理上的差异。
- 生成 SQL 前形成指标字段证据和输出说明。

不能直接作为 verified 事实使用：

- 未经过表卡、schema probe、dry-run 或小窗口验证的字段名。
- 未经过 `da_assets/SQL晋升治理.md` 的 SQL 示例。
- 未确认分母的异常率、综合提升率等 owner 决策口径。

写 SQL 时必须显式说明：

- 日期口径：分区日期还是业务日期。
- 分母：活跃用户、新用户、安装用户、启动用户、局数或广告 PV。
- banner 是否计入收入和频次。
- 产品和端：BB / DT / MB、GP / iOS。
- 验证状态：`candidate_sql`、`dry_run_passed`、`small_window_verified` 或 `verified_sql`。

## 通用核心指标

| 指标 | 标准口径 | SQL 写作要求 |
|---|---|---|
| DAU / 活跃用户数 | 当日启动或命中产品活跃口径的去重用户数 | 不同产品活跃口径不同；必须说明使用启动口径、白名单事件口径还是游戏行为口径。 |
| 新用户数 | 当日安装且当日启动 / 活跃的用户数 | 常见实现为 `install_date = active_date` 或 `retention_days = 0`；以表卡字段为准。 |
| 次日留存率 / RR1 | 口径日活跃用户中，次日仍活跃的用户数 / 口径日活跃用户数 | 输出中写明分母日期，不把实验场景的人均留存天数误写成 RR1。 |
| 3 日留存率 / RR3 | 口径日活跃用户中，第 3 日仍活跃的用户数 / 口径日活跃用户数 | 周期窗口必须覆盖口径日和回访日。 |
| 人均局数 | 总游戏局数 / 口径用户数 | 局数必须区分开始局、结束局、成功/失败/重开局。 |
| 人均时长 | 总游戏时长或 APP 使用时长 / 口径用户数 | 必须区分游戏内结算时长、游戏时长、APP 总时长。 |
| 人均冷启次数 | 总冷启动次数 / 口径用户数 | 字段来源必须来自表卡或 live schema。 |
| 人均总收入（含 banner） | 广告收入合计（插屏 + 激励 + banner）/ 口径用户数 | 必须说明 banner 是否存在、是否计入。 |
| 人均总收入（不含 banner） | 插屏 + 激励广告收入 / 口径用户数 | BB 和 DT 字段族不同，不能混用。 |
| 人均总频次（不含 banner） | 插屏 + 激励广告展示次数 / 口径用户数 | 不把 banner PV 混入非 banner 频次。 |
| ECPM | 非 banner 广告收入 * 1000 / 非 banner 广告展示次数 | 若需求要求含 banner，必须单独命名为含 banner ECPM。 |
| 人均插屏频次 | 插屏广告展示次数 / 口径用户数 | 分母优先与收入指标保持一致。 |
| 人均插屏收入 | 插屏广告收入 / 口径用户数 | 与插屏 PV 一起输出时可补插屏 ECPM。 |
| 插屏 ECPM | 插屏广告收入 * 1000 / 插屏广告展示次数 | 分母为插屏 PV，不是总 PV。 |
| 人均激励频次 | 激励广告展示次数 / 口径用户数 | 分母优先与收入指标保持一致。 |
| 人均激励收入 | 激励广告收入 / 口径用户数 | 与激励 PV 一起输出时可补激励 ECPM。 |
| 激励 ECPM | 激励广告收入 * 1000 / 激励广告展示次数 | 分母为激励 PV，不是总 PV。 |
| 广告密度 | 非 banner 广告展示次数 / 游戏局数 | 局数口径必须与游戏指标一致。 |

## 产品字段族差异

| 产品 | 收入口径 | 频次口径 | banner 处理 | 注意事项 |
|---|---|---|---|---|
| Block Blast | 常见字段族为 `ad_revenue`、`inter_ad_revenue`、`rewarded_ad_revenue` | 常见字段族为 `ad_pv`、`inter_ad_pv`、`rewarded_ad_pv` | 含 banner 收入通常为 `ad_revenue + banner_ad_revenue`；不含 banner 使用 `ad_revenue` | 字段和表名必须以当前表卡 / schema 为准。 |
| Double Tile | 常见字段族为 `busi_ad_revenue`、`busi_inter_ad_revenue`、`busi_rewarded_ad_revenue` | 常见字段族为 `busi_ad_pv`、`busi_inter_ad_pv`、`busi_rewarded_ad_pv` | 含 banner 收入通常为 `busi_ad_revenue + banner_ad_revenue`；不含 banner 使用 `busi_ad_revenue` | 不要把 BB 的 `ad_revenue` 字段名直接套到 DT。 |
| Mahjong Blast | 主看广告收入事件，并拆出插屏、激励收入 | 主看广告展示事件，并拆出插屏、激励 PV | 当前 GP / iOS 通常无 banner，banner 指标一般接近 0 | MB 不能直接沿用 BB / DT 多维表收入字段口径。 |

## Mahjong Blast 专项口径

MB 的指标口径与 BB / DT 差异较大。写 MB SQL 前，必须先确认产品过滤、版本过滤、实验过滤和行为事件范围。

### 活跃口径

| 口径 | 定义 | 使用建议 |
|---|---|---|
| `start_uv` | 命中麻将白名单活跃事件之一的用户数 | 适合看大盘活跃和看板主口径。 |
| `install_game_join_uv` | 发生过 `g_game_open` / `g_game_start` / `g_game_end` 之一的用户数 | 适合看真正进入游戏行为链路的用户；比 `start_uv` 更严格。 |

输出 MB 指标时必须说明使用了哪一个活跃口径，不能只写“活跃用户”。

### 局数口径

| 指标 | 标准口径 |
|---|---|
| `game_cnt` | `g_game_end` 次数，包含“重新开始”。 |
| `success_game_cnt` | `g_game_end` 且状态为成功。 |
| `fail_game_cnt` | `g_game_end` 且状态为失败。 |
| `retry_game_cnt` | `g_game_end` 且状态为重新开始。 |

### 收入口径

| 指标 | 标准口径 |
|---|---|
| 广告收入 | 以 MB 广告收入事件为主，不直接沿用 BB / DT 多维表收入字段。 |
| 插屏收入 | 从广告收入事件中按插屏广告类型拆出。 |
| 激励收入 | 从广告收入事件中按激励广告类型拆出。 |
| banner 收入 | 当前通常接近 0；如需求涉及 banner，必须验证事件和字段。 |

### 异常值处理

| 字段 | 处理规则 |
|---|---|
| 插屏收入 | 单方案、人天、模式粒度大于 5 时按 5 计。 |
| 激励收入 | 单方案、人天、模式粒度大于 5 时按 5 计。 |
| 游戏局数 | 大于 300 时记为 0。 |
| 游戏分数 | 大于 1,000,000 时记为 0。 |
| 单局结算时长 | 大于 24 小时记为 0；大于 2 小时封顶为 2 小时。 |

### MB 核心指标

| 指标 | 标准口径 | 状态 |
|---|---|---|
| 人均活跃天 | `start_uv / install_uv` | active |
| 人均收入（含横幅） | `(inter_ad_revenue + rewarded_ad_revenue + banner_ad_revenue) / install_uv` | active |
| 人均收入（不含横幅） | `(inter_ad_revenue + rewarded_ad_revenue) / install_uv` | active |
| 人均广告次数 | `(ad_pv + banner_ad_pv) / install_uv`；无 banner 时约等于 `ad_pv / install_uv` | active |
| 人均结算时长 | `game_realtime / install_uv` | active |
| 人均结算局数 | `game_cnt / install_uv` | active |
| 人均 APP 时长 | `usage_duration / install_uv` | active |
| 游戏对局率 | `install_game_join_uv / install_uv` | active |
| 人均插屏收入 | `inter_ad_revenue / install_uv` | active |
| 人均激励收入 | `rewarded_ad_revenue / install_uv` | active |
| ECPM | `ad_revenue / ad_pv * 1000`，通常约等于 `(inter_ad_revenue + rewarded_ad_revenue) / ad_pv * 1000` | active |
| 插屏 ECPM | `inter_ad_revenue / inter_ad_pv * 1000` | active |
| 激励 ECPM | `rewarded_ad_revenue / rewarded_ad_pv * 1000` | active |
| 每小时广告次数 | `ad_pv / (game_realtime / 3600)` | active |
| 人均单局时长 | `game_realtime / game_cnt` | active |
| 异常率 | `s_crash_or_anr_uv / install_uv` 或 `s_crash_or_anr_uv / start_uv` | needs_confirmation：分母需 owner 确认 |
| 综合提升率 | 留存提升率 * 0.6 + 收入提升率 * 0.15 + 人均广次提升率 * 0.05 + 结算时长提升率 * 0.15 + 结算局数提升率 * 0.05 | needs_confirmation：只可作为候选评分说明 |

### MB 常用过滤

MB 查询通常需要同时约束：

- `app_name = 'nova_mahjong_gp'` 或对应 iOS app_name。
- `game_mode = 0`，如果需求限定主模式。
- `is_formal = true`，如果需求限定正式局。
- app 版本满足看板口径要求；版本比较逻辑必须经过字段验证。
- 新用户 / 老用户口径必须通过 `install_day`、`install_date` 或表卡确认字段过滤。

## SQL 输出要求

生成游戏 KPI SQL 时，输出说明至少包含：

- 产品、端、用户范围和实验范围。
- 活跃口径、新用户口径、留存口径。
- 收入是否含 banner，ECPM 分母是否含 banner。
- 局数使用开始局、结束局还是结算局。
- 异常值处理是否写入 SQL。
- 字段证据来源：表卡、semantic_contract、verified_sql、live schema 或待确认。

如果用户只说“看核心指标”，默认输出紧凑核心集：

```text
DAU、新用户、RR1、RR3、人均局数、人均时长、人均冷启、人均收入（含/不含 banner）、人均总频次、ECPM、插屏收入/频次/ECPM、激励收入/频次/ECPM、广告密度
```

如果用户明确是商业化实验，优先输出：

```text
插屏 action、插屏 ready、插屏展示 PV、插屏收入、插屏 ECPM、激励 action、激励 ready、激励展示 PV、激励收入、激励 ECPM
```

如果用户明确是玩法 / 产品实验，优先输出：

```text
DAU、新用户、留存、人均局数、人均游戏时长、人均 APP 时长、人均收入、ECPM、核心玩法链路指标
```

## 维护规则

本文与 `ai_hive` 表卡、`knowledge/agent_knowledge/semantic_contract/model.json`、verified SQL 或 live schema 冲突时，以后者和业务 owner 确认为准。发现冲突后不要临场覆盖口径，先记录为待治理项，再按 SQL promotion 或表卡治理流程更新。
