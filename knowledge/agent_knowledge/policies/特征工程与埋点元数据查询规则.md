# 特征工程与埋点元数据查询规则

> 状态：active  
> 创建日期：2026-06-19  
> 适用范围：模型特征工程主题表、CS 埋点管理平台元数据表，以及它们与白名单事件表、实验、商业化查询的关系。

## 使用边界

本文用于判断“能不能用模型特征表或埋点元数据表辅助写 SQL”，不直接提供 verified SQL。

可以作为当前默认规则使用：

- 区分模型输入特征、模型输出标签和业务事实指标。
- 用埋点元数据预校验事件名、参数名、用户属性名和 Hudi 字段映射。
- 在生成白名单事件 SQL 前，说明字段来自表列还是 `properties` JSON。

不能直接作为 verified 事实使用：

- 未进入 `ai_hive/agent_knowledge/catalog.yaml` 和表卡的具体候选表。
- 未经 schema probe / 小窗口验证的字段是否存在、字段类型、分区和枚举值。
- 模型预测分、uplift label、相似人群 label 等模型结果。
- 元数据表中的事件定义记录本身；它只说明“定义存在”，不说明用户真的发生了事件。

候选表未表卡化时输出：

```text
candidate_table_requires_intake
```

## 模型特征工程主题

当前候选表：

| 端 | 候选表 | 使用边界 |
|---|---|---|
| BB GP | `hungry_studio.dws_block_blast_gp_user_feature_v1_da` | 用户特征、模型输入和模型输出线索；需补表卡。 |
| BB iOS | `hungry_studio.dws_block_blast_ios_user_feature_v1_da` | 用户特征、模型输入和模型输出线索；需补表卡。 |

模型特征表只适合以下场景：

- 解释模型输入特征是否覆盖某类行为、广告或用户历史。
- 做特征分布、缺失率、模型输出分层的聚合检查。
- 给点位候选、用户分层或模型回溯提供线索。

模型特征表不适合以下场景：

- 直接计算官方 DAU、留存、收入、ROI 或广告链路指标。
- 用预测值替代真实行为或真实收入。
- 输出用户级明细或设备级明细。
- 在没有 owner / 算法确认时，把模型 label 直接作为投放治理动作依据。

字段族识别：

| 字段族 | 常见字段 | 规则 |
|---|---|---|
| 用户和归因 | `id`、`country`、`country_group`、`af_media_source`、`media_source_group`、`device_type` | 只用于聚合分析；国家层级仍遵循 `国家等级映射.md`。 |
| 历史活跃 | `his_active_days`、`his_active_rate`、`last_login_ndays`、`his_max_score` | 必须说明历史窗口和锚点，不能默认等同当前窗口事实。 |
| 窗口特征 | `day_1`、`day_3`、`day_7`、`day_14`、`day_30`、`day_90` 相关字段 | 字段名里的窗口需要确认相对安装日、激活日还是模型锚点。 |
| 广告和玩法 | `ad_pv`、`ad_revenue`、`inter_*`、`rewarded_*`、`ecpm_*`、`game_cnt`、`start_pv`、`combo_*` | 只能作特征解释；正式广告指标仍回到商业化 / 事件 / 聚合事实表。 |
| 模型输出 | `*_y_preds`、`*_uplift_label`、`gmm_similarity_label` | 预测或标签，不是已发生业务事实；输出必须标注 model_output。 |
| 标识符 | `idfa`、`gaid`、`id` | PII / 用户级标识，不得输出明细。 |

使用特征表时必须在输出中说明：

- 这是 feature / model_output / label 分析，不是业务事实口径。
- 表是否已经表卡化；未表卡化时标 `candidate_table_requires_intake`。
- `dt`、`install_datetime`、`max_active_date`、`day_N` 字段的时间含义是否已验证。
- PII 字段只用于内部去重或聚合，不输出用户级结果。

## 埋点元数据主题

当前候选表：

| 表 | 粒度 | 用途 |
|---|---|---|
| `hungry_studio.dim_cs_data_origin_event_bgd_games_project` | 产品 / 项目 × 平台 | 查 `game_id`、`app_id`、产品名、端和项目状态。 |
| `hungry_studio.dim_cs_data_origin_event_bgd_bi_events_v2` | 产品 × 事件 | 查事件名、中文名、触发点、事件类型和主题。 |
| `hungry_studio.dim_cs_data_origin_event_bgd_bi_attr` | 产品 × 事件 × 参数 | 查事件参数名、Hudi 字段映射、字段层级、类型和枚举。 |
| `hungry_studio.dim_cs_data_origin_event_bgd_bi_os_user_attr` | 产品 × 用户属性 | 查用户属性名、Hudi 字段映射、字段层级和类型。 |

这些表是埋点定义和字段映射来源，不是行为事实表。它们适合在写白名单事件 SQL 前回答：

- 某产品是否定义了某事件。
- 某事件是否有某个参数。
- 参数应该用 `event_attribute_name` 从 `properties` 取，还是用 `event_tab_field` 读取 Hudi 展开列。
- 某用户属性在产品下是否存在。
- 同一事件或参数在不同产品 / 端是否一致。

常用关系：

```text
games_project.game_id -> bi_events_v2.game_id
games_project.game_id -> bi_attr.game_id
games_project.game_id -> bi_os_user_attr.game_id
bi_events_v2.name = bi_attr.event_name
```

常用过滤：

| 表 | 过滤建议 |
|---|---|
| `games_project` | 优先 `game_type = '正式'`、`state = 1`、`deleted = 0`。 |
| `bi_events_v2` | 优先 `status = 1`；`event_type = 0` 表示普通事件，`event_type = 1` 表示密集事件。 |
| `bi_attr` | 优先 `status = 1`；`field_level = 1/2/3` 分别对应公共、模型、道具等字段层级。 |
| `bi_os_user_attr` | 优先 `status = 1`；字段类型按元数据解释，进入 SQL 前仍需验证。 |

| game_id | 元数据产品名 | os | 项目 `app_name` / 说明 |

字段名规则：

- `event_attribute_name` 是埋点 JSON key，适合生成 `properties` 取数路径。
- `event_tab_field` 是 Hudi / 事件表展开列名线索；进入 SQL 前仍要确认目标事实表是否真的有该列。
- `event_attribute_name` 和 `event_tab_field` 可能大小写或下划线不同，例如驼峰参数被展开为小写列名。
- 若 `event_tab_field` 为空或事实表无该列，再考虑从 `properties` 取 `event_attribute_name`。
- 若元数据、静态文档和事实表 schema 冲突，先标 `field_definition_conflict`，不要自行改名或合并。

## 与白名单事件表联动

写白名单事件 SQL 前，埋点元数据可以作为字段定义预检：

1. 先按产品 / 端定位 `game_id`。
2. 用事件元数据确认 `event_name` 是否启用。
3. 用参数元数据确认参数名、字段层级、数据类型和 Hudi 映射。
4. 再回到目标白名单事件表卡或 live schema，确认字段是展开列还是 JSON path。
5. 最终按 `白名单事件表查询协议.md` 加 `dt`、`event_name`、`app_name`、PII 和扫描护栏。

不要用元数据表替代事实表做 PV、UV、收入、留存或漏斗计算。

## 输出要求

涉及模型特征或埋点元数据时，输出必须说明：

- route_taken：模型特征 / 埋点元数据 / 白名单事件事实表。
- data_source：使用的表卡、catalog、schema probe 或候选表。
- validation_status：verified、schema_probe、candidate_table_requires_intake 或未验证。
- fact_boundary：特征表不是官方事实表，元数据表不是行为事实表。
- pii_boundary：不输出 `id`、`idfa`、`gaid`、设备 ID、IP、user_agent 或原始 `properties` 全量。
