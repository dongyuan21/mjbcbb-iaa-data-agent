# 事实切面分离与唯一性治理方案

> 状态：draft_pending_review
> 作者：Data Agent 知识库
> 创建时间：2026-07-16
> 范围：`da_assets/`、`knowledge/`、`ai_hive/`、`ai_ck/`、`task_routes/` 之间的事实唯一性治理
> 审阅目标：请审阅本方案的架构合理性、切面划分完整性、门禁可行性，以及是否有更简单的替代方案。

## 一、背景

### 1.1 知识库现状

本工作区是一个面向投放 ROI 分析的 Data Agent 知识库，包含以下顶层目录：

| 目录 | 职责 | 默认召回 |
|---|---|---:|
| `knowledge/` | Agent 默认召回的事实基座（policies、semantic_contract、report_knowledge） | 是 |
| `da_assets/` | DA 报告→可信知识的蒸馏管线（verified_sql、candidate_sql、analysis_sop、decision_cases、raw） | 部分 |
| `ai_hive/` | MaxCompute/Hive 表卡（字段、分区、PII、query_rules） | 按命中 |
| `ai_ck/` | ClickHouse/MI 表卡和指标解释 | 按命中 |
| `task_routes/` | 任务路由控制面（一任务一 YAML） | 是（INDEX 轻量路由） |

### 1.2 问题

`knowledge/` 和 `da_assets/` 中都存在 solid 知识。以"投放红黄线阈值"这一个事实为例，它分散在 5 个文件中：

| 位置 | 存了什么 | 角色 |
|---|---|---|
| `knowledge/agent_knowledge/policies/投放ROI治理政策.md` | 三条线定义、使用方式、Agent 行为约束 | 规则逻辑 |
| `knowledge/agent_knowledge/report_knowledge/PACKAGE_ROI_TARGET_THRESHOLDS.csv` | 21 行包体阈值数值 | 机器可读数值 |
| `knowledge/agent_knowledge/report_knowledge/包体ROI目标阈值.md` | 人类可读说明 + 来源 + 确认状态 | 数值说明 |
| `da_assets/decision_cases/20260625_红黄线双日review规则DA确认.md` | DA 确认纪要 + 试运行状态 | 确认过程 |
| `da_assets/raw/2026-06-16_发行红绿线执行说明_docx.md` | 原始 docx | 来源材料 |

类似地，"SDK 回收定义"同时出现在 `policies/投放与ROI预估SQL协议.md`（口径规则）和 `da_assets/verified_sql/` 中的多条 SQL（实现），以及 `ai_ck/agent_knowledge/tables/` 的表卡（字段定义）中。

### 1.3 风险

1. **内容复制导致漂移**：同一数值/定义被复制到多个文件，修改时漏改某份会导致事实不一致。
2. **Agent 无法判断权威来源**：回答"红线是多少"时，policies 和 report_knowledge 都有相关内容，Agent 不确定读哪个。
3. **长期维护成本高**：没有注册表，新增事实时不知道该放哪里，也不知道已有的切面是否完整。

## 二、核心设计：事实切面分离

### 2.1 设计原则

一个完整的事实由多个**切面**组成，每个切面有且只有一个**权威写入点**：

```
一个完整事实 = 规则逻辑 + 数值数据 + 确认状态 + 来源证据 + SQL 实现 + 分析流程 + 表卡 + 机器契约
```

**核心规则**：
- 每个切面只有一个权威写入点。
- 其他文件引用时写 path，不复制内容。
- 新增事实需先在 `authority_map.yaml` 注册，再在各切面文件中写入。
- 切面为 `null` 表示该事实暂无此切面（如纯规则无 SQL 实现）。

### 2.2 切面定义

| 切面 | 含义 | 权威目录 | 示例 |
|---|---|---|---|
| `rule_logic` | 规则逻辑：是什么、怎么用、Agent 行为约束 | `knowledge/agent_knowledge/policies/` | 投放ROI治理政策.md |
| `numeric_data` | 数值数据：具体阈值、映射表、机器可读 CSV | `knowledge/agent_knowledge/report_knowledge/` | PACKAGE_ROI_TARGET_THRESHOLDS.csv |
| `data_explanation` | 人类可读说明：数值的来源、确认状态、适用边界 | `knowledge/agent_knowledge/report_knowledge/` | 包体ROI目标阈值.md |
| `confirmation` | 确认过程：谁在什么时候确认了什么 | `da_assets/decision_cases/` | 红黄线双日review规则DA确认.md |
| `source` | 来源材料：原始 docx、截图、导出件 | `da_assets/raw/` | 发行红绿线执行说明_docx.md |
| `sql_implementation` | SQL 实现：可复跑的 verified SQL | `da_assets/verified_sql/` | vsql_20260715_*.md |
| `sop` | 分析流程：先看什么、再看什么、怎么拆解 | `da_assets/analysis_sop/` | LTV倍率下降归因SOP.md |
| `table_card` | 表卡：字段、分区、PII、query_rules | `ai_hive/` 或 `ai_ck/` | tj_ad_sdk_revenue.yaml |
| `semantic_contract` | 机器契约：跨表实体、指标、join | `knowledge/agent_knowledge/semantic_contract/` | metrics.yaml |
| `related_task_route` | 任务路由：触发词、first_read、上下文预算 | `task_routes/` | roi_or_campaign_analysis.yaml |

### 2.3 引用链示例

以红黄线为例，正确的引用链：

```
policies/投放ROI治理政策.md
  ├─ 引用 → report_knowledge/PACKAGE_ROI_TARGET_THRESHOLDS.csv （不复制数值）
  └─ 引用 → decision_cases/20260625_红黄线双日review规则DA确认.md （不复制确认过程）

report_knowledge/包体ROI目标阈值.md
  ├─ 引用 → raw/2026-06-16_发行红绿线执行说明_docx.md （不复制原文）
  └─ 引用 → policies/投放ROI治理政策.md （不复制规则逻辑）

decision_cases/20260625_红黄线双日review规则DA确认.md
  └─ 引用 → report_knowledge/PACKAGE_ROI_TARGET_THRESHOLDS.csv （不复制数值）
```

### 2.4 切面优先级（补充 Source Priority）

现有 Source Priority 按**文件可信度**排序：

```text
verified_sql / confirmed policy
→ knowledge/agent_knowledge/agent_knowledge/semantic_contract/model.json
→ ai_hive / ai_ck 表卡
→ analysis_sop
→ decision_cases
→ reviewed image extracts
→ raw / draft
```

补充**切面优先级**——当回答不同类型问题时，优先读取不同切面：

| 问题类型 | 优先读取切面 | 权威目录 |
|---|---|---|
| "红线是多少" / "阈值是多少" | numeric_data | knowledge/agent_knowledge/report_knowledge/ |
| "红线怎么用" / "规则是什么" | rule_logic | knowledge/agent_knowledge/policies/ |
| "红线怎么确认的" | confirmation | da_assets/decision_cases/ |
| "红线 SQL 怎么算" | sql_implementation | da_assets/verified_sql/ |
| "这个指标怎么定义" | semantic_contract + rule_logic | knowledge/agent_knowledge/semantic_contract/ + policies/ |
| "这张表有什么字段" | table_card | ai_hive/ 或 ai_ck/ |
| "怎么分析这个问题" | sop | da_assets/analysis_sop/ |

## 三、`da_assets/` 与 `knowledge/` 的边界

### 3.1 为什么 `da_assets/` 需要独立存在

`da_assets/` 是"蒸馏管线"，不是"第二个 knowledge"。两者的根本区别：

| 维度 | `knowledge/` | `da_assets/` |
|---|---|---|
| 定位 | 已确认事实基座 | 从原始报告到事实的蒸馏过程产物 |
| 内容稳定性 | 静态注册表，手动确认后变更 | 有状态机（candidate→validated→verified→deprecated） |
| 可信度 | 全部 confirmed/active/trial_active | 混合（verified / draft / candidate / partial_verified） |
| 默认召回 | 是 | 部分（verified_sql 按 task_routes 命中拉取） |
| 门禁 | check_knowledge_consistency.py | check_sql_promotion.py |

`da_assets/` 独立存在的核心价值：
1. **知识生命周期管理**：verified_sql 有 `last_validated_at` 过期和 `supersedes` 生命周期，不适合放进 `knowledge/` 的静态注册表。
2. **可信度分层**：`knowledge/` 默认召回是 confirmed 级，`da_assets/` 里有大量 draft/candidate 内容，混在一起 Agent 无法区分。
3. **来源追溯链完整**：raw → sop → candidate → verified → decision_case，这条蒸馏链需要物理容器。

### 3.2 边界规则

| 内容类型 | 唯一归属 | 不应出现在 |
|---|---|---|
| 规则逻辑（必须遵守的规则） | `knowledge/agent_knowledge/policies/` | da_assets/ |
| 数值数据（阈值、映射表） | `knowledge/agent_knowledge/report_knowledge/` | da_assets/、policies/ |
| 分析步骤（可参考的流程） | `da_assets/analysis_sop/` | policies/ |
| 事件快照（单次风险/后验） | `da_assets/decision_cases/` | knowledge/ |
| 可复跑 SQL | `da_assets/verified_sql/` | knowledge/ |
| 原始材料 | `da_assets/raw/` | knowledge/ |

**晋升规则**：
- `decision_cases/` 中闭环且被确认为长期事实的结论 → 晋升到 `knowledge/agent_knowledge/report_knowledge/` 或 `policies/`，原 case 保留为过程记录。
- `analysis_sop/` 中被确认为必须遵守的规则 → 晋升到 `policies/`，原 SOP 保留为参考流程。
- `verified_sql/` 不向 `knowledge/` 晋升，可信度由 SQL 晋升门禁保证。

## 四、实现机制

### 4.1 authority_map.yaml

位置：`knowledge/agent_knowledge/authority_map.yaml`

注册每个事实的所有切面权威写入点。格式见文件本身。

**使用方式**：
- 新增事实前，先在 authority_map.yaml 注册。
- Agent 回答问题时，先查 authority_map 确定权威切面，再读对应文件。
- 门禁脚本检查 authority_map 中注册的 path 是否存在、是否可达。

### 4.2 门禁脚本：check_authority_map.py

位置：`tools/scripts/check_authority_map.py`

检查项：
1. authority_map.yaml 中注册的每个 path 是否实际存在。
2. authority_map.yaml 中是否有重复注册（同一 path 被注册为多个事实的同一切面）。
3. 扫描 policies/ 和 verified_sql/ 中是否出现了与 report_knowledge/ 中相同的具体数值（内容复制检测）。
4. 扫描 decision_cases/ 中是否复制了完整的规则定义（应引用而非复制）。

### 4.3 与现有门禁的关系

| 门禁 | 检查对象 | 与本方案的关系 |
|---|---|---|
| check_knowledge_consistency.py | knowledge/ 文件注册和格式 | 不变 |
| check_sql_promotion.py | da_assets/ SQL 晋升状态机 | 不变 |
| check_table_card_quality.py | ai_hive/ ai_ck/ 表卡质量 | 不变 |
| **check_authority_map.py**（新增） | 跨目录事实唯一性 | **本方案新增** |

## 六、待审阅问题

1. **切面划分是否完整**：当前定义了 10 个切面，是否有遗漏？例如"数据新鲜度 SLA"是否需要单独切面，还是归入 table_card？
2. **内容复制检测的可行性**：门禁脚本扫描"相同数值"在技术上可行吗？是否应该用更简单的"引用格式检查"替代（如检查 policies/ 中是否内联了 CSV 数值）？
3. **authority_map 的维护成本**：每新增一个事实都需要手动注册，是否会成为治理瓶颈？是否需要从 index.yaml / catalog.yaml 自动生成？
4. **切面优先级的执行方式**：当前是文档约定，是否需要在 task_routes/ 中机器化（如每个 task_route 声明它需要读哪些切面）？
5. **是否有更简单的替代方案**：例如不引入 authority_map，而是在每个文件头部加 `authority_for: [fact_id, facet]` frontmatter，由门禁脚本扫描全库自动构建映射？
