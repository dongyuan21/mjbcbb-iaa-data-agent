## S2S 的定义

S2S 是服务端到服务端的事件回传。投放场景中，它把用户达到某个行为或模型判断结果，通过服务端 HTTP 告诉 AF、Firebase、Meta、Google、TikTok、AppLovin 等系统，让广告平台优化算法获得深度信号。

## 与 SDK 上报的差异

| 维度 | SDK 上报 | S2S 上报 |
|---|---|---|
| 触发位置 | App 客户端 | 服务端 / DataWorks Python / 微服务 / 模型 worker |
| 可控性 | 受客户端网络、权限、SDK 初始化影响 | 服务端可控，可重试、补发、审计 |
| 可信度 | 客户端可被篡改 | 更高，适合虚拟事件和模型事件 |
| 典型用途 | 真实业务事件 | 虚拟点位、PLTV、CAPI、预测高价值事件 |

## “数仓做 S2S”的真实含义

8方块中强调：ODPS / Hive 本体不直接调 HTTP。

更准确的链路是：

```text
MaxCompute / ODPS SQL 算名单
  -> DataWorks 调度或任务编排
  -> Python / 微服务 / worker 调 HTTP API
  -> AF / Firebase / Meta / Google / partner
```

因此 agent 回答时不应说“ODPS 调 S2S”，而应说“数仓计算名单，执行层负责 HTTP 回传”。

## S2S owner 三类候选

| owner | 典型位置 | 场景 |
|---|---|---|
| 数据工程 / 数据平台 | DataWorks Python 节点 / 离线任务 | T+1 虚拟事件、Cost 数据、通用数仓回传 |
| 后端 / 增长工程 | 微服务 / 定时任务 | 实时规则引擎、高 QPS 回传 |
| 算法 / ML 工程 | 模型打分服务旁 worker | 模型实时打分、PLTV、FB CAPI |

待审核：公司当前各 S2S 链路的真实 owner 不能仅凭 8方块草稿判断。

## PM / Agent 必问的问题

1. 虚拟 / 自定义事件回传 AF 的代码跑在哪个项目下？
2. 是 DataWorks Python 节点、独立微服务，还是模型 worker？
3. 失败重试和监控在哪一层做？
4. 幂等 key 是什么，如何避免重复 POST？
5. 事件名、参数、时区和归因 ID 如何验收？

## IAA S2S 设计原则候选

从 8方块 IAA-S2S 文档抽取的候选原则：

- IAA 游戏缺少天然 IAP 深度信号，需要 deep event / 虚拟点位补充优化目标。
- VO / CPE 可双轨，不一定二选一。
- 事件阈值可以形成梯度，让媒体学习不同 value bucket。
- D0-D1 是学习黄金窗口，预测型 S2S 价值在于把 D3/D7 信号提前。

待审核：

- 具体事件名、阈值、CPA 数字可能是当时案例，不应直接 promote 为全局规则。
- 真 IAP 与 hack purchase 的边界仍需业务确认。
