# Phase 0 总结（人话版）

> 日期：2026-07-23

## 这个 Phase 0 做了什么

我们要把 UA（用户增长）团队改广告预算的操作记录，变成一套可以追溯、可以分析、可以回测的系统。Phase 0 就是"搞清楚我们有什么、能做什么、不能做什么"。

## 三个平台的操作记录能力

| 平台 | 能拿到什么 | 可信度 | 能不能用来分析 |
|---|---|---|---|
| Google | 平台原生变更日志（改之前和改之后都有）+ MI 操作日志 | 最高 | 能做事实分析、行为模仿、效果评估 |
| Meta | MI 操作日志（通过 XMP 工具或 Meta 后台操作，都是人工操作） | 中等 | 能做事实分析和行为模仿；效果评估要补数据 |
| AppLovin | MI 里没有操作记录，是手动下载的，只能靠"今天的配置减昨天的配置"来猜 | 最低 | 只能做事实时间线；行为模仿和效果评估做不了 |

## 利润怎么算

- **收入**：用 SDK 收入（游戏内广告/内购直接回传的），AF 收入做对照
- **成本**：用折后消耗（打了返点折扣的实际花费）
- **D7 利润**：7 天累计收入 - 折后消耗（第 0 天到第 6 天）
- **D14 利润**：14 天累计收入 - 折后消耗（第 0 天到第 13 天）

这些算法不是拍脑袋定的，全部从数仓现有的知识库里找到的，和你们现在跑的 verified SQL 一致。

## 什么不能做

- 不能自动停投、放量、改预算（Data Agent 只读分析，不执行投放动作）
- 不能把"没查到操作日志"当成"没操作"（可能是接口没查全）
- 不能把 AppLovin 的配置快照差分当成可信操作记录
- 不能用操作人的明文邮箱做分析（要脱敏）

## 还有什么问题没解决

| 问题 | 严重吗 | 什么时候要解决 |
|---|---|---|
| AppLovin 操作是手动下载的，MI 里没有记录 | 中——AppLovin 的分析能力受限 | 做 AppLovin 分析之前 |
| 操作人脱敏还在用普通 SHA256，没升级成 HMAC | 低——不阻断主线，只阻断操作人维度分析 | 正式入仓前 |
| 利润公式里有些细节没最终确认（返点版本、partial-day 等） | 低——Phase 1A 不需要 | 做效果评估之前 |
| 7 张表卡缺 freshness 段，自动探测覆盖不全 | 低——手动探测已补齐 | 后续表准入流程 |

## 下一步建议

**先做 Google**。因为 Google 的数据最完整（有原生变更日志 + MI 操作日志），可以最快跑通从"操作记录"到"决策 Episode"到"效果回测"的全链路。

Google 跑通后，再复制到 Meta（数据中等）和 AppLovin（数据最弱，需先解决操作采集问题）。
