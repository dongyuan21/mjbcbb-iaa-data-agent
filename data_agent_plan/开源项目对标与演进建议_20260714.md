# Data Agent 开源项目对标与演进建议

> 状态：`architecture_benchmark`
> 调研日期：2026-07-14
> 目的：对标当前 Data Agent 的知识层、语义契约层、Hive / ClickHouse 数据资产层与 Runtime，明确可借鉴能力和后续演进顺序。
> 边界：本文只记录架构对标和工程建议，不引入新的业务口径，不把外部项目能力视为本工程已完成功能。

## 一、结论

当前工程不需要因为出现新的开源框架而推倒重来。

本工程已经形成一条相对完整的受控链路：

```text
业务知识与任务路由
  -> 语义契约
  -> Hive / ClickHouse 表卡与只读执行
  -> candidate / verified 证据分级
  -> freshness、PII、质量检查和回归门禁
  -> Runtime、SSE、trace 与报告输出
```

与常见的 RAG + Text2SQL Demo 相比，当前优势是证据治理、数据状态、知识状态和执行边界已经被纳入同一套工作流。与成熟开源项目相比，主要差距不在架构概念，而在以下四点：

1. 语义契约还需要进一步执行化和编译化。
2. 路由准确性需要独立标注集和可校准指标。
3. 用户身份、数据权限和审计需要贯穿 Runtime。
4. 线上反馈需要经过人工审核和晋升门禁后再进入稳定记忆。

## 三、各项目与本工程的对应关系

### 1. WrenAI：整体架构对标

WrenAI 的 Modeling Definition Language（MDL）既是 Agent 可读的语义合同，也参与查询规划和 SQL 展开。其 Context Layer 还把语义模型之外的默认过滤、选表规则、例外、澄清条件和历史经验作为独立知识管理。

与本工程的对应关系：

```text
Wren instructions / knowledge
  <-> knowledge/ 与 task_routes/

Wren MDL
  <-> semantic_contract/model.json

Wren models / relationships / query execution
  <-> ai_hive、ai_ck、表卡和 MC / CK executor
```

值得借鉴的重点不是复制其 UI，而是让语义契约真正参与 SQL 规划、合法性检查和错误反馈。

参考：[WrenAI MDL](https://docs.getwren.ai/oss/engine/concept/what_is_mdl)、[WrenAI Context](https://docs.getwren.ai/oss/concepts/what_is_context)。

### 2. MetricFlow：语义层执行化对标

MetricFlow 把指标请求编译成数据流查询计划，再生成目标引擎 SQL，支持多跳关联、比例指标、累计指标和不同时间粒度。

本工程可以借鉴以下中间表示：

```yaml
metric_request:
  metrics:
    - roi
  dimensions:
    - campaign
    - country
  time_granularity: day
  filters: []
  source_preference: verified_first
```

Runtime 应先验证指标、维度、粒度和 join path 是否兼容，再决定复用 verified SQL 或生成 candidate SQL。

参考：[MetricFlow](https://github.com/dbt-labs/metricflow)。

### 3. Vanna：Runtime 生产化对标

Vanna 2.0 强调用户身份从请求入口贯穿到每个工具，并提供工具权限、会话隔离、审计和流式交互能力。

本工程可重点参考：

- SSO 用户、用户组和 workspace context 注入每次工具调用。
- MC / CK executor 在工具层做权限判断，而不是只依赖 prompt。
- 审计记录保存用户、路由、检索资产、SQL、脱敏后的参数和执行结果状态。
- LLM 只读取受控摘要，前端可以展示完整分页结果，避免大结果集进入上下文。
- 成功 SQL 和工具调用先进入 candidate memory，经审核后再晋升。

参考：[Vanna 2.0 Migration](https://vanna.ai/docs/migration)、[Vanna Security](https://vanna.ai/data-security)。

### 4. OpenMetadata：表卡和信任图对标

OpenMetadata 把技术元数据、血缘、数据质量、freshness、Owner、认证状态、策略和业务术语连接成统一元数据图。

当前不建议直接引入完整平台。可以先借鉴其数据结构，为现有表卡逐步补齐：

- owner / steward；
- upstream / downstream lineage；
- certification 和生命周期；
- freshness 与质量检查历史；
- 使用频率和推荐数据集；
- 字段级 lineage 与变更影响。

参考：[OpenMetadata](https://github.com/open-metadata/OpenMetadata)。

### 5. LangGraph：路由模式对标

LangGraph 支持单路由和多路 fan-out。一个问题可以路由到零个、一个或多个专项流程，再统一汇总。

本工程可借鉴其模式，但不需要因此替换 PI：

```text
规则和向量召回 Top-K route
  -> 结构化重排
  -> 单意图直接进入
  -> 多意图按需 fan-out
  -> 语义层和资产层去重
  -> 汇总证据与结论
```

参考：[LangGraph Router](https://docs.langchain.com/oss/python/langchain/multi-agent/router)。

### 6. Cube：语义 Runtime 与性能对标

Cube 的 Agent 不直接访问原始数据表，而是查询语义运行时；运行时确定性应用语义模型和访问策略，再生成底层查询。它还通过预聚合和 refresh key 控制查询性能与新鲜度。

本工程进入多用户、高并发阶段后，可以参考：

- 指标和关联规则在查询前强制校验；
- 行级、字段级和成员级访问控制；
- 高频指标预聚合；
- 查询命中 CK 聚合层，否则回源 MC；
- 聚合层 freshness 不满足时拒绝或降级。

参考：[Cube Architecture](https://docs.cube.dev/docs/introduction)。

## 四、建议的演进顺序

### P0：把路由和语义层变成可验证系统

#### 1. 建立路由标注集

建议从 100～300 条脱敏业务问题开始，每条至少定义：

```yaml
question: 看 BB GP 145 期插屏 ready 和收入
expected_routes:
  - commercial_experiment
expected_slots:
  product: BB
  platform: GP
  experiment: "145"
required_assets:
  - 商业化SQL协议
  - 实验配置与方案查询规则
forbidden_asset_states:
  - raw
  - draft
```

持续统计：

- Top-1 Accuracy；
- Top-2 Recall；
- 槽位准确率；
- 必要知识召回率；
- 拒绝执行率；
- 错误执行率。

其中最重要的风险指标是：错误路由后仍然执行 SQL 的比例。

#### 2. 增加可执行语义校验

Runtime 在执行 SQL 前必须校验：

- 指标和维度是否兼容；
- join 是否存在于允许路径；
- 两侧粒度是否一致；
- 指标是否展开成已确认公式；
- 跨层指标是否违反 canonical owner；
- 查询字段是否命中 PII 禁止项；
- 数据源和分区是否通过 freshness 门禁。

### P1：生产化 Runtime 与元数据治理

1. 身份、角色和 workspace context 贯穿 Runtime。
2. 在 executor 层强制工具权限和数据权限。
3. 增加用户、路由、资产、SQL 和结果状态的审计链。
4. 为表卡补 owner、血缘、认证状态和质量历史。
5. 支持多意图 Top-K 路由和必要的并行 fan-out。

### P2：性能和规模化

1. 高频指标增加预聚合或 CK 优先路径。
2. 路由引入 embedding 召回，但保留规则和拒绝执行门禁。
3. 增加 token、缓存命中、查询成本和端到端耗时观测。
4. 根据维护成本再评估是否引入 OpenMetadata、Cube 或其他独立服务。

## 五、明确不做的事情

- 不因 Star 数高而替换现有 PI Runtime。
- 不把向量相似度当作可直接执行的概率。
- 不让 LLM 自报置信分后直接查询。
- 不把用户一次确认自动写成 verified 资产。
- 不在没有真实负载和维护预算前引入完整元数据平台。
- 不把开源项目的能力描述成当前工程已经完成的能力。

## 六、对外表达

面试或架构评审时可使用以下表述：

> 我们没有把系统定位成一个通用 Text2SQL Demo，而是围绕业务知识、语义契约和真实数据资产建设受控分析链路。整体思路与 WrenAI 的 Context Layer、MetricFlow 的语义编译和 Vanna 的生产 Runtime 有相似之处，但针对 MaxCompute、ClickHouse 和投放 ROI 场景增加了证据分层、freshness、PII 和只读决策边界。下一阶段重点不是继续堆文档，而是把语义契约执行化、路由评测量化，并让身份权限和反馈闭环进入 Runtime。
