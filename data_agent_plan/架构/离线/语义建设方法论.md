# Data Agent 语义建设方法论

> 状态：`active_architecture`
> 建立：2026-08-12
> 适用：Data Agent 的离线语义建设、线上问题观察与运行时语义发布。
> 关系：本文件是“信任怎样生产”的方法论；现行可消费语义仍以
> `knowledge/agent_knowledge/semantic_contract/model.json` 为准，单表事实仍以 数据资产目录 为准。

## 1. 裁决

语义层不是表字段说明的汇编，也不是线上用户问题的自动摘要。它是把**已确认的业务概念**、
**可追溯的数据绑定**和**问题的受控解释方式**，编译成 Runtime 可消费合同的系统。

建设原则如下：

> 真实用户问题决定优先建设什么；权威来源决定语义是什么；门禁决定何时可以进入 Runtime。

因此，线上问题只能产生“候选需求”，不能直接成为指标定义、渠道归类、join 或默认口径。

## 2. 四类资产，各自回答不同问题

| 资产 | 回答什么 | 权威来源 | 是否可直接给 Runtime |
|---|---|---|---:|
| 数据资产目录 | 表、列、粒度、分区、PII、单表限制是什么 | DDL、引擎元数据、生产代码、已验证 probe | 是，受注册与权限控制 |
| Semantic Contract | 指标、实体、维度、跨表关系、口径选择和失败语义是什么 | 已确认 policy、数据资产目录、已验证 SQL、生产源对账 | 是，编译后消费 |
| 场景合同（Scenario Contract） | 某一类真实问题应如何理解、追问、路由和输出 | 已确认语义合同 + 真实问题簇 | 是，确认后可进入路由/评测 |
| 问题观察与候选池 | 用户现在在问什么、哪里经常失败或歧义 | 脱敏线上问题、追问、反馈、失败记录 | 否，只能做建设输入 |

不要把四类资产合成一份大文档。特别是：一个真实问题不是事实源；一次 SQL 跑通也不是指标晋升。

## 3. 语义层的最小单位：语义场景

不按“表”或“指标名”建设语义层，而按能闭环的一类用户问题建设**语义场景**。

一个场景至少要回答：

1. 用户想作出什么判断；
2. 允许哪些自然语言问法；
3. 有哪些必须澄清的歧义；
4. 使用哪个指标口径、哪些维度；
5. 数据、页面或生产代码的权威来源分别是什么；
6. 如何绑定表、字段、join、时间范围和新鲜度；
7. 证据不足、未知值或跨源冲突时如何 fail closed；
8. 什么算正确答案，以及如何回归验证。

建议以如下“场景卡”作为设计草案；只有其中的定义与绑定被确认后，才分别写入
Semantic Contract、数据资产目录、policy、TaskRoute 或评测集。

```yaml
scenario_id: ua_channel_dnu_analysis
user_goal: 按渠道解释新增设备的变化
intent_examples:
  - 最近一周各渠道 DNU 怎么变了
  - MI 里信息流新增下降了吗
required_clarifications:
  - DNU 口径：MI 注册设备(af) / 行为宽表 D0 / Activation 去重
  - 分析视角：MI 页面复现 / DA 全量渠道分析
authorities:
  metric_definition: pending_or_confirmed_authority
  channel_classification: pending_or_confirmed_authority
bindings:
  metrics: []
  dimensions: []
  tables: []
guardrails:
  - 未选 DNU 口径时必须追问
  - 未知渠道保留原始值，不自动归类
acceptance_cases: []
status: candidate | needs_authority | confirmed
```

这不是另一个运行时真相源，而是建设时用来防止“先写 SQL、后补定义”的最小设计单位。

## 4. 冷启动：从高价值场景开始，不从问题堆开始

冷启动目标不是覆盖所有表和所有问法，而是用少量场景建立完整的“理解 → 证据 → 查询 →
解释 → 验证”闭环。

### 4.1 选择首批场景

为每个候选场景按以下维度排序：

| 维度 | 需要回答的问题 |
|---|---|
| 业务价值 | 是否直接支撑日常经营、复盘或风险预警？ |
| 用户频率 | 是否持续出现而非一次性需求？ |
| 证据成熟度 | 是否已有可查表、生产实现、确认 policy 或 verified SQL？ |
| 歧义风险 | 指标或分类是否容易被错误默认？ |
| 可验证性 | 能否构造有限窗口的对账和回归问题？ |
| 复用性 | 新建的实体/维度/关系能否服务后续多个场景？ |

第一期只选 1–3 个“高价值且证据可闭环”的场景。没有权威来源的高价值问题同样要登记，
但状态应为 `needs_authority`，不能用模型推测抢跑。

### 4.2 每个首批场景的交付门槛

一个冷启动场景至少具备：

- 经过确认的业务目标、指标范围和不支持边界；
- 已注册的数据来源和字段证据；
- 明确的默认值、澄清问题与 fail-closed 行为；
- 至少一个可重跑的小窗口验证；
- 至少 5 个真实或等价的验收问法，包含正例、歧义例和拒答例；
- 可追溯版本与变更原因。

没有这些，不把“模型能够回答一次”称为语义场景已完成。

## 5. 线上问题怎样进入建设，而不污染事实

线上问题是需求雷达。每日可自动收集**脱敏后的结构化观察记录**，但不自动修改正式语义。

建议记录：

| 记录项 | 用途 | 约束 |
|---|---|---|
| `intent_cluster` | 聚类同类业务意图 | 不把原话当定义 |
| `ambiguity_type` | 指标、时间、对象、渠道、比较基线等歧义 | 用于改善澄清设计 |
| `route_outcome` | 是否路由成功、是否需要人工、是否拒答 | 用于发现路由缺口 |
| `asset_status` | 使用了 confirmed / candidate / 无资产 | 防止候选被伪装为事实 |
| `answer_outcome` | 完整、部分、拒答、数据不可用 | 用于覆盖度统计 |
| `feedback_signal` | 用户修正、追问、显式反馈 | 用于优先级，不直接改变口径 |
| `source_gap` | 缺表、缺字段、缺权威、映射未知、freshness 不足 | 转为待办或证据收集任务 |

不默认沉淀原始问题全文、用户身份、设备明细、SQL 原文、token、cookie 或敏感结果。需要保留原话时，
应按现有审计和隐私规则最小化、脱敏并设置留存期。

## 6. 更新节奏：每日观察，周期晋升，变更触发校验

语义层不应每日“重新抽取并覆盖”。不同对象有不同节奏：

| 节奏 | 做什么 | 不做什么 |
|---|---|---|
| 每日 | 收集脱敏问题信号、聚类、统计未覆盖与误解、检测 schema/freshness 异常 | 自动改指标公式、默认口径、渠道分类或 join |
| 每周 / 双周 | 评审问题簇、排序候选场景、补齐证据、编写场景卡和回归问题 | 把所有低频问题都提升为正式语义 |
| 按变更触发 | DDL/schema、生产代码、MI 接口、渠道映射、confirmed policy 变化时重新对账与回归 | 用旧快照掩盖真实变更 |
| 紧急修复 | 对已上线的错误定义、错误路由或安全边界做最小修复并回归 | 因一次异常而重写整套语义模型 |

一次正式更新至少要同时更新“定义、证据、回归、版本说明”中受影响的部分；未受影响的资产不重写。

## 7. 候选到 Runtime 的晋升链

```text
脱敏线上问题 / 业务访谈 / 既有资产
                ↓
         问题簇与场景候选
                ↓
       权威来源与数据绑定核验
          ↓                 ↓
     证据充分             缺少权威
          ↓                 ↓
  语义草案 + 回归集    needs_authority / TODO
          ↓
   人工确认 + 合同/质量门禁
          ↓
 Semantic Contract 编译、注册与发布
          ↓
 Runtime 只读消费 + 线上观测
```

每一阶段的职责如下：

| 阶段 | 可产出 | 不可产出 |
|---|---|---|
| `observed` | 问题簇、频率、失败模式 | 新的正式业务定义 |
| `candidate` | 场景卡、候选指标/映射、待验证假设 | Runtime 默认行为 |
| `needs_authority` | 明确缺什么、由谁确认 | 模型猜测的补丁 |
| `evidence_ready` | 可审计来源、有限验证、回归草案 | 自动晋升 |
| `confirmed` | 可编译合同、受控路由、回归用例 | 任意跨场景泛化 |
| `retired` | 迁移指针、停用说明 | 继续默认召回旧定义 |

## 8. 何时需要改哪些资产

不要因为一个问题就全仓更新。按变化性质处理：

| 发现的问题 | 应优先改 | 典型例子 |
|---|---|---|
| 表/字段/分区理解错误 | 数据资产目录 | 字段粒度、PII、必须日期过滤缺失 |
| 指标、实体、跨表关系或分类边界缺失 | Semantic Contract | 同一个“DNU”存在多套已确认口径 |
| 业务规则、默认解释、阈值或人工裁决 | policy / decision record | 是否默认排除预装 |
| 问题识别、澄清与资产选择错误 | TaskRoute / Question Contract | 未限定 DNU 时没有追问 |
| 已确认语义未被正确执行 | Runtime binding / executor | 选对口径但 SQL 绑定错误 |
| 缺少验证 | eval / regression | 新场景没有歧义例与拒答例 |

先判定缺口属于哪一层，再改对应资产。禁止为了“让回答更顺”把规则复制到多个层。

## 9. 质量指标：看覆盖和可信度，不看文档数量

语义建设的健康度应至少按以下维度观察：

| 指标 | 说明 |
|---|---|
| 场景覆盖率 | 高频问题簇中，能给出受证据支持答案或正确澄清的比例 |
| 歧义处理正确率 | 应追问的问题是否追问，而不是猜测默认值 |
| 权威绑定覆盖率 | 已发布场景中，指标/分类/join 是否都有来源与版本 |
| 未知值保留率 | 未映射渠道、空值、未归因值是否被错误吞并 |
| 回归稳定性 | 新增或修改场景后，既有场景是否仍通过 |
| 线上纠正率 | 用户纠正或人工回退是否集中在同一语义缺口 |
| 建设时效 | 从高频缺口发现到“确认 / 明确阻塞”的周期 |

“收录了多少问题”“写了多少 YAML”“覆盖了多少表”都只能作为辅助指标，不能代替上述质量信号。

## 10. 后续讨论和建设顺序

后续每个新话题都按下面顺序讨论，先定义再实现：

1. **场景**：用户真正想判断什么，为什么优先？
2. **歧义**：哪些词必须追问，哪些可以安全默认？
3. **权威**：每个定义、分类、时间语义分别由什么来源裁决？
4. **绑定**：表、字段、join、过滤、新鲜度和跨源边界是什么？
5. **失败语义**：未知、冲突、缺数据、未成熟时返回什么？
6. **验收**：用哪些真实问法、对账和回归证明它可用？
7. **发布与观测**：如何进入 Runtime，线上如何发现下一轮缺口？

只有前六项足够清楚，才进入 SQL、Prompt 或 Runtime 实现讨论。

## 11. 与现有工程的边界

- 本文件是方法论和路线图，不替代 `knowledge/` 下的 canonical policy 或 Semantic Contract；
- `data_agent_plan/` 不承载实时探测结果、线上原始问题或未审计业务事实；
- Runtime 不得把本轮对话、一次查询成功或线上问题自动写回正式语义；
- 有待确认的业务定义必须进入 `TODO/` 或决策流程，并以 `needs_authority` / `needs_decision`
  显式表达；
- 任何正式晋升仍遵循 数据资产目录、Semantic Contract、SQL 晋升和回归门禁。
