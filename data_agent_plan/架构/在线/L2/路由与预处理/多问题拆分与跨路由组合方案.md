# 多问题拆分与跨路由组合方案

> 状态：active_plan
> 创建：2026-07-24
> 更新：2026-07-24
> 范围：处理用户输入包含多个独立问题（拆分）或一个复杂问题需要多路由知识（组合）的架构设计。
> 边界：本文件只定义路由增强策略，不定义业务口径、不改数据资产目录内容、不涉及投放动作。
> 关联：`低置信度Fallback与路由监控方案.md`（fallback 通道）、`task_routes/INDEX.yaml`（路由入口）、`runtime/backend/app/services/knowledge.py`（路由实现）。

---

## 一、问题定义

当前路由系统是"一问一路由"模型：一个用户输入 → 一个 route → 一个 first_read → 一套上下文。但生产中存在两种需要突破此模型的输入：

### 情况 1：多问题捆绑（可拆分的独立问题）

```
用户输入："示例产品 美国 DNU 下滑怎么回事？另外帮我看下素材冷启动通过率。"

本质：两个独立问题装在一句话里
  → Q1: 示例产品 DNU → roi_or_campaign_analysis
  → Q2: 素材冷启动 → material_analysis
期望：各自路由，各自回答，最后合并输出
```

特征：
- 含分隔词（"另外""顺便""还有""第二个问题"）
- 两个子问题的答案互不依赖
- 可以并行处理

### 情况 2：复杂单问题（不可拆分，需多路由知识）

```
用户输入："示例产品 美国 DNU 下滑，是素材效果变差、Google 预算被改了、还是 DAU 留存下降？"

本质：一个归因分析问题，需要同时加载多个域的知识
  → roi_or_campaign_analysis（DNU 趋势、消耗）
  → material_analysis（素材效率指标）
  → google_ads_config_change_analysis（预算/操作变更日志）
  → product_behavior_or_experiment_analysis（留存变化）
期望：综合归因，输出一份排除法分析，不是 4 个独立回答
```

特征：
- 含归因/对比/排除信号（"是…还是""哪个因素""原因是什么"）
- 答案必须是综合结论，不能拆成独立回答
- 子域之间有逻辑关系（排除法、权重比较）

### 为什么这两种情况需要不同的架构解法

| 维度 | 情况 1（拆分） | 情况 2（组合） |
|------|-------------|-------------|
| 子问题关系 | 独立，无逻辑依赖 | 有逻辑关系（归因排除法） |
| 期望输出 | 多个独立回答合并 | 一个综合分析 |
| 路由需求 | 多次独立路由 | 主路由 + 辅助上下文 |
| Context budget | 各自独立 budget | 共享一个 budget，需分配 |
| Output guardrails | 各用各 route 的 guardrails | 以主 route 为准 |
| Objective | 各用各 route 的 objective | 以主 route 为准 |

## 二、已有基础设施

当前 runtime 中已存在的"跨 route"机制：

| 机制 | 位置 | 时机 | 能力 | 局限 |
|------|------|------|------|------|
| `conditional_next_hops` | `task_routes/<id>.yaml` | 事中（Runtime 回答过程中触发） | 在分析过程中发现需要跳到另一个 route 时，追加加载该 route 的 first_read | 顺序链式，不能事前预判；LLM 需要在回答中明确触发跳转条件 |
| `conditional_protocols` | `task_routes/<id>.yaml` | 事中（路由内子信号命中） | 同一 route 内，检测到特定关键词后额外加载策略文件 | 只能在当前 route 内扩展，不能跨到其他 route 的数据资产目录 |
| `runner_up_task_id` / `runner_up_score` | `RouteDecision` 返回值 | 路由时 | 记录次优 route 和分数 | 当前只用于调试/日志，未用于上下文组合 |

**关键洞察**：`runner_up` 信息已经存在但未被利用。这是实现"情况 2"的天然入口。

## 三、情况 1 方案对比：多问题拆分

### 方案 A：LLM 事前拆分

```
用户输入 → 启发式正则判断明确分隔词 → 拆分为 [Q1, Q2, ...] → 各自路由 → 各自回答 → 合并输出
```

| 维度 | 评价 |
|------|------|
| 正确性 | 高——LLM 理解语义，能识别隐式分隔 |
| 成本 | 每次多一次 LLM 调用（~2K input + ~200 output） |
| 延迟 | +0.5-1s |
| 可调试性 | 中——LLM 拆分结果可记录，但逻辑不透明 |
| 适用范围 | 广——能处理无明确分隔词的多问题 |

### 方案 B：Runtime 串行处理（不拆分）

```
用户输入 → 路由到 primary route → Runtime 在多轮中顺序处理每个子问题
```

| 维度 | 评价 |
|------|------|
| 正确性 | 低——第二个子问题的 route context 可能不对（沿用第一个 route 的 first_read） |
| 成本 | 零额外开发/调用成本 |
| 延迟 | 不变 |
| 可调试性 | 差——依赖 Runtime 自主判断，不确定是否会处理第二个子问题 |
| 适用范围 | 窄——只对简单追问有效，复杂多问题会丢失 |

### 方案 C：启发式正则分隔

```
用户输入 → 正则检测分隔词（"另外""顺便""第二个问题"）→ 按分隔词切分 → 各段独立路由
```

| 维度 | 评价 |
|------|------|
| 正确性 | 中——覆盖有明确分隔词的情况；无分隔词时 miss |
| 成本 | 极低——纯正则，无 LLM 调用 |
| 延迟 | 可忽略 |
| 可调试性 | 极高——正则规则明确 |
| 适用范围 | 窄——只能处理有明确分隔词的输入 |

### 方案对比总结

| | 方案 A (LLM 拆分) | 方案 B (Runtime 串行) | 方案 C (正则分隔) |
|---|---|---|---|
| 正确性 | ★★★★★ | ★★ | ★★★ |
| 成本 | ★★★ | ★★★★★ | ★★★★★ |
| 延迟 | ★★★ | ★★★★★ | ★★★★★ |
| 可调试性 | ★★★ | ★ | ★★★★★ |
| 覆盖面 | ★★★★★ | ★★ | ★★★ |

### 推荐方案：A + C 组合（正则先行，LLM 补充）

```
用户输入
  │
  v
Step 0: 正则分隔检测（零成本，高确定性）
  │
  ├── 命中分隔词 → 直接拆分，各段独立路由
  │                 不消耗 LLM 调用
  │
  └── 未命中分隔词
        │
        v
Step 1: KnowledgeRouter.route()
  │
  └── 双峰检测（primary.confidence > 0.6 且 runner_up.score > 0.5）
        │
        └── 触发 LLM 判断：
            "这个输入是多个独立问题，还是一个需要跨域分析的单问题？"
            │
            ├── "多个独立问题" → 启发式正则返回子问题列表 → 各自路由
            └── "一个跨域问题" → 走情况 2 逻辑
```

**为什么不只用 LLM？** 因为有明确分隔词的情况（"另外""顺便"）占多问题捆绑的 60-70%，用正则处理这部分可以避免大量不必要的 LLM 调用。

## 四、情况 2 方案对比：跨路由组合

### 方案 A：Primary + Secondary Read

```
路由结果：primary route (high) + runner_up route (also high)
  → 以 primary route 为主（70% budget），从 runner_up 借 top-3 first_read 文件（30% budget）
  → objective / guardrails / evidence 都以 primary 为准
  → secondary 只提供"辅助证据上下文"
```

| 维度 | 评价 |
|------|------|
| 正确性 | 高——主路由框架不变，辅助知识只是补充 |
| 成本 | 零 LLM 额外调用——只是多读几个文件 |
| 延迟 | 可忽略（多读 3 个文件的 IO） |
| 可控性 | 高——budget 硬约束，不会爆 context |
| 复杂度 | 低——复用现有 context 组装逻辑 |
| 局限 | 只能借 runner_up 一个 route；如果需要 3-4 个 route 的知识则不够 |

### 方案 B：加强 conditional_next_hops（事前触发版）

```
路由时识别"需要跨域归因"信号
  → 在路由阶段就触发 next_hop（不等 Runtime 事中发现）
  → 一次性加载 primary + hop target 的 first_read
```

| 维度 | 评价 |
|------|------|
| 正确性 | 高——利用已有的 next_hop 定义，关系明确 |
| 成本 | 零 LLM 额外调用 |
| 延迟 | 可忽略 |
| 可控性 | 高——next_hop 有 `output_boundary` |
| 复杂度 | 中——需要在 route YAML 中定义"事前触发条件" vs "事中触发条件" |
| 局限 | 需要为每对 route 显式写 next_hop 规则；组合爆炸风险 |

### 方案 C：归因分析 Meta-Route

```
新建一个专门的 "cross_domain_attribution" 路由：
  trigger: "是…还是""哪个因素""归因""排除"
  first_read: 多个域的 SOP 入口 + 数据资产目录目录
  objective: "跨域归因排除法分析"
```

| 维度 | 评价 |
|------|------|
| 正确性 | 中——一个 route 装太多知识，可能 context 不够精确 |
| 成本 | 零额外调用 |
| 延迟 | 不变 |
| 可控性 | 中——一个大 route 的 guardrails 难以精确 |
| 复杂度 | 低——只需新建一个 route 文件 |
| 局限 | 变成"万能 route"，违背"一任务一文件"原则；知识量大时 budget 不够 |

### 方案 D：LLM 编排（plan → 多步执行）

```
LLM 先输出执行计划：
  "1. 先查 DNU 趋势（roi route）
   2. 再查素材效率变化（material route）
   3. 再查 Google 操作日志（google_ads route）
   4. 综合归因"
→ 逐步执行每一步，每步加载对应 route context
→ 最后综合回答
```

| 维度 | 评价 |
|------|------|
| 正确性 | 最高——每步都有精确 context |
| 成本 | 最高——多次 LLM 调用 + 多次 SQL 执行 |
| 延迟 | 最高——串行多步 |
| 可控性 | 最低——LLM 自主决定步骤，可能发散 |
| 复杂度 | 最高——需要 plan executor、step state、中间结果传递 |
| 局限 | 过度工程化；对你的场景（用户不在意速度但在意正确性）不一定比 A 好 |

### 方案对比总结

| | 方案 A (Primary+Secondary) | 方案 B (事前 next_hop) | 方案 C (Meta-Route) | 方案 D (LLM 编排) |
|---|---|---|---|---|
| 正确性 | ★★★★ | ★★★★ | ★★★ | ★★★★★ |
| 成本 | ★★★★★ | ★★★★★ | ★★★★★ | ★★ |
| 延迟 | ★★★★★ | ★★★★★ | ★★★★★ | ★★ |
| 可控性 | ★★★★ | ★★★★ | ★★★ | ★★ |
| 工程复杂度 | ★★★★★ (低) | ★★★★ | ★★★★★ (低) | ★★ (高) |
| 扩展性 | ★★★★ | ★★★ (组合爆炸) | ★★ | ★★★★★ |
| 适合当前阶段 | ✅ | ✅ | ⚠️ | ❌ (过度工程) |

### 推荐方案：A（Primary + Secondary Read）+ 保留 B 作为精准场景的补充

理由：

1. **A 方案是 80/20 解法**——用 30% 的 budget 从 runner_up 借 3 个文件，已经能覆盖大多数"需要看一下另一个域"的场景
2. **B 方案留给已确认的高频组合**——比如 `roi_or_campaign_analysis → google_ads_config_change_analysis` 这种已有的 next_hop，加一个"事前触发条件"即可
3. **D 方案留给未来**——如果监控数据显示 A+B 覆盖不了的复杂场景 > 10%，再考虑升级为 LLM 编排

## 五、推荐方案详细设计

### 5.1 情况 1 实现：启发式拆分 + LLM 判断

#### 5.1.1 启发式分隔检测

```python
# runtime/backend/app/services/question_decompose.py（新增）

import re
from typing import Optional

# 明确的多问题分隔信号（中文）
SPLIT_PATTERNS = [
    r"(?:。|？|！)\s*(?:另外|此外|除此之外|还有|顺便|再问|第二个问题|还想)",
    r"(?:。|？|！)\s*(?:然后|接着|再帮我|再看看|还有个)",
    r"[；;]\s*(?:另外|此外|还有|顺便)",
]

# 分隔后子问题的最小长度（过短可能是误切）
MIN_SUB_QUESTION_LENGTH = 8


def heuristic_split(question: str) -> Optional[list[str]]:
    """
    用正则检测明确分隔词，拆分为子问题列表。
    返回 None 表示未检测到多问题。
    """
    for pattern in SPLIT_PATTERNS:
        match = re.search(pattern, question)
        if match:
            # 在分隔词前切分
            parts = re.split(pattern, question)
            parts = [p.strip() for p in parts if len(p.strip()) >= MIN_SUB_QUESTION_LENGTH]
            if len(parts) >= 2:
                return parts
    return None
```

#### 5.1.2 已退役的 LLM 判断（仅保留历史设计）

> 当前 Runtime 只保留 5.1.1 的 `heuristic_split`；以下 LLM split/composite 与 secondary-read 设计均已退役，不得作为当前路线图或实现依据。

```python
# 续 question_decompose.py

DECOMPOSE_PROMPT = """你是问题分类助手。判断下面的用户输入是：
A) 多个独立问题的组合（各问题互不依赖，可以分开回答）
B) 一个需要跨域分析的复杂单问题（答案必须是综合结论）

用户输入：{question}

回答格式：
- 如果是 A，回答：SPLIT|子问题1|子问题2|...
- 如果是 B，回答：COMPOSITE
不要解释。"""


async def llm_classify_and_split(question: str) -> tuple[str, list[str]]:
    """
    LLM 判断是拆分（SPLIT）还是组合（COMPOSITE）。
    返回 ("split", [Q1, Q2, ...]) 或 ("composite", [原问题])
    """
    response = await lightweight_llm_call(
        DECOMPOSE_PROMPT.format(question=question),
        max_tokens=200,
    )
    if response.startswith("SPLIT|"):
        parts = response.split("|")[1:]
        parts = [p.strip() for p in parts if len(p.strip()) >= MIN_SUB_QUESTION_LENGTH]
        if len(parts) >= 2:
            return ("split", parts)
    return ("composite", [question])
```

#### 5.1.3 拆分后的执行流

```python
# 续 question_decompose.py / 或在 knowledge.py 中调用

async def execute_multi_question(questions: list[str], router, runtime) -> str:
    """
    各子问题独立路由、独立组装上下文、独立回答，最后合并。
    """
    results = []
    for i, q in enumerate(questions, 1):
        route = router.route(q)
        context = router.build_knowledge_context_parts(q, route, ...)
        answer = await runtime.ask(q, context)
        results.append({
            "sub_question": q,
            "route": route.task_id,
            "answer": answer,
        })

    # 合并输出
    merged = f"共 {len(results)} 个问题，分别回答如下：\n\n"
    for r in results:
        merged += f"### {r['sub_question']}\n\n{r['answer']}\n\n---\n\n"
    return merged
```

#### 5.1.4 合并逻辑的注意事项

| 要求 | 处理方式 |
|------|---------|
| freshness_status | 取所有子回答中最保守的（有一个 stale 则整体标 stale） |
| threshold_status | 按子问题独立保留 |
| evidence（SQL） | 每个子回答独立保留 SQL 证据 |
| needs_decision | 任一子回答有 needs_decision 则整体保留 |
| 上下文 budget | 各子问题独立 budget，不共享 |

### 5.2 情况 2 实现：Primary + Secondary Read

#### 5.2.1 触发条件

```python
# runtime/backend/app/services/knowledge.py 新增

# 归因/对比/排除信号（触发 composition）
COMPOSITION_SIGNALS = [
    r"是.{2,20}还是",      # "是素材还是预算"
    r"原因[是在]",          # "原因是什么"
    r"归因",               # "归因分析"
    r"排除.{0,10}原因",    # "排除素材原因"
    r"哪[个些]因素",       # "哪个因素导致"
    r"分别[看查分析]",     # "分别看素材和渠道"
    r"综合[分判看]",       # "综合分析"
    r"既.{2,15}又",        # "既看消耗又看留存"
    r"多[个方]面",         # "多方面分析"
    r"从.{2,10}和.{2,10}两个",  # "从素材和预算两个角度"
]

def needs_composition(question: str, route: RouteDecision) -> bool:
    """判断是否需要从 runner_up route 借上下文。"""
    # 条件 1：runner_up 存在且分数足够高
    if not route.runner_up_task_id:
        return False
    if route.runner_up_score is None or route.runner_up_score < 0.5:
        return False

    # 条件 2：primary 和 runner_up 属于不同域
    if route.task_id == route.runner_up_task_id:
        return False

    # 条件 3：问题含归因/对比/排除信号
    return any(re.search(p, question) for p in COMPOSITION_SIGNALS)
```

#### 5.2.2 Secondary Read 的上下文组装

```python
# runtime/backend/app/services/knowledge.py 新增

# Budget 分配常量
PRIMARY_BUDGET_RATIO = 0.70    # 主路由占 70%
SECONDARY_BUDGET_RATIO = 0.30  # 辅助路由占 30%
SECONDARY_MAX_FILES = 3        # 辅助路由最多借 3 个 first_read 文件


async def build_composite_context(
    question: str,
    primary_route: RouteDecision,
    runner_up_route_id: str,
) -> dict[str, str]:
    """
    主路由 + 辅助路由的组合上下文。
    """
    total_budget = context_budget_chars(primary_route)

    # 1. Primary context（70% budget）
    primary_budget = int(total_budget * PRIMARY_BUDGET_RATIO)
    primary_parts = build_knowledge_context_parts(
        question, primary_route, budget_override=primary_budget
    )

    # 2. 加载 runner_up route 的 task detail
    runner_up_detail = load_task_route(runner_up_route_id)
    runner_up_first_read = runner_up_detail.get("first_read", [])

    # 3. 从 runner_up 的 first_read 中选 top-N 文件（按与问题的相关性排序）
    scored_files = []
    for f in runner_up_first_read[:10]:  # 只扫前 10 个
        score = score_first_read_file(question, f)
        scored_files.append((f, score))
    scored_files.sort(key=lambda x: x[1], reverse=True)
    selected_files = [f for f, _ in scored_files[:SECONDARY_MAX_FILES]]

    # 4. 读取选中文件，组装 secondary context
    secondary_budget = int(total_budget * SECONDARY_BUDGET_RATIO)
    secondary_parts = read_files_within_budget(selected_files, secondary_budget)

    # 5. 合并
    primary_parts["secondary_context"] = (
        f"## 辅助域上下文 (来自 {runner_up_route_id})\n\n"
        f"> 以下内容来自辅助路由，仅作为归因排除的参考证据。"
        f"回答框架、guardrails 和 objective 以主路由为准。\n\n"
        + secondary_parts
    )

    return primary_parts
```

#### 5.2.3 上下文预算分配

```
┌──────────────────────────────────────────────────────────┐
│  组合问题的 Context Budget 分配                            │
│                                                          │
│  总 budget = primary route 的 context_budget_chars        │
│  （默认 30000 chars，重型 live_sql 场景 120000 chars）      │
│                                                          │
│  ┌─────────────────────────────────────────────┐         │
│  │  Primary (70%)                              │         │
│  │    ├── query_guidance:     上限 15%         │         │
│  │    ├── first_read_policies: 保底 30%        │         │
```

## 七、与 conditional_next_hops 的关系

四个机制共存，覆盖不同时机：

| 机制 | 时机 | 触发方 | 加载方式 | 适用场景 |
|------|------|--------|---------|---------|
| `conditional_protocols` | 事中·路由内 | 关键词命中 | 额外策略文件 | 同 route 内子领域扩展 |
| `conditional_next_hops` | 事中·跨路由 | Runtime 分析过程中发现跳转条件成立 | 追加另一个 route 的 first_read | "ROI 分析中定位到 Google campaign → 加载操作日志" |
| **Question decomposition（新）** | 事前·路由前 | 启发式正则判断 | 拆分为多个独立请求 | 多问题捆绑 |
| **Secondary read（新）** | 事前·路由后 | 双峰 + composition 信号 | 主 route 70% + runner_up 30% | 跨域归因/排除法 |

执行顺序：

```
事前拆分 → 路由 → secondary read → Runtime 执行 → 事中 conditional_protocols / next_hops
```

**不冲突点**：

- secondary read 加载的是 runner_up 的 top-3 文件（事前决定的辅助证据）
- conditional_next_hops 是 Runtime 事中发现需要更深入某个域时追加的精确文件
- 两者可以同时生效：事前给了辅助证据，事中如果需要更深入还能跳

## 八、边界与约束

### 8.1 安全边界

| 约束 | 规则 |
|------|------|
| 拆分后子问题数量 | 最多 3 个（防止恶意/过长输入导致 N 次路由） |
| Secondary read 文件数 | 最多 3 个 first_read 文件（budget 硬约束） |
| 可借的 route 范围 | 只能借 `remote_default_task_ids` 中的 route（不借 internal_codex 路由） |
| Secondary context 中不加载 | output_guardrails, objective, completion_boundary（以 primary 为准） |
| 总 context budget | 不因 composition 而突破 primary route 定义的 budget |

### 8.2 不做的事（明确排除）

| 不做 | 原因 |
|------|------|
| 3 个以上 route 同时组合 | budget 不够分，正确性反而下降 |
| 动态 plan + 多步串行执行（方案 D） | 过度工程，当前阶段不需要 |
| 自动发现所有相关 route | 用 runner_up 即可；top-3 以下的 route 通常不相关 |
| composition 覆盖 internal_codex 路由 | 治理类路由不会出现在线上用户问题中 |

## 十、验收标准

| 验收项 | 标准 |
|---|---|
| 单路由主干不变 | 无双峰、无分隔词的普通问题走原流程，regression 17/17 全绿 |
| 拆分正确性 | 人工构造 10 个多问题捆绑 case，正则+LLM 拆分准确率 > 90% |
| 组合正确性 | 人工构造 10 个跨域归因 case，secondary read 加载的文件与人工判断一致 > 80% |
| Budget 不爆 | composition 后实际 context chars 不超过 primary route budget |
| 不误拆 | 单问题（如"示例产品 DNU 下滑是素材还是预算"）不被拆成两个独立问题 |
| 延迟 | 正则拆分 < 10ms；LLM 判断 < 2s；整体增加延迟 < 3s |
