## 三、Phase 2：定期聚合报表

### 3.1 聚合脚本

```python
# tools/scripts/route_quality_weekly_report.py（新增）

"""
从 MySQL trace 表提取过去 N 天的 route_decision_reason，
生成路由质量周报。

输出：eval/route_quality/路由质量周报_YYYYMMDD.md
"""

from collections import Counter
from datetime import datetime, timedelta

def generate_weekly_report(days: int = 7) -> dict:
    """主入口：生成周报数据"""

    traces = fetch_route_traces(days)  # 从 MySQL 读取
    total = len(traces)
    if total == 0:
        return {"error": "no_traces_in_period"}

    report = {}

    # ── 1. 总览 ──
    report["period"] = f"last_{days}_days"
    report["total_queries"] = total

    # ── 2. 置信度分布 ──
    report["confidence_distribution"] = {
        "high": count_by(traces, "confidence_level", "high"),
        "medium": count_by(traces, "confidence_level", "medium"),
        "low": count_by(traces, "confidence_level", "low"),
    }
    report["low_confidence_rate"] = report["confidence_distribution"]["low"] / total

    # ── 3. Route 热度分布 ──
    report["route_distribution"] = dict(
        Counter(t["task_id"] for t in traces).most_common()
    )

    # ── 4. 低分 case 提取 ──
    low_cases = [t for t in traces if t["confidence"] < 0.6]
    report["low_confidence_count"] = len(low_cases)

    # ── 5. 双峰 case（margin <= 3）──
    close_margin = [
        t for t in traces
        if t.get("runner_up_score") and (t["route_score"] - t["runner_up_score"]) <= 3
    ]
    report["close_margin_count"] = len(close_margin)
    report["close_margin_rate"] = len(close_margin) / total

    # ── 6. 低分 case 聚类 ──
    report["low_confidence_clusters"] = cluster_by_keywords(low_cases)

    # ── 7. Route 间混淆热力图 ──
    report["confusion_pairs"] = extract_confusion_pairs(close_margin)

    # ── 8. Action items ──
    report["action_items"] = generate_action_items(report)

    return report
```

### 3.2 聚类算法

```python
def cluster_by_keywords(cases: list[dict], jaccard_threshold: float = 0.3) -> list[dict]:
    """
    按 matched_keywords 的 Jaccard 相似度聚类。
    同一 cluster 的 case 可能需要同一个 fix。
    """
    clusters = []
    used = set()

    for i, case in enumerate(cases):
        if i in used:
            continue
        cluster = [case]
        used.add(i)
        kw_i = set(case.get("matched_keywords") or [])

        for j in range(i + 1, len(cases)):
            if j in used:
                continue
            kw_j = set(cases[j].get("matched_keywords") or [])
            union = kw_i | kw_j
            if not union:
                continue
            jaccard = len(kw_i & kw_j) / len(union)
            if jaccard > jaccard_threshold:
                cluster.append(cases[j])
                used.add(j)

        if len(cluster) >= 2:  # 至少出现 2 次才视为 pattern
            clusters.append({
                "size": len(cluster),
                "representative_keywords": sorted(kw_i),
                "primary_route": Counter(c["task_id"] for c in cluster).most_common(1)[0][0],
                "runner_up_routes": [c.get("runner_up_task_id") for c in cluster if c.get("runner_up_task_id")],
                "avg_score": sum(c["route_score"] for c in cluster) / len(cluster),
                "sample_trace_ids": [c.get("trace_id") for c in cluster[:3]],
            })

    return sorted(clusters, key=lambda x: x["size"], reverse=True)
```

### 3.3 混淆对提取

```python
def extract_confusion_pairs(close_margin_cases: list[dict]) -> list[dict]:
    """
    从双峰 case 中提取 route 间混淆对热力图。
    """
    pair_counts = Counter()
    for case in close_margin_cases:
        primary = case["task_id"]
        runner_up = case.get("runner_up_task_id")
        if runner_up:
            pair = tuple(sorted([primary, runner_up]))
            pair_counts[pair] += 1

    return [
        {"route_a": pair[0], "route_b": pair[1], "count": count}
        for pair, count in pair_counts.most_common(10)
    ]
```

## 四、Phase 3：问题诊断决策树

当周报中出现异常 case 时，用以下决策树判断修复策略：

```
异常 case
  │
  ├── A. 低置信度（confidence < 0.6）
  │     │
  │     ├── 问题确实属于某个已有 route，只是措辞没命中
  │     │     │
  │     │     └── FIX: 加 trigger_example 或 positive_signal
  │     │           验证: 新增 1 个 golden case
  │     │
  │     ├── 问题属于全新模式，18 route 都不覆盖
  │     │     │
  │     │     ├── 出现 >= 5 次/周 → FIX: 新建 route
  │     │     ├── 出现 2-4 次/周 → MONITOR: 继续观察
  │     │     └── 出现 1 次 → IGNORE: 可能是噪音
  │     │
  │     └── 问题属于产品边界外（竞品/非我方数据）
  │           │
  │           └── LABEL: out-of-scope，由 fallback 兜底返回
  │
  ├── B. 双峰（margin ≤ 3，两个 route 分数接近）
  │     │
  │     ├── 问题本质只属于一个 route
  │     │     │
  │     │     └── FIX: 加 negative_signal 到不该命中的 route
  │     │           或加 _looks_like_* booster 拉开差距
  │     │           验证: 新增 1 个 hard-negative golden case
  │     │
  │     └── 问题确实跨域（需要两个 route 的知识）
  │           │
  │           └── FIX: 参考「多问题拆分与跨路由组合方案.md」
  │                 Secondary Read 或 composition 机制
  │
  └── C. 路由正确但答案错误（answer quality 反向关联）
        │
        ├── 答错原因是知识缺口（数据资产目录/SOP/verified_sql 不够）
        │     │
        │     └── FIX: 补知识（不改路由）
        │           → 补数据资产目录 字段 / 加 verified_sql / 更新 SOP
        │
        ├── 答错原因是 SQL 错误（选错表/字段/条件）
        │     │
        │     └── FIX: 加 known_pitfall 或 query_rules
        │           → 更新数据资产目录 / 加 output_guardrail
        │
        └── 答错原因是 freshness（数据过期）
              │
              └── NOT A FIX: 是数据源 SLA 问题
                    → 记录 freshness blocker，不改路由或知识
```

## 六、Phase 5：Answer Quality 反向关联

### 6.1 问题定义

路由质量监控只能发现"路由错了"的问题。但还有一类更隐蔽的问题：

```
路由对了，但答案错了
  → 路由系统无责
  → 原因在知识层或执行层
  → 如果不关联，这类问题永远不会被路由监控捕获
```

### 6.2 数据源

当前 trace 中还有：
- `answer_quality_feedback`（如果有用户反馈按钮）
- `query_records`（SQL 执行结果）
- `stop_reason`（Runtime 结束原因：success / tool_failure / timeout）

### 6.3 反向关联逻辑

```python
def classify_bad_answer(trace:<已脱敏> -> str:
    """
    对"路由正确但答案可能有问题"的 case 做原因分类。
    """
    # 信号 1: 用户显式负反馈
    if trace.get("user_feedback") == "unsatisfied":
        return "user_negative_feedback"

    # 信号 2: Runtime 执行失败
    if trace.get("stop_reason") in ("tool_failure", "timeout", "no_progress"):
        return "execution_failure"

    # 信号 3: SQL 返回 0 行（可能选错表/条件）
    if trace.get("query_records"):
        for qr in trace["query_records"]:
            if qr.get("row_count") == 0 and qr.get("status") == "success":
                return "zero_rows_possible_wrong_filter"

    # 信号 4: 同一问题模式有人满意有人不满意（跨用户不一致）
    # 需要聚合时检测，不在单 trace 内判断

    return "unknown"
```

### 6.5 与路由缺口的区分

| 现象 | 诊断 | 修复方向 |
|------|------|---------|
| 路由错了 + 答案错了 | 路由缺口 | 修路由（Phase 4） |
| 路由对了 + 答案对了 | 正常 | 无需修复 |
| 路由对了 + 答案错了 | 知识/执行缺口 | 补知识/修 SQL/加 guardrail |
| 路由错了 + 答案对了 | 偶然正确（运气） | 仍需修路由（下次可能不 lucky） |

## 九、验收标准

| 验收项 | 标准 |
|---|---|
| 周报可自动生成 | `route_quality_weekly_report.py --days 7` 输出完整 Markdown |

| 不增加线上延迟 | 全部是离线聚合，不在请求路径中 |
