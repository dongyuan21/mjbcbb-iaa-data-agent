# L5 执行授权与查询安全校验说明

> 状态：`active_architecture`
>
> 适用范围：Runtime 通过 MC / CK 执行只读 SQL 的统一 L5 边界。
>
> 代码流程图：[`图/L5执行授权与查询安全流程.excalidraw`](图/L5执行授权与查询安全流程.excalidraw)
>
> 本文解释“为什么有这么多检查”，不是新增安全规则。当前实际行为以源码、测试和运行证据为准。

## 一、先记住核心结论

L5 不是检查一件事，而是在确认三个不同问题：

```text
1. 这次调用是不是合法的 Runtime 查询调用？
2. 这条 SQL 是否符合只读、安全和当前表合同？
3. 查询结果是否可以安全返回并作为本轮证据保存？
```

统一入口是：

[`runtime/backend/app/services/runtime_tool_registry.py:805`](../../../runtime/backend/app/services/runtime_tool_registry.py:805)

```python
async def authorize_and_execute(...)
```

它同时承接两类来源：

- `tool_loop`：模型通过 `query_maxcompute` / `query_clickhouse` 发起的查询；
- `bootstrap`：Runtime 的 verified SQL 或其他受控启动路径发起的查询。

两条路径必须经过同一个 L5 授权入口，避免 bootstrap 因为“SQL 已 verified”而绕开当前表卡、AST、PII 和只读检查。

## 二、整体流程

```text
调用方
  ↓
authorize_and_execute
  ↓
调用来源、engine、tool、timeout、Runtime 上下文检查
  ↓
只读预检查
  ↓
SQL AST / 数据资产目录 policy
  ↓
物理表提取 + 当前 DataContractBinding 校验
  ↓
PII 输出检查
  ↓
生成 allow contract_binding
  ↓
MC / CK executor
  ↓
结果行数、结果大小和证据元数据检查
  ↓
返回 ToolResult
```

[`图/L5执行授权与查询安全流程.excalidraw`](图/L5执行授权与查询安全流程.excalidraw)

## 三、逐步校验说明

### 0. 统一入口：禁止调用方自行执行

**代码：** `runtime_tool_registry.py:805` 的 `authorize_and_execute`。

**做什么：** 所有自由 SQL 查询，无论来自 model tool loop 还是 bootstrap，都先进入同一函数。

**预防什么：**

- 某条调用路径只做了 verified SQL 检查，却没有做当前表合同检查；
- 某个特殊工具绕过通用 SQL Guard；
- tool loop 和 bootstrap 出现两套不一致的授权语义。

**为什么不是重复设计：** 这是 L5 的单一权力边界。后面的检查可以分层，但不能让调用方决定是否跳过入口。

---

### 1. 校验 `source`：查询来自哪条 Runtime 路径

**代码：** `runtime_tool_registry.py:821`。

允许值只有：

- `tool_loop`
- `bootstrap`

**预防什么：** 未登记的内部调用来源伪装成合法查询，导致执行证据无法解释，也无法区分模型工具调用和服务端 bootstrap。

**失败结果：** `invalid_execution_source`，直接 deny。

**注意：** `source` 只是执行来源标识，不是授权本身。即便来源是 `bootstrap`，仍然要过后续完整 L5 检查。

---

### 2. 校验 `engine` 与 `tool` 是否匹配

**代码：** `runtime_tool_registry.py:833`。

当前主要映射：

| engine | 允许的 tool |
|---|---|
| `maxcompute` | `query_maxcompute` |
| `clickhouse` | `query_clickhouse` 及受控 MI CK 工具 |

**预防什么：**

- 把 MaxCompute SQL 送到 ClickHouse executor；
- 把 ClickHouse SQL 送到 MaxCompute executor；
- 通过伪造 tool 名绕过某个引擎的安全边界；
- 将一个只应生成受控 SQL 的 adapter 当成自由 SQL 工具使用。

**失败结果：** `invalid_query_engine`，直接 deny。

这一步只确认“调用组合合法”，不判断 SQL 内容是否安全。

---

### 3. 校验 `timeout`

**代码：** `runtime_tool_registry.py:861`。

**做什么：** 如果传入 timeout，必须是正整数。

**预防什么：**

- 非法 timeout 导致 executor 行为不确定；
- `0`、负数或布尔值混入执行参数；
- 调用方借 timeout 参数制造无限等待或绕过运行时预算。

**失败结果：** `invalid_query_timeout`，直接 deny。

这不是 SQL 语义检查，而是执行资源参数检查。

---

### 4. 检查 Runtime 上下文是否已经进入授权失败状态

**代码：** `runtime_tool_registry.py:876`。

`context.authorization_error_code` 如果已存在，说明前置 bootstrap、Registry 或 ContractView 准备已经失败。

**预防什么：**

- 前面已经确认“当前没有可用授权上下文”，后面却继续尝试执行；
- 通过重新提交相同 SQL 把前置授权失败隐藏掉；
- 把 Registry 不可用、DataContractView 缺失等问题误当成普通 SQL 错误。

**失败结果：** 返回已有的 typed authorization error，不执行 executor。

这是 fail-closed 的“状态继承”检查。

---

### 5. 只读 SQL 预检查

**代码：** `runtime_tool_registry.py:894` 调用 `app/services/executors.py` 的 `ensure_read_only`。

**做什么：** 先做轻量、早失败的检查：

- SQL 是否以允许的只读形式开始；
- 是否包含明显的写操作关键词；
- 是否为单条语句；
- 是否能被基础 SQL parser 解析；
- 是否包含明显不允许的 SELECT modifier 或脚本执行结构。

**预防什么：**

- `INSERT`、`UPDATE`、`DELETE`、`DROP` 等写操作；
- 多语句注入；
- 脚本/TRANSFORM 等超出只读分析边界的执行；
- 在进入较重 AST / 合同校验前浪费资源。

**失败结果：** 归为 `invalid_sql` 或对应的只读拒绝，不执行查询。

**为什么后面还要再做 AST 检查：**

这一步是早期 preflight，不是完整授权。它不负责证明物理表、`must_filter`、扫描范围和当前合同绑定；这些由下一步完成。

---

### 6. SQL AST 与 数据资产目录 policy 检查

**代码入口：**

- `runtime_tool_registry.py:895` 的 `_model_sql_guard`；
- `runtime/tools/data_query.py:921` 的 `guard_model_sql`；
- 更底层由 `_guard_query` / `_ast_guard` 执行 SQL policy。

**做什么：** 将 SQL 解析成 AST，并检查包括：

- SQL 语法和表达式是否支持；
- 物理表是否可识别；
- 是否存在未知表或不允许的结构；
- 是否满足 数据资产目录 中的分区 / `must_filter` 规则；
- 是否超过表级扫描限制；
- 是否满足聚合-only、detail 输出等约束；
- 是否需要对 SQL 做受控规范化或 probe 归一化。

**预防什么：**

- 只读形式下仍然访问未知表；
- 省略必要分区过滤，造成全表扫描；
- 用 SQL 结构绕过表卡限制；
- 通过 wildcard、动态列或不安全表达式输出不受控明细；
- 把“SQL 能解析”误认为“SQL 被授权”。

**失败结果：** 返回具体 policy error，例如 `unknown_table_policy`、扫描限制错误或不支持表达式错误。

**关键边界：** `guard_model_sql` 会返回 SQL 实际引用的 `physical_tables`，但它本身不持有 Runtime 本轮状态，也不单独授予执行权。

---

### 7. 校验 Registry revision 和 DataContractBinding 是否仍然当前

**代码：** `runtime_tool_registry.py:610–670` 的 `_model_sql_guard`。

这里是 L5 最关键的“当前性”检查。

#### 7.1 清理旧 Registry binding

如果本轮绑定的 `registry_revision` 与当前 Registry revision 不一致，返回：

```text
stale_data_contract_binding
```

**预防：** 等待、恢复或跨 worker 执行时，继续借用旧表卡的授权结果。

#### 7.2 必须有成功读取产生的 DataContract evidence

如果没有 `context.data_contract_bindings`，返回：

```text
missing_data_contract_evidence
```

**预防：**

- 只凭模型提供的 asset ID 执行；
- 只凭 catalog 搜索命中执行；
- 只凭 route 或 verified SQL 的元数据执行；
- 把“看见过一个表名”误当成“当前表合同已读取”。

#### 7.3 SQL 每一张物理表都必须匹配 binding

对 AST 提取出的每个物理表调用 `_binding_for_table`。匹配失败返回：

```text
table_not_bound_to_evidence
```

**预防：**

- SQL 偷换成未读取的表；
- 查询跨 engine 借用 binding；
- 多个 binding 模糊覆盖同一张表；
- 语义合同读到了，但真实 SQL 用的是另一张物理表。

#### 7.4 所有物理表必须来自同一个 Registry revision

如果不同表绑定了不同 revision，返回：

```text
registry_revision_conflict
```

**预防：** 一条跨表 SQL 混用不同版本的表合同，导致字段、过滤和状态判断不一致。

---

### 8. DataContractBinding 从哪里产生

**代码：** `runtime_tool_registry.py:1043`、`1065`。

只有一次成功的：

```text
read_data_contract_view
```

同时具备完整的 FQN、engine、contract revision、Registry revision 和 read receipt，才会注册 `DataContractBinding`。

以下内容都不会产生 SQL 授权 binding：

- `search_catalog` 搜索结果；
- `read_policy`；
- `retrieve_semantic_contract`；
- `retrieve_verified_sql`；
- 模型自己提交的 asset ID；
- route 的 `first_read` 或 `allowed_assets`。

**预防什么：** 把“知识发现”和“执行授权”混在一起。

这是 L3 可读面进入 L5 可执行面的唯一关键桥梁。

---

### 9. PII / detail output 检查

**代码：** `runtime_tool_registry.py:909` 的 `check_pii_guardrail`；底层 executor 也保留兜底检查。

**做什么：** 检查投影中是否直接输出 PII、聚合-only 字段或动态 wildcard 投影。

**预防什么：**

- 输出用户级标识、设备级标识或其他敏感字段；
- 使用 `*`、`table.*` 或动态列扩展绕过字段级限制；
- 把可以用于聚合的字段直接作为明细返回。

**失败结果：** 例如 `pii_blocked`、`dynamic_projection_blocked`。

**为什么看起来像重复检查：** AST policy 已经覆盖一部分字段策略，入口处再次调用 PII guard 是执行前的显式兜底；executor 层还有一层是为了防止其他路径直接调用 executor 时失去保护。

这属于“保护重复”，不是三套不同业务口径。未来可以收敛实现，但不能在没有调用方盘点和回归证明前直接删除。

---

### 10. 生成 allow contract binding

**代码：** `runtime_tool_registry.py:921` 的 `_allow_contract_binding`。

**做什么：** 将本次 SQL 实际匹配到的 asset、FQN、engine、contract revision、Registry revision 和 read receipt 组成服务端 allow receipt。

**预防什么：**

- 之后的 trace 或 answer 把模型参数当成授权证据；
- 证据链无法说明本次 SQL 使用了哪一版表合同；
- SQL 与 evidence asset 的映射不稳定。

**重要结果：** 后续 `evidence_asset_ids` 只能从这个 allow receipt 投影，不能由模型直接提交。

---

### 11. 调用 MC / CK executor

**代码：** `runtime_tool_registry.py:946`。

只有前面所有授权检查通过，才选择：

- `run_maxcompute`；或
- `run_clickhouse`。

**预防什么：** 未通过 L5 的 SQL 到达真实数据库。

executor 不是主要授权者，但会保留最小的只读、PII、引擎和资源兜底，防止未来出现绕过 `authorize_and_execute` 的调用路径。

---

### 12. 结果行数和结果大小限制

**代码：** `runtime_tool_registry.py:952`、`965`。

**做什么：**

- 限制返回给模型的行数；
- 限制序列化 payload 的大小。

**预防什么：**

- 大量明细冲击模型上下文；
- 单次查询结果导致 Runtime 内存或网络压力；
- 通过合法 SQL 读取过大的结果集。

**失败结果：** `tool_result_row_limit_exceeded` 或 `tool_result_too_large`。

注意：查询已经执行并返回了结果后才做的结果大小检查，不能替代 SQL 扫描限制；它保护的是“返回面”，不是“数据库扫描面”。

## 四、这些检查是不是过度设计

不能只按 `if` 的数量判断。建议分成两组：

### 必须保留的安全职责

| 职责 | 不能省略的原因 |
|---|---|
| 单一 L5 入口 | 防止调用路径绕过授权 |
| engine/tool/source 校验 | 防止错引擎和伪造来源 |
| 只读检查 | 防止写操作和多语句 |
| AST + physical table policy | 防止未知表、危险表达式和扫描越界 |
| 当前 DataContractBinding | 防止模型参数和旧合同直接授权 |
| PII / detail guard | 防止敏感明细输出 |
| 结果大小限制 | 防止返回面资源失控 |

### 当前实现中可以继续评估的重复

| 可能重复 | 当前理由 | 后续可做什么 |
|---|---|---|
| 入口 `ensure_read_only` 与 AST read-only policy | 一个早失败，一个是完整 policy | 明确 canonical owner，保留最小 preflight |
| 入口 PII 与 executor PII | 一个保护统一入口，一个保护底层旁路 | 盘点所有 executor caller 后再收敛 |
| tool loop 与 bootstrap 共用检查 | 两条来源都必须安全 | 保留共用入口，不复制规则 |

因此当前结论是：

> **架构意图是合理的纵深防御；实现上存在可收敛的重复，但还不能因为“看起来多”就删检查。**

真正的治理目标不是让检查数量最少，而是让每个检查都有：

1. 唯一责任；
2. 明确输入；
3. 明确拒绝原因；
4. 可追溯测试；
5. 不与其他检查争夺同一份事实。

## 六、与 L3 / L5 / L6 的关系

```text
L6：表卡和语义合同定义“约束是什么”
  ↓
L3：Runtime 受控读取 DataContractView，形成可读证据
  ↓
L5：authorize_and_execute 将当前 SQL 与 binding 对齐，并决定能否执行
```

因此：

- 表卡的 `must_filter` 是 L6 内容；
- `read_data_contract_view` 是 L3 到 L5 的证据入口；
- `_model_sql_guard` 是把 SQL 物理表和本轮表卡绑定起来的 L5 检查；
- `authorize_and_execute` 是 L5 的统一执行闸门；
- executor 是执行实现和最后一道安全兜底，不应成为业务授权真相源。
