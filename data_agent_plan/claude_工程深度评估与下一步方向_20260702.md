## 1. 总体评价（一句话 + 展开）

**一句话：这是一个"把地基做硬、方向正确、证据纪律极其诚实"的成熟工程；底座（数据资产 / 语义契约 / 门禁回归 / 路由控制面）已达生产级 4–5 档，但价值链最上层的一环——自研 Runtime 的"自然语言→带证据的稳定答案"——尚未跨过验收线，整链因此还差一档才闭环。**

展开：

- **自底向上路线被真实、按序、可复现地执行**，不是 PPT：数据资产 → 机器可读语义契约 → 门禁/回归 → 一任务一文件路由控制面 → 自研 PI+FastAPI+React Runtime，逐层推进未跳级。Phase 6 触发条件（≥10 verified SQL / 3 SOP / 1 闭环 case + 全门禁通过）已被现实大幅超额满足（≈28 / 24 / 12）后才启动 Runtime，节奏与规划完全对齐。
- **最难得的是证据纪律与诚实**：`verified/confirmed` 才当默认事实；L3 verified 仅 2/122 张也不注水（明确声明 `complete≠verified`）；join 无证据写 TODO 而非编造（31/122）；freshness 一律标 `snapshot_only`；只读预警的产品边界被写进治理本体（`AGENT_AUTONOMY.md §6`）和路由 `not_a_gap`。
- **偏差方向健康**：几乎所有文档都是"落后 / 低估"现实，而非"夸大"能力——没有发现任何"声称已完成但实为空壳"的过度声明。这在自建工程里非常罕见，说明团队更倾向于低报。
- **真正短板集中在两点**：①（关键路径）Runtime 端到端答案正确性不稳定；②（次要）自动化强制力——门禁与自我迭代真实有效，但靠约定/手动/`--mode verify` 触发，**无 CI / pre-commit / scheduler**，破坏门禁的提交不会被机器拦；叠加自报快照过期漂移（README 停 06-18、`runtime/README` 状态行仍写 `phase0_scaffold`、语义覆盖率算法自相矛盾）。

## 3. 关键路径（唯一瓶颈）

> **Runtime 端到端答案正确性 = 复杂多步分析题的 Text2SQL 生成 + 结论合成。**

资产/语义/门禁/路由五层全部 4–5 档且（快照口径）回归全绿，价值链的底座已闭环；但最上层的 PI replay 10 题回归集**从未两轮连续全绿**，实跑多为单题且 `fail/fail/pass` 抖动：

- 典型证据（`eval/PI调用日志复核_20260630_{deploy,rerun,deploy2}`）：同一题 `PI_D30_ARPU_TOP20` 三跑 = fail / fail / pass。0630 失败题**路由正确、preflight 通过、16 次工具执行成功**，却有 5/16 条 `query_records` 失败，最终 `final_answer_failed + intermediate_sql_failed`。
- 失败根因**高度集中在 LLM 即兴写 SQL**：嵌套聚合塞进 `WHERE`、对无 `dt` 字段的 CK 视图 `SELECT max(dt)`、`ck_schema_mismatch`，以及 SSE 答案中途截断。
- `eval/PI调用日志复核_20260702`：当日 35 条 query_records 挂 5 条、2 页面失败 2 内部失败。

**为什么它是唯一关键路径**：这一环卡住，只读 POC 就无法向 DA/UA 交付可信答案，则下面五层做得再硬价值也释放不出来。其余所有方向，要么是这条路径的**根因**（补 verified SQL / 确定性护栏），要么是**不阻塞它的打磨项**（快照刷新、CI 强制、canonical 收敛）。
