# bugfix_doc

工程级"问题 → 修复 → 验证"的 bugfix 记录区（区别于 `TODO/` 的近期待办、`da_assets/decision_cases/` 的投放决策复盘）。

本目录的文档是给**后续维护者**看的，不是 session 流水账。写的时候遵循下面的规范。

## 命名约定

```text
YYYYMMDD_<主题>.md      # 例：20260615_ai_ck_结构治理问题.md
```

- 日期用问题记录日，不是修复日。
- 主题用简短中文，点明问题对象与性质，不写方案。

## 写作规范

### 必含（每篇都要有）

按以下顺序组织，每节用 `##` 标题：

1. **问题**：问题是什么、证据是什么（扫描数据 / 报错 / 实测结论）、影响范围。编号 + 级别（P0/P1/P2）+ 状态。
2. **解决方案**：做了什么、为什么这么做。方案要讲清楚设计决策，不只列做了什么。
3. **验收**：跑了什么校验、结果是什么（脚本名 + 通过/失败 + 关键数值）。
4. **遗留观察项**：未解决的、待 DA/owner 拍板的、后续话题。没有就写"无"。
5. **方法论沉淀**：供后续参考的原则（1-5 条）。这是 bugfix 文档的核心价值——让同类问题不再重犯。

### 禁含（写了就要删）

| 禁含内容 | 原因 |
|---|---|
| 基础设施地址（IP、`//203`、集群名、`aliyunDB`/`ckDB` 等） | 泄露内部拓扑，且会过时 |
| 凭证（AK/SK、密码、token、cookie、SSO ticket） | 安全红线（`AGENTS.md` Rule 6） |
| session 流水账（"经用户同意"、"session 收尾补"、"用户进内网后"、"本轮剩余项"） | 对后续读者无价值，且让文档膨胀 |
| 执行过程流水账（"第一版错了又重写"、"先做了 P0 再做 P1"、"用户拍板 XXX"） | 只留结论，不留过程 |
| 第三方工具点名（JoyDataAgent/Datus/Cursor 等） | 脱敏，且与问题无关 |
| 逐文件落地清单（"新增 A.py、改了 B.yaml、补了 C.md"） | 看 git diff 即可，不必抄进文档 |
| 过时的"待拍板"标注 | 已闭环就标已闭环，别留"待拍板" |

### 格式要求

- **长度**：目标 ≤ 80 行。超过 100 行说明在堆流水账，需要精简。
- **语言**：中文简体为主，英文术语放括号内（如"门禁（gate）"、"数据新鲜度（freshness）"）。
- **代码**：只保留对理解问题/方案必要的 SQL 或代码片段，不整段贴脚本输出。
- **表格**：用表格收口扫描数据、对比、验收结果，不用大段文字描述。
- **引用**：引用其他文件用相对路径（如 `tools/scripts/stamp_ai_hive_pii.py`），不写绝对路径。

### 标题与状态

- 文档头用 `>` blockquote 标注：记录日期、范围、状态（已闭环/进行中/已归档）。
- 已闭环的文档在状态行写"已闭环"，正文保留方法论价值，session 细节精简掉。
- 不新增"拍板结论"、"整改执行结果"、"落地清单"这类 session 节；它们的结论合并进"解决方案"和"方法论沉淀"。
