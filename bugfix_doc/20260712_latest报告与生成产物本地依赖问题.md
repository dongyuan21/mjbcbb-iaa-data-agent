# 20260712 latest 报告与生成产物本地依赖问题

> 记录日期：2026-07-12
> 范围：回归/复核/评估脚本的 `*_latest.*` 产物本地依赖
> 级别：P1 / 工程可复现性问题
> 状态：已定位原因，待后续按需治理

## 一、问题

当前工作区里回归、复核或评估看起来能通过，但把仓库复制到干净副本后部分流程会失败。

`*_latest.*` 文件（如 `eval/xxx_latest.md` / `.json` / `.xlsx`）是评估、回归、复核脚本跑完后生成的"最新结果文件"，更像运行记录和结果缓存，不是业务源码。`.gitignore` 有意排除了 `eval/**/*.md`、`eval/**/*.json`、`eval/**/*.csv`、`eval/**/*.xlsx`、`eval/PI调用日志复核_*/`、`eval/redline_review/`、`outputs/`、`raw_exports/` 等本地生成物。

根因不是"代码逻辑坏了"，也不是"`.gitignore` 有错"，而是**有些流程把"结果文件存在"当成了默认前提**：代码或脚本没做到"先从原始输入重建结果""缺少 latest 文件时自动重新生成"或"明确报错提示需要先刷新报告"。于是本机有 latest 文件 → 下游顺利；干净副本没有 → 卡住或结果不一致。

证据：`eval/agent_regression/regression_cases.yaml`、`task_routes/redline_bidaily_review.yaml`、`tools/scripts/build_pi_failure_remediation.py` 等多处直接引用 `*_latest.*` 路径。

## 二、影响范围

- 评估报告、回归报告、复核快照、部分 latest 导出件。
- 依赖本地生成物作为前置输入的验证链路。
- 干净检出环境、CI 或新机器复现。
- 任何把 latest 当成"固定存在文件"的脚本或路由。

## 三、解决方案（建议，按需治理）

| 治理方式 | 适用场景 | 重点 |
|---|---|---|
| 保持忽略，补重建脚本 | 产物大、经常变、没必要入库 | 让干净检出也能一键生成 |
| 关键报告纳入版本控制 | 这份结果本身就是知识资产 | 明确哪些文件必须提交、谁负责更新 |
| 改造下游流程不依赖文件存在 | 文件只是临时缓存 | 脚本先检查，不存在就自动生成或明确报错 |

具体建议：

1. 把关键回归链路改成"脚本可重建输入"，不依赖现成 latest 文件。
2. 需要长期保留的结论另存为可追踪文档，放入 `bugfix_doc/`、`da_assets/` 或对应知识目录。
3. 对依赖本地生成物的流程补一条干净检出验证，确认缺哪些前置文件。
4. 给每个 latest 产物补明确的生成入口和依赖说明。

## 四、验收

待治理后验收：干净检出环境下，回归/复核/评估链路能一键重建前置产物或明确报错，不出现"本机能跑、干净副本失败"。

## 五、遗留观察项

无。本问题为工程可复现性方向记录，按需排期治理。

## 六、方法论沉淀

1. **`.gitignore` 排除生成物是有意选择，但必须配套可重建机制**：没有配套重建，干净检出就会少关键输入。
2. **下游流程不能把"文件存在"当默认前提**：脚本要么先重建、要么自动生成、要么明确报错，不能静默依赖本地缓存。
3. **结果文件和生成脚本要有明确版本关系**：干净副本需要知道该用哪次结果、怎么生成，否则复现不可控。
