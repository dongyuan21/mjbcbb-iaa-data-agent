# <提交标识> 知识层收敛与语义契约归并记录

> 记录日期：2026-06-20
> 范围：`数据资产目录/`、`数据资产目录/`、`knowledge/` 与原 `semantic_model/` 的目录边界、召回边界和维护归属
> 状态：已闭环。原顶层 `semantic_model/` 已归并为 `knowledge/agent_knowledge/semantic_contract/`。

## 一、问题

`数据资产目录` / `数据资产目录` 完成三层划分后，顶层 `semantic_model/` 继续独立存在产生三个问题：

1. **目录语义重复**：`knowledge/` 已是业务知识根（政策、报告知识、召回边界），`semantic_model/` 也是 Agent 跨表语义知识根。两个顶层都像"知识根"，新人和 Agent 难判断先读谁。
2. **同一事实可能双写**：跨表指标、治理状态、诊断规则既可能写进 `knowledge/policies`，也可能写进 `semantic_model/metrics.yaml` / `governance.yaml`，业务规则更新时两处易不一致。
3. **Agent 上下文膨胀**：默认 bootstrap 同时读 `knowledge` 与 `semantic_model`，把政策散文、语义 YAML、编译模型、历史审计材料混到同一层。

这不是命名洁癖，而是后续补表、SQL 规则、语义口径时的归属问题——归属不清，知识越补越像平铺文件堆。

## 二、为什么没把 semantic_model 融进 数据资产目录 / 数据资产目录

**不能按物理库归属跨表语义**：

| 资产 | 正确职责 | 不适合承接跨表语义的原因 |
|---|---|---|
| `数据资产目录/` | MaxCompute 单表数据资产目录、口径决策、PII、分区、join 证据 | 只代表 MC 侧事实源；塞跨源 ROI 语义会让数据资产目录变业务百科 |
| `数据资产目录/` | ClickHouse / MI 数据资产目录、页面字段、CK 指标语义、样例验证 | 只代表 CK/MI 查询层；正式事实和历史归因不应被 CK 目录吸收 |
| `semantic_contract` | 跨表实体、指标、维度、join、治理状态、诊断规则的机器契约 | 消费 `数据资产目录`/`数据资产目录`/`policies`，不拥有物理表 |

`数据资产目录` 和 `数据资产目录` 是"表怎么查、字段怎么用"的事实层；`semantic_contract` 是"多个事实层怎样组成业务问题"的合约层。把合约塞回任一物理表目录，都会把跨源问题变成单源偏见。

## 三、解决方案：并入 knowledge

保留语义层的机器结构，但纳入 `knowledge` 的三层治理：

| 原职责 | 新位置 | 召回边界 |
|---|---|---|
| Agent 运行时语义模型 | `knowledge/agent_knowledge/semantic_contract/model.json` | 默认入口 |
| 源 YAML | `knowledge/agent_knowledge/semantic_contract/*.yaml` | 维护/排错时读取，不默认全量塞上下文 |
| 编译与 SQL composer 回归 | `knowledge/engineering_artifacts/semantic_contract/` | 工程维护，不作业务事实 |
| 未晋升语义候选 | `knowledge/audit_archive/semantic_contract/` | 审计线索，不默认召回 |

`knowledge` 成为唯一的业务/语义知识根；`semantic_contract` 是其中的机器可读契约子层，而不是另一个知识根。

## 四、最终归属规则

后续补材料按下面规则走（详见 `knowledge/agent_knowledge/governance/知识库三层结构规范.md`）：

| 新增内容 | 归属 |
|---|---|
| MaxCompute / Hive 表、字段、分区、PII、must_filter、单表 example SQL | `数据资产目录/agent_knowledge/tables/` |
| CK / MI 表、字段画像、页面字段、CK 样例验证、MI 页面能力 | `数据资产目录/agent_knowledge/` |
| CK / MI 专属指标解释（分析平台 页面字段、蓝底预估、页面筛选器） | `数据资产目录/agent_knowledge/metrics/` |
| 跨表实体、指标、维度、join、治理状态、异常诊断 | `knowledge/agent_knowledge/semantic_contract/` |
| SQL 写作协议、业务分析协议、投放治理政策、默认召回边界 | `knowledge/agent_knowledge/policies/` |
| 历史报告抽出的阈值、经验、试运行规则（必须带周期和适用边界） | `knowledge/agent_knowledge/report_knowledge/` |
| 可复用且已验证 SQL | `da_assets/verified_sql/` |
| 候选 SQL | `da_assets/candidate_sql/` |

关键原则：

1. 数据资产目录不写成业务百科；只保留单表事实、过滤、PII、join 证据和安全示例。
2. 政策不复制进语义契约；语义契约引用政策结论或状态，不搬运整段政策正文。
3. `model.json` 是跨表语义运行时入口；源 YAML 是维护材料，不默认整包召回。
4. 未经验证的候选语义进入 audit / TODO，不进入默认 `model.json`。

## 六、遗留观察项

1. 新增 Hive / CK 表时，数据资产目录准入模板需持续提醒"跨表指标不要写进数据资产目录正文"，否则语义会慢慢回流。
2. `数据资产目录/agent_knowledge/metrics/` 与 `semantic_contract/metrics.yaml` 有天然边界：前者解释 MI/CK 页面与指标，后者定义可组合的跨表机器指标，后续维护应避免互相复制。
3. `knowledge/agent_knowledge/report_knowledge/` 的历史阈值如被纳入当前判断，必须显式晋升为 policy 或 semantic_contract 状态，不能靠历史报告默认生效。

## 七、方法论沉淀

1. **跨表语义不按物理库归属**：合约层消费事实层但不拥有物理表，把合约塞回任一物理表目录会把跨源问题变成单源偏见。
2. **目录语义不能重复**：两个顶层都像"知识根"时，新人和 Agent 都难判断先读谁，必须收敛成单一知识根。
3. **三层治理要单源化**：三层定义只在一个 canonical 文件写，各库 README 指向它，避免三处复制漂移。
