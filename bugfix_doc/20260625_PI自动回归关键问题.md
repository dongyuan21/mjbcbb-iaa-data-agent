## 继续验证补充

继续执行到验证完毕后，又暴露并修复了 4 类问题：

1. MaxCompute 聚合 smoke SQL 不稳定：
   - 现象：PI 生成 `SELECT dt, COUNT(1) ... LIMIT 1`，未写 `GROUP BY dt`，MC 报 `column ... dt should appear in GROUP BY key`。
   - 修复：`runtime/tools/data_query.py` 对窄范围 partition count smoke 自动补 `GROUP BY`；prompt 同步要求维度列 + 聚合必须 group by。
   - 提交：`6964c29 fix(runtime): normalize MC aggregate smoke queries`

2. MaxCompute freshness probe 全分区扫描：
   - 现象：PI 生成 `SELECT MAX(dt), MAX(SUBSTR(active_time_utc8,...)) ...`，没有 `dt` 分区谓词，MC 拒绝全分区扫描。
   - 修复：`data_query.py` 对此类 freshness probe 降级为安全的 `SELECT MAX(dt) AS max_dt FROM <table>`；prompt 禁止无分区谓词读取非分区字段。
   - 提交：`7bac38d fix(runtime): normalize MC freshness probes`

3. 回归脚本同步 `/api/chat` 长请求超时：
   - 现象：线上 PI 长查询时，HTTP 空读超时，脚本无法稳定拿到 session_id。
   - 修复：`tools/scripts/pi_replay_regression.py` 改用 `/api/chat/stream`，通过 SSE heartbeat 保持连接。
   - 提交：`e15d722 fix(runtime): anchor D7 cohort replay date`

4. D7 cohort 日期漂移：
   - 现象：PI 曾在无显式日期时把 cohort 从 `2026-06-17` 漂到 `2026-06-16`。
   - 修复：prompt 固化规则：用户未指定 cohort 日期且问题要求 D7 时，使用收入表最新成熟分区 `revenue_latest_dt - 7 天`；最新收入分区为 `2026-06-24` 时，cohort 必须是 `2026-06-17`，不能因激活表单分区 0 行改成更早日期。
   - 回归 case 增加 `assistant_must_include: "2026-06-17"`。
   - 提交：`e15d722 fix(runtime): anchor D7 cohort replay date`
