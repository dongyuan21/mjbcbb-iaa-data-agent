# 20260721 L1 Snip 工具结果截断验证记录

> 记录日期：2026-07-21
> 范围：Runtime 运行时工具调用结果截断（上下文工程相位 D 附 L1）
> 级别：性能优化
> 证据：commit `3f026984` + 端到端 CK 实测
> 状态：已验证、已部署

## 一、问题

Runtime 运行时工具调用（`query_maxcompute` / `query_clickhouse`）返回的结果直接塞进 Runtime 内部 LLM 的 context，单次工具结果最多 1000 行 / 512KB，挤占 prompt 预算。改动前 `_bounded_result` 采用"拒绝式"——超限即 `ok:false` 不返回任何数据，Runtime 拿不到数据被迫重查，反而多花 token 和 round-trip。

设计依据：`data_agent_plan/多轮对话与上下文压缩工程设计.md`；改动文件：`runtime/tools/data_query.py` 的 `_bounded_result`。

## 二、解决方案

把 `_bounded_result` 从"拒绝式"改为"截断式 + 指针"分三级：

| 级别 | 条件 | 行为 |
|---|---|---|
| 小结果 | ≤200 行 且 ≤100KB | 原样返回，无截断标记 |
| 中等结果 | >200 行 或 >100KB，但 ≤5000 行 且 ≤2MB | 截断到前 200 行 + `truncated:true` + `truncated_row_count` + `truncation_note` |
| 超大结果 | >5000 行 或 >2MB | 硬拒绝 `ok:false` + `result_too_large`（防内存爆炸） |

常量：`SNIP_ROW_THRESHOLD=200` / `SNIP_BYTE_THRESHOLD=100KB` / `SNIP_KEEP_ROWS=200` / `SNIP_HARD_REJECT_ROWS=5000` / `SNIP_HARD_REJECT_BYTES=2MB`。

Runtime prompt 适配（`runtime_business_route.j2` 第 17 条约束）：工具结果含 `truncated: true` 时，基于前 200 行做聚合判断或样本分析，不反复重试同一查询；如需完整数据，缩小日期窗口或改用 GROUP BY 聚合。

## 三、验收

| 项 | 结果 |
|---|---|
| 单元测试 `test_l1_snip.py`（6 个） | 全 PASS：小结果原样 / 中等截断 / 超大硬拒绝 / 字节阈值触发 / 失败结果原样 / 非 list rows |
| 旧测试适配 `test_data_query_tool.py`（2 个） | 1001 行从 `result_limit_exceeded` 改为 `truncated:true`；513KB 单行从 `result_bytes_exceeded` 改为 `truncated:true` |
| 端到端 CK 实测 | 231 行聚合 → 截断到 200 行 + `truncated_row_count:231`；1000 行聚合 → 截断到 200 行 + `truncated_row_count:1000` |
| agent regression | `route_golden_cases` 186/186、`retrieval_route_cases` 17/19（与 baseline 一致）、backend pytest 1185 passed（0 regression） |

## 四、成效

| 场景 | 改动前 | 改动后 | 省 |
|---|---:|---:|---:|
| 1000 行 ≈ 500KB | ~125K tokens | 200 行 ≈ 100KB / ~25K tokens | ~100K tokens（极端） |
| 300 行 ≈ 60KB | ~15K tokens | 200 行 ≈ 40KB / ~10K tokens | ~5K tokens（典型） |
| 1000 行被拒绝 → 重查 | 多 1 轮 round-trip | 200 行可用，不重查 | 省 1 次重查 |

四轮上下文压缩累计：bootstrap 压缩 ~10.6KB/会话 + Runtime prompt 外置 ~1K tokens/请求 + knowledge_context 检索化 ~18-23K tokens/请求 + L1 Snip ~5-100K tokens/调用。

## 五、遗留观察项

1. **L2/L3/L4 未实现**：多轮 history 压缩（MicroCompact / Collapse / AutoCompact）留作后续；当前 history 只含 answer_markdown（自然语言）不含工具结果，L1 已覆盖主要矛盾。
2. **backend executors.py 无保护**：FastAPI 服务的 `executors.py` 路径无 `_bounded_result` 等价物；Runtime 不走这条链路，当前不影响，若 backend 也服务 LLM 工具调用需补齐。
3. **TS 层纯透传**：`readonly_data_query.ts` 对结果 0 截断依赖 Python 层；若未来 TS 层加 `max_rows` 配置需同步调整。
4. **表卡瘦身**：表卡 8-17KB 占 first_read 43%，是独立优化方向，见 `bugfix_doc/20260721_Runtime运行时表卡摘要瘦身.md`。

## 六、方法论沉淀

1. **超限应截断而非拒绝**：拒绝式让 Agent 拿不到数据被迫重查，多花 round-trip；截断式给前 N 行 + 指针，Agent 能基于样本继续。
2. **截断要分三级**：小结果原样 / 中等截断 + 标记 / 超大硬拒绝，兼顾可用性和内存安全。
3. **截断标记要可追溯**：`truncated_row_count` 保留原始行数，Agent 和后续分析知道完整结果规模。
4. **prompt 要适配截断语义**：告诉 Agent 截断时基于样本做聚合判断，不反复重试同一查询。
