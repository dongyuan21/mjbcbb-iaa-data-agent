# 配置层与运行层割裂问题

## 问题概览

- 级别：P1 / 架构与安全边界问题
- 状态：部分修复，尚未闭环
- 现象：路由配置里已经声明了 `allowed_assets`、`first_read`、`output_guardrails` 等约束，但运行时并没有把这些约束全部变成强制过滤条件

## 背景

当前工程已经把任务路由拆成了两层：

- 配置层：`task_routes/*.yaml` 负责声明每类任务的路由、首读资料、允许资产、协议和护栏
- 运行层：`runtime/backend/app/services/knowledge.py`、`runtime/backend/app/services/pi_agent.py` 负责把这些规则组装成实际上下文，再交给模型执行

这类分层本身没有问题，问题出在“声明”和“执行”之间没有完全打通。

## 现象

我们看到的实际情况是：

1. 配置里已经有规则。
2. `RouteDecision` 里也能接到这些规则。
3. 运行时会把 `first_read`、协议、护栏注入 prompt。
4. 但 `allowed_assets` 还没有成为运行时的硬过滤条件。
5. 因此工程表现为“纸面上有约束，现场执行不一定照做”。

## 证据

### 1. 路由解析已经把规则读出来了

在 [runtime/backend/app/services/knowledge.py](/Users/<dev>/HS/点位/数仓/runtime/backend/app/services/knowledge.py) 中，路由器会从 `task_routes/<task_id>.yaml` 读取：

- `first_read`
- `allowed_assets`
- `mandatory_protocols`
- `output_guardrails`
- `completion_boundary`
- `conditional_next_hops`
- `context_budget`

这说明“配置层”已经成熟到可以表达规则。

### 2. 运行时会注入部分规则

同一文件里的 `build_knowledge_context_parts()` 会把下面内容放进 prompt：

- 查询相关 guidance
- verified SQL 资产
- 表卡摘录
- `first_read` 策略 / 协议

也就是说，运行层不是完全空白，它已经能把一部分配置转成上下文。

### 3. 但 `allowed_assets` 没有进入真正的资产筛选

从现有实现看：

- `allowed_assets` 只是在 `RouteDecision` 里保存下来
- `verified_sql_assets(question)` 仍然是按问题关键词扫 `da_assets/index.yaml`
- 没有看到基于 `route.allowed_assets` 的显式白名单过滤
- 没有看到“越权资产拒绝”的运行时门禁

这意味着运行层目前更像“读了规则”，但没有“按规则拦截”。

### 4. 现有测试主要覆盖正向流程

当前能看到的测试更偏向：

- clarification gate 是否触发
- provider metadata 是否正确
- route / prompt 结构是否能跑通

但还没看到明确的负向测试去证明：

- raw / draft / archived 资产进不来
- 非 allowed_assets 不能进入上下文
- 路由改变后越权内容会被硬拦

## 当前修复进展

### 已完成

- 路由结构已经拆出来了
- `RouteDecision` 已经能承载 `allowed_assets`、`first_read`、护栏和上下文预算
- 运行时已经能把 `first_read` 和部分协议写入 prompt
- 任务路由文件层已经有比较完整的声明式配置

### 还没完成

- `allowed_assets` 的运行时强过滤
- 检索阶段的白名单裁剪
- 上下文拼装前的二次校验
- 越权资产的负向测试
- “配置改了，运行一定跟着变”的端到端证明

### 结论

目前修复进度大概是：

- **配置层：已完成**
- **运行层注入：部分完成**
- **运行层强制执行：未完成**

所以它还停留在“有规则、能读规则、但不能证明规则已被严格执行”的阶段。

## 根因分析

这个割裂通常不是单一原因，而是几件事叠加：

1. 先把配置层做出来了
- 先把路由、资产、协议写清楚
- 这是对的，但只完成了“声明”

2. 运行层实现得偏轻
- 运行层更像上下文拼接器
- 还没升级成真正的门禁层

3. 缺少中间的契约编译层
- 没有把配置编译成硬约束
- 没有把声明式规则变成可执行的过滤器

4. 缺少反向测试
- 只测“该来的能来”
- 没测“不该来的能不能被挡住”

## 具体风险

- 越权知识可能进入上下文
- 回答看起来对，但实际上混入了不该用的资产
- 路由演进后，旧逻辑可能继续放行更多内容
- 审计时很难证明“系统真的遵守了配置”

## 后续建议

1. 把 `allowed_assets` 变成运行时硬过滤
- 检索结果必须先过白名单
- 不在名单里的资产不能进入 prompt

2. 在上下文拼装前做二次校验
- 明确记录“放行了什么、拒绝了什么”
- 让日志可审计

3. 补负向测试
- 测 raw / draft / archived 资产
- 测跨 route 资产
- 测配置缺失时是否默认放行

4. 建立“配置到运行”的契约层
- 把 `task_routes/*.yaml` 编译成运行时 policy
- 让运行层只能按 policy 工作

## 一句话总结

这个问题不是“先做配置层”本身有错，而是配置层虽然已经写出来了，运行层还没有把它变成硬约束，所以现在只能算“部分修复”，还没闭环。
