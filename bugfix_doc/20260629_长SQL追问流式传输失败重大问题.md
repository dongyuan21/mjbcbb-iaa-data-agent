# 20260629 长 SQL 追问流式传输失败重大问题

> 记录日期：2026-06-29
> 范围：数仓 Agent Web 端流式对话传输层
> 级别：P0 用户可见链路失败
> 状态：已修复并部署 test

## 一、问题

用户在同一会话中追问并粘贴长 SQL 后，页面状态栏显示 `Separator is found, but chunk is longer than limit`。该报错不是 SQL 执行结果，也不是 MC/CK/LLM 的业务错误，而是流式请求链路在处理超长内容时失败。

影响范围：`数仓 Agent` Web 端流式对话，尤其是粘贴长 SQL、长报错、长上下文追问。

## 二、根因

旧实现用浏览器原生 `EventSource` 发起 SSE：`GET /api/chat/stream?message=<完整用户问题>&session_id=...`。

`EventSource` 只能用 GET，请求正文无法放 body，前端把用户完整问题放进 URL query。普通短问题没问题，但用户粘贴长 SQL 时：URL 被编码成极长 query string，浏览器/Ingress/ASGI parser/SSE 解析链路任一环节都可能触发长度或 chunk 限制，失败表现为流式连接中断，前端把错误写入任务状态。

这是**长 prompt 传输协议选择错误**，不是用户 SQL 内容本身错误。

## 三、解决方案

| 改动 | 内容 |
|---|---|
| 后端 | 新增 `POST /api/chat/stream`，接收 `ChatRequest` JSON body；原 `GET /api/chat/stream` 保留为兼容入口 |
| 前端 | 从 `EventSource(GET)` 改为 `fetch(POST)`，手动解析 SSE 帧，继续支持 status/thought/tool_start/tool_result/repair/answer/error |
| 停止回答 | 从 `EventSource.close()` 改为 `AbortController.abort()` |

关键文件：`runtime/backend/app/main.py`、`runtime/frontend/src/App.tsx`。提交 `438f796`。

## 六、方法论沉淀

1. **长文本输入不得用 GET query 传输正文**：URL 长度受浏览器/Ingress/parser 多层限制，长 SQL/报错粘贴必崩。
2. **SSE 携带用户输入应 POST 建流**：或采用"POST 创建任务 + GET 订阅任务事件"两段式，GET 入口定位为兼容短请求。
3. **流式协议要覆盖长 prompt smoke**：前端涉及流式协议时，不能只用短文本验证，必须覆盖长 SQL/长报错粘贴场景。
