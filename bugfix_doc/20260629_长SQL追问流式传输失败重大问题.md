# 2026-06-29 长 SQL 追问流式传输失败重大问题

## 问题概览

| 项 | 内容 |
|---|---|
| 编号 | BUGFIX-20260629-CHAT-STREAM-LONG-PROMPT |
| 级别 | P0 用户可见链路失败 |
| 状态 | 已修复并部署 test |
| 问题类型 | 传输层 / 前端建流协议设计缺陷 |
| 用户可见症状 | 在已有问题上下文中追问并粘贴长 SQL 后，页面状态栏显示 `Separator is found, but chunk is longer than limit` |
| 影响范围 | `数仓 Agent` Web 端流式对话；尤其是粘贴长 SQL、长报错、长上下文追问 |

## 现象

用户在同一会话中追问：

```text
要不参考下这个 sql 呢？ WITH ...
```

问题正文包含一整段很长的 SQL。页面没有正常继续回答，而是在任务状态区域显示：

```text
Separator is found, but chunk is longer than limit
```

该报错不是 SQL 执行结果，也不是 MC / CK / LLM 的业务错误，而是流式请求链路在处理超长内容时失败。

## 根因

旧实现使用浏览器原生 `EventSource` 发起 SSE：

```text
GET /api/chat/stream?message=<完整用户问题>&session_id=...&agent_model=...
```

`EventSource` 只能使用 GET，请求正文无法放在 body 中。当前前端因此把用户完整问题放进 URL query。普通短问题没问题，但一旦用户粘贴长 SQL：

- URL 会被编码成极长 query string；
- 浏览器、Ingress、ASGI/HTTP parser、SSE 解析链路中任一环节都可能触发长度或 chunk 限制；
- 失败会表现成流式连接中断，前端把错误写入当前任务状态。

因此，这是一个**长 prompt 传输协议选择错误**，不是用户 SQL 内容本身错误。

## 证据

线上 Pod 日志中能看到对应请求进入后端时，长 SQL 被完整塞进 URL：

```text
GET /api/chat/stream?message=...WITH...超长SQL...&session_id=...&agent_model=qwen3.7-max HTTP/1.1
```

同一轮截图中的错误：

```text
Separator is found, but chunk is longer than limit
```

与“单条 URL / 单个流式 chunk 超出解析限制”的形态一致。

## 修复

修复提交：

```text
438f796 fix chat stream for long prompts
```

修复内容：

- 后端新增 `POST /api/chat/stream`，接收 `ChatRequest` JSON body。
- 原 `GET /api/chat/stream` 保留，兼容旧入口和短请求。
- 前端从 `EventSource(GET)` 改为 `fetch(POST)`。
- 前端手动解析 SSE 帧，继续支持 `status` / `thought` / `tool_start` / `tool_result` / `repair` / `answer` / `error`。
- 停止当前回答从 `EventSource.close()` 改为 `AbortController.abort()`。

关键文件：

- `runtime/backend/app/main.py`
- `runtime/frontend/src/App.tsx`

## 后续防线

- 长文本输入、SQL 粘贴、报错粘贴等场景不得使用 GET query 传输正文。
- SSE 如需携带用户输入，应采用 `POST` 建流，或采用“POST 创建任务 + GET 订阅任务事件”的两段式。
- 前端涉及流式协议时，需覆盖长 prompt smoke，避免只用短文本验证。
- 后端保留 GET 入口时，应将其定位为兼容入口，不作为长文本主路径。
