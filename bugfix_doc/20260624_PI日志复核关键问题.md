## 二、解决方案

第一阶段：在单体 PI 外围增加确定性语义护栏（不拆 multi-agent）。

| 落点 | 修复 |
|---|---|
| `runtime/backend/app/services/pi_agent.py` | 新增 D7 累计收入 SQL 检测：BB 激活 cohort + 行为收入查询把 D7 写成 `dt = cohort_date + 7` 或只枚举 D0/D7 两天时，即使 SQL 成功也返回"D7 累计收入口径错误"；正确累计窗口 `dt >= cohort_date AND dt <= cohort_date + 7` 不被误拦 |
| `runtime/backend/app/services/knowledge.py` | 问题级表路由提示补充 D7 累计窗口规则 |
| `task_routes/text2sql_or_sql_planning.yaml` | D7 累计口径写入 output guardrails |
| `da_assets/analysis_sop/PI查询执行复核护栏.md` | 沉淀 D7/Dn 累计收入默认口径和单调性 sanity check |
| `runtime/backend/tests/test_pi_review_guardrails.py` | bad/good SQL 两类回归测试 |

正确 SQL 形态：D0 收入 = `dt = cohort_date`；D7 累计 = `dt >= cohort_date AND dt <= cohort_date + 7`；人均分母 = 同一 activation cohort 的 `COUNT(DISTINCT distinct_id)`。

## 五、方法论沉淀

1. **D7/Dn 默认是累计口径**：只有用户明确说"D7 当天"才用单日收入；SQL 生成阶段为 D7 累加模板约束，禁止只写 `dt = cohort_date + 7`。
2. **结果校验加单调性检查**：非负收入下 D7 累计均值低于 D0 时必须停止自检口径，这是口径错误的强信号。
3. **口径护栏用确定性代码而非提示词**：PI 提示词无法稳定保证口径，在 pi_agent 外围加 SQL 形态检测才是可靠护栏。
4. **用户未给日期时固定成熟 cohort 策略**：必须声明"最新 D7 成熟 cohort"并在回答中写明选择原因，不得混合多个 cohort 日期。
