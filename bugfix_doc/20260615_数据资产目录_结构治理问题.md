## 一、问题

`数据资产目录/` 早期是从 CK 在线 schema 一次性导出建起来的，存在三类结构性问题：

1. **平铺无分层**：`table_profiles/` 平铺 136 个文件，68% 是 `_local`/temp/test/staging/replica 等噪声或已停更版本，Agent 召回时无法区分主次。
2. **catalog 与召回脱节**：catalog 只索引 5 张表，131 个 profile 悬空；`agent_manifest`/README 不含 profile 召回规则，Agent 不知道哪些表能默认用。
3. **缺完整 数据资产目录与验证**：P0 数据资产目录只到 partial、字段不全；无版本探测和示例查询在线验证脚本，数据资产目录里"v2 活 v3 死"这类会过时的判断靠手写。

## 二、方法论修正

第一版按"文件名后缀（_local/temp/test）"机械分层是错的。正确做法是**先理解业务上下文、确认哪些表真正被生产使用、最常用 SQL 是什么，再由"使用角色"驱动索引**：

- 业务上下文：`shucang_market` 是休闲益智手游买量投放的 CK OLAP 报表库，服务 分析平台 看板 + 分析平台 点位平台。
- 核心链路：点位映射 → 消耗 spend → 回收 revenue（SDK 默认 / AF 对照）→ 留存 cohort → ROI/LTV（应用层按 date_diff 拼装 + correction 纠偏）→ 预测 forecast。
- 生产真实使用：以 MI 后端 分析平台 路由代码为 ground truth，确认生产查的是 `_view`（视图），canonical（权威形态）应是 view，不是物理表。

## 三、解决方案

### 1. 使用驱动分层（catalog.yaml `tiers`）

按生产使用角色分四层，取代机械后缀分层：

| tier | 含义 | 数量 |
|---|---|---|
| tier0 | 生产主链路（spend / sdk_revenue / revenue / af_cohort / 点位映射 / ROI 纠偏 / convert_type），canonical = view | 7 |
| tier1 | ROI 衍生 / 预测 / 再营销 / ASA | 11 |
| tier2 | 维表 / 字典 / 桥接 | 11 |
| tier3 | 素材 / KOL / 媒体 API / 实验 | 14 |

噪声与停更表（89 个）移入 `_raw_dump/`，不进默认召回。

### 2. 完整 数据资产目录补全 + scope 扩展

- 在线 DESCRIBE 后为 tier0 缺的 correction / convert_type 建完整 数据资产目录。
- 经确认将 `ad_revenue` 库纳入 scope（canonical = `v2_di`，v1/v3 已停更），建 `示例表` + `tj_ad_revenue_ltv_list_utc`（180 日 LTV）。
- 内网环境下补全 tier1 完整 数据资产目录 11 张，数据资产目录 完整 数据资产目录 9 → 20。

### 3. 自动化验证脚本（替代手写判断）

| 脚本 | 产物 | 作用 |
|---|---|---|
| `build_数据资产目录_profile_index.py` | `INDEX.md` | 读 catalog.tiers 自动生成按 tier 分层的索引 |
| `probe_table_versions.py` | `table_version_registry.yaml` | 自动探测多版本族 max(分区日)，判 alive/dead，取代数据资产目录里会过时的文字判断 |
| `verify_ck_example_queries.py` | `示例查询验证报告.md` | 在线执行每张卡 example_queries，把手写示例升级为执行验证 |
| `verify_ck_metric_sanity.py` | `metric_sanity.json` | canonical 主链路近 14 天指标 sanity 检查（>0），只用 sanity 阈值，不含业务红线 |
| `refresh_数据资产目录.sh` | 一键刷新五件产物 | freshness / 版本登记 / example 验证 / metric sanity / profile 索引 |

### 4. Agent 友好性（P0+P1）

- **反向指针**：`数据资产目录/README.md` + `catalog.yaml` 指向 `semantic_contract/model.json`，Agent 跨表拼 SQL 有入口。
- **ad_revenue 纳入语义层**：`entities.yaml` + `metrics.yaml` 新增 `ad_revenue_usd`/`ad_revenue_dn`/`ad_ltv_dn`；`ltv_list` 卡拆出里程碑列以过列校验。
- **freshness 扩面**：`probe_freshness.py` 数据驱动，自动覆盖到 9 张 CK 卡；加 `--source clickhouse` 开关。
- **回归过期检测**：`run_regression.py` 加产物过期 gate（警告级，阈值 3 天），freshness / version_registry / example_verification 时间戳过期时告警。

### 5. MI 后端代码核查（收窄"待 DA"清单）

用 MI 后端代码核对了离线表口径归属：

- `示例表` / `media_country_roi` / `market_roi_prediction` —— MI 后端零引用，是离线 ROI 预测/聚合管线产物，多版本 canonical 由离线 pipeline / DA 定，**不以 MI 为准**。
- ROI 数组下标（MI 口径）：`roiFieldName(day)="roi_"+day`（0 基），业务 ROI_N = 字段 `roi_(N-1)`（如 ROI7 = roi_6）；MI 不读 CK 预测表，而是应用层自算真实段 + 外部预测服务补到 D360。与 `semantic_contract/metrics.yaml revenue_n` 口径一致。

## 五、方法论沉淀（供后续参考）

1. **不要按文件名后缀机械分层**，要先理解业务上下文和生产真实使用，由"使用角色"驱动索引。
2. **canonical 形态以生产查询为准**：生产查 view，canonical 就是 view，不是物理表。
3. **会过时的判断交给脚本探测，不手写进数据资产目录**：版本 alive/dead、freshness、example 是否可执行，都由脚本定期刷新，不靠人写死。
4. **多版本 canonical 归属看代码引用**：MI 后端零引用的表是离线管线产物，口径归属不在 MI，由离线 pipeline / DA 定。
5. **scope 扩展需显式确认**：是否纳入新库（如 ad_revenue）要经确认并记录 canonical 版本，不默认全收。
