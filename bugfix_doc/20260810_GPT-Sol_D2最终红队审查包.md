## 目标与严格边界

这是一个只读分析型 Data Agent Runtime。模型 provider 调用是不可回滚的外部副作用；本设计的目标不是精确核算供应商账单，而是确保一个 Runtime turn 的 provider 预算不会被超卖。

v1 明确不做：

- provider idempotency key、callback、receipt inbox、status lookup、账单对账；
- 自动 retry 已发出或不确定的调用；
- 将预算状态机变成业务 workflow engine；
- 修改 SQL/L5/P2 ContractView/P3 终态授权；
- 任何 E3 特判、授权放宽、阈值放宽或部署。

`Runtime budget accounting` 只回答“能否准入下一次 provider 调用”；它允许保守估算。它不是 provider billing reconciliation。

## 三个独立状态机

1. **Job Lease FSM**：`job_id + owner + lease_token + expires_at`。只有当前 owner 可写资源账本。任一数据库 mutation 都在 SQL 条件中再次断言此 lease 仍为 running、owner/token 匹配且未过期。
2. **Provider Reservation FSM**：`RESERVED → ISSUED → SETTLED_ACTUAL | SETTLED_CONSERVATIVE`；唯一例外是未 issue 的 `RESERVED → CANCELLED_PRE_ISSUE`。一个 `immutable_attempt_id` 只可对应一次 durable dispatch claim。
3. **Runtime Turn/P3 FSM**：业务回答、waiting、incomplete、terminal 仍由既有 Runtime/P3 独立决定。Reservation settlement 绝不可直接写 Runtime terminal 或 P3 terminal。

关键身份职责互不替代：

- `lease_token`：哪个 Worker 现在有写权限；
- `immutable_attempt_id`：哪一次外部副作用尝试；
- `reservation_row_version`：该 reservation 的 CAS 版本；
- `dispatch_row_version`：一次性 dispatch permit 的 CAS 版本。

## Durable 数据模型

### TurnBudget

每个 `turn_id` 一行，字段：`job_id`（外键、普通索引，**不唯一**）、`turn_id`（全局唯一）、`cap`、`active_provider_liability`、`settled_runtime_consumption`、`admission_state(open | degraded_no_admission)`、`revision`。

一个 Job 可以在澄清/恢复后承载多个顺序 turn，因此绝不能用 `job_id` 唯一键阻止第二个 turn 建账。

### ProviderCallReservation

字段：`reservation_id`（唯一 opaque ID）、`turn_budget_id`、`immutable_attempt_id`（唯一）、`reserved_input_tokens`、`reserved_output_tokens`、`reserved_total_tokens`、`granted_max_output_tokens`、`visible_tools_hash`、`state`、`row_version`、`issued_job_lease_token`、`dispatch_claimed_at`、`ambiguity_reason`、`settled_runtime_consumption` 与时间戳。

不持久化 prompt、answer、SQL、rows、raw response、raw error 或 provider 私有 payload。

## 核心不变量

任意时刻必须满足：

```text
settled_runtime_consumption + active_provider_liability <= cap
durable_dispatch_claim_count(immutable_attempt_id) <= 1
only current job lease owner may mutate TurnBudget or Reservation
ISSUED liability never silently returns to available
reservation settlement never directly transitions Runtime Turn or P3 terminal
```

## 准入与调用协议

1. Worker 仅在持有当前 lease 时，为某个 `turn_id` 初始化 budget。初始化使用带 `EXISTS(current lease)` 谓词的单条 `INSERT … SELECT`；不是“先读 lease 再插入”，避免 TOCTOU。
2. 每次模型调用前，Runtime 计算 provider payload 的安全 token 估算 `estimated_input_tokens`，并把现有服务器已授权的 tool schema 计算为 `visible_tools_hash`。
3. 在 `TurnBudget.revision` CAS 事务中，读取：

```text
remaining_before_call = cap - settled_runtime_consumption - active_provider_liability
granted_max_output_tokens = min(requested_provider_max_output,
                                remaining_before_call - estimated_input_tokens)
```

若 grant 小于 provider 的结构正数最小值（当前为 1；不是新的产品预算数字），则准入拒绝，provider 不得调用。CAS 冲突最多重读三次；它只重试本地准入读取，不会重试 provider attempt。
4. 成功后在同一事务增加 `active_provider_liability` 并插入 `RESERVED` reservation。
5. 发送前先 CAS `RESERVED → ISSUED`，并记录当前 lease token；提交成功才可能发送。
6. 再以 `dispatch_claimed_at IS NULL + reservation row version + current lease` CAS 生成一次 `ProviderDispatchPermit`。adapter 只有拿到该 permit 才可以发请求。该 durable claim 只保证 Runtime 最多尝试发送一次；没有 provider idempotency/status 时，不声称 provider 物理 exactly-once。
7. adapter 原样把 `permit.granted_max_output_tokens` 传给 provider；不得自行扩大、缩小或重算。发送前后可见 tool hash 不一致时，尚未 issue 的 reservation 仅可取消；不能带着新工具面发送。
8. provider await 返回或异常后，先结算再让 ToolLoop 解释 assistant tool call、再进入既有 Registry/L5。工具执行不能回滚 provider settlement。

## 结算规则

`SETTLED_ACTUAL` 只有同时满足下列条件才允许：当前 Worker lease 仍有效；reservation=ISSUED；attempt ID、dispatch permit row version、issued lease token 都匹配；dispatch claim 存在；没有不确定性；usage schema 完整；总 token 不超过 reservation；输出 token 不超过 approved grant。

若 provider usage 缺失/畸形，或 timeout/cancel/transport error/worker crash/lease loss，则当前 owner（若仍有 lease）以 reservation 全额保守结算为 `SETTLED_CONSERVATIVE`。新 owner 接管发现旧 `ISSUED` 时，也只能保守结算；不得重发旧 attempt。

若 usage 超过 reservation 或超过 approved output grant：仍以 reservation 全额保守结算，且同一 TurnBudget 写 `degraded_no_admission`。所有 Worker 后续 provider admission 都拒绝；这不是业务 terminal。

旧 Worker lease 失效后迟到收到 provider response：不能 settlement、ToolLoop mutation 或 P3 interaction；最多写非权威、content-free telemetry `late_provider_response_seen=true`，它不得反向改变任何 Runtime 状态。

## D0 / D2 开关

- `off`：当前行为；
- `shadow`：真实 provider transport、`max_tokens`、ToolLoop、P3 都完全不变，只输出 content-free would 字段（estimate、would reserve/issue/settle mode、有限 reason、observed count）；
- `enforce`：只能由具有 Worker job lease 的 durable 路径进入。没有 lease 的 inline 请求在 provider 调用前 fail closed，不允许降级为未治理调用。

当前 feature 默认 `off`，没有 Test 部署、没有真实 provider 或 E3 复验。

## 已完成的本地确定性测试

全部使用 SQLite / fake model，不联网、不部署：

- 两个并发 reserve 在 cap=10、每次 liability=8 时，只有一个成功，始终满足总消费加 liability 不超过 cap；
- 对同一 `immutable_attempt_id`，只有一次 durable dispatch claim；第二次 claim 被拒；
- `ISSUED` 后 timeout、cancel、crash、usage missing 都全额保守结算，不释放 liability；
- lease takeover 后，旧 owner 不能 actual settle、conservative settle 或新 reserve；迟到 response 仅观察；
- same-owner 且 permit/lease/version 匹配时才 actual settle；超总 reservation 或超 approved output 时全局 `degraded_no_admission`；
- 实际 ToolLoop 路径断言 provider settlement 在 Registry tool handler 前完成；
- dispatch 前工具 hash 漂移只取消 `RESERVED`，provider 不被调用；
- 同一 Job 的两个顺序 turn 建立两个独立 budget；
- 首轮实际结算 2 token 后，第二轮 max grant 从 20 自动缩小为 18，证明 grant 基于持久化剩余而不是重新使用整个 cap；
- migration 在临时 SQLite 上真实 upgrade/downgrade，包含 `job_id` 非唯一索引与 `turn_id` 唯一约束；
- 相关聚焦回归：39 passed。

## 请重点红队的问题

1. `INSERT … SELECT` lease fence、admission revision CAS、issue CAS、dispatch claim CAS 和 settlement CAS 是否形成足够的本地 authority boundary？是否仍有能导致 stale owner 写账的路径？
2. “每 turn 一个 budget、同 Job 可多 turn”是否正确？是否应改成其他唯一性模型？
3. 动态 grant 是否应该在 reservation CAS 中计算，而不是在 adapter 本地先决定？现在的设计是否足够避免已结算预算被重复使用？
