# <提交标识> 数据资产目录 PII 护栏问题记录

> 记录日期：2026-06-15
> 范围：`数据资产目录/`（MaxCompute / Hive 表知识库）的 PII（个人可识别信息）护栏一致性
> 状态：已闭环。本文件保留问题与方案供后续参考，session 流水账已精简。
> 政策依据：`AGENTS.md` Always Applied Rule 5「不保存 AK/SK、数据库密码、SSO ticket、MI token、cookie、用户级明细、设备 ID、IP、user_agent」

## 一、问题

PII = 能定位到某个具体人 / 某台具体设备的字段。要防的不是库内脱敏，而是 Agent 自动生成并执行 SQL 时，把这些列的**原始明细值带进 LLM 上下文 / 聊天记录 / 第三方模型日志**。护栏的载体是数据资产目录里的 `query_rules.pii_columns_do_not_log`。全库扫描发现三类问题：

1. **标注覆盖严重不足且不一致**：100 张卡中 52 张 `pii_columns_do_not_log` 为空；`device_id` 21 张漏标、`latwgs/lngwgs`（经纬度）全部漏标、`account_id` 全部漏标。Agent 读到的护栏时有时无。
2. **三处真理源互相打架**：`agent_manifest.yaml` hard_rules 列 4 个、`数据地图.md` 列 3 个、各数据资产目录各列各的，无权威全集，也没有脚本能据此校验。
3. **PII 语义二元化过粗**：`distinct_id`/`appsflyer_id`/`customer_user_id`/`device_id`/`account_id` 既是 PII 又是必需的 join 键 / 去重键（如安装激活分母 `COUNT(DISTINCT COALESCE(customer_user_id, appsflyer_id))`）。一个布尔"禁列"会让 Agent 要么违规、要么不敢用，连分母都算不出。

## 二、解决方案

### 1. 建单一真理源 + 两档分类

新增 `数据资产目录/PII_POLICY.yaml`，两档分类取代布尔禁列：

| 档位 | 含义 | 列示例 |
|---|---|---|
| `forbidden_output` | 绝不可 SELECT / 输出 / 日志 | gaid / idfa / idfv / oaid / android_id / ip / user_agent / latwgs / lngwgs / email / s_pushtoken 等 |
| `aggregation_only` | 可做 join / `COUNT(DISTINCT)`，禁落明细行 | distinct_id / device_id / appsflyer_id / customer_user_id / account_id / uuid |

### 2. 脚本自动盖章（根治手工漏标）

新增 `tools/scripts/stamp_数据资产目录_pii.py`：对每张卡取 `PII_POLICY ∩ 该卡实际列`，自动写回 `pii_columns_do_not_log` + 新增 `pii_aggregation_only`；接入 `sync_数据资产目录_schema.py` 流程，后续新表同步即自动盖章。

### 3. 三处真理源统一指向 canonical

`agent_manifest.yaml` hard_rules / `数据地图.md` 改为**指向** `PII_POLICY.yaml`，不再硬编码列名；新增一条「聚合键可用于 COUNT/JOIN，禁输出明细」。

## 三、验收

- 100 卡盖章命中：forbidden_output 46 卡 / aggregation_only 66 卡。
- 一致性校验：100 卡 `pii_columns_do_not_log` == `PII_POLICY ∩ 该卡实际列`，全部一致。
- 幂等性：重复跑 `stamp_数据资产目录_pii.py` 无额外 diff。
- YAML 全合法；catalog / rag_bundle 重生成。

## 四、遗留观察项

1. **JSON 内嵌 PII 绕过列名匹配**：盖章按"列名"匹配，但有的 PII 以 JSON 形式藏在普通列里（如 `示例表` 的 `custom_data`，`get_json_object(custom_data,'$.ta_distinct_id')` 抽出的是用户级 id，列名匹配抓不到）。后续：对 `custom_data`/`properties`/`event_properties` 等 JSON 容器列做 `aggregation_only` 级提示，或在执行层处理。属后续话题，不硬补。
2. 列名按精确匹配。若后续同步引入新的 PII 列变体（如新媒体 API 的 id 字段），需登记进 `PII_POLICY.yaml` 再跑盖章。
3. 护栏是"知识层"约束（告诉 Agent 别输出），非运行时强制；是否在执行层加 PII 列拦截（如 SQL 静态检查）属另一议题，未做。

## 五、方法论沉淀

1. **PII 护栏要分两档**：彻底禁输出 vs 允许聚合/join 禁明细。布尔禁列会让 Agent 不敢用必需的聚合键。
2. **真理源必须单一且脚本化**：人工散填三处必然打架，canonical 字典 + 自动盖章才能根治"下次又失配"。
3. **列名匹配有盲区**：JSON 内嵌 PII 抓不到，要么对 JSON 容器列做提示，要么在执行层处理。
