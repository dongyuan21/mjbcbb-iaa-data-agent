## 一、问题

同一问题「分析 block_blast_gp 每个渠道每个国家，top20% 累积 d30arpu，能占 d30 总 arpu 的比例」跨用户不稳定（详见关联文档）。本文档定稿该问题的业务口径、表路由和 verified SQL，作为回归验收的权威依据。

## 二、口径定稿（2026-06-30 业务确认）

| 项 | 定稿 |
|---|---|
| Top20% 语义 | **A · 每个 `(media_source, country)` 格子内，用户 D30 累计 ARPU Top20%** |
| 收入口径 | **DA 行为收入**（`dws_block_blast_all_user_multi_dim_hi.ad_revenue`，非 SDK attributed） |
| Cohort | **仅 D30 完整安装日**；数据最新日 `t-1` 时，成熟安装窗 **`install_date ∈ [t-59, t-30]`**（30 个完整 D30 cohort 日） |
| D30 窗口 | 安装日起 **D0–D29** 共 30 日行为 `dt` 累计 `ad_revenue` |
| 输出粒度 | 每渠道×国家一行：`top20_user_revenue_share_in_segment`（Top20% 用户占**该格** D30 DA 收入比例） |
| 小样本 | 候选 SQL 默认 `HAVING cohort_users >= 20`；不足标 `needs_decision` / 小样本提醒 |

### Top20% 两种解释（存档）

| 维度 | **A · 每渠道×国家内，用户 Top20%** ✅ 已确认 | **B · 渠道×国家组合 Top20%**（user_a 历史） |
|---|---|---|
| 排序对象 | 每个格子内部用户，按 D30 累计 ARPU | 所有组合，按组合 D30 ARPU |
| 输出 | 每格子一行 Top20% 用户占该格 D30 收入 X% | 高 ARPU 的 20% 组合占全站 D30 收入 X% |

user_a 历史报告走的是 B + SDK 路径，与确认口径不一致；verified 晋升后以本表为准。

### 成熟 Cohort 窗说明

最新数据日 `t-1` 时，`install_date = t-30` 是 `[t-30,t-1]` 内唯一完整 D30 日；业务要"近 30 个安装日且 D30 完整" → **`[t-59, t-30]`**（30 个成熟安装日，行为扫描 `dt ∈ [t-59, t-1]`）。

## 七、方法论沉淀

1. **口径要先定稿解释再写 SQL**：Top20% 有"格子内用户"和"组合"两种解释，不定稿会写成两个不同 SQL，跨用户不稳定。
2. **成熟 cohort 窗要显式计算**：D30 完整要求安装日 + 30 天行为都在数据窗内，`[t-59, t-30]` 是 30 个成熟安装日的正确推导，不能让 PI 自由选日期。
3. **用户级计算放 CTE，外层只输出聚合**：既满足 PII 护栏（不输出 distinct_id），又满足业务粒度（每格一行占比）。
4. **verified SQL 要修 MaxCompute 语法约束**：`CROSS JOIN params` 在 MC 被禁，改用 `(SELECT … FROM params LIMIT 1)` 子查询。
