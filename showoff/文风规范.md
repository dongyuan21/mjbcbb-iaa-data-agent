# Showoff 文风规范

> 适用范围：`showoff/` 下所有 Markdown 和 HTML 展示材料。  
> 目标：对外汇报时让业务、DA、数仓、投放和管理同学都能听懂；保留严谨边界，但不把内部工程细节直接堆给读者。

## 总原则

`showoff` 的文风是：先结论、再解释、后边界。

每份材料都要回答三个问题：

1. 这套系统解决什么业务问题。
2. 当前已经做到什么程度。
3. 哪些事情仍然需要人工确认或继续建设。

不要把 `showoff` 写成开发文档、脚本说明、字段手册或内部验收报告。字段名、脚本名、目录名可以出现，但只能服务于汇报主线。

## 推荐结构

每份 Markdown 建议按这个顺序写：

1. 标题：直接说明主题，不写抽象口号。
2. 汇报定位：说明这份材料给谁看、用于什么场景。
3. 一句话说明：用 1 段话讲清楚核心观点。
4. 为什么需要：先讲业务痛点，再讲系统能力。
5. 架构或流程图：图要能在会议上口头讲清楚。
6. 当前能力：用表格列出已具备能力和边界。
7. 下一步或维护边界：讲清楚还缺什么、谁来确认。

HTML 投屏页可以更短，但要和 Markdown 使用同一套口径。

## 实现状态的用词

能力状态必须标明证据平面，避免把“已有组件”写成“已上线”：

| 用词 | 最低证据 | 不能据此推出 |
|---|---|---|
| 当前代码已实现 | 当前源码或组件测试 | API / Worker 主链一定经过它 |
| 主链已接 | 真实入口调用链与端到端记录 | 某个环境已经发布成功 |
| 环境已验证 | 指定环境的版本、配置、健康和真实 trace | 所有环境都一样 |
| 历史快照 / 历史记录 | 日期明确的旧报告或发布记录 | 当前资产数量、通过率或配置 |

当证据只到第一行，写“组件已实现，主链待接”；当证据只到第三行，写清环境、日期与版本。不要只写“已上线”“已完成”而不说明证据平面。

## 语言风格

| 要这样写 | 不要这样写 |
|---|---|
| 这张表的使用说明 | 表卡元数据治理 |
| 数据是否到齐 | freshness gate |
| 已验证 SQL | verified SQL |
| 复盘案例 | decision case |
| 关联键 | join key |
| 常见误用 / 口径风险 | pitfall |
| 待人工拍板 | needs_decision |
| 业务口径合同 | semantic contract |
| 查询层 / 报表层 | OLAP layer，如果听众不熟悉 |

可以保留目录名，例如 `ai_hive/`、`ai_ck/`、`knowledge/agent_knowledge/semantic_contract/`、`da_assets/`，但第一次出现时要用中文解释。

## 开头写法

推荐：

```text
这份材料说明 MaxCompute 表知识库如何支撑 Data Agent：先把表能不能查、怎么查、有什么风险讲清楚，再把稳定口径交给语义层复用。
```

不推荐：

```text
本文档展示 ai_hive L0-L3 table card ingestion pipeline 与 semantic_contract source_table / base_columns 映射关系。
```

## 图表写法

图表只保留汇报中能讲清楚的层次：

- 节点名用中文短句。
- 箭头表达因果或流程，不画所有文件依赖。
- 一张图最好只表达一个问题。
- Mermaid 节点里不要塞过长字段名。
- 图后要有 1 段话解释“这张图想说明什么”。

推荐图标题：

- “数据到结论的路径”
- “MC 与 CK 的分工”
- “Agent 处理一个问题的流程”

不推荐图标题：

- “catalog / manifest / source_table / must_filter 映射图”
- “L2 agent_queryable 到 L3 verified promotion pipeline”

## 术语保留边界

以下术语可以保留，但需要控制出现频率：

| 术语 | 使用方式 |
|---|---|
| `ai_hive/` | 第一次解释为 MaxCompute / Hive 表知识库 |
| `ai_ck/` | 第一次解释为 ClickHouse / MI 报表知识库 |
| `knowledge/agent_knowledge/semantic_contract/` | 第一次解释为业务口径合同层 |
| `da_assets/` | 第一次解释为可复用分析资产层 |
| `knowledge/` | 第一次解释为业务规则和分析协议 |
| `tools/`、`eval/` | 第一次解释为质量检查和回归验证 |

除非是在附录或维护说明里，否则不要主动展开字段名、脚本参数、YAML 字段和底层状态枚举。

## 必须保留的严谨边界

无论文风多简化，以下边界必须写清楚：

- 当前定位是只读分析基座，不表达自动停投、放量、降预算。
- 原始材料、草稿、截图抽取和旧快照不能当作已验证事实。
- 数据未到时要提示数据延迟，不能直接判断业务变差。
- MC 和 CK 跨源问题要分别查询后对齐，不直接跨库 SQL join。
- 阈值、动作和预算策略由人拍板。
- 不展示凭证、用户级明细、设备 ID、IP、Token、Cookie、SSO ticket。

## 自检清单

提交或更新 `showoff/` 文档前，至少检查：

- 开头 10 行内能看懂这份材料给谁看、解决什么问题。
- 每个内部目录名第一次出现都有中文解释。
- 没有连续三段都在讲脚本、字段、状态枚举。
- 图表能在 1 分钟内口头讲完。
- 结尾明确当前能力和不能做什么。
- 不含密钥、账号、用户级明细或敏感字段样例。
