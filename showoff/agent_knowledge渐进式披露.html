Stage 0 · HTTP / SSE

前端提问 → Runtime 流式入口

用户在前端输入问题，POST /api/chat/stream 建立 SSE 长连接。请求体为 ChatRequest（message、session_id、agent_model 等）。

  1. a
    浏览器发起 SSEEventSource 监听 status / step / context_metrics / answer 事件
    —
  2. b
    FastAPI 入口main.py → chat_stream_events() 创建 SSEStream，立即 retry
    —
  3. c
    鉴权与用户上下文UserContext 注入；不携带 AK/SK，查数走 Runtime 本地 helper
    —
Stage 1 · Session & Job

会话落库 + Job 生命周期

在真正路由知识之前，Runtime 先保证会话可追溯：创建/续用 session、生成 job_id，通过 SSE 向前端推送阶段状态。

  1. 1
    ensure_session()按 session_id 创建或续用对话会话
    DB
  2. 2
    create_job()title = 问题前 80 字；状态 submitted
    DB
  3. 3
    SSE status: submitted立即返回 job_id + session_id 给前端
    —
  4. 4
    update_job → runningSSE status: routing — 用户看到「正在路由」
    —
  • SSE event: status → stage=submitted | routing | fetching | done
  • SSE event: context_metrics → 各阶段 token 估算（阶段 11 产出）
Stage 2 · Bootstrap

仓库根控制面 — 知道「去哪找」，不读业务正文

AGENT_RETRIEVAL_MAP.yaml 的 default_bootstrap 是 Agent 挂载时的轻量地基。Cursor / Runtime 开发时读；问答时不把 catalog、model.json、表卡塞进常驻上下文。

  1. 1
    读 AGENT_RETRIEVAL_MAP.yaml定位 canonical_owners、never_default_recall、document_routing
    ~8 KB
  2. 2
    读 AGENTS.md + README硬规则：只预警不投放、freshness 先验证、表卡门禁
    ~12 KB
  3. 3
    读三库 agent_manifest.yaml各库 bootstrap_read_order、asset_layers、source_priority
    ~18 KB
  4. 4
    读 task_routes/INDEX.yaml轻量路由器：只有 id + trigger_examples，无 first_read 正文
    ~4 KB
  5. 5

Stage 4 · INDEX Scoring

9 类任务竞选 — 只读 INDEX，不读任务正文

KnowledgeRouter.route() 遍历 INDEX 中 9 个 task，分别计算得分。本问题同时命中「查」类与数据查询信号，text2sql 胜出。

task_id命中信号得分
text2sql_or_sql_planning检查、消耗、收入 + data_query +5最高
roi_or_campaign_analysis消耗（无 ROI 强信号）低
table_question无表/字段/meta 问法；data_query 时 -4负向
mi_roi360_analysis无 MI/ROI360 触发词0
其余 5 类无匹配 trigger0

若所有 task 得分 ≤ 0 → 回退 general_answer（不加载数仓知识，直接通用问答）。

    清单

    边界
  5. 5

Stage 6 · Provider

选定 Agent Provider + 任务档位

build_agent_provider_registry().select(route.task_id) 当前默认走 PI RPC Agent。同时根据 task_profile 解析 prompt_block、max_turns、工具预算。

  • Provider PiRpcAgent（pi_agent.py）
  • Profile live_sql — SQL 必须带证据链；禁止把 SELECT 1 当业务答案
  • 工具 runtime/tools/data_query.py → mc / ck / freshness
# agent.py _prepare_with_provider 同步完成（在 PI 启动前）

Stage 7 · first_read

按任务清单拉取协议摘要（前 5 个文件 × 2000 字符）

read_first_read_contents(route) 遍历 RouteDecision.first_read，逐个 _safe_read(path, max_chars=2000)。失败/不存在则跳过，不阻断流程。

  • 读 knowledge/agent_knowledge/policies/SQL写作业务协议.md
  • 读 knowledge/agent_knowledge/policies/SQL表路由协议.md
  • 读 da_assets/analysis_sop/PI查询执行复核护栏.md
  • 读 knowledge/agent_knowledge/policies/游戏核心指标口径语义.md
  • 读 knowledge/agent_knowledge/semantic_contract/model.json（摘要截断）
  • 读 da_assets/index.yaml（索引，非 SQL 正文）
  • … 其余 first_read 条目同理，最多 5 个文件进入本段

注意：first_read 在 build_knowledge_context_parts 里是最后拼入的段（见阶段 11），但逻辑上代表「任务级必读协议」层。

Stage 9 · Query Guidance

问题级硬护栏 — 在通用表卡之前注入

query_specific_guidance() 检测问题模式。本问题命中 _is_spend_revenue_query + kcolb_tsalb → 注入 BB 消耗+收入专用路由提示，优先级高于通用 excerpt。

  • 口径 自然日发生 vs cohort 回收 — 禁止混日期语义
  • 消耗 ads_market_tj_ad_spend_active_v2 · active_date + bundle_id
  • SDK收入 ads_market_tj_ad_sdk_revenue_attributed_di · dt vs active_date
  • DA行为收入 ads_market_device_camp_dau_behavior_di · 无消耗字段
  • 禁止 kcolb_collection / DT 表族因含 cost/revenue 被误选

Stage 13 · Execution

PI 多轮工具调用 → 带证据的最终回答

知识上下文只指导「怎么查」；真实数值来自 MC/CK 工具。本问题典型执行序列：

  1. 1
    freshness / max(dt)对 spend + revenue 候选表做分区探测
    probe
  2. 2
    smoke 小窗口验证 bundle_id、active_date、国家过滤行数非零
    smoke
  3. 3
    业务 SQL分别查 26 日消耗与自然日收入（或声明 cohort 口径）
    SQL
  4. 4
    0 行诊断若 row_count=0 继续拆过滤条件，禁止用 probe 冒充答案
    护栏
  5. 5
    纯文本总结数值 + 口径 + 表分区 + freshness_status + 风险说明
    answer
  6. 6
    落库与 SSEstore_exchange → event: answer → job done → query_records 回填
    DB
