# Data Agent 意图识别与任务路由

> 适合读者：业务、DA（数据分析师）、数仓、投放、管理同学
> 场景：了解用户提一个问题后，Agent 是怎么判断"这是什么类型的问题"，再决定读哪些知识、走哪条分析流程

## 一句话说明

用户问题进来后，Agent 先做一次**意图识别**：判断这是投放 ROI 问题、还是查表问题、还是要写 SQL、还是 MI 报表分析……判断的**主路径是确定性的关键词打分，不是让大模型自由分类**。这样同一个问题每次都会稳定地走到同一条分析通道，结果可记录、可复查、可回归。大模型只在拿不准时作为兜底，代码默认关闭；实际环境配置需另行核验。

## 一、为什么不用大模型直接分类

最直觉的做法是"把问题丢给大模型，让它说这是什么类型"。这套系统故意没有把它作为主路径，原因是：

| 痛点 | 说明 |
|---|---|
| 结果不稳定 | 同一个问题，大模型这次判成 ROI 分析、下次判成写 SQL，线上行为无法复现 |
| 无法复查 | 出错时只能看到"它选了 A"，看不到"为什么选 A、差点选了什么" |
| 无法回归 | 每次改动都要重新人工验证，没法用固定用例守住路由质量 |
| 有延迟和成本 | 每个问题都多一次大模型调用 |

所以主路径设计成**确定性打分**：每种问题类型预先声明好触发信号，问题进来按信号打分，最高分就是识别结果。这条路径零大模型调用、毫秒级、可以写进日志逐条复查。

## 二、Agent 认识哪些"问题类型"

系统把业务问题归成一份**任务路由清单**（目录 `task_routes/`，可以理解为"问题类型目录"），当前有 18 种类型，按业务域分组：

| 业务域 | 包含的问题类型（举例） |
|---|---|
| 数据与 SQL 基础 | 查表字段、选表、写 SQL、数据是否到齐 |
| 投放 ROI 与 Campaign | ROI/消耗/DNU 分析、红黄线双日复盘、Google Ads 变更、MI 报表分析 |
| 变现与产品实验 | 广告变现拆解、玩家行为/留存/版本实验 |
| 点位与素材 | 点位 S2S 回传、素材效率 |
| 知识入库与治理 | 报告入库、知识治理、表准入（仅内部维护用） |
| 问答链路复核 | 执行日志、回归样本复核（仅内部维护用） |

每种类型只是一个轻量入口，命中之后才会去加载它自己的详细配置（该读哪些政策、哪些数据资产目录、输出要注意什么）。没命中的类型不会被加载，控制面始终保持很小。

## 三、意图识别怎么打分

问题进来后，和每种类型的声明信号逐一比对，四个来源累加成一个分数：

| 打分来源 | 分值 | 含义 |
|---|---:|---|
| 命中"典型问法"例句 | +1 / 条 | 每种类型预置了几条代表性问法 |
| 命中"正向信号词" | +2 / 条 | 这种类型特有的关键词 |
| 命中"排除信号词" | −2 / 条 | 出现这些词说明**不该**是这种类型 |
| 命中"补充关键词表" | +1 / 条 | 工程侧维护的一批高频词 |

匹配时有防误伤处理：像 `roi` 这种很短的英文词，要求前后是词边界，避免把 `android` 里的 `roi` 也算命中。

**光靠基础分还不够**，真正拉开差距的是一批**判别规则**。当系统识别出某种明确意图时，会一边给目标类型大幅加分，一边把容易抢单的相邻类型压低。举个最典型的例子——当判断出"用户只想要 SQL 语句、不要分析结论"时：

```
判定为"只要 SQL"
  → 写 SQL 类型            +10 分
  → ROI 分析类型            −8 分（压制，避免抢单）
  → 变现/产品实验类型        −8 分（压制）
```

ROI 分析、查表、表准入、数据底座巡检等场景都有各自的这类成对规则。所以实际的意图识别不是简单的关键词计数，而是一套人工编码的判别逻辑，专门解决"相似问题容易走错通道"的问题。

如果所有类型的最高分都 ≤ 0，说明这问题不属于任何已知业务类型，Agent 直接落到"通用回答"，不调用任何数据工具，也不会硬凑一个类型。

## 四、置信度：不是概率，是保守的三档

打出来的分数不是概率，所以系统再把它换算成三个档位，作为后续"要不要兜底"的依据：

| 情况 | 置信度档位 |
|---|---|
| 冠军和亚军分差很小（咬得紧） | 低 |
| 分够高，且明显领先亚军 | 高 |
| 其余 | 中 |

这里有个刻意保守的设计：**只要冠亚军咬得紧就判为低置信，哪怕冠军绝对分很高**。因为分高但两个类型难分伯仲，恰恰说明这个问题本身模糊，需要兜底或澄清，而不是自信地冲进某一条通道。

## 五、拿不准时的两条兜底

当置信度偏低时，系统有两条兜底，一条常开、一条默认关：

| 兜底方式 | 状态 | 做什么 |
|---|---|---|
| 补充候选表提示 | 常开 | 额外做一次目录关键词搜索，把最相关的几张表作为"参考线索"放进上下文，帮 Agent 选表；有严格的篇幅上限，不挤占正常预算 |
| 大模型兜底选类型 | 默认关 | 把问题和精简版类型清单给大模型，让它从**白名单内**选一种或回"都不匹配" |

大模型兜底这条特别强调安全边界：它只能在允许线上用户访问的类型里选，选中后仍然走该类型原本的知识读取规则和输出约束，**边界一分都不放松**；一旦超时或出错，就退回确定性打分的结果。当前它是"写好但没启用"的状态，即使启用也会先用**影子模式**（只记录大模型的意见、不真正改变路由）观察一段时间，确认稳定后才逐步启用。

## 六、选定类型之后：还有一层"子话题"识别

选中一个大类型只是第一步。系统接着读这种类型的详细配置，里面还挂着若干**子话题规则**——同样用问题里的关键词再匹配一次，命中哪个子话题就追加读取对应的专项政策。

比如同样都进了"写 SQL"这个大类型，问示例产品的核心指标和问 Game Top 的玩法数据，会追加读取不同的业务政策文件。这样既保证大类型稳定，又能让不同细分场景读到最贴合的口径。

## 七、多轮对话里的意图继承

以上讲的是"单个问题怎么识别"。在连续对话里，还有一层**轮次判断**：这一轮到底是全新问题、还是在追问、纠正、切话题。当前主链会在高置信追问或纠正时注入有限原始历史文本后再识别；结构化的产品、时间、口径状态尚未在所有入口完成持久化闭环。

这一层的机制（规则层 + 大模型兜底、会话状态版本化）在专门文档里详细讲，这里不展开，见 [多轮对话与上下文继承.md](./多轮对话与上下文继承.md)。

## 八、识别之前，还有几道预处理

问题在进入意图识别之前，会先过几道轻量处理，都是为了让识别更准：

- **写操作拦截**：用户如果说"帮我停投/改预算"，直接按只读边界挡回，不进入分析流程。
- **长背景剥离**：用户粘贴一大段背景时，先把核心问题摘出来做识别，背景另作辅助，不干扰打分。
- **多问题拆分**：一句话里塞了好几个问题时，拆开分别识别、分别回答再合并。

## 九、为什么能复查

每次意图识别都会把**前几名类型的得分、各自命中了哪些信号、触发了哪些判别规则**一起记录到运行痕迹里。所以线上一旦出现"这个问题为什么走错通道"，能直接翻出打分明细，看到是哪个信号或哪条规则导致的，而不是只能猜。这也是这套确定性设计相比"纯大模型分类"最实在的好处。

## 十、当前能力边界

| 能做 | 不能做 / 边界 |
|---|---|
| 确定性识别 18 种业务问题类型，毫秒级、可复查 | 不追求"理解任意开放式问题"，超出已知类型就落通用回答 |
| 用判别规则解决相似问题走错通道 | 判别规则是人工维护的，新场景需要人工补信号 |
| 低置信度时补候选表线索 | 大模型兜底默认关闭，启用也先影子观察 |
| 连续对话里对高置信续问注入有限历史再识别 | 结构化 checkpoint、并发恢复和长会话压缩尚未完成主链闭环（见多轮文档） |
| 线上用户只暴露业务类型，内部工程类型不可见 | 类型的暴露范围由配置控制，不对线上放开工程通道 |

意图识别只负责"判断问题类型、决定读什么"，不负责给出投放动作。识别再准，最终的阈值、放量、停投等决策仍由业务同学拍板——这是产品边界，不是能力缺失。
