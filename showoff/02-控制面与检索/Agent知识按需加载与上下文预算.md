# 知识库变大，单次问答成本为什么不线性上涨

> 汇报定位：给业务、DA、数仓、投放和管理同学。说明投放知识库持续变厚时，Data Agent 如何控制单次问答塞给模型的资料量。

## 一句话说明

知识库可以持续变厚；单次问答只带轻量导航与路由，再按问题类型命中后取资料，不把整库塞进每一次问答。

## 为什么需要这件事

知识库越做越厚是好事：表说明、口径规则、已验证 SQL、复盘案例都在沉淀。但如果每次提问都整库塞给模型，会同时踩三个坑：

1. **变贵**：资料越多，单次消耗越大。
2. **变慢、抓错重点**：无关资料淹没关键信息。
3. **不可扩展**：每增一张表，每次问答都跟着变重。

目标：知识库可继续补，单次问答只看这个问题真正需要的那一小部分。

## 一个问题的资料加载路径

```mermaid
flowchart LR
  Q[一个投放数据问题] --> Boot[开场常驻<br/>导航 + 路由索引]
  Boot --> Route[按问题类型分流<br/>只取这一类任务清单]
  Route --> Hit[命中具体表 / 口径<br/>才读对应说明卡]
  Hit --> Ans[带证据和数据时效的回答]
```

要点：

- 开场只带轻量「导航 + 路由索引」，用来定位问题属于哪一类。
- 一类问题对应一个任务文件；命中后才读该类的先读清单与允许资产。
- `ai_hive/`、`ai_ck/` 里的表说明卡永远是命中哪张读哪张，不整包加载。
- 绝大部分资料在库里，但不进每一次问答。

## 历史瘦身测量（不是当前状态）

曾在一个历史资产快照中，把开场常驻从偏重清单压成只留轻量导航，重索引与任务规则改为用到才取：

| 项 | 改前 | 改后 |
|---|---|---|
| 开场常驻 | 约 224 KB（含重索引） | 约 54 KB（轻量导航） |
| 路由 | 大块任务规则一起读 | 路由索引 + 命中的那一个任务文件 |
| 表说明卡 | 有进开场的风险 | 命中才读单张 |

这些数字只说明当时的改造方向，不可作为当前 Runtime 的预算、资产规模或成本结论。当前总成本仍会随模型工具调用、读取内容和查询轮次变化；原则是固定 bootstrap 不随全库资产规模线性增长，增量知识进入按需层。

## 能力与限制

**能力**

- 按问题类型分流，只取相关任务资料。
- 表卡、口径、已验证 SQL 等重资产按需读取。
- 改路由或知识后，有门禁检查分流是否漏项、是否指向失效资料。

**限制**

- 只读分析：解释、拆解、校验、提示风险；不自动停投、放量、改预算。
- 数据未到齐时提示延迟，不把空结果或过期数据当业务变差。
- 阈值、投放动作、预算策略由业务负责人拍板。
- 本文讲的是资料加载方式与成本控制，不是业务口径结论。
