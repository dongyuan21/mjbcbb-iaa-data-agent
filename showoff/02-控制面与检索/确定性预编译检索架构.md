# 默认预编译先验与受治理探索架构

> 汇报定位：给技术同学、架构评审或外部交流。说明 Data Agent 在封闭域中使用 route-scoped 初始先验和受治理工具读取知识。
> 更新：2026-08-02

## 概览

用户问题进入后，Python 按 route 组装初始先验。模型后续仅能通过 Runtime 登记工具读取知识或执行只读查询，不能访问任意文件。

代码默认路径是 `DATA_AGENT_EXPLORATION_MODE=off`，但某个环境的实际配置必须以实时部署核验为准。它不再是唯一永久路径：已实现的探索模式把它定义为**完整覆盖时的快路径**。只有 typed execution plan、freshness 与所需 claim 都完整覆盖，才可直接结束；跨域、开放题或覆盖不足时，`on` 模式会以 slim prior 加受治理的只读知识工具继续取证。该模式尚未通过真实 A/B 与 Test 灰度，不应据本文推断已经启用。

## 流程

```
用户问题
  │
  ▼
Python KnowledgeRouter（关键词集合评分）
  │  ← 50+ 启发式 _looks_like_* 函数
  │  ← 对 18 条 task_route 的 trigger_examples 做 token 交集评分
  │
  ▼
命中 task_route（如 roi_or_campaign_analysis）
  │  ← 只加载这一条路由的 first_read / allowed_assets / output_guardrails
  │
  ▼
5 通道预编译上下文（带 context_budget 机械上限）
  │  ┌─ 30%  route 策略文件（first_read 精确路径列表）
  │  ├─ 20%  表卡摘要（按 token overlap 选中具体表）
  │  ├─ 20%  verified SQL（按 tag/title 匹配）
  │  ├─ 15%  语义契约切片（metrics / joins / entities 命中条目）
  │  └─ 15%  查询指引（route 专属查询护栏）
  │
  ▼
组装 Runtime messages
  │
  ▼
MinimalToolLoop 执行（固定 9 个受治理工具，零任意文件系统访问）
  ├─ MC / CK 只读查询 + freshness
  ├─ catalog + DataContractView + policy
  └─ semantic contract + verified SQL 检索/读取
  │
  ▼
带证据链的结构化回答
```

## 四个核心特征

| 特征 | 说明 |
|------|------|
| **确定性先验** | 同一个问题 + 同一份知识库 → 同样的 route prior 和初始上下文；后续工具选择仍可能有模型差异。 |
| **预编译 + 按需读取** | `off` 先提供较完整上下文，`on` 使用 slim prior；两者都只允许通过受治理工具继续取证。 |
| **精确白名单** | 每条 route 的 `first_read` 是手工维护的精确文件路径列表，不是模糊匹配。 |
| **机械限幅** | `context_budget`（默认 30K chars，最大 120K）硬性限制注入量，避免上下文膨胀。 |

## 为什么不用 RAG（向量召回）

| RAG 的问题 | 确定性预编译的解法 |
|------|------|
| 表卡被切成 chunk 后，`query_rules`、`known_pitfalls`、`join_keys` 分散到不同 chunk，LLM 看不到完整约束 | 表卡作为整体加载，约束完整不丢失 |
| Embedding "消耗" 可能同时命中 5 张不相关表的消耗字段 | 路由先确定任务类型，再只加载该任务关联的少数表 |
| Chunk 没有结构标注，LLM 需要自己判断哪些是 must_filter、哪些是 pitfall | YAML 字段明确标注语义角色，LLM 直接消费 |
| 更新一张表卡需要重新 embedding 全部 chunk | YAML 修改即生效，git diff 可审计 |
| 无法做字段级门禁 | `check_table_card_quality.py` 验证每张卡的字段完整性 |

**适用前提**：知识域封闭、问题模式可枚举、需要 precision 而非 recall。

## 为什么不用 Agentic Grep（LLM 自主搜索）

| Agentic Grep 的问题 | 确定性预编译的解法 |
|------|------|
| LLM 可能搜偏、遗漏关键文件 | 白名单确保关键文件不遗漏 |
| 多轮 tool call 消耗大量 token 和时间 | Python 本地评分，毫秒级完成 |
| 搜索路径不确定，难以回归测试 | route 决策可复现；当前用例数与结果必须读取最新门禁报告 |
| 搜索结果不受 scope 控制，可能读到 raw/draft | `never_default_recall` + `allowed_assets` 严格隔离 |

**注意**：已退役的外部命令执行链已物理移除。当前模型只能调用 Runtime registry 登记的 9 个进程内工具，不能访问任意文件系统。

## 与两种主流方案的定位对比

```
                    正确性优先 ←──────────────→ 覆盖率优先
                         │                         │
  确定性预编译 ●─────────┤                         │
  （本系统）            │                         │
                         │          Agentic Grep ──● 
                         │         （Cursor/Claude Code）
                         │                         │
                         │              Vector RAG ●──
                         │            （通用问答/开放域）
```

- **确定性预编译**：适合封闭域、高 precision 要求、知识可枚举
- **Agentic Grep**：适合开放代码库探索、不可预知的问题形态
- **Vector RAG**：适合海量非结构化文档、通用问答

## 行业参考

| # | 来源 | 关键结论 | 链接 |
|---|------|---------|------|
| 1 | Anthropic: Contextual Retrieval (2024) | 知识库 <200K token 时，直接把全部塞进 prompt 比 RAG 效果还好。BM25+embedding 混合比纯 embedding 好 49%。 | https://www.anthropic.com/research/contextual-retrieval |
| 2 | Anthropic: Building Effective Agents (2024) | "Optimizing single LLM calls with retrieval and in-context examples is usually enough"——不要过度工程化 | https://www.anthropic.com/research/building-effective-agents |
| 3 | Microsoft GraphRAG (2024) | Naive RAG 两大失败模式：①无法跨文档 connect the dots ②无法做整体性概括。结构化知识图稳定优于 chunk RAG | https://arxiv.org/abs/2404.16130 |
| 4 | Agentic RAG Survey (arXiv 2501.09136, 2025) | 传统 RAG "constrained by static workflows and lack adaptability for multi-step reasoning" | https://arxiv.org/abs/2501.09136 |
| 5 | Sourcegraph/Cody 实践 (2024) | 尝试 embedding 后主动放弃，回归 Jaccard keyword 匹配。原因："adding irrelevant context can make response quality worse"——precision > recall | https://sourcegraph.com/blog/the-lifecycle-of-a-code-ai-completion |
| 6 | Simon Willison: Search-Based RAG (2024) | 全文关键词搜索（SQLite FTS + OR）做 RAG，效果好且 1 小时搭完，比 embedding 简单 | https://simonwillison.net/2024/Jun/21/search-based-rag/ |
| 7 | LangChain: Agentic RAG with LangGraph | Corrective-RAG + Self-RAG：检索后评分→不相关则重写 query→再检索。本质是加反馈环 | https://www.langchain.com/blog/agentic-rag-with-langgraph |

### 参考文献适用性评估：Code Agent vs Data Agent

上述参考多出自 Code Agent 领域，并非全部直接对口。以下区分适用程度：

| 参考来源 | 对本系统适用程度 | 原因 |
|------|------|------|
| Sourcegraph "precision > recall" | ✅ 直接适用 | 不管 code 还是 data，加载错误上下文都会降低回答质量。表卡 `must_filter` 如果被错误召回的表覆盖掉，后果更严重 |
| Anthropic 200K 规则 | ✅ 直接适用 | 这是通用结论，和域无关 |
| GraphRAG "结构化优于 chunk" | ✅ 直接适用 | 我们的 `semantic_contract` 就是 mini Knowledge Graph |
| Claude Code grep 模式 | ⚠️ 部分适用 | Code agent 的文件量大（10K+ files），我们的知识量小（~200 files），不需要 agentic grep 的理由比 code 场景更充分 |
| Cursor/Windsurf 实践 | ⚠️ 启发性 | 它们的确定性索引（AST/符号表）对应我们的 `catalog.yaml`，思路一致但实现不同 |

### 更对口的参考：Text2SQL / Data Agent 方向

本系统本质是 **Schema Linking + Task Routing + Constrained SQL Generation**，不是通用问答。以下是该领域的核心参考：

| 来源 | 关键结论 |
|------|---------|
| BIRD benchmark (2023) | Text2SQL 最大失败原因不是 SQL 生成错误，而是选错表/字段。schema linking（选表）准确率决定最终 SQL 准确率 |
| DIN-SQL (2023, arXiv 2304.11015) | 将 Text2SQL 拆成 schema linking → query classification → SQL generation 三步，schema linking 用确定性过滤比 embedding 检索效果好 |
| C3 SQL (2023) | "Clear Prompting, Calibration, Consistency"——用 schema 结构化提示比让 LLM 自己从 embedding 召回的 chunk 里找表效果好 |
| Salesforce LOTUS / TAG (2024) | Table-Augmented Generation：对结构化数据，先路由到正确表再生成 SQL，比把表切 chunk 做 RAG 准确率高 20%+ |
| 本系统回归测试 | 路由和知识门禁有独立回归；整体结果、freshness blocker 和资产完整性必须以最新 `eval/agent_regression/Agent回归报告.md` 为准 |

**该领域的共识**：确定性 schema filtering > embedding 检索。
