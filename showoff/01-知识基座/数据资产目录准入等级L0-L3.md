# 数据资产目录 状态与读取标签（L0-L3）

> 汇报定位：解释为什么一张 MaxCompute / Hive / ClickHouse 表不能只靠 DDL（建表语句）就进入 Agent 默认召回，以及它要经过哪几级才能被 Agent 安全使用。
> 适合听众：DA、数仓、投放分析同学，以及需要理解"Agent 为什么不会乱查表"的业务同学。
> 权威依据：`数据资产目录/engineering_artifacts/Hive表准入标准.md`、`数据资产目录/engineering_artifacts/ClickHouse表准入标准.md`。
> 时效边界：本文说明共通的准入思路，不是数据资产目录数量、门禁结果或某一张表的实时准入结论。具体对象必须回到对应库的准入标准、catalog 和最新验证记录判断。

## 一句话说明

DDL（建表语句）只能证明"表有这些字段"，证明不了"一行代表什么、为什么能和别的表 join、有哪些看不见的坑"。数据资产目录 使用一个 `documentation_status` 表达资产的完整度、验证程度和当前可用边界；L0-L3 只是帮助人沟通的读取标签，不是另一套并行状态。

## 为什么需要分级

如果只靠 DDL，Agent 写 SQL 时会踩这些坑：

| DDL 看得出来的 | DDL 看不出来的 |
|---|---|
| 字段名、字段类型 | 一行代表什么（grain，粒度） |
| 分区字段叫什么 | 分区字段的业务含义（`示例产品` vs `active_date` vs `event_date` vs `revenue_date` 不能混用） |
| 表在哪个 project | 这张表和那张表为什么能 join（关联键证据） |
| 字段注释 | 字段注释会误导（注释写"收入"但实际是"含退款的毛收入"） |
|  | 哪些字段是 PII（个人敏感信息），不能输出明细 |
|  | 比率指标（ROI、CTR、CPI）跨维度汇总要重算，不能直接相加 |
|  | 生产血缘 join 不等于分析 join（表 A 灌进表 B，不代表查业务问题时该用 A join B） |

**粒度（grain）是什么**：粒度回答"这张表的一行数据代表什么"。例如：

| 表 | grain（粒度） |
|---|---|
| `示例表` | `install_date × bundle_id × project × os_system × media_source × country` —— 一行 = 一个安装日期×包体×项目×系统×媒体×国家的组合 |
| `示例表` | `bundle_id × activity_date × media_source × country × os_system` —— 一行 = 一个包体×活跃日期×媒体×国家×系统的组合 |

粒度写不清，Agent 就会把"日级表"当"小时级表"查，或者把"设备级明细表"当"聚合表"用，跑出错口径的数。

## 统一状态

| `documentation_status` | 可用边界 | 必备条件 |
|---|---|---|
| `stub`（约等于 L0） | 只表示发现过这张表，**禁止写 SQL** | 表名、project、发现来源、待补原因 |
| `partial`（约等于 L1） | 可查已明确字段和分区，**不能默认复杂 join** | DDL / PyODPS schema、字段注释、分区、grain、source_docs 的部分证据 |
| `complete`（约等于 L2） | Agent 可生成受限 SQL，并说明风险；不等于完全验证 | `partial` + `query_rules`、PII、`join_keys`、`known_pitfalls`、安全 `example_queries` |
| `partial_verified`（L2 与 L3 之间） | 只能按已验证范围使用，并保留待确认项 | `complete` + 小窗口、样例或部分对账证据 |
| `verified`（约等于 L3） | 可进入高频默认分析或语义层候选 | 关键口径、样例、新鲜度和证据链完成，并有 owner / DA / 数仓确认或 verified SQL |
| `deprecated_stale` | 排除当前事实和默认召回，仅供追溯 | 明确的停用或过期决策 |

**关键规则**：`complete` 不等于 `verified`；`partial_verified` 也不等于 `verified`。导入 DDL、字段数量或 schema 成功不能自动把状态写成 `complete` 或更高状态。MaxCompute / Hive 是事实源，默认召回和语义晋升必须比 ClickHouse 更保守。

> 上表为面向汇报的共同抽象。Hive 与 ClickHouse 的 L1/L3 证据要求并不完全相同；实际准入以各自的权威标准为准，不能用本表替代具体库的检查清单。

> **当前收口边界**：文档完整度、可查询性与证据可信度不能混成一个状态。当前工程仍在收敛数据资产目录、catalog 与 Runtime registry 对同一资产的授权语义；在该门禁闭环前，不能仅凭 `documentation_status` 宣称某张表已经获得所有 Runtime 入口的一致授权。见 [`TODO/归档/2026-08-07_知识状态Runtime授权收口/知识状态与Runtime授权一致性收口.md`](../../TODO/归档/2026-08-07_知识状态Runtime授权收口/知识状态与Runtime授权一致性收口.md)。

## 数据资产目录必填区块

| 区块 | 要求 | 为什么 |
|---|---|---|
| `table` | `fqn`（全限定名）、`alias`、`layer`、`domain`、`one_line_summary` | Agent 选表时的身份证 |
| `grain` | 一行代表什么，日期和维度粒度必须写清 | 防止把日级表当小时级表查 |
| `partitions` / `date_fields` | `示例产品`、`hour`、`active_date`、`event_date`、`revenue_date` 等含义不能混用 | 防止日期口径错配 |
| `query_rules` | `must_filter`、PII 子集、扫描窗口、使用注意 | 防止无界扫描大表、输出 PII 明细 |
| `join_keys` | 只写推荐分析 join；必须带 evidence 或 TODO/待确认 | 防止把生产血缘 join 当分析 join |
| `known_pitfalls` | DDL 看不出的坑；不知道就写待确认，不硬编 | 防止字段注释误导、比率汇总出错 |
| `example_queries` | 至少一条小窗口、带分区、不输出 PII 明细的安全样例 | Agent 生成 SQL 时的安全模板 |
| `source_docs` | 只引用可追溯文件；raw / draft 只能作为线索 | 防止把草稿当事实 |

## 证据边界（什么能当事实，什么只能当证据）

| 材料 | 放哪里 | 能否直接当事实 |
|---|---|---|
| DDL / PyODPS schema / DataWorks 字段 | 数据资产目录 `columns` / `source_docs` | 只能证明结构 |
| 生产 SQL / run 日志脱敏摘要 | `da_assets/raw/` 或 `数据资产目录/audit_archive/evidence/` | 只能作证据 |
| 小窗口验证 / 对账 SQL | `da_assets/verified_sql/` | 通过门禁后可作为高置信证据 |
| 当前 freshness（数据新鲜度） | `freshness_snapshot.json` | 刷新后才可判断当前状态 |
| 业务阈值 / 官方口径 | `knowledge/` 或 `semantic_contract/` | 必须 owner / DA 确认 |

## 标准流程

```
1. 明确目标表、用途、优先级和是否要进入 Agent 默认分析
2. 用 maxcompute-dataworks 或 PyODPS 获取 schema；涉及当前状态时先 live probe
3. 新建或更新 agent_knowledge/tables/<table>.yaml，补齐表身份、grain、分区、字段、source_docs
4. 按 PII_POLICY.yaml 盖章 PII
5. 补 query_rules、join_keys、known_pitfalls、example_queries
6. 证据不足的 join / pitfall / 官方口径写 TODO，不伪装成 confirmed
7. 重建 catalog 并跑门禁
```

门禁命令：

```bash
python3 tools/scripts/rebuild_数据资产目录_catalog.py
python3 tools/scripts/check_da_metadata_quality.py
```

如果影响高频问答、语义层或 verified SQL，再跑：

```bash
python3 knowledge/engineering_artifacts/semantic_contract/build_model.py
python3 knowledge/engineering_artifacts/semantic_contract/eval/compose_sql.py
python3 eval/agent_regression/run_regression.py
```

## 谁能决定什么

| 类型 | 脚本 | Agent | 人 |
|---|---|---|---|
| YAML 解析、catalog 对齐、PII 漏标 | 可以检查 | 可以修 | 不需要 |
| schema / 字段类型 / 分区 | 可以采集 | 可以入卡 | 不需要，除非权限不足 |
| grain、日期语义、query_rules | 不能自动决定 | 基于证据整理 | 争议时确认 |
| join_keys、known_pitfalls | 不能猜 | 有证据才写 | 证据不足必须确认 |
| `verified` / 默认口径 / 阈值 | 不能决定 | 整理候选和证据 | 必须确认 |

## 常见反模式（不要这么做）

- 只有 DDL 就标 `complete` 或 `verified`。
- 为清门禁硬补 join。
- 把生产血缘 join 当分析 join。
- 混用 `示例产品`、`active_date`、`event_date`、`revenue_date`。
- 把 raw 截图、旧报告或历史 snapshot 当当前事实。
- 输出设备 ID、IP、user_agent、token 或用户级明细。

## 如何确认当前状态

- 数据资产目录范围与状态：读取对应的 `数据资产目录/`、`数据资产目录/` catalog / 数据资产目录文件。
- 是否可默认召回或执行：同时核对数据资产目录状态、证据、route allowlist、DataContractView 与当前授权一致性门禁；不要把单一 `documentation_status` 当作最终授权结论。
- 当前质量门禁：重新运行 `python3 tools/scripts/check_da_metadata_quality.py`，不要用本文或旧报告中的数字替代本次结果。
