> 这是 Data Agent 的受维护架构索引：用稳定的责任边界解释系统从「数据源」到「Agent 输出」的主路径，也可直接用于汇报。

> 结构基线：执行主链为单一 Python Runtime + `MinimalToolLoop`。正文插图为 Excalidraw PNG；可编辑源在 [`架构图-excalidraw/`](架构图-excalidraw/)，mermaid 备份见 [`当前系统架构图-mermaid备份.md`](当前系统架构图-mermaid备份.md)。

## 如何保持它及时且稳定

这份图不以“最后更新日期”冒充新鲜度，而是按事实类型维护：稳定事实写在本文，易变事实只写权威入口。

| 事实类型 | 本文保留什么 | 当前事实去哪里确认 | 何时必须复核本文 |
|---|---|---|---|
| Runtime 主链、控制权与工具面 | 谁拥有状态、授权、执行和终态；固定工具面的边界 | `runtime/README.md`、`data_agent_plan/Runtime控制面架构/`、当前源码 | 接入、Worker、ToolLoop、SQL binding 或工具 registry 改动时 |
| 知识与路由治理 | 三层分工、资产状态边界、route 只是先验 | `AGENT_RETRIEVAL_MAP.yaml`、`task_routes/`、catalog 与语义合同 | 资产准入规则、默认召回或路由协议改动时 |
| 部署拓扑与环境状态 | 三服务需要一致这一约束 | `runtime/README.md`、山海实时版本/健康/smoke 证据 | 服务拆分合并、部署方式或发布验收规则改动时 |
| 表卡数量、freshness、回归结果 | 不固化数字；只说明应有门禁与证据 | catalog、`eval/` 最新报告、freshness 实时 probe / 快照 | 不因一次探测结果而改图；仅当指标定义或证据机制改动时 |

每次影响上表第一列的改动，在合入前都要做一次“本文是否仍成立”的复核：若责任边界或主路径变了，同步正文、Excalidraw 源与 PNG；若只变了运行状态，只更新其权威证据，不改架构图。这样“当前”指当前架构合同，而不是一张很快失效的运行快照。

## 一句话说明

Data Agent 工程不是平铺的脚本堆，而是按「**知识 → 控制 → 运行 → 评测**」四块展示视图构建的闭环：知识基座存事实，控制面决定先读什么，运行层用进程内 `MinimalToolLoop` 执行问答，评测闭环保证质量和精度。这里的四块仅用于汇报，**不对应** Runtime 权威架构中的 L1–L6；白盒责任边界见 [`从一个问题看懂Data Agent.md`](从一个问题看懂Data%20Agent.md)。

## 1. 系统全景（四层栈）

![图1 系统全景四层栈](%E6%9E%B6%E6%9E%84%E5%9B%BE-excalidraw/%E5%9B%BE1-%E7%B3%BB%E7%BB%9F%E5%85%A8%E6%99%AF%E5%9B%9B%E5%B1%82%E6%A0%88.png)

四层栈每一层只对一件事负责：

| 层 | 只负责 | 不负责 |
|---|---|---|
| 知识基座 | 存放事实（表卡、口径合同、已验证 SQL） | 决定什么时候读 |
| 控制面 | 决定先读什么、哪些可信、哪些禁区 | 跑 SQL、产出答案 |
| 运行层 | 执行问答、跑 SQL、流式输出 | 改知识、改口径 |
| 评测闭环 | 验收知识齐备性、SQL 正确性、线上行为 | 直接回答用户 |

运行层物理形态（与四层栈编号无关）：山海 Test 同 commit 三服务——API / Web、`runtime_worker`、Freshness Worker。执行主链是单一 Python Runtime，不经过外部 Node 执行器。

## 2. 知识基座内部的三层模型

每个知识库（ai_hive / ai_ck / knowledge）内部都按三层物理存放；`agent_knowledge` 是默认召回候选层，实际是否进入上下文还受 route allowlist、资产状态与 `first_read` 约束：

![图2 知识基座三层模型](%E6%9E%B6%E6%9E%84%E5%9B%BE-excalidraw/%E5%9B%BE2-%E7%9F%A5%E8%AF%86%E5%9F%BA%E5%BA%A7%E4%B8%89%E5%B1%82%E6%A8%A1%E5%9E%8B.png)

| 层级 | 用途 | 默认召回 |
|---|---|---:|
| agent_knowledge（Agent 知识层） | 日常问答、选表、写 SQL、解释口径 | 候选（仍受路由/状态/first_read 约束） |
| engineering_artifacts（工程沉淀层） | 构建、同步、探测、门禁、回归、快照 | 否 |
| audit_archive（审计归档层） | 来源追溯、历史探索、未晋升材料、证据 | 否 |

## 5. 运行层：一个问题如何变成答案

![图5 运行层问答主路径](%E6%9E%B6%E6%9E%84%E5%9B%BE-excalidraw/%E5%9B%BE5-%E8%BF%90%E8%A1%8C%E5%B1%82%E9%97%AE%E7%AD%94%E4%B8%BB%E8%B7%AF%E5%BE%84.png)

### 5.1 分层解释：每一步做什么

| 步骤 | 所在层 | 做什么 | 产物 / 约束 |
|---:|---|---|---|
| 1–3 | API 与任务层 | 接收问题、鉴权、写入完整 `request_payload`、submitted event 与 outbox | 同一请求可追踪；网络中断不丢失任务 |
| 4 | `runtime_worker` | 以租约领取 Job，防止多个 Worker 同时执行同一任务 | 状态从 `queued` 到 `running`，最终原子收口 |
| 5–6 | 控制面 | 识别问题类型、路由到任务协议；route 只做软先验 | 路由可记录、可复查；不要求用户预先选表 |
| 7 | 知识装配 | 按路由构建受控先验；需要 SQL 时，模型必须先通过工具成功读取 `DataContractView` | route 只做排序；合同读取记录才可进入服务端 SQL binding |
| 8–9 | 运行面 | 进程内 `MinimalToolLoop` 调用固定 9 个 Runtime 注册工具 | SQL 写入、投放平台写操作、任意文件系统访问均不开放 |
| 10–11 | 证据与交付层 | 同事务提交答案、trace、query record、job 终态与 SSE 事件 | 回答必须区分事实、推断、数据限制和人工决策项 |

主路径可记成：

```text
用户问题 → FastAPI / durable job → Redis 队列 → runtime_worker
  → KnowledgeRouter + route-scoped prior → MinimalToolLoop（固定 9 工具）
  → read_data_contract_view → 服务端 SQL L5 binding
  → SQL L5 binding → runtime/tools/data_query.py → MC / CK
  → MySQL job、trace、query_records、durable SSE events → 前端
```

Redis 只负责队列和唤醒，不是真相源。最终答案与终态以 MySQL 事务为准。

### 5.2 默认 `off`：主路径是「先路由，后一次性装配」

代码默认模式是 `DATA_AGENT_EXPLORATION_MODE=off`。某个 Test/Production 环境此刻的实际模式必须以实时部署配置核验；在 `off` 模式下，一个问题的初始知识路径是确定性的：

![图6 默认 off 主路径](%E6%9E%B6%E6%9E%84%E5%9B%BE-excalidraw/%E5%9B%BE6-%E9%BB%98%E8%AE%A4off%E4%B8%BB%E8%B7%AF%E5%BE%84.png)

这不是「先让模型在整个仓库里搜索，再决定读什么」。路由和资产边界先由控制面确定；模型只看到已经获准的上下文和只读工具面。若证据不足，答案会保留 `missing_source`、`incomplete` 或 `needs_decision`，而不是通过猜测补全。

### 5.3 哪里会循环，如何控制

循环只发生在 **`MinimalToolLoop` 的模型 ↔ 受控工具交换**，不是文件系统自由搜索循环。模型可建议 tool call；SQL 授权、预算、取消与终态仍由 Runtime 拥有。代码默认 `off` 且工具面稳定；某个环境是否运行 shadow、A/B 或 `on` 灰度，必须以本次运行与部署证据核验。

| 循环 / 重试点 | 触发条件 | 控制方式 | 终止方式 |
|---|---|---|---|
| Job 重投递 | Worker 暂时失联、租约超时或可恢复投递失败 | MySQL Job 状态、Redis outbox、租约 fencing | 已完成/失败的终态不可重复写入 |
| ToolLoop 多轮分析 | 需要执行已授权的只读 SQL 或知识读取 | 固定 9 工具 catalog、步数/时长预算、只读策略 | 证据足够、达到上限、连续无进展、取消或安全拒绝 |
| SQL 执行 | 模型请求 MC/CK 数据 | `DataContractView` 服务端 binding、SQL 白名单、写黑名单、PII 与分区守卫 | 成功获得证据；或明确返回错误/数据不足 |
| 探索型知识取证（已实现、默认未启用） | 仅未来受控模式下，已装配上下文覆盖不足 | 白名单资产、scope token、共享 run 预算、registry/hash 快照 | 预算耗尽、快照漂移 fail-closed、证据满足或安全拒绝 |

因此，系统不是「无限循环的 Agent」：每一类循环都有对象级身份、预算、时间、工具面与终态记录。循环失败也不能静默改用新资产或扩大权限。

运行层硬护栏（不靠提示词，靠代码强制）：

| 护栏 | 实现 |
|---|---|
| 只读前缀 | 只允许 select/show/with/describe 开头 |
| 写操作黑名单 | 拦 insert/update/delete/drop/alter/truncate/create 等 |
| PII 列黑名单 | 拦设备 ID/IP/user_agent 等，必须聚合 + GROUP BY |
| 分区列强制 | 大表必须带 dt/active_date 过滤 |
| DataContract binding | SQL 授权由服务端根据本轮成功读取的合同视图自动绑定；模型不能自带授权参数 |
| 固定工具面 | 9 个 Runtime 注册工具；route 只影响先验与提示，不充当工具权限 |
| 任务画像 | `live_sql` / `long_report` / `default` 分别有轮次与工具预算；以当前 runtime 配置为准 |

九个模型可见工具：`query_maxcompute`、`query_clickhouse`、`check_data_freshness`、`search_catalog`、`read_data_contract_view`、`read_policy`、`retrieve_semantic_contract`、`retrieve_verified_sql`、`read_verified_sql`。

### 5.4 旧执行链已移除

历史过渡链路已整体移除。生产主链不依赖 Node 作为执行路径；模型只能通过受控的 Python Runtime Tool Registry 调用固定九种工具。

## 7. 这套架构的边界

| 边界 | 对外表达 |
|---|---|
| 只读优先 | 当前系统先做分析和解释，不自动改预算、停投或放量 |
| 数据成熟度 | 数据未到时先提示延迟，不把空结果当业务变差 |
| 证据分层 | 原始材料、草稿只能作线索，已验证 / 已确认内容才能作默认事实 |
| 跨源处理 | MC 和 CK 分别查询，应用层对齐，不直接跨库 SQL join |
| 人类拍板 | 阈值、动作和策略仍由业务 owner（负责人）确认 |
| Runtime 权威 | 问题合同、预算、取消、SQL 授权与终态属于 Runtime；模型只提候选计划 |
| 部署一致性 | 山海三服务（API / Worker / Freshness）必须同 commit 部署，任一版本不一致 = deployment drift |

## 8. 当前能力边界（非实时状态面板）

| 能力 | 状态 |
|---|---|
| 知识基座 | 表卡、语义合同、政策与已验证 SQL 均有索引和晋升状态；具体数量以各 catalog/index 为准 |
| 控制面 | 通过 `AGENT_RETRIEVAL_MAP.yaml` 与 `task_routes/` 做受控路由；任务数量以当前 `task_routes/INDEX.yaml` 为准 |
| 运行层 | FastAPI、MySQL、Redis、`MinimalToolLoop` 与 Worker/Freshness 组成可恢复只读问答链路；环境状态必须以实时部署核验为准 |
| 评测闭环 | 以 `eval/` 和 `tools/scripts/` 中当前用例、门禁脚本及最新报告为准；历史 PASS/WARN 不能替代本次验证 |
| 探索型能力 | 已实现受控审计和离线门禁；代码默认 `off`。是否已开展 shadow、A/B 或 `on` 灰度必须读取本次运行与部署证据 |

> 本文是架构说明，不是实时运行状态、资产数量或质量结论。需要确认「现在有多少张表卡、最近回归是否通过、Test 是否健康」等问题时，应直接读取对应的 catalog、门禁报告或实时部署核验结果。
