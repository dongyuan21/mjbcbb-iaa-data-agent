## 适用边界

这个模板只解决“MI 口径够用版”的 Day0 ARPU 看数和输出，不要求完全复刻 DA 的首日 ARPU 异动报告。

可回答：

- 指定包体近几天 Day0 ARPU 是否下降。
- 下降主要来自 `revenue_0`、`total_registers` 还是 `total_media_installs` 变化。
- 异常集中在哪些 media / country / campaign。
- SDK 回收与 AF 回收是否给出不同判断。

暂不回答：

- `ad_source × ad_format` 的 eCPM / 展示次数精确归因。
- 产品桶 / 商业化桶完全复刻。
- 自动停投、放量、降预算。

如果需要继续归因到广告展示和 eCPM，转到 `da_assets/verified_sql/vsql_20260613_day0_arpu_anomaly_attribution.md`，用 `ARPU = 人均展示次数 × eCPM / 1000` 拆。

## 固定口径

| 项 | 口径 |
|---|---|
| 页面 | MI ROI360 |
| 必填过滤 | `active_date`、`bundle_id` |
| 预测版本 | 优先 `--forecast-version auto`；BB 走 V6，非 BB 走 MI 返回的 XY 系列 |
| 回收源 | 默认 `revenue_source=sdk`；AF 只作对照 |
| 成本 | 如涉及 CPI / ROI，默认折后消耗 `total_cost_zhe` |
| Day0 收入 | `revenue_0`，即 1 日收入 / `date_diff=0` 收入 |
| AF ARPU | `af_arpu = revenue_0 / total_registers` |
| Media ARPU | `media_arpu = revenue_0 / total_media_installs` |
| organic | 需要时同时看 `all` 与 `paid_nonorganic`；不要混成同一结论 |
| 观察窗口 | Day0 ARPU 趋势预检可先拉近 5 个 `active_date`；投放动作仍按 ROI 治理政策，冷启动至少观察 7 天 |

## 输入参数

| 参数 | 说明 |
|---|---|
| `bundle_id` | 必填，不猜包体 |
| `start_date / end_date` | 默认先看近 5 个成熟 `active_date`，异常归因再补 baseline |
| `media_scope` | 默认 `all`，投放复盘建议再跑 `paid_nonorganic` |
| `grain` | 默认先 `active_date,bundle_id`，再下钻 `media_source,country,campaign_name` |
| `revenue_source` | 默认 `sdk`，口径争议或对账时补 `af` |
| `compare_window` | 异动归因需要，日常预检可以先不填 |

## 查询顺序

### 1. 大盘趋势

先看包体日粒度，确认 Day0 ARPU 是否真的变动。

```bash
python3 tools/scripts/query_mi_roi360.py \
  --bundle-id "<bundle_id>" \
  --start-date "<yyyy-mm-dd>" \
  --end-date "<yyyy-mm-dd>" \
  --endpoint rows \
  --forecast-version auto \
  --media-scope all \
  --revenue-source sdk \
  --dimensions "active_date,bundle_id" \
  --metrics "revenue_0,total_registers,total_media_installs,af_arpu,media_arpu,total_cost_zhe,af_cpi,roi_0,roi_6,roi_29" \
  --limit 5000
```

判断：

- `af_arpu` 下降，且 `revenue_0` 下降幅度大于 `total_registers`，优先看回收 / 变现侧。
- `af_arpu` 下降，但 `total_registers` 大幅上升，先看新增结构变化和低价值流量占比。
- `af_arpu` 与 `media_arpu` 分歧明显，先解释 AF install 与媒体侧安装分母差异。
- `roi_0` 与 `af_arpu` 同向下降时，记录为 Day0 回收压力；是否动作仍看 campaign 生命周期和 ROI 红线。

### 2. 投放口径

再看付费非自然量，避免 organic 结构把投放判断稀释。

```bash
python3 tools/scripts/query_mi_roi360.py \
  --bundle-id "<bundle_id>" \
  --start-date "<yyyy-mm-dd>" \
  --end-date "<yyyy-mm-dd>" \
  --endpoint rows \
  --forecast-version auto \
  --media-scope paid_nonorganic \
  --revenue-source sdk \
  --dimensions "active_date,bundle_id,media_source,country,campaign_name" \
  --metrics "revenue_0,total_registers,total_media_installs,af_arpu,media_arpu,total_cost_zhe,af_cpi,roi_0,roi_6,roi_29,ipm" \
  --limit 5000
```

输出排序建议：

- 先按 `total_cost_zhe` 或 `total_registers` 找贡献大的对象。
- 再看 `af_arpu`、`roi_0` 是否同步变差。
- 日均消耗 `< 300 USD` 的 campaign 只能观察。
- 头部 campaign 接近 ROI 红线，输出 `needs_decision`，交给人决策。

### 3. SDK vs AF 对照

只在发现回收源可能影响结论时补跑 AF。

```bash
python3 tools/scripts/query_mi_roi360.py \
  --bundle-id "<bundle_id>" \
  --start-date "<yyyy-mm-dd>" \
  --end-date "<yyyy-mm-dd>" \
  --endpoint rows \
  --forecast-version auto \
  --media-scope paid_nonorganic \
  --revenue-source af \
  --dimensions "active_date,bundle_id,media_source,country,campaign_name" \
  --metrics "revenue_0,total_registers,total_media_installs,af_arpu,media_arpu,roi_0,roi_6,roi_29" \
  --limit 5000
```

判断：

- SDK 与 AF 同向下降：可以把方向判断写得更稳。
- SDK 下降但 AF 不降：标 `revenue_source_gap`，不要把 SDK 口径异常直接解释为投放质量劣化。
- AF 下降但 SDK 不降：说明 AF 对照口径异常或归因变化，默认仍以 SDK 为主。

## 升级到完整归因的条件

满足任一条件时，不停留在 MI 模板：

- 大盘或头部 campaign Day0 ARPU 连续下滑，且 `revenue_0` 明显下降。
- `af_arpu` / `media_arpu` 都下降，但安装分母没有异常放大。
- 需要判断素材、广告格式、广告源、产品桶或商业化桶。
- 业务要求解释“为什么 ARPU 下跌”，而不是只要 MI 看板上的异常对象列表。

升级路径：

1. 先引用本模板输出 MI 事实。
2. 再跑 `da_assets/verified_sql/vsql_20260613_day0_arpu_anomaly_attribution.md`。
3. 输出时明确区分 MI 看板口径与 DA 归因 SQL 口径。

## 安全规则

- 不保存 Authorization、cookie、token、SSO ticket。
- 查询结果只保留聚合摘要，不长期保存大量 campaign / adset / ad 明细。
- 不从截图或热力图反推精确数值。
- 不把 MI 预检结论升级成投放动作；动作仍受 ROI 治理政策和人审边界约束。
