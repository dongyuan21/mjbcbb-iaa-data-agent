## 预测主链路

Nexus ROI360 UA 主链路在 `backend/boards/internal/service/report/handler/roi/ua/roihandler.go`：

1. `batchQueryJoinAndForecast` 先做基础查询、right / retention join、spend / revenue reduce。
2. `NewForecastCondition` 从 filters 解析 `forecast_version`、`forecast_date`、`forecast_id`、`forecast_snapshot_date`、`bundle_id`、单值国家 / 媒体 / campaign 等。
3. `LocalRoiCompute` 用真实收入和成本先算已有节点 ROI。
4. `CallForecast` 要求维度同时包含 `active_date` 和 `bundle_id`，否则不调用预测。
5. `CallForecastRoi` 按版本分流到 XY 批量接口或 base 单行接口。
6. `ApplyForecastCorrection` 只在 `_纠偏` 版本启用，对预测段 ROI 乘纠偏系数。
7. `CallForecastRoi360Snapshots` 只在 metrics 选择 `roi_360_3d/7d/14d/30d` 时计算快照字段。
8. `ComputeForecastRevenue` 用最终 ROI 反推预测段 `revenue_N`。
9. `ApplyExtMetrics` 计算 LTV 与 LTV 倍率。
10. 展示层按 `index`、`roi_360_range` 和快照字段打 `#E0FFFF` 蓝底。

Agent 回答时要把这条链路说清楚，尤其不要把 “CK 最新分区 D360=0” 直接解释成 “MI 没有预测值”。

## forecast version 决策树

### 1. 显式筛选优先

如果请求里有 `forecast_version`：

- 该版本优先于默认版本。
- 如果后缀是 `_纠偏`，`NewForecastCondition` 会设置 `CorrectionEnabled=true`，并把版本名去掉 `_纠偏` 后继续请求预测服务。
- 行内会写回 `forecast_version`，用于解释不同包体 / 行的版本来源。

### 2. 未显式筛选时查默认版本

如果没有显式 `forecast_version`，Nexus 通过 `ForecastService.GetDefaultForecast` 查默认版本：

```text
prj_pag_list JOIN forecase_version_config
WHERE status = 1 AND mode = 'roi' AND is_default = 1
```

单包 options 返回该包所有可选版本；多包 options 取版本交集。默认值和 options 都可能随 MI 配置变化，Agent 不能硬编码 “所有包都是 v6”。

### 3. XY / base 分流只看版本前缀

`CallForecastRoi` 的分流规则很直接：

| version 形态 | 请求路径 | 说明 |
|---|---|---|
| `xy_` 开头 | XY batch | 走 `/api/v1/roi-forecast/run`，支持批量与 `roi_range` |
| 其它版本 | base request | 走 `/ltv_pred`，base 代码会清空 `campaign` 和 `roi_range` |

因此 `v6_sdk` 在当前 Nexus 代码中不是因为名字含 `sdk` 就走特殊 SDK 接口；它不以 `xy_` 开头，按分流规则进入 base request。模型内部是否使用 SDK 特征不是 Nexus 代码可证明的事实，只能说“MI 配置暴露了 `v6_sdk` 版本，Nexus 按版本名前缀选择调用路径”。

## 预测 request 字段

`buildForecastRequest` 组装预测请求时的主要字段：

| 字段 | 来源 / 规则 |
|---|---|
| `project` | `basics.ProjectStore[bundle_id]` 或默认版本配置里的 project |
| `version` | 显式 filter 或默认 forecast match |
| `bundle_id` | 行内 `bundle_id` 优先 |
| `media_source` | 行内值优先，其次单值 filter |
| `country` | 行内值优先，其次单值 filter |
| `convert_type` | 行内值优先，其次 filter |
| `campaign` | 行内 `campaign_name` 优先，其次单值 filter；base 请求会清空 |
| `data` | 已有真实 ROI 节点数组，来自 `LocalRoiCompute` |
| `start_dt` | 行内 `active_date`，格式化为 `YYYYMMDD` |
| `days_num` | 360 |
| `pre_model_day` | `forecast_snapshot_date` |
| `roi_range` | 主 ROI360 预测为 true；base 请求会清空 |

`LocalRoiCompute` 先用真实收入和成本算本地 ROI：

- 成本优先使用 `forecast_end_date_spend`，否则用 `cost_zhe`。
- 成本为 0 时跳过。
- `roi_N = revenue_N / cost * 100`，四位小数。
- `forecast_date` / `forecast_id` 可限制本地真实节点长度。

## index 与蓝底

预测结果写回时会记录行内 `index`：

```text
index = 已有本地 ROI 节点数 + date_diff 起点偏移
```

展示层根据 `index` 判断预测段：

| 字段 | 蓝底规则 |
|---|---|
| `roi_N` / `revenue_N` | 当 N >= `index` 时蓝底 |
| `roi_360_range` | 有值即蓝底 |
| `roi_360_3d/7d/14d/30d` | 快照预测字段，有值即蓝底 |
| summary 行 | 使用所有行最小 forecast index 判断 |

蓝底色固定是 `#E0FFFF`。蓝底代表“预测段 / 预测字段”，不是高 ROI、低 ROI、达标或异常。

## 纠偏链路

`_纠偏` 后缀只负责启用纠偏，不作为预测服务版本原样传下去。纠偏表：

```text
shucang_market.market_roi_obs_correction_coef_media
```

关键规则：

- `table_source` 使用去掉 `_纠偏` 后的版本名。
- key 需要 `bundle_id + media_source + active_date`。
- 只取 `state=1`。
- 同一个 bundle / media 取最新 `coef_dt`。
- `roi_N` 是 0-indexed，系数表 `target_day` 是 1-indexed，因此 `roi_6` 对应 `target_day=7`。
- 如果某个 day 没有系数，按“继承前面日期的比例往后顺延”。
- 只修正预测段，不修改真实段。
- `ComputeForecastRevenue` 在纠偏之后执行，所以预测收入会跟随纠偏后的 ROI 反推。

## 派生指标

### revenue_N

`ComputeForecastRevenue` 只在预测段填充收入：

```text
revenue_N = round(roi_N, 2) / 100 * cost_zhe
```

它只为本次查询需要的 `revenue_N` 或由 `roi_N` 隐含需要的收入字段补值。回答收入类问题时要说明这是由预测 ROI 反推，不是独立预测收入事实。

### LTV 与倍率

`ApplyExtMetrics` 在 ROI 最终就绪后计算：

- `ltv_N = revenue_(N-1) / total_registers`
- `ltv_360_2` 这类倍率走 ROI 比值，而不是两个 LTV 字段独立相除。

Day0 ARPU / LTV 分母仍按既有模板说明：要区分 `total_registers`、媒体 installs、AF installs 和页面字段。

## summary 降级边界

Nexus 代码里的阈值常量是 `summaryRowsThreshold = 5000`。

summary 行有两条路径：

| 行数 | 路径 | 风险 |
|---|---|---|
| `total <= 5000` | 拉 rows 后做行级聚合 | ROI / revenue / retention 可跟随行级预测 |
| `total > 5000` | DB aggregate | 会清空 `roi_*`、`retention_*`、`revenue_*` 等字段，避免不准确汇总 |

所以 “summary 没有 ROI360 / revenue_359” 不一定是预测失败，可能是大结果集触发 DB 聚合降级。排查时应缩小维度或改 rows 小窗口验证。

## roi_360_3d/7d/14d/30d 与 trend360

`roi_360_3d/7d/14d/30d` 是快照字段：

- 只有 metrics 选中时触发。
- 使用前 N 个真实 ROI 节点去预测 360 日 ROI。
- 写回单个字段，不修改主链路的 `index` / `forecast_version`。

`roi_trend_360` 是另一条 trend service 链路：

- 不是普通 `roi_359`，也不是快照字段。
- 只支持 `active_date`、`bundle_id`、`country`、`media_source` 等有限维度。
- `revenue_source=af` 时跳过。
- 有硬编码版本能力：BB / BB iOS / BBVN 支持 `v6`、`xy_v6`，其它包主要走 `xy_v5`。
- 结果写到 cell children，用于趋势曲线。

## 常见问题排查模板

### 问：D360 或 ROI360 是 0，是否说明真实回收为 0？

答题顺序：

1. 先区分 MI runtime forecast、CK 宽表和页面 summary。
2. 检查本次查询是否保留 `active_date + bundle_id` 维度；没有则主预测不会触发。
3. 检查 `forecast_version/options?bundle_id={bundle_id}`，确认版本是否支持当前包。
4. 检查是否为最新日、小包、夜间 20:00-05:00 预测落表窗口或 CK `update_at` 时序问题。
5. 检查成本是否为 0、真实 ROI 节点是否为空、summary 是否触发 `total > 5000` 降级。
6. 结论只能写“候选原因 / 待验项”，不能直接说真实 D360=0 或停投。

### 问：为什么蓝底和 CK 宽表不一致？

答题顺序：

1. 蓝底来自 MI runtime forecast 展示层 `#E0FFFF`。
2. CK 宽表是落表结果，有 `update_at`、`actual_roi_days` 和预测任务时序。
3. 如果 MI rows 蓝底已有值但 CK 最新分区为 0，要按“runtime 已出、宽表未落或未覆盖”的候选方向排查。
4. 需要给出验证时间、bundle、active_date、forecast version、revenue_source 和 CK 分区。

### 问：Campaign、包体、渠道会不会影响 ROI360 预测？

答题顺序：

1. 会。`bundle_id`、`media_source`、`country`、`convert_type`、`campaign_name` 都可能进入预测 request。
2. 但 base 请求会清空 `campaign` 和 `roi_range`，XY batch 支持 `roi_range` 和 campaign 字段。
3. 所以 campaign 影响要结合当前 `forecast_version` 是否走 XY 族来判断，不能只看页面筛选项。

### 问：v6、v6_sdk、xy_v5 到底选哪个？

答题顺序：

1. 先查当前包体 options。
2. 显式 filter 优先；无 filter 走 MI 默认版本配置。
3. `xy_` 前缀走 XY batch，其它走 base。
4. `v6_sdk` 是 MI 配置暴露的版本名，Nexus 只能证明它按 base 路径调用；模型内部 SDK 规则需要继续研究预测服务，不可脑补。
