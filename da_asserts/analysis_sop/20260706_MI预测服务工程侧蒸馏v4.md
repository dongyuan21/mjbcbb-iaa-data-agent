## 结论先行

| 事项 | 当前结论 |
|---|---|
| Base 服务 | `ltv_pred` 是单条预测接口，低延迟、无 OpenAPI / docs / health 暴露；错误 body 返回 `preds=[]` 形态 |
| XY 服务 | `roi-forecast/run` 是 `FastAPI` 批量接口，`/openapi.json` 只声明 body 为对象数组；空数组返回 `code=00000,data=[]` |
| 离线落表 | `market-data-collector/collectors/roi_pro` 是离线预测调用与落表管道，不是服务本体 |
| 批处理版本 | `ltv_prediction.py` / `ltv_prediction_oss2.py` 走单条；`ltv_prediction_batch.py` / `ltv_prediction_batch_v2.py` 走批量 |
| DataWorks 版本 | `ltv_prediction_mc_odps.py` 走 Base 单条；`ltv_prediction_mc_odps_batch.py` 走 XY 批量 |
| 服务本体源码 | 本机 `HS/coding`、山海当前可见 app 列表中未定位到预测服务仓库或部署 app |
| 模型内部 | 特征工程、训练窗口、模型文件、`v6_sdk` 是否使用 SDK 专属特征，仍未被源码证明 |

## 服务接口 live shape

### XY / roi-forecast

只读 live probe：

| URL | 结果 |
|---|---|
| `GET http://10.9.83.92:8000/` | HTTP 200，`{"message":"Hello roi"}` |
| `GET http://10.9.83.92:8000/docs` | HTTP 200，Swagger UI |
| `GET http://10.9.83.92:8000/openapi.json` | HTTP 200，FastAPI `0.1.0` |
| `GET http://10.9.83.92:8000/health` | HTTP 404 |
| `POST /api/v1/roi-forecast/run` body `{}` | HTTP 422，提示 body 应为 list |
| `POST /api/v1/roi-forecast/run` body `[]` | HTTP 200，`code=00000,msg=操作成功,data=[]` |

OpenAPI 只暴露两条 path：

```text
GET /
POST /api/v1/roi-forecast/run
```

`run` 的 request body schema 是：

```text
type: array
items: object
additionalProperties: true
```

这意味着接口层不在 OpenAPI 里声明强字段约束；字段语义必须从 Nexus 和离线调用方代码反推，而不是从 OpenAPI 直接取得。

## 离线预测 request

### Base 单条

`ltv_prediction_mc_odps.py` / `ltv_prediction.py` 的单条 payload：

```json
{
  "version": "v6",
  "bundle_id": "<bundle_id>",
  "media_source": "<media_source>",
  "country": "<country>",
  "data": [1.2, 3.4],
  "start_dt": "20260701",
  "convert_type": "all",
  "days_num": 360,
  "project": "<project>",
  "pre_model_day": "<optional>"
}
```

### XY 批量

`ltv_prediction_batch_v2.py` / `ltv_prediction_mc_odps_batch.py` 的 batch payload 是对象数组：

```json
[
  {
    "version": "xy_v5",
    "bundle_id": "<bundle_id>",
    "media_source": "<media_source>",
    "country": "<country>",
    "data": [1.2, 3.4],
    "start_dt": "20260701",
    "convert_type": "all",
    "days_num": 360,
    "project": "<project>",
    "pre_model_day": "<optional>"
  }
]
```

批量响应调用方按如下结构处理：

```text
{"code":"00000","data":[...]}
```

`data` 列表与请求顺序一一对应。调用方保存的是完整预测结果 JSON，不在知识库沉淀 raw 明细。

## 性能证据

Nexus 压测报告 `backend/boards/internal/integration/forecast/bench/PERF_REPORT.md` 提供接口性能边界：

| 服务 | 性能结论 |
|---|---|

这个性能报告只能证明服务调用性能，不能证明模型公式或特征。

## Agent 使用约束

1. 不把 `market-data-collector` 调用方逻辑说成预测服务内部算法。
2. 不把 `pgp-v1-xgboost` 的用户级 LTV/高价值用户模型套到 MI ROI360 cohort 预测。
3. 查询服务只能做 health / docs / OpenAPI / 空 body 这类低成本 probe；大 batch 或真实样本必须有明确业务目的。
4. 如果要保存离线预测表事实，必须先用 MaxCompute / ClickHouse live probe 验表、验分区、验字段。
5. 对线上用户回答时仍以只读分析和预警为边界，不输出自动投放动作。
6. 回归锚点：`FastAPI` 只证明 XY 服务框架和接口 shape；`无法解析 JSON 数据` 是 Base 空 body probe 的错误形态；`dws_ltv_prediction_result` 与 `dws_ltv_prediction_batch_result` 是离线预测建议落表，不等同于 MI runtime forecast。
