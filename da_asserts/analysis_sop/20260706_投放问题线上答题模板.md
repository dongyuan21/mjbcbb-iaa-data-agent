## 模板 A：ROI360 forecast 时序与 D360 零值

### 触发问题

- “ROI360 为什么是 0？”
- “蓝底是不是预估值？”
- “CK 宽表 `sdk_revenue_day360=0` 是否说明没有 ROI360 预测？”
- “最新分区 D360 为 0，能不能解释为停投 / 真实 D360=0？”

### 必读资产

| 资产 | 作用 |
|---|---|
| `skills/mi_skill/SKILL.md` | MI ROI360 页面默认语义、字段和安全边界 |
| `da_assets/analysis_sop/20260702_MI_ROI360分媒体导出与D360零值排查SOP.md` | D360=0 排查 checklist |
| `da_assets/analysis_sop/20260706_投放看板live验证记录.md` | 最新 live evidence：MI runtime forecast 与 CK 落表时序差异 |
| `ai_ck/agent_knowledge/tables/ads_market_roi_cohort_sdk_multidim.yaml` | CK 宽表字段、`actual_roi_days`、`update_at` |

### 必查字段

| 类别 | 字段 / 参数 |
|---|---|
| 页面口径 | `forecast_version`、`revenue_source`、`bundle_id`、`active_date` |
| CK 宽表 | `dim_level`、`cost_zhe`、`registers`、`sdk_revenue_day360`、`sdk_roi_day360`、`actual_roi_days`、`update_at` |
| 产品族 | BB 默认 `v6_sdk` / V6 族；非 BB 小包默认查 XY 族可用版本 |
| 覆盖性 | country / campaign 粒度是否有 forecast 覆盖，`country_group=other` 是否造成缺口 |

### live evidence 锚点

2026-07-06 live 验数显示：

- 2026-07-05 CK `bundle` 粒度存在 D360 全零：`cost_zhe_sum=1783112.88`，`d360_zero_rows=20`，`d360_nonzero_rows=0`。
- 同期 MI runtime 对 BB GP 可返回 `roi_6`、`roi_29`、`roi_359` forecast。
- 到 `bundle_media_campaign` 粒度会出现一部分 campaign D360 非零、一部分仍为 0，说明这是 forecast 覆盖 / 落表时序问题，不是统一业务零值。

### 回答必须包含

- 区分 `MI ROI360 页面 / runtime forecast` 与 `CK 宽表落表值`。
- 说明 `D360=0` 不能直接解释为真实 ROI360 为 0，也不能解释为停投。
- 输出 `actual_roi_days`、`update_at`、`forecast_version`、`dim_level` 的检查结果。
- 当最新分区未成熟时，标 `forecast_landing_timing_check` 或 `forecast_coverage_check`。
- 只输出预警和待查项；最终投放动作标 `needs_decision`。

### 回答不得包含

- “D360=0 就是没有预测”。
- “D360=0 就是真实 ROI360 为 0”。
- “应该立即停投 / 放量”。
- 跳过 `update_at`、`actual_roi_days`、`forecast_version` 的判断。

### 输出骨架

```text
问题识别：
这是 ROI360 forecast 时序 / D360 零值排查，不是直接投放动作判断。

口径与参数：
active_date=<date/window>，bundle_id=<bundle>，dim_level=<grain>，forecast_version=<version>，revenue_source=<sdk/af>。

主要事实：
1. CK 宽表当前 <grain> 粒度 D360 零值覆盖为 <rate>，latest update_at=<time>。
2. actual_roi_days=<n>，说明真实回收段尚未覆盖 D360。
3. MI runtime / 页面是否返回 roi_359=<value or unknown>。

判断与解释：
D360 零值优先解释为 forecast 覆盖 / 落表时序 / 粒度覆盖问题；不能直接解释为真实 ROI360 为 0。

needs_decision：
若该对象是头部计划或接近红线，只输出预警，交给 owner 决策。
```

## 模板 B：DNU install_time 与 dt 迟到分区

### 触发问题

- “昨天 DNU 掉了多少？”
- “Google DNU 掉量是不是投放问题？”
- “install_time 是昨天，但 dt 只扫当天可以吗？”
- “为什么要扫 T+1 / T+2？”

### 必读资产

| 资产 | 作用 |
|---|---|
| `da_assets/analysis_sop/20260618_DNU安装时间与分区迟到护栏SOP.md` | DNU 业务日期与分区日期护栏 |
| `da_assets/verified_sql/vsql_20260613_bb_us_ua_media_source_dnu_delta.md` | 已验证 DNU media_source 拆解样例 |
| `da_assets/analysis_sop/20260706_投放看板live验证记录.md` | 2026-07-05 BB GP US DNU T+1 迟到 live evidence |

### 必查字段

| 类别 | 字段 / 参数 |
|---|---|
| 业务日期 | `install_time` / `active_time_utc8` 派生的 install cohort |
| 分区日期 | `dt`，必须扫到目标表 `latest_partition` 或至少 T+1 |
| 维度 | `bundle_id`、`country`、`media_source`、`campaign_name` |
| 判断状态 | `partial_partition_scan`、`dt_scan_window`、`latest_partition` |

### live evidence 锚点

BB GP US `install_date=2026-07-05`，同日分区 vs 扫到 `dt=2026-07-06`：

| media_source | same_day_dnu | through_latest_dnu | late_dnu |
|---|---:|---:|---:|
| organic | 13289 | 24923 | 11634 |
| aura_int | 8312 | 15663 | 7351 |
| digitalturbine_int | 7650 | 14242 | 6592 |
| googleadwords_int | 6781 | 13167 | 6386 |
| applovin_int | 1920 | 3494 | 1574 |

### 回答必须包含

- 明确 `业务日期窗口` 与 `dt 扫描窗口`。
- 先 probe 或引用当前 `latest_partition`，再判断是否纳入 T+1。
- 如果只扫到业务日当天，必须标 `partial_partition_scan`，不能给强下滑结论。
- 修正版应扫到 latest 或至少 T+1，再比较同日分区与 through-latest 的差异。

### 回答不得包含

- 把空分区当 0。
- 把迟到分区漏扫直接解释为真实 DNU 下滑。
- 在未重跑修正版前联查 Google change log 并给归因结论。

### 输出骨架

```text
问题识别：
这是 DNU / activation cohort 分析，需要先排除 dt 迟到分区风险。

口径与参数：
业务 install_date=<date>，dt_scan_window=<start~end>，latest_partition=<date>。

数据新鲜度：
若 dt_scan_end < install_date + 1，则本次只能标 partial_partition_scan。

主要事实：
同日扫描 DNU=<same_day>，扫到 latest 后 DNU=<through_latest>，late_dnu=<delta>。

判断与解释：
当前差异首先说明分区迟到影响显著；修正后再判断是否存在真实投放下滑。
```

## 模板 C：Day0 ARPU 分母与回收源

### 触发问题

- “Day0 ARPU 下跌怎么看？”
- “是 `revenue_0` 下降，还是分母变大？”
- “`total_registers` 和 `total_media_installs` 能混用吗？”
- “SDK 回收下降但 AF 回收不降，算投放质量变差吗？”

### 必读资产

| 资产 | 作用 |
|---|---|
| `da_assets/analysis_sop/20260620_Day0_ARPU_MI查询输出模板.md` | MI 快速预检模板 |
| `da_assets/verified_sql/vsql_20260613_day0_arpu_anomaly_attribution.md` | 完整首日 ARPU 归因 SQL |
| `da_assets/analysis_sop/20260706_投放看板live验证记录.md` | 分母差异 live evidence |

### 必查字段

| 类别 | 字段 / 参数 |
|---|---|
| 收入 | MI `revenue_0`；CK 代理验证可显式标 `sdk_revenue_day1` |
| AF 分母 | `total_registers`，对应 `af_arpu = revenue_0 / total_registers` |
| 媒体分母 | `total_media_installs`，对应 `media_arpu = revenue_0 / total_media_installs` |
| 回收源 | `revenue_source=sdk` 默认；AF 只作对照 |

### live evidence 锚点

2026-07-05 主包抽样显示分母差异会造成数倍到数十倍 ARPU 差异，例如：

- BB iOS：`arpu_by_registers=0.1242`，`arpu_by_media_installs=0.0161`。
- Mahjong iOS：`0.4473` vs `0.0236`。
- BC iOS：`0.5839` vs `0.0281`。

### 回答必须包含

- 显式声明当前 ARPU 使用哪个分母。
- 同时检查 `revenue_0`、`total_registers`、`total_media_installs`，不要只看比率。
- 若 SDK 与 AF 回收方向不一致，标 `revenue_source_gap`，不能直接解释为投放质量劣化。
- 当用户问“为什么 ARPU 下跌”而不只是 MI 快速看数时，升级到 verified SQL 拆 `ARPU = 人均展示次数 × eCPM / 1000`。

### 回答不得包含

- 混用 `registers`、AF install、media install。
- 把 MI 快速预检当完整 DA 归因报告。
- 未验数直接断言是 eCPM 或展示次数导致。

### 输出骨架

```text
问题识别：
这是 Day0 ARPU 快速预检；若要解释广告变现原因，需要升级到完整 DA 归因 SQL。

口径与参数：
revenue_source=<sdk/af>，af_arpu=revenue_0/total_registers，media_arpu=revenue_0/total_media_installs。

主要事实：
1. revenue_0 变化 <pct>。
2. total_registers 变化 <pct>。
3. total_media_installs 变化 <pct>。
4. af_arpu 与 media_arpu 是否同向。

判断与解释：
若分母变化是主因，先解释新增结构 / 媒体安装口径；若 revenue_0 下滑更大，再升级到展示次数和 eCPM 拆解。
```

## 模板 D：Google change log 因果边界

### 触发问题

- “Google campaign DNU 下滑是不是有人改预算 / 状态？”
- “change log 命中能不能证明原因？”
- “没有 change log 命中是不是没人操作？”

### 必读资产

| 资产 | 作用 |
|---|---|
| `task_routes/google_ads_config_change_analysis.yaml` | Google 操作记录路由与输出边界 |
| `da_assets/verified_sql/vsql_20260618_google_ads_config_change_monitoring.md` | Google change_event 安全聚合 SQL |
| `da_assets/verified_sql/vsql_20260618_google_campaign_dnu_changelog_triage.md` | DNU 与 change log 联查 SQL |
| `ai_hive/agent_knowledge/tables/ods_market_google_ads_config_wide_hi.yaml` | 表字段、PII 禁止输出规则 |

### 必查字段

| 类别 | 字段 / 参数 |
|---|---|
| 时间窗口 | `dt`、`hour`，必须同时过滤 |
| 对齐 key | `customer_id + campaign_id`；下钻时再加 `ad_group_id`、`ad_id` |
| 聚合输出 | `change_event_change_resource_type`、`change_event_resource_change_operation`、字段命中计数 |
| 禁止输出 | `change_event_user_email`、old/new raw resource JSON |

### live evidence 锚点

2026-07-06 Google change log 可读，安全聚合结果包括：

- `CAMPAIGN_CRITERION CREATE` 25 次。
- `AD_GROUP_AD CREATE` 11 次。
- `CAMPAIGN UPDATE` 4 次，其中状态变更 2 次。
- `CAMPAIGN_BUDGET CREATE` 1 次，预算金额字段变更 1 次。

### 回答必须包含

- `change_log_hit_status`：命中 / 未命中 / 窗口不完整。
- 命中时表达为“同窗口候选操作证据”，不是因果证明。
- 未命中时表达为 `no_change_log_hit_in_window`，不能说“无人操作”。
- 必须先确认 DNU 查询已纳入 T+1 迟到分区；否则先修 DNU 再联查操作记录。
- 禁止输出操作人邮箱和 raw JSON。

### 回答不得包含

- “change log 命中就是 DNU 下滑原因”。
- “未命中说明没人操作 / 没有任何平台变更”。
- 输出 `change_event_user_email` 或 raw old/new resource。
- 直接让业务回滚、改预算或停投。

### 输出骨架

```text
问题识别：
这是 Google campaign DNU / 指标异动与操作记录联查，不是因果定责。

口径与参数：
metric_window=<date/hour>，change_log_window=<dt/hour>，join_key=<customer_id+campaign_id...>。

主要事实：
1. DNU 查询是否已纳入 T+1 迟到分区。
2. change_log_hit_status=<hit/no_hit/window_incomplete>。
3. 命中的 resource_type / operation / changed_fields 聚合。

判断与解释：
命中只能说明同窗口存在候选操作记录；是否导致 DNU/ROI 变化，需要继续结合消耗、展示、点击、registers 和 owner 复盘。
```
