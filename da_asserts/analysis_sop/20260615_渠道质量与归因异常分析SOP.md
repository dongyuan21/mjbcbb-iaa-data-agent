## 分析目标

用可复核的分层证据识别“渠道质量风险候选”，而不是自动给出停投、扣量或扣款结论。输出应区分 `risk_candidate`、`needs_business_review` 和 `verified_issue`。

## 输入

| 输入 | 说明 |
|---|---|
| 时间范围 | 必须明确 dt 或 install/event date；默认先小窗口验证再扩大 |
| 对象范围 | bundle_id/app_id、platform、media_source、campaign/site/ad |
| 指标 | install 数、CTIT 分布、match_type 分布、gp_referrer 来源、site_id、素材类型 |
| 数据表 | `dwd_market_appsflyer_activation_push_data_di`、`ods_appsflyer_locker_sync_data_installs_mc_di`、`ads_market_tj_ad_spend_active_v2` |
| 语义候选 | `../../knowledge/audit_archive/semantic_contract/raw_exports_knowledge_proposals.yaml` |

## 分析步骤

1. 确认表和分区新鲜度，所有大表查询带 `dt` 过滤。
2. 先按 bundle/platform/media_source 聚合安装量，判断是否为单渠道、单平台或单 site 异常。
3. 计算 CTIT 分布：快速筛查可用 6 段；深度报告使用 B1-B10 细分。
4. 分层查看 `match_type`，区分 SRN、gp_referrer、id_matching、probabilistic、preload。
5. Android 渠道检查 `gp_referrer`：提取真实来源后与 AF media_source 对比。
6. Moloco 素材检查 ad/ad_bak 命名：区分 Native、Video、Playable。
7. 输出候选风险、证据强度、反例解释和需要人工确认的动作。

## 输出格式

- 问题识别：渠道质量 / 归因异常 / 素材类型 / 数据口径。
- 口径与参数：表、日期、bundle/app_id、platform、media_source、过滤条件。
- 数据新鲜度：最新分区、是否成熟、是否延迟。
- 主要事实：只输出聚合指标，不输出用户/设备级明细。
- 风险判断：`risk_candidate` / `needs_business_review` / `verified_issue`。
- 人工确认项：停投、扣量、扣款、渠道谈判、预算收缩等动作。

## 判断规则

| 规则 | 状态 | 说明 |
|---|---|---|
| CTIT < 5s / <10s | risk_signal | 用户 2026-06-15 确认：若红线白皮书无补充标准，只做风险提示 |
| CTIT > 24h / >72h | risk_signal | Click Flood 候选，需排除展示归因和窗口差异；是否治理需 DA 确认 |
| gp_referrer=organic + AF 付费渠道 + id_matching | draft | 疑似归因劫持候选，SRN/preload/gclid 为例外 |
| Moloco Native | draft | 优先匹配 `-NV-` 形式，不使用宽泛 `%nv%` 直接做正式规则 |
| 处置动作 | needs_decision | 停投、降预算、扣款、扩量必须由人或已签字策略决定 |

## 风险和待确认

- raw 中部分 CTIT 基准来自 2026-02 或 2026-04 单次实测，不可默认作为长期阈值。
- `dwd_market_appsflyer_activation_push_data_di` 不是安装/激活默认分母；分母问题按 `../../ai_hive/agent_knowledge/口径决策记录.md`。
- gp_referrer 只覆盖 Android，iOS/SKAN 需另走 SKAN 和 ATT 口径。
- 模板 A 中的 inmobidsp 示例是一次性报告实例，不是默认渠道治理规则。

## 待提给 DA 的问题

1. 如果红线白皮书没有补充标准，CTIT 的 `<5s`、`<10s`、`>24h`、`>72h` 是否只能作为风险提示，还是允许进入正式治理/扣量规则？
2. gp_referrer 与 AF 归因不一致时，哪些 `match_type` / 渠道需要作为例外白名单？
3. Moloco Native/Video/Playable 是否以 `ad_bak` 命名规则为准；`-NV-` 是否是正式识别 Native 的唯一可靠标记？
